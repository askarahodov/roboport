# Правила работы ИИ-агентов ROBOport

**Обязательный язык:** требования, объяснения, комментарии к бизнес-логике, описания PR и GitHub Issues — **русский**. Английский сохраняется для идентификаторов кода, библиотек, имен API/HTTP, SQL, путей, команд и стандартных терминов. Тексты UI — русский с подготовкой к i18n. Не переводить ключи JSON и названия таблиц произвольно.

## Единственная цель продукта: автомобильная система СТО (решение 28.10.2026)

**Стратегия подтверждена заказчиком:** полнофункциональная система автосервиса с охватом AutoDealer Online; роботы полностью исключаются из конечной предметной области, пользовательского UI, публикуемого API и актуальной базы знаний. Временные robot-таблицы/маршруты допустимы **только как миграционные legacy-зависимости** до #165. Новая разработка не должна расширять робототехнический продукт и не должна выдавать legacy service_ticket/inventory за автомобильные WorkOrder/Stock. Канонические планы: `docs/auto/PRODUCT.md`, `docs/auto/FUNCTIONAL_MATRIX.md`, `docs/auto/FEATURE_ROADMAP.md`, `docs/auto/ADR-001.md`, #107, #108, #109, #165–#174. Переход Strangler обязан иметь проверенный cutover/decommission, а не бесконечное сосуществование.

## Ранние архитектурные решения AUTO (с 26.10.2026)
Для новых автомобильных модулей использовать docs/auto/PRODUCT.md, docs/auto/ARCHITECTURE.md, docs/auto/ADR-001.md и Issues #107–#119. Документацию и инструкцию пользователя обновлять в том же PR по docs/DOCUMENTATION_POLICY.md; при отсутствии влияния указывать причину. Старые документы описывают существующий робототехнический домен и остаются обязательными для неизменяемых legacy-компонентов. Никаких destructive migrations и реальных ПДн, пока не пройдены соответствующие гейты. Каждая новая автомобильная функция требует контракт/ACL/тесты и не получает доступ к старым заявкам только по VIN.

## 1. Иерархия источников

1. Для новой автомобильной предметной области — `docs/auto/ADR-001.md`, `docs/auto/PRODUCT.md`, актуальная GitHub Issue, проверенное текущее поведение кода. Для существующего robot domain — `docs/architecture/ADR.md`.
2. `TECHNICAL_SPEC.md` — **только legacy robot domain**; не использовать его требования для новых автомобилей, OEM, заказ-нарядов.
3. `docs/TECH_STACK.md`, `docs/REPOSITORY_STRUCTURE.md`, `docs/security/SECURITY_MODEL.md`.
4. Контракт `contracts/openapi.yaml`, FSM и data model; проектные расхождения оформлять ADR и обновлением тестов.
5. Текущая GitHub Issue с критериями приёмки. **Номер `#N` — канонический идентификатор задачи.** Не использовать старую нумерацию RP в качестве источника истины.

## 2. Роли

- **Оркестратор:** прочитать зависимости, выбрать Ready-задачу, разбить на подзадачи, инициировать специализированных subagents, не дублировать одни и те же изменения.
- **Архитектор:** сверить ADR/FSM/DDL/OpenAPI, выявить конфликт до реализации, ограничить область PR.
- **Разработчик:** минимальный завершённый вертикальный срез, бизнес-guards на сервере, типы и тесты.
- **Специалист по БД:** реальные одноразовые PostgreSQL миграции, ACID, отрицательные и конкурентные тесты.
- **Тестировщик (независимый):** реально запустить тесты, проверить негативные сценарии; может остановить PR.
- **Security-review:** BOLA/IDOR, локальная сессия/CSRF/Argon2id, RBAC+ACL, приватный MinIO, хранение секретов, аудит и проверки object-level доступа.
- **Документатор/дизайнер:** русский текст, обновление контрактов, визуальные и accessibility checks.

## 3. Цикл задачи

**Inspect → Plan → Implement + tests → Self-review → Update docs → PR → GitHub Actions CI → Independent review → Merge gate**. Один GitHub Issue = одно проверяемое поведение/результат. Название ветки `feature/issue-N-short-name`; PR включает `Refs #N`; исходная Issue закрывается вручную после полного DoD и успешного post-merge main CI. При красных тестах искать первопричину и повторно запускать; запрет на отключение проверки ради зелёного отчёта. 

**Решение заказчика 26.11.2026 — CI-first:** автоматические тесты, lint/typecheck, build и документные проверки выполняются в GitHub Actions вместо локального запуска агентом. Локальные тесты не обязательны и не запускаются по умолчанию; отсутствие локального Git/PG17/Chromium не является блокером. До первого PR подготовить полный связанный пакет кода, тестов и документации, затем проверять требуемые jobs на точном HEAD. Указывать run URL/SHA, фактические результаты и skipped отдельно. `PENDING` до завершения CI; `BLOCKED` только если необходимая проверка действительно недоступна в CI (или нужен внешний gate). Не выдавать непроведённую проверку за PASS. Impact selector, обязательные PG17/ACL/security проверки, независимые review, ручная приёмка и полный post-merge main CI остаются в силе. При FAIL исправить первопричину и повторить CI, не отключать проверки.

**Каждый PR содержит блок Documentation impact:** пути изменённых технических документов и инструкций всех затронутых ролей либо конкретное обоснование `none`; только реальные `current` функции, остальные `planned/legacy` по [политике](docs/DOCUMENTATION_POLICY.md).

**Каждый PR обязательно содержит:** `Issue`, `Цель`, `Изменённые файлы`, `Контракт/API`, `Миграции`, `GitHub Actions run + HEAD SHA + jobs/результаты (команды и exit codes из доступных логов)`, `Негативные тесты`, `Риски и откат`, `Что не проверено`, `Скриншоты light/dark/mobile (для UI)`.


### Постоянное полномочие заказчика на самостоятельный Merge (26.11.2026)

[Явное решение заказчика, зафиксированное в #119](https://github.com/askarahodov/roboport/issues/119#issuecomment-7187468307): агенту разрешено самостоятельно объединять PR в `main`, закрывать полностью выполненные исходные Issues и продолжать разработку без повторного подтверждения. Полномочие действует для репозитория askarahodov/roboport до явного отзыва или изменения заказчиком, в том числе в последующих рабочих сессиях. Перед работой читать актуальный `AGENTS.md` и регламент; не полагаться на память чата.

**Обязательные условия:** актуальный стабильный main CI, применимые обязательные GitHub Actions jobs на точном HEAD PR успешны (skipped отдельно, не PASS), независимый Code Review без нерешённых замечаний на этом HEAD, необходимый Security Review и другие обязательные проверки/приёмка пройдены, нет конфликтов. При изменении HEAD/значимом изменении базы повторно проверить актуальность доказательств. Объединять только через PR, не обходить branch protection и не подменять независимые approvals. После merge проверить полный main CI на фактическом merge SHA; до его успеха не объединять следующий PR. При FAIL остановить дальнейшие слияния, исправить первопричину проверенным PR и подтвердить main CI. Закрывать исходную Issue вручную только после полного AC/DoD и успешного post-merge main CI; до этого использовать `Refs #N`, не `Closes #N`, чтобы GitHub не закрыл задачу раньше приёмки.

**Границы полномочия:** production-деплой, удаление данных, разрушительные операции требуют отдельного явного разрешения. Не снимает #119, legal/privacy/licensing/ops gates, ручную приёмку и security review там, где они необходимы; не разрешает real PII/платежи, изменение production IAM/network, breaking API без согласования или ослабление защиты. Крупные связанные функциональные блоки, минимум PR и повторных тестов при сохранении обязательных gates. Это разрешение агенту действовать в рабочей сессии, а не настройка фонового бота или GitHub auto-merge.

### Gitflow / порядок веток и очередь интеграции (27.11.2026)

По решению заказчика применяется облегчённый Gitflow (trunk-based): единственная постоянная интеграционная ветка `main`, временные `feature/issue-N-short-name`, `fix/issue-N-short-name`, `chore/short-name`; отдельную `develop` не создавать. Release/hotfix — только по согласованной процедуре релиза. Не делать прямых push/force-push в main, не переиспользовать ветку после merge, не дублировать одну функциональную область в нескольких PR.

**WIP: не более двух открытых продуктовых PR на репозиторий, включая draft, и не более одного на агента.** В начале каждой сессии сверять открытые PR (включая чужие), точные HEAD, CI, review, треды, зависимости и все удалённые ветки. При превышении лимита не начинать новую продуктовую ветку/PR: сначала исправлять красные/устаревшие PR, получать необходимый независимый review, интегрировать готовые в порядке зависимостей и возраста. Исключение — один служебный PR для устранения блокирующего дефекта CI/безопасности/регламента; объяснить причину, не считать это продуктовым прогрессом. Уже открытые PR не закрывать ради лимита и не переносить в draft для обхода. Если есть внешний blocker, явно указать точный SHA, недостающий gate, владельца/канал эскалации; не накапливать новые PR и не имитировать approval. Не запускать повторно тот же review без изменения HEAD или подтверждённой ошибки доставки.

**Merge и уборка — часть DoD:** один PR за раз, при выполнении всех существующих gates, затем полный зелёный main CI на merge SHA, сверка результата с Issue и cleanup. Объединённую ветку удалить после подтверждения актуального зелёного main, только если она принадлежит репозиторию, является временной, HEAD не менялся, подтверждён merge именно в main и merge SHA входит в текущий main; не используется открытым PR ни как head, ни как base, не защищена. Удаление по точному SHA/lease, не по возрасту/названию. При отказе сохранить ветку, записать причину. Не удалять main/default/protected/release/hotfix, ветки открытых PR, чужие форки, уникальные или неразобранные закрытые без merge / orphan / legacy ветки; старые legacy dispositions не отменяются. Закрытые без merge ветки — отдельная сверка с сохранением SHA и явным решением об архивировании/удалении. Разовый список семи уже достижимых из main SHA разрешён по инвентаризации 27.11.2026 и поручению заказчика убрать ненужные ветки; при любом изменении SHA/доступности из main, открытом PR или защите не удалять. Это не общее разрешение для orphan/legacy. Никаких force-push общего/чужого HEAD, удаления тегов или production/БД данных.

[Регламент Gitflow](docs/implementation/GITFLOW.md), [workflow безопасной уборки](.github/workflows/branch-hygiene.yml). Автоматизация только после её merge и успешной проверки; не заменяет независимые approvals.

### Серверная платформа Linux-only (26.11.2026)

[Решение заказчика](https://github.com/askarahodov/roboport/issues/119#issuecomment-7187571899): backend/API, PostgreSQL, контейнеры, фоновые процессы и эксплуатация разворачиваются исключительно на Linux. Native Windows/CMD bootstrap и отдельный Windows CI не входят в требования продукта. Клиентский веб-интерфейс остаётся доступным через поддерживаемые браузеры, в том числе на Windows; это не заявление о пройденном Windows browser QA. Все шесть Linux CI jobs на main обязательны: impact, docs, postgres, api, web, browser-e2e. Полные PostgreSQL/backup/restore, API/ACL/security, build и browser E2E/Docsify сохраняются; production требует отдельного разрешения.

## 4. Безусловные инварианты

- A не видит заявки/документы B; смена владельца робота не передаёт старую историю.
- `SAFETY_HOLD` блокирует ремонт, `QC_FAILED` блокирует выдачу.
- `SENT` смета immutable; согласие на новую версию только отдельным действием.
- Каждая мутация проверяет роль, объект, состояние и идемпотентность; replay не обходит отзыв доступа.
- Совместимость запчастей только по подтверждённым P/N, ревизии, региону и модели.
- Audit append-only; ни логи, ни Issues не содержат PII/токенов/клиентских документов.
- Публичный бренд и реальные данные запрещены до специальных release-gates.

## 5. Стоп-сигналы

Не создавать внешние аккаунты, платежи, публичные сервисы и инфраструктуру без явной задачи. Не запускать `db/legacy_drafts/*.sql` на настоящих БД. Не объявлять draft OpenAPI реализованным. Не заменять оригинальный SVG угловой R (C) на гексагон A. При неразрешённой коллизии требований — блокировка узкой задачи + ADR, остальные независимые задачи можно продолжать.

Формат постановки задач: [`docs/implementation/ISSUE_STANDARD.md`](docs/implementation/ISSUE_STANDARD.md).

Пошаговый безопасный выбор следующей Ready Issue, PR/CI repair и checkpoint: [`docs/implementation/AUTONOMOUS_AGENT_WORKFLOW.md`](docs/implementation/AUTONOMOUS_AGENT_WORKFLOW.md). Это регламент запускаемого агента, а не автоматически работающий GitHub-бот.
