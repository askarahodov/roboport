# Стандарт GitHub Issue для ИИ-агента

**Единственный идентификатор задачи — номер GitHub Issue `#N`.** Все остальные прежние `RP-001` и т. п. — исторические обозначения и не используются для зависимостей. Issue должна быть настолько маленькой, чтобы агент мог выполнить её в одном обозримом PR и подтвердить результат.

## Обязательный шаблон

```markdown
# [Модуль] Наблюдаемый результат (по-русски)

## Зачем
Роль пользователя, исходное состояние, наблюдаемое поведение после изменения.

## Входит в задачу
- Конкретные операции API/экраны/таблицы/команды.

## Не входит
- Что запрещено или должно остаться отдельной задачей.

## Входные материалы
- Точные пути к ТЗ/ADR/OpenAPI/дизайн-токенам.

## Зависимости
- #N (обязательная), #M (опциональная); что проверить перед началом.

## Изменяемые файлы
- apps/...; docs/...; tests/...; почему именно они.

## Порядок реализации
1. Исследовать текущее поведение и конфликт контрактов.
2. Внести минимальные изменения.
3. Написать happy/negative/boundary тесты.
4. Запустить тесты и проверки.
5. Обновить документы и PR.

## Критерии приёмки (измеримые)
- [ ] AC1: заданные входы → точный статус/ответ/состояние.
- [ ] AC2: отказные входы → точный статус без утечки информации.
- [ ] AC3: проверка ролей/идемпотентности/состояний, если применимо.
- [ ] AC4: зелёный CI и выполнение независимым TESTER.

## Команды проверки
`...` — ожидаемый результат; отметить фактический exit code.

## Доказательства в PR
- Список изменённых файлов и ссылок на тесты.
- Реальный CI run URL; номера тестов, skipped и BLOCKED.
- Скриншоты Light/Dark/390px для UI.

## Риски/откат
Что может испортиться, как вернуть предыдущую версию.

## Definition of Done
Все AC зелёные, независимый обзор пройден, нет обхода защиты;
иначе задача остаётся OPEN/BLOCKED с точным пояснением.
```

## Состояния

`Backlog` → `Ready` (все зависимости и контракты доступны) → `In progress` → `In review` → `Done` (слияние и тесты). `Blocked` ставится только при зафиксированном препятствии с ссылкой на лог. **Создание Issue само по себе не означает начало работы.**

## Качество текста

- Не писать «сделать авторизацию» без указания проверяемых сценариев и токенов.
- Не писать «настроить CI» без перечисления реально запускаемых команд и требуемых артефактов.
- Не писать «всё работает», если запускалось только на fixture.
- Не назначать задачу, требующую PostgreSQL, без ссылки на доступный одноразовый стенд или как `Blocked`.
- Не смешивать реальную бизнес-операцию и изменение косметики в одном Issue.
