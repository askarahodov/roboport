# Безопасный цикл одного AI coding agent

> Статус: регламент для агентного выполнения задач, **не** действующий фоновый бот. Документ разрешает агенту контролируемый PR merge в рабочей сессии по решению заказчика 26.11.2026, но не включает GitHub auto-merge или запуск AI от события GitHub.

## Источники истины и ограничения

- Продукт — автомобильная система «БоксРитм»: [PRODUCT](../auto/PRODUCT.md), [ADR-001](../auto/ADR-001.md), [дорожная карта](../auto/FEATURE_ROADMAP.md). Robot domain — только контролируемое legacy до #165.
- Приоритеты и критерии задачи — **текущая GitHub Issue #N** и [ISSUE_STANDARD](ISSUE_STANDARD.md); правила реализации и язык — [AGENTS](../../AGENTS.md).
- Серверная платформа и обязательный CI — Linux-only по решению заказчика 26.11.2026; клиентский браузер не ограничивается ОС. Полный gate main — шесть jobs, Windows CMD не требуется.
- CI: [workflow](../../.github/workflows/ci.yml), консервативный [impact selector](../../scripts/ci_impact.py), [операционные указания](../operations/DEV_ENVIRONMENT.md). Пропуск job на PR по impact **не равен PASS**; release gate на `main` и #119 не отменяется.
- `TECHNICAL_SPEC.md` описывает исторический robot domain и не задаёт требования для новой автомобильной функциональности.

## Цикл

1. **Discover.** Получить актуальные открытые Issues, открытые PR и состояние `main`. Искать работу в порядке P0 → P1 → P2 → P3, выбирая максимально полный связанный функциональный блок исходной задачи вместо серии мелких PR.
2. **Ready gate.** Выбирать Issue, только если сформулированы Goal, scope, acceptance criteria, зависимости, необходимые проверки и документация. Убедиться, что блокирующие зависимости завершены или явно разрешён независимый срез. Если Issue неполная, уточнить её в той же Issue; не создавать дочерние задачи для промежуточных checkpoints и не выдумывать продуктовые решения. Не начинать задачу, которую уже реализует чужой PR/агент.
3. **Inspect.** Сверить текущий SHA, затронутые файлы и последние PR, прочитать реализацию, контракт, связанные тесты, ADR и руководство пользователя. Указать blast radius и security/privacy риски. При смене `main` или появлении конкурирующего PR — повторить проверку до записи.
4. **Plan.** Зафиксировать максимально полный проверяемый вертикальный блок, проверяемые Given/When/Then, файлы, зависимости, rollback и выбор scoped tests. Выбирать существующие компоненты, не выполнять массовое форматирование.
5. **Implement.** Ветка `feature/issue-N-short-name` от актуальной `main`; один агент владеет затронутой областью. Не писать напрямую в `main`. Код, тесты и актуальные RU инструкции — в одном PR.
6. **Validate plan.** Подготовить применимые lint/typecheck/unit/integration/E2E и документные проверки для GitHub Actions. Локальный запуск агентом не требуется; отсутствие локального окружения не блокирует PR. До CI результат `PENDING`. После CI указать **run URL, точный HEAD SHA, jobs, фактические результаты и exit codes из доступных логов**; skipped не PASS, недоступная обязательная проверка — BLOCKED. Не исправлять продуктовый дефект изменением ожидаемого значения теста.
7. **Self-review.** Отдельно проверить diff на правильность, BOLA/IDOR, ACL, concurrency, совместимость, миграции, тесты и docs impact. Исправить найденную root cause и включить затронутые проверки в CI.
8. **PR.** Открыть PR в `main` с Issue, целью, изменениями, планом CI и фактическими результатами по мере их появления, негативными кейсами, рисками, rollback, документацией и честным списком непроверенного по `AGENTS.md`. Использовать `Refs #N`; закрывать Issue вручную после полного DoD и проверенного post-merge main CI. Частичный срез не закрывает родительский эпик.
9. **CI repair / independent review.** Проверять GitHub Actions для текущего **head SHA**. При FAIL прочитать упавший job/логи, классифицировать product/test/environment fault, исправить первопричину в той же ветке и повторить проверку; после нового push старый зелёный run не является доказательством. Skipped jobs учитывать отдельно. После изменений подтвердить независимое review на актуальном HEAD; независимая ручная/security/legal/ops приёмка не подменяется CI. Не отключать тесты/guard/security ради зелёного статуса.
10. **Merge gate.** По [постоянному полномочию заказчика](../../AGENTS.md) дополнительное подтверждение обычного PR merge не требуется. Сверить точный HEAD, актуальность базы, зелёный main, применимые обязательные CI, независимый Code Review без unresolved, необходимый Security Review/прочие обязательные approvals, отсутствие конфликтов; не обходить protection. После merge проверить полный main CI на merge SHA; следующий merge только после его успеха. При FAIL остановить дальнейшие слияния, исправить первопричину через проверенный PR и подтвердить main.
11. **Checkpoint / Next.** Зафиксировать Completed, Validation (включая skipped/blocked), Findings, Remaining, Blockers, Next. Завершение Issue — только после требуемых зелёных checks, review, merge и проверки post-merge `main`; production readiness дополнительно требует #119. При отсутствии блокеров повторить шаг Discover для следующей независимой Ready-задачи.

## Стоп-условия

Остановить **затронутую** работу и запросить решение при неполных правах/секретах, неоднозначном критичном бизнес-правиле, конфликтующих изменениях, потенциально разрушительной миграции, удалении данных, изменениях production IAM/network, публичном запуске, реальных платежах/ПДн или breaking API. Обычный контролируемый PR merge разрешён заказчиком 26.11.2026 до отзыва; GitHub auto-merge, production deploy, удаление данных и разрушительные операции не входят в полномочие и требуют отдельного разрешения/контроля. Независимые задачи не блокируются чужим неподтверждённым результатом.

## Проверяемая запись checkpoint

```text
Issue: #N
Head SHA: <sha>
Completed: <фактическое изменение>
Validation: <CI run URL, SHA, jobs/результаты, exit codes из доступных логов; отдельно skipped/pending/blocked>
Findings: <дефекты и риски>
Remaining: <невыполненные критерии>
Blockers: <только подтверждённые>
Next: <Ready Issue или нужное решение>
```

Этот регламент описывает **поведение агента при запуске**. Для непрерывного автоматического цикла по событиям GitHub нужна отдельная проверяемая интеграция с разрешениями, триггерами и обработкой секретов; наличие инструкции само по себе её не создаёт.


## Пакетирование изменений и экономия CI (24.11.2026)

По решению заказчика выбирать максимально завершённую функциональную вертикаль в исходной Issue, объединяя связанные backend/API/UI/ACL/негативные тесты/docs в одном PR. Не создавать дочерние Issues ради промежуточных checkpoints. До открытия PR подготовить полный набор связанных изменений в одной feature-ветке, подготовить затронутые тесты для CI и выполнять предварительный self-review. Открывать PR только после сборки готового пакета (допустимы несколько коммитов до открытия) и запрашивать review один раз вместо промежуточных push в открытый PR. Замечания и найденные ошибки на одном HEAD собрать, исправить единым коммитом и повторить применимый CI на новом HEAD. Не объединять несвязанные рискованные миграции или production изменения ради экономии. Существующий impact selector, security/ACL/PG17 и полный main CI не ослабляются; skipped не PASS. По решению заказчика 26.11.2026 GitHub PR CI является основным способом автоматической проверки вместо локального запуска; один итоговый прогон на собранный пакет, дополнительные прогоны только при изменении HEAD, исправлении или необходимости обязательной проверки. Метрика: число PR/run на завершённый функциональный блок, не число пропущенных проверок.


## Критерий завершения исходных задач (решение заказчика 24.11.2026)

До открытия PR сверяем весь исходный scope/AC, а не только найденный дефект. Накопление связанных функциональных изменений допускается в нескольких коммитах **до первого PR/полного CI**; предпочтителен целый модуль или группа зависимых Issues. Отдельные изменения ради промежуточной статистики не отправлять на полный CI. Перед итоговым PR составить AC → реализация → тест → доказательство → remaining с конкретными внешними блокерами. При полном DoD закрыть исходную Issue после проверенного main; не подменять юридическое или независимое согласование кодом и не расширять неподтверждённые бизнес-правила. Если всё доступное техническое выполнено, а остаются только внешние approvals, не создавать очередные косметические PR — выбрать следующую независимую крупную задачу. Основная метрика — действительно завершённые исходные Issues; количество PR не является результатом.


### Полный PostgreSQL gate для runtime API (24.11.2026)

После #586 полный main CI выявил регрессию timeline, не вошедшую в PR scope: 769 PASS, 1 FAIL, 5 SKIP (изолированный MinIO). Любое изменение runtime-модуля apps/api/roboport_api/ теперь запускает весь PostgreSQL integration suite до merge, даже когда изменён или добавлен тест. Только ранее верифицированные изолированные offline-группы сохраняют сокращённый gate. Тесты без runtime-изменений могут запускаться выборочно. Main/manual остаются полными. Не объединять следующий PR при красном main; после исправления подтвердить полный gate и main CI.
