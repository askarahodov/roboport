# Безопасный цикл одного AI coding agent

> Статус: регламент для агентного выполнения задач, **не** действующий фоновый бот. Документ не включает авто-merge или запуск AI от события GitHub.

## Источники истины и ограничения

- Продукт — автомобильная система «БоксРитм»: [PRODUCT](../auto/PRODUCT.md), [ADR-001](../auto/ADR-001.md), [дорожная карта](../auto/FEATURE_ROADMAP.md). Robot domain — только контролируемое legacy до #165.
- Приоритеты и критерии задачи — **текущая GitHub Issue #N** и [ISSUE_STANDARD](ISSUE_STANDARD.md); правила реализации и язык — [AGENTS](../../AGENTS.md).
- CI: [workflow](../../.github/workflows/ci.yml), консервативный [impact selector](../../scripts/ci_impact.py), [операционные указания](../operations/DEV_ENVIRONMENT.md). Пропуск job на PR по impact **не равен PASS**; release gate на `main` и #119 не отменяется.
- `TECHNICAL_SPEC.md` описывает исторический robot domain и не задаёт требования для новой автомобильной функциональности.

## Цикл

1. **Discover.** Получить актуальные открытые Issues, открытые PR и состояние `main`. Искать работу в порядке P0 → P1 → P2 → P3, но не начинать эпик целиком вместо небольшого завершённого среза.
2. **Ready gate.** Выбирать Issue, только если сформулированы Goal, scope, acceptance criteria, зависимости, необходимые проверки и документация. Убедиться, что блокирующие зависимости завершены или явно разрешён независимый срез. Если Issue неполная, уточнить её или создать отдельную небольшую задачу; не выдумывать продуктовые решения. Не начинать задачу, которую уже реализует чужой PR/агент.
3. **Inspect.** Сверить текущий SHA, затронутые файлы и последние PR, прочитать реализацию, контракт, связанные тесты, ADR и руководство пользователя. Указать blast radius и security/privacy риски. При смене `main` или появлении конкурирующего PR — повторить проверку до записи.
4. **Plan.** Зафиксировать минимальный вертикальный срез, проверяемые Given/When/Then, файлы, зависимости, rollback и выбор scoped tests. Выбирать существующие компоненты, не выполнять массовое форматирование.
5. **Implement.** Ветка `feature/issue-N-short-name` от актуальной `main`; один агент владеет затронутой областью. Не писать напрямую в `main`. Код, тесты и актуальные RU инструкции — в одном PR.
6. **Validate.** Выполнить применимые lint/typecheck/unit/integration/E2E и документные проверки; указать **конкретные команды, exit codes и SHA**. Для локального отсутствующего PG17/Chromium/credentials написать `BLOCKED`, а не `PASS`. Не исправлять продуктовый дефект изменением ожидаемого значения теста.
7. **Review.** Отдельно проверить diff на правильность, BOLA/IDOR, ACL, concurrency, совместимость, миграции, тесты и docs impact. Исправить найденную root cause и повторить затронутые проверки.
8. **PR.** Открыть PR в `main` с Issue, целью, изменениями, тестами и exit codes, негативными кейсами, рисками, rollback, документацией и честным списком непроверенного по `AGENTS.md`. `Closes #N` допустимо **только** при полном выполнении критериев; частичный срез не закрывает родительский эпик.
9. **CI repair.** Проверять GitHub Actions для текущего **head SHA**. При FAIL прочитать упавший job/логи, классифицировать product/test/environment fault, исправить первопричину в той же ветке и повторить проверку; после нового push старый зелёный run не является доказательством. Skipped jobs учитывать отдельно. Не отключать тесты/guard/security ради зелёного статуса.
10. **Checkpoint / Next.** Зафиксировать Completed, Validation (включая skipped/blocked), Findings, Remaining, Blockers, Next. Завершение Issue — только после требуемых зелёных checks, review, merge и проверки post-merge `main`; production readiness дополнительно требует #119. При отсутствии блокеров повторить шаг Discover для следующей независимой Ready-задачи.

## Стоп-условия

Остановить **затронутую** работу и запросить решение при неполных правах/секретах, неоднозначном критичном бизнес-правиле, конфликтующих изменениях, потенциально разрушительной миграции, удалении данных, изменениях production IAM/network, публичном запуске, реальных платежах/ПДн или breaking API. Не выполнять auto-merge и production deploy без отдельного полномочия/контроля. Независимые задачи не блокируются чужим неподтверждённым результатом.

## Проверяемая запись checkpoint

```text
Issue: #N
Head SHA: <sha>
Completed: <фактическое изменение>
Validation: <команды, exit codes, CI run; отдельно skipped>
Findings: <дефекты и риски>
Remaining: <невыполненные критерии>
Blockers: <только подтверждённые>
Next: <Ready Issue или нужное решение>
```

Этот регламент описывает **поведение агента при запуске**. Для непрерывного автоматического цикла по событиям GitHub нужна отдельная проверяемая интеграция с разрешениями, триггерами и обработкой секретов; наличие инструкции само по себе её не создаёт.
