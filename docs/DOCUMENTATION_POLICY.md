# Политика документации Airmatik Pro Service

**Статус:** правило инженерной работы, действует при разработке автомобильных функций. Связанные GitHub Issues: [#107](https://github.com/askarahodov/roboport/issues/107), [#121](https://github.com/askarahodov/roboport/issues/121), [#122](https://github.com/askarahodov/roboport/issues/122)–[#125](https://github.com/askarahodov/roboport/issues/125).

## Принципы

1. Документация — часть продукта и **Definition of Done** каждой функции. Меняется тот же PR, что меняет функцию; отдельный PR на документацию нужен для аудита, корректировки и переноса существующего содержания.
2. Не смешивать **`current`** (подтверждено кодом/тестом), **`planned`** (требование/дизайн) и **`legacy`** (существующий робототехнический домен на период миграции). По умолчанию не объявлять план реализованным.
3. Источник истины для текущего поведения — код и исполняемые тесты, для целевой архитектуры — согласованные ADR и продуктовые требования. При расхождении исправлять документы вместе с кодом или фиксировать открытый blocker.
4. Все пользовательские и смысловые технические тексты на русском. Код, названия полей, API и команды сохраняют точный синтаксис.
5. Не добавлять реальные ПДн, VIN, номера телефонов, логины, клиентские документы, внутренние адреса и секреты в примеры и скриншоты. Использовать синтетические данные и фиктивные реквизиты.
6. Для новой роли, кнопки, маршрута, бизнес-правила, статуса, API endpoint, миграции, переменной окружения или процесса обязательно выполнить документационный impact assessment.
7. Не дублировать бизнес-правила. Ссылаться на канонические ADR/контракты, где это возможно.

## Структура руководства по действию

Каждая инструкция пользователя должна содержать:

- **Статус:** current/planned/legacy; соответствующая версия приложения/commit или релиз.
- **Для кого:** роль и права, необходимые предварительные условия.
- **Когда использовать:** цель операции и точка входа в интерфейс.
- **Действия:** нумерованные шаги с точными надписями кнопок/полей и страниц.
- **Результат:** что видно после успешной операции; где проверить.
- **Ошибки/исключения:** нет прав, неверные данные, конфликт/устаревшая версия, отсутствие сети, отмена/возврат.
- **Скриншоты:** только синтетические; источник и дата проверки.
- **Проверено:** ссылка на UI/API сценарий или ручной протокол QA.

Если операция не реализована, документ может быть требованием или UX-планом, но он не должен выглядеть как инструкция действующего продукта.

## Техническая документация

При изменениях обновляются применимые разделы:
- API → `contracts/openapi.yaml`, описание endpoint/error/auth, генерация SDK;
- БД → актуальная ER/DDL модель, Alembic revision, совместимость, rollback и тесты;
- Backend/права → модульные границы, FSM, роли, ownership/ACL;
- Frontend → маршруты, UI состояния, screen flows, navigation;
- Инфраструктура → Compose, `.env.example`, secrets, health, процедуры backup/restore, команды Linux и Windows CMD;
- Интеграция OEM → provider contracts, source revision/licensing, ошибки, актуальность;
- Mobile → versioned API, отдельный auth flow, offline, уведомления.

## Проверка в каждой Issue и PR

**Документационный чек-лист (обязательно):**
- [ ] Обновлены относящиеся к изменению technical docs.
- [ ] Обновлены руководства пользователей затронутых ролей или явно отмечено, что UI/сценарий ещё planned.
- [ ] Все утверждения отражают реально существующие экраны, API и статусы.
- [ ] Ссылки/якоря и примеры конфигурации проверены; не добавлены секреты/ПДн.
- [ ] Приложены пути файлов и доказательства: соответствующий тест, E2E или ручная проверка.
- [ ] Если документационного влияния нет, в PR указана проверяемая причина: `Documentation impact: none — <причина>`.

## Гейты

- **Перед merge:** PR reviewer сверяет документацию с diff, tests и UI. Отсутствующий docs impact — Changes Requested.
- **Перед release:** QA проверяет пошаговые инструкции на тестовом релизе, навигацию, отображение скриншотов и доступность разделов; версии user docs соответствуют release tag.
- **После изменения UX/API:** инструкции обновляются в том же PR, а не отдельной «когда-нибудь» задачей.
- **Автоматизация:** задача #125 внедряет CI-проверки Markdown links/anchors, navigation, schema agreement, доступности/отображения.

## Риски миграции

README и текущая техническая спецификация пока описывают роботов. Не объявлять эти документы целевой документацией автосервиса. Зафиксировать карту legacy → auto в #122, сохранить существующие доказательства безопасности и синтетический dev-mode до полного cutover.

## Автоматическая проверка ссылок (реализована в #125)

Запуск из корня репозитория:

```bash
python scripts/check_docs_links.py
PYTHONPATH=apps/api python -m pytest -q tests/bootstrap/test_docs_links.py
```

Проверка не требует сети: проходит по корневым Markdown-файлам, `docs/**/*.md` и `infra/**/*.md`, проверяет существование относительных ссылок, запрет переходов за пределы репозитория и GitHub-якоря заголовков. Внешние HTTPS URL **не** проверяются на доступность (это отдельный мониторинг), как и фактическое соответствие скриншотов UI. Этот gate добавлен в GitHub Actions `api` job.

Если исправить битую ссылку невозможно из-за ещё не реализованного документа, не добавляйте ссылку на отсутствующий файл: вместо неё укажите `planned` и соответствующую GitHub Issue.
