# API — контракт, реализации и правила дальнейшего развития

**Статус: current только для проверенных endpoint в текущем robot domain; новые автомобильные API пока planned.** Дата сверки 26.10.2026.

Источник истины для **намерений** — `contracts/openapi.yaml`; для **фактических HTTP-handler** — `apps/api/roboport_api/main.py`, auth/oidc handlers и исполняемые `tests/contract/`, `tests/integration/`. Файл контракта не является доказательством, что операция реализована.

## Уже существует в текущем коде

- Публичный каталог роботов и пагинация (например `/api/v1/catalog/brands`, `/api/v1/catalog/models`).
- Синтетические учётные записи: HTTP login/logout/session, OIDC/Keycloak PKCE и проверка полномочий.
- Закрытые API заявок/смет, согласие на версию, жизненный цикл ремонта и складские действия.
- Сотруднические очереди, аудит, запросы на подтверждение гостевых заявок и обращения к приватным документам.
- Health endpoints `/health/live` и `/health/ready` (503 без необходимых служб — fail-closed).

**Не подтверждено:** что каждый path/operationId из OpenAPI уже реализован или доступен в любом режиме. Для нового авто-API требуются отдельные контракты и HTTP tests.

## Требования к новой операции Airmatik

1. Префикс `/api/v1/auto/`, стабильный `operationId`, OpenAPI + сгенерированные TS-типы в том же PR.
2. Серверная проверка сессии, RBAC и права на конкретные vehicle/order/location; VIN и связь автомобиля с клиентом **не дают** автоматически право на старый заказ.
3. Отказные состояния 400/401/403/404/409/422/429 и `Error {code,message,requestId}` без утечки PII, ID других пользователей или признака существования чужого объекта.
4. В транзакционных мутациях — серверный state guard, idempotency и безопасное поведение при retry/concurrency.
5. Приватные документы отдавать только после ACL, с no-store и аудитом. Внешние каталожные токены не передавать во frontend или мобильное приложение.
6. На каждый endpoint писать проверку счастливо/негативно/границы, затем проверять `contracts/openapi.yaml` скриптом и независимым валидатором в CI.
7. Документация каждого API и пользовательского сценария обновляется в том же PR. Следовать [политике](../DOCUMENTATION_POLICY.md).

## Проверки

В GitHub Actions: `python scripts/check_contract.py`, `python -m openapi_spec_validator contracts/openapi.yaml`, `PYTHONPATH=apps/api python -m pytest -q tests/contract`, отдельные PostgreSQL интеграционные тесты. Это проверяет отдельные грани, а не автоматически весь бизнес-контракт.

Автомобильные endpoints появятся в [#112](https://github.com/askarahodov/roboport/issues/112) и связанных задачах. Схемы `auto_vehicle` уже существуют, но REST/пользовательская регистрация автомобиля ещё planned.
