# Руководитель

> **Статус: частично current в синтетическом dev.** Независимое решение по тестовой привязке реализовано; production управление филиалом, отчёты и реальные доказательства остаются planned.

**Операции из текущего интерфейса:** [карта рабочих операций «БоксРитм»](STAFF_TASKS.md). Ссылка на справку по этому разделу доступна в `/staff` после проверки серверной роли; 401/403 остаются отказами, не подсказкой изменить чужой UUID. Ручная QA отложена.

## Для кого

Руководитель сервиса. Доступ к каждой операции должен проверяться по активной сессии, роли и конкретному объекту.

## Какие задачи появятся

Контроль загрузки постов, очереди заказов, сроков, качества, управления филиалами и отчётами.

## Что реально доступно сейчас

В закрытом dev-кабинете MANAGER может независимо подтвердить/отозвать связь клиент–авто (`/staff`), опубликовать версию сметы (`/staff/auto-estimates`), начать работы (`/staff/auto-execution`), выполнить **только условную** сверку и запечатать технический пакет (`/staff/auto-demo-close`). Полноценная касса, прибыль, зарплаты и выдача **не реализованы**. [Контракт](../auto/OPERATIONS_EVIDENCE.md).

## Подготовка пользовательской инструкции

Для ещё **не реализованных** операций отдельные экраны, скриншоты и пользовательские инструкции появятся только после согласования и проверки. Точные dev-операции и доказательства приведены ниже.

**Зависимости:** #113, #114, #116, #123. [Текущая карта продукта](../auto/PRODUCT.md) · [правила актуальности](../DOCUMENTATION_POLICY.md) · [индекс ролей](INDEX.md).

**До релиза:** запрещены настоящие VIN, телефоны, клиентские документы и платёжные данные в dev-стенде.

## Пошагово: решение менеджера (current dev)

1. Войти по HTTPS loopback под отдельной тестовой учётной записью `MANAGER`, назначенной на тот же автомобиль.
2. Убедиться, что клиент предъявил выданный приёмщиком одноразовый код. **Само знание UUID не является доказательством**; проверка настоящего права собственности ещё не реализована.
3. В `/staff` → «Автомобили (dev)» ввести UUID подтверждения в блоке **«Независимая проверка менеджером»**. Выбрать **«Подтвердить связь»** или **«Отклонить связь»**. Повторный review и самостоятельное одобрение автором кода запрещены backend.
4. Для отзыва использовать отдельное поле **«UUID связи для отзыва»**, отметить **«Подтверждаю отзыв тестовой связи»**, затем нажать **«Отозвать доступ»**. Отзыв вступает в силу на следующий запрос клиента.
5. При `403/404` не повторять операцию чужой учётной записью: сначала проверить серверное назначение и состояние процесса; 409 означает конфликт состояния там, где такой ответ предусмотрен.

**Ограничение:** массовая очередь авто-проверок, управление филиалами и выдача MANAGER/object scope через UI пока не реализованы. Все UUID — только синтетические.

## Делегирование INTAKE на конкретную тестовую машину

1. Войти с действующей ролью MANAGER и **отдельным назначением MANAGER** на синтетический автомобиль; глобальная роль без объекта недостаточна.
2. В `/staff` → «Автомобили (dev)» в блоке «Делегирование приёмщика (dev)» ввести UUID машины и UUID сотрудника с действующей ролью INTAKE. Нажать «Назначить приёмщика».
3. «Обновить назначения» показывает активных INTAKE **только по этой машине** (UUID, без ФИО/email). После отзыва права приёмщика перестанут действовать на следующем запросе.
4. Для отзыва нажать «Отозвать назначение» рядом с сотрудником; статус отзыва сохраняется в неизменяемом журнале. При 403/404/409 проверить назначение менеджера, глобальную роль сотрудника и наличие уже действующей записи.

Эта функция не назначает MANAGER/ADMIN, не управляет филиалами, не создаёт сотрудников и не даёт доступ к реальным данным. [Техническая процедура](../auto/VEHICLE_OWNERSHIP.md).


### Повтор назначения после сетевого сбоя (dev)

При назначении INTAKE интерфейс использует `Idempotency-Key`. Повтор с тем же автомобилем и сотрудником после потери ответа безопасно получает существующий результат; замена параметров вызывает новый ключ. После отзыва назначение не считается повторно действующим. Подробнее — [технический протокол](../auto/VEHICLE_OWNERSHIP.md).


### Повтор решения по заявке после потери ответа (dev)

При «Подтвердить связь» или «Отклонить связь» интерфейс использует уникальный `Idempotency-Key`, который сохраняется в памяти до успешного результата и повторяется при повторной отправке **той же** UUID-заявки с тем же решением. Сервер повторно проверяет MANAGER scope и независимость; при изменении решения, отзыве роли или машины прежний успешный ответ не используется. Повтор не создаёт второго события audit. См. [протокол](../auto/VEHICLE_OWNERSHIP.md).


## Добавление услуги в автомобильный заказ-наряд (только synthetic dev)

На локальном HTTPS loopback-стенде откройте раздел **«Услуги наряда (dev)»** (`/staff/auto-order-services`). Укажите UUID организации, филиала и существующего автомобильного заказ-наряда. При действующей роли MANAGER филиала и подтверждённой связи клиента с автомобилем появятся списки **«Уже выбранные услуги»** и **«Каталог филиала»**. Нажмите **«Добавить услугу»**, затем проверьте, что она отображается в выбранных, а кнопка стала **«Уже добавлена»**. Повтор не создаёт дубликат. Если доступ отозван, запись отменена, связь неподтверждена или чужой филиал — экран скрывает каталог и возвращает отказ; не пытайтесь изменить UUID для обхода защиты. При ошибке сети сначала нажмите «Повторить загрузку», чтобы проверить результат до повторного действия. Это только выбор синтетической услуги, без цен, списаний, ремонта, согласования сметы и документов. Подробный [контракт и приёмка](../auto/WORKSHOP_OPERATIONS.md).


## Публикация неизменяемой автомобильной сметы (current-dev)

Откройте `/staff/auto-estimates` под ролью `MANAGER` нужного филиала. Введите UUID организации, филиала и ранее созданного заказ-наряда с выбранными услугами; для **каждой** строки задайте точную сумму **в копейках**. Кнопка **«Опубликовать версию»** создаёт новый неизменяемый снимок услуг с контрольной суммой и номером версии. До решения клиента можно выпустить уточнённую версию; прежняя сохраняется для аудита, но согласовать её уже нельзя. После `APPROVED` или `DECLINED` новые версии и услуги блокируются. При 403 проверьте действующие права на филиал и подтверждение связи; при 409 обновите список, не пытайтесь редактировать согласованную запись. Работа только с искусственными данными, без фискализации и реальных подписей. [Полный контракт](../auto/ESTIMATES.md).


## Запуск согласованного исполнения (current-dev)

После последней одобренной клиентом версии сметы и приёмочного осмотра в `/staff/auto-execution` укажите UUID организации, филиала, заказ-наряда. Нажмите **«Начать работы (MANAGER)»**. Без одобрения либо после отзыва подтверждения клиент–автомобиль операция запрещена. После запуска сотрудники фиксируют работу и материалы, но **не** открывают выдачу автомобиля. [Пошаговый процесс](../auto/EXECUTION.md).


## Условная сверка и технический пакет перед выдачей (current-dev)

В синтетическом HTTPS loopback dev, после независимого QC PASS, откройте `/staff/auto-demo-close`, введите UUID организации, филиала и заказ-наряда. Сверьте сумму согласованной сметы в копейках. **«Условное внесение»** и **«Условный возврат»** создают только тестовые события: это не реальные платежи. Дождитесь нулевого условного остатка и закрытия всех складских резервов; после этого нажмите **«Зафиксировать технический пакет (MANAGER)»**. Пакет immutable, содержит SHA-256 и не является актом выдачи. Любой 403 или 409 требует проверки роли, текущей связи и журнала, а не смены чужих UUID. [Подробный процесс](../auto/DEMO_CLOSE.md). **Выдача автомобиля и юридические финансовые действия не разрешены**.

## Загрузка постов руководителя (current-dev, #171)

Откройте `/staff/auto-bay-occupancy` → заполните UUID организации/филиала, выберите **до 31 локального календарного дня** → нажмите **«Сформировать отчёт»**. Нужна действующая филиальная роль `MANAGER`, сессия и работающий филиал. В таблице отображаются **текущие** записи и календарные посто-часы, без VIN/ФИО/цен. После переноса или отмены данные меняются при повторном запросе; старая бронь не входит в отчёт. Часы дня учитывают DST (23/25), а процент — доля **от круглосуточной календарной ёмкости**, не реальная производственная загрузка по графику сотрудников. При `403` таблица очищается; при `422` проверьте даты; при сетевой ошибке повторите запрос. Указание чужой организации не даёт доступа. [Формулы, API и тесты](../auto/REPORTING.md). Финансовый и BI модуль с выручкой, валовой прибылью, ABC/XYZ остаётся `planned` (#171/#119).


### Учёт действующих смен и назначений в отчёте (current-dev, #171)

В разделе **«Загрузка постов (dev)»** та же таблица показывает дополнительные столбцы: сколько сотрудников имеют действующие смены и сколько **плановых** часов смен/назначений приходится на выбранные локальные сутки. После переноса или отмены брони старое назначение исключено; после снятия смены из текущего плана исключается и она. Столбец «Доля назначений от смен» означает долю забронированных часов специалиста **от действующих смен**, а не фактически выполненную работу. При отсутствии смен вместо процента отображается **«Нет действующих смен»**. Руководитель не получает фамилии/UUID сотрудников из отчёта. Для закрытия реальной производительности и зарплаты необходимы учёт рабочего времени, подтверждённые нормы, финансовые документы и отдельные согласования. [Формулы и API](../auto/REPORTING.md).


## Зарегистрированные трудозатраты из заказ-нарядов (current-dev, #171)

Откройте `/staff/auto-bay-occupancy`, введите свой филиал и локальные дни → **«Сформировать отчёт»**. Столбцы **«Записи труда»**, **«Минуты по журналу»** и **«Завершено исполнений»** показывают агрегаты из неизменяемых событий автомобильных WorkOrder. Механик сохраняет `actualMinutes` в `/staff/auto-execution`: запись учитывается по локальному дню её создания, повтор POST не удваивает сумму. Завершение исполнения не является QC PASS, оплатой или выдачей. Менеджер видит только агрегаты своего филиала, без ФИО/UUID работников или клиентов; табель, payroll, финансы остаются `planned`. [Методика](../auto/REPORTING.md).


## Создания, переносы и повторные бронирования (current-dev, #171)

В `/staff/auto-bay-occupancy` откройте отчёт за локальные дни выбранного филиала. Столбцы «Новые записи», «Отмены», «Переносы» относятся к **датам регистрации действий**; «Начала записей», «Клиенты по записям», «Повторные бронирования» относятся к **дню начала актуальной неотменённой брони**. Повторный клиент — это клиент с ещё одной более ранней записью того же филиала, даже если она была отменена. Одна запись, перенесённая несколько раз, не превращается в несколько клиентов. **Это не подсчёт состоявшихся визитов**, не retention на фактических покупках и не выручка: факт приёма автомобиля и финансовые основания здесь не зарегистрированы. При 403 обновите роль, при 422 проверьте диапазон; чужой филиал и отозванная сессия не дают доступа. [Формулы и тесты](../auto/REPORTING.md).

## Реестр обращений CRM своего филиала (current-dev, #169)

Откройте `/staff/auto-crm-leads` со scoped MANAGER сессией. Список включает только обращения с действующей подтверждённой связью своего филиала; смотрите источник, ответственного и неизменяемые переходы `NEW → QUALIFIED → BOOKED` или `LOST` с кодом отказа. `BOOKED` — связь с существующим Appointment, **не** факт посещения, оплаты или отправки сообщения. ### Аудит внутренних CRM-задач приёмщика (current-dev, #169)

Откройте `/staff/auto-crm-leads`, выберите организацию/филиал
с активной ролью `MANAGER`, затем обращение и блок
«Задачи по обращению». Видны назначенный владелец,
тип задачи, срок и финальное событие `DONE`/`CANCELED`.
Менеджер может создать задачу владельцу обращения, завершить

после `BOOKED` или `LOST` новые задачи блокируются.
Это внутренняя плановая работа персонала, **не отправка клиенту
и не автоматическая рассылка**. [Описание и доказательства](../auto/CRM.md).


## Контроль ремонта и повторное обслуживание (current-dev, #169)

В `/staff/auto-crm-leads` руководитель с действующей филиальной
ролью MANAGER может выбрать подтверждённое обращение «Записан»
своего филиала, связанное с уже завершённым заказ-нарядом и
независимым QC PASS. Раздел «Контроль после выполненного ремонта»
позволяет создать единственную **внутреннюю** задачу SERVICE_REVIEW
по UUID наряда и сроку (не далее 90 дней). Проверка попадёт в
общую очередь. Повтор с исходным `requestKey` безопасен,
вторая задача по тому же наряду запрещена (`409`).
При отзыве роли/verified-связи `403` запрещает операции.
Это не сообщение, повторная бронь, юридический акт или факт контакта
с клиентом. [Процедура и негативные сценарии](../auto/CRM.md).

и обращение с действующей подтверждённой связью. Нажмите

## Воронка CRM по источникам и текущим этапам (current-dev, #171)

Откройте `/staff/auto-crm-funnel` («Воронка CRM (dev)»).
Укажите **UUID организации** и **UUID филиала**, где вы MANAGER.
В полях «С даты создания» и «По дату создания» выберите
от 1 до 31 локального календарного дня включительно и
нажмите **«Построить воронку CRM»**.

В таблице «Текущие этапы по источникам обращений» проверьте
строку **«Все источники»** и три источника: Сайт, Звонок,
Личное обращение. Для каждого видны «Всего», «Новое»,
«Обработано», «Записан», «Отказ», «Доля записанных».
Во второй таблице — причины текущих отказов
(Стоимость, Сроки, Нет ответа, Прочее).

Чтобы сохранить все показатели для внутренней проверки, после
построения нажмите **«Скачать воронку CRM в CSV»**. Будет скачан
CSV UTF-8 с разделителем `;`: строка всех источников, три отдельных
источника, итоги этапов и причины отказа. Доля записанных
указана в базисных пунктах (2500 = 25%), пустая ячейка
означает отсутствие обращений. Выгрузка перепроверяет
права руководителя и формируется по текущим данным.
При отзыве роли `403` файл не выдаётся, открытая таблица
скрывается; ошибку сети можно повторить кнопкой.

**Как интерпретировать:** дата относится к **созданию**
обращения, а этап — к **последней зарегистрированной стадии
сейчас**. Доля записанных не означает состоявшийся ремонт,
оплату или выручку. Отозванное подтверждение автомобиля больше
не учитывается; у пустой когорты доля показана «—».
Коды PHONE/WALK_IN — лишь тестовые источники, не факт
связи с клиентом. Отчёт не содержит персональных данных.

Если кнопка отключена, проверьте UUID и период. При `403`
проверьте серверную роль MANAGER именно для филиала,
при `422` — даты; при `5xx` или повреждённом ответе
данные скрываются, запрос можно выполнить заново.
Смена филиала/даты сбрасывает предыдущие результаты.
[API, методика и проверки](../auto/REPORTING.md).


## ABC/XYZ по выданным запчастям (current-dev, #171)

Для операционного анализа склада откройте
`/staff/auto-stock-abc-xyz` — пункт
«ABC/XYZ склада (dev)». Введите UUID тестовой
организации и филиала, где у вас действующая
роль `MANAGER`. Выберите «С месяца» и
«По месяц» так, чтобы охватить **3–12 уже
завершённых календарных месяцев**, нажмите
**«Построить ABC/XYZ»**.

Вверху видны количество SKU (включая товары без
выдач), сумма зарегистрированных выдач,
возвратов и разница, затем числа товаров
классов A/B/C, X/Y/Z и без выдач.
В таблице сортировка от большего объёма
выдач к меньшему; нажимайте
**«Следующая страница»** (25 позиций)
и **«Предыдущая страница»**, чтобы
просмотреть весь ассортимент. Отдельно
показаны месячные выдачи и коэффициент
вариации.

Нажмите **«Скачать весь отчёт CSV»** после расчёта,
чтобы получить ведомость всего филиала (максимум 10 000 SKU),
а не только текущую страницу. CSV содержит артикул,
UUID товара, классы и помесячные количества; разделитель `;`,
кодировка UTF-8. Права MANAGER проверяются повторно при
скачивании. При отзыве прав список очищается; при `409`
файл не выгружается частично. Это свежий срез данных,
который может отличаться от ранее открытой таблицы.

**Важно:** классы ABC рассчитаны только
по количеству выданных складских единиц;
у разных SKU нет гарантированной общей
единицы или подтверждённой стоимости.
XYZ не учитывает возвраты в месячной
вариации. Это **не финансовый ABC,
себестоимость, прогноз закупок или
факт оплаты**. Для решений о деньгах
нужны подтверждённые цены и отдельная
методика.

Если кнопка неактивна, проверьте месяц,
диапазон и UUID. `403` — нет роли
MANAGER именно этого филиала; `422` —
неверный диапазон; `409` — превышена
техническая вместимость отчёта
(данные намеренно не обрезаются).
Смена филиала или ошибка запроса
скрывает предыдущую таблицу.

### Ответ на уточнение клиентской сметы (current-dev, #114)

В /staff/auto-estimates менеджер с действующей ролью своего филиала увидит актуальную опубликованную версию и код причины уточнения клиента. Пока ответа нет, публикация новой версии блокируется. Кнопка «Ответить: пояснение предоставлено» сохраняет EXPLAINED и даёт клиенту возможность решить по текущей неизменённой смете; это технический ответ, не отправка сообщения. Кнопка «Ответить: подготовить новую версию» сохраняет NEW_VERSION_REQUIRED, запрещает решение по старой версии и позволяет менеджеру опубликовать новый полный снимок через «Стоимость услуги» / «Опубликовать версию». Для вопроса сохраняется ровно один immutable ответ; повтор с тем же ключом идемпотентен. Чужой филиал и отзыв прав/vehicle proof — 403, повтор с другим ответом или устаревшая версия — 409. Только синтетические заказы; не юридическая подпись и не production.


## Смета с тарифом нормо-часа (current-dev, #114/#167)

В `/staff/auto-estimates` укажите UUID своей организации, филиала и наряда с выбранными услугами. На форме **«Новая неизменяемая версия»** в списке **«Способ расчёта стоимости»** выберите **«По нормо-часу и тарифной категории»**. Для каждой услуги укажите «Категория тарифа ...» (общий/диагностика/мастер) и «Ставка нормо-часа ..., коп./час». Поле «Расчёт ...» показывает предварительную стоимость по плановым минутам услуги с округлением 0,5 копейки вверх. Нажмите **«Опубликовать версию»**: сервер сам проверит список услуг и пересчитает суммы.

После публикации видны код тарифной категории, ставка, минуты и сумма каждой строки. Клиент получит их внутри **именно этой** версии на `/account/auto-estimates` и сможет согласовать либо отклонить. Для пересмотра тарифа до решения создайте новую версию; ранее опубликованные данные неизменны. Ручной режим по-прежнему работает. 422 означает неверные поля/слишком большую сумму, 409 — изменившийся набор услуг, устаревшую версию или иной payload по старому ключу, 403 — отозванный доступ; при сетевой ошибке — **«Повторить тот же запрос»**. Роль MANAGER необходима для публикации. Выбор категории не подтверждает реальные квалификации механика и не начисляет оплату/зарплату. [Полный расчёт и API](../auto/ESTIMATES.md).


## Независимая приёмка частичной закупки по WorkOrder (current-dev, #443)

В `/staff/warehouse-supplier-orders` менеджер своего филиала видит **только синтетический** реестр с источником, ценой и статусами: заказано / документировано / принято / оценено / отменено / к поставке. Создаёт закупку и черновик доставки только сотрудник с действующим **WAREHOUSE** object grant; видимость пункта меню MANAGER не заменяет этого разрешения.

В `/staff/warehouse-receiving` отдельный MANAGER просматривает очередь и принимает черновик, который создал WAREHOUSE, после чего фиксирует `currency=RUB`, `purchase_unit_net_minor`, `supplier_price_revision`, `supplier_quoted_at` по неизменяемому заказу. Эти значения приходят из защищённой очереди **«Показать документы без оценки»** и автоматически подставляются при **«Выбрать для оценки»**; вручную вводится только условный НДС. Нельзя переоценить проведённый документ другой ценой, принять чужой филиал или самостоятельно подтвердить собственную складскую приёмку. 409 — перечитать документ и выбранное предложение, не дублировать запись. Реальные расчёты с поставщиками и НДС по юридическим документам остаются planned. [Полная инструкция](../auto/SUPPLIER_PURCHASES.md).


## Управление документами, сметой и скидками с ограничениями (#446, dev)

Действующая роль MANAGER сама по себе больше не гарантирует права на
каждый документ: ADMIN может отдельно ограничить `READ`, `CREATE`,
`EDIT`, `CLOSE`, `WRITE` и `PRICE_SALES` в своём филиале или
для конкретного сотрудника. На `/staff/auto-estimates` запрет
`PRICE_SALES` **не показывает частичную сумму**, а возвращает 403.
`DISCOUNT=DENY` запрещает публикацию сметы с `discountBps>0`,
но сохраняет возможность опубликовать обычную смету при наличии
`CREATE`. Ответ на запрос клиента об уточнении требует `EDIT`.
На `/staff/auto-demo-close` чтение технической сверки требует
`READ` и `PRICE_SALES`, новые условные записи — `CREATE`,
запечатывание пакета и `CLOSED_TECHNICAL` — `CLOSE`.
Любое действие также требует live MANAGER, исходный customer proof,
принятую смету и QC; `ALLOW` не отменяет эти бизнес-условия.
При 403 не перебирайте UUID, обратитесь к ADMIN за разрешённым
изменением политики; при 409 перечитайте актуальный документ, не
дублируйте финансовое событие. Реальные деньги и юридические подписи
не обрабатываются. [Границы ACL](../auto/DOCUMENT_ACCESS.md).
