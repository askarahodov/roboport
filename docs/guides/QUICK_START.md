# Быстрый старт по ролям — автомобильный сервис (synthetic dev)

> **Версия базы:** автомобильная UI-навигация после cutover PR по #165, 09.11.2026; серверные инструкции сверяются с текущим `main`.
> **Проверяемый статус:** `current-dev` означает только закрытый синтетический
> HTTPS loopback-стенд, **не** production. `planned` — кнопки и операции нет.
> `legacy` — робототехническая система, не руководство автосервиса.

## Важные правила до первого действия

Нужна заранее подготовленная тестовая PostgreSQL 17, включённые
`ROBOport_SYNTHETIC_AUTO_API` и `ROBOport_SYNTHETIC_AUTH_API` только в
разрешённом loopback-контуре, тестовая учётная запись и действующий grant
конкретной организации/филиала. **Не вводите** настоящие VIN, телефоны,
фамилии, номера заказов, паспортные сведения, файлы клиента или реквизиты карт.
Обычная публичная страница или знакомый UUID **не дают права** выполнить
операцию. Вход/просмотр разрешён только после серверной проверки сессии.

Действия нескольких ролей в одном тестовом заказе выполняйте **отдельными
учётными записями**, а не путём самоназначения ролей. Отзыв полномочий должен
всегда блокировать дальнейшую операцию. При неизвестном результате записи
повторяйте запрос **с прежним** ключом через одноимённую кнопку, а не
создавайте второй платёж, резерв, приёмку или согласие.

## Навигация после UI cutover

Главная `/` относится только к автомобильному сервису. Клиентские разделы: `/account/vehicles`, `/account/auto-booking`, `/account/auto-orders`, `/account/settings`. В `/staff` открывается список автомобильных задач согласно действующим ролям, а не старая очередь `service_ticket`. Robot URLs `/robots`, `/catalog/*`, `/request-demo`, `/account/claim` больше не отображают страницы; закрытые клиентские `/account/robots`, `/account/tickets`, `/account/estimates`, `/account/documents` не дают доступ к старой истории. Исторические robot HTTP-маршруты удалены из live ASGI; архивные данные и контрактные черновики ещё требуют отдельного decommission #165; в них нельзя вводить реальные сведения.

**Пошаговая справка для сотрудников из самого /staff:** [карта рабочих операций](STAFF_TASKS.md) — точные маршруты и роли, безопасные 401/403/409, ссылки для каждого раздела, граница synthetic/production.

**Навигатор по конкретной задаче:** [роль → экран → проверка → отказ](ROLE_NAVIGATOR.md). Он различает доступный synthetic dev и запрещённые production-операции.

## Один воспроизводимый автомобильный заказ-наряд: от записи до технического пакета

1. **INTAKE** создаёт/проверяет synthetic запись на пост в
   [календаре](../auto/WORKSHOP_OPERATIONS.md). До назначения автомобиля
   клиент подтверждает одноразовый код, затем **другой MANAGER**
   независимо одобряет конкретную связь. Без `verified_at` не должно
   возникнуть ни истории клиента, ни права на заказ.
2. **INTAKE** создаёт WorkOrder через действующую запись, добавляет выбранные
   услуги в `/staff/auto-order-services` и фиксирует осмотр автомобиля
   в `/staff/auto-workshop-qc`. Состав работ уже нельзя произвольно
   менять после первой опубликованной сметы.
3. **MANAGER** публикует цены *по всем* выбранным услугам в
   `/staff/auto-estimates` (в целых копейках, RUB). Версии immutable.
   **CLIENT** открывает собственный список в `/account/auto-orders`,
   нажимает **«Подробнее о заказе»**, проверяет последнюю версию и
   **«Согласовать последнюю версию»** либо **«Отклонить последнюю версию»**.
   Старую версию нельзя согласовать, после принятого решения нельзя
   тихо изменить смету.
4. **MANAGER** запускает работу в `/staff/auto-execution`;
   **MECHANIC** фиксирует фактические минуты каждой согласованной услуги;
   **WAREHOUSE** выдаёт из заранее зарезервированной партии;
   **MECHANIC** подтверждает получение. Неполные услуги/выдачи
   блокируют завершение. Последний этап — **независимый QC другим
   механиком**, только после закрытия работ.
5. **MANAGER** на `/staff/auto-demo-close` сверяет только синтетические
   `SIM_PAYMENT`/`SIM_REFUND`, **WAREHOUSE** освобождает остатки резерва,
   затем MANAGER создаёт одноразовый неизменяемый технический пакет SHA-256.
   **CLIENT** видит его в истории своего заказа.
6. **STOP:** пакет не является актом выдачи, `releaseAllowed: false`;
   реальные деньги, фискализация, юридические подписи и передача автомобиля
   запрещены до отдельного релизного решения по #119.

## Ошибки: безопасные первые действия

| Что видите | Что делать | Чего не делать |
|---|---|---|
| **401** — нет действующей сессии | Выйти из dev-экрана и войти заново через тестовую авторизацию | Не переносить cookie/секреты между пользователями |
| **403** — недостаточно прав или связь отозвана | Проверить назначение на конкретный филиал, роль и подтверждение клиент–авто; обратиться к администратору | Не подставлять другой UUID для обхода |
| **404** — скрытый или неизвестный объект | Проверить собственный список; чужой заказ специально не раскрывается | Не перебирать идентификаторы |
| **409** — конфликт версии/остатка/последовательности | Перечитать состояние и актуальную смету; исправить условия и повторить только разрешённое действие | Не переписывать согласованную смету, не выдавать «задним числом» |
| **422** — ошибка ввода | Проверить формат UUID, целые копейки/минуты и обязательные поля | Не использовать реальные реквизиты для проверки |
| **429** — лимит подтверждения | Дождаться допустимого окна и обратиться к приёмщику | Не создавать новые подтверждения для обхода |
| Сеть оборвалась после POST | **«Повторить тот же запрос/решение»** с исходным ключом либо перечитать журнал | Не генерировать новый ключ и не дублировать действие |

[источники и сценарии](../auto/OPERATIONS_EVIDENCE.md).
Правила подготовки безопасных [скриншотов и ручной приёмки](SCREENSHOT_EVIDENCE.md).

### Техническая проверка preflight перед автомобильным выпуском (current-dev)

Для сверки происхождения CI используйте [консолидированный release preflight](../auto/RELEASE_PREFLIGHT.md), а не только зелёную страницу Actions: требуется **тот же полный SHA, что и текущий HEAD main**, один `push` run и 5/5 job, данные проверяются по GitHub API дважды на стабильность ref. Прежний успешный SHA после нового push не является release evidence. Даже успешная техническая сверка возвращает `verdict=BLOCKED` и `productionApproved=false` до независимой проверки security/legal/ops и закрытия требований #119. Не используйте synthetic дев-аккаунты и тестовые доказательства для реального релиза.


### Проверка восстановления целого автомобильного процесса (только CI)

Для synthetic PG17 доступен новый [контрольный пункт восстановления Appointment → WorkOrder → склад → история](../auto/RESTORE_CHECKPOINT.md): перед `pg_dump -Fc` CI создаёт изолированную фикстуру и SHA-256 фактического graph, затем выполняет `pg_restore`, сверку двух баз и отрицательные проверки триггеров на clone. Не используйте этот скрипт с production DSN, реальными VIN/ПДн или для публичного restore; он требует disposable `127.0.0.1:5432/roboport`. Полный реальный backup/restore и юридический/security/ops gate #119 всё ещё не подтверждены.
