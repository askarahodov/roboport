# Воспроизводимые скриншоты и проверка ролевой базы знаний

> **Состояние:** автоматические screenshots и навигационный smoke тестируются
> только на локальных синтетических страницах Docsify. Это **не независимая
> ручная QA-приёмка** и не скриншоты реального клиента.

## Как воспроизвести

В checkout точного Git SHA выполните из корня репозитория:

```bash
python scripts/check_docs_links.py
cd apps/web
npm ci
npx playwright install chromium
npm run test:docs:e2e
```

Windows CMD — аналогично:

```cmd
python scripts/check_docs_links.py
cd apps\web
npm ci
npx playwright install chromium
npm run test:docs:e2e
```

Docsify автоматически обслуживает Markdown из `docs/` на
`http://127.0.0.1:3080/docs/`. Скрипт Playwright
`apps/web/e2e-docs/role-screenshots.spec.ts` строит screenshots
**всех восьми ролевых руководств** на ширинах **390, 1280 и 1440 px**,
с цветовыми схемами **light, dark и auto**, без cookie, реальных VIN, имён,
платёжных реквизитов и иных персональных данных.
Ролевые руководства дают 8 × 3 × 3 = **72 снимка**, а навигатор задач дополнительно 1 × 3 × 3 = **9 снимков**; итого **81 проверяемый PNG**, плюс скриншоты ошибок
и текущие проверки навигации/поиска в `portal.spec.ts`.

Снимки сохраняются в каталоге результатов Playwright
`apps/web/test-results`. В GitHub Actions job `browser-e2e`
публикует артефакт **`roboport-browser-evidence`**, а `windows-cmd`
— **`roboport-windows-cmd-evidence`**. Срок хранения — 14 дней;
в обязательном PR указывайте ссылку на точный run ID, commit SHA
и реальное присутствие PNG/trace в артефакте. Отсутствующие screenshots
**нельзя** заменять макетами без пометки.

## Чек-лист независимого ручного QA

После автоматического прогона проверяющий с отдельной test-role и
синтетическими данными последовательно открывает:

| Что проверить | Desktop 1280 | Mobile 390 | Особые отказы |
|---|---|---|---|
| Администратор и журнал | light/dark | light/dark | 403 чужая организация, нет опасного bootstrap |
| Приёмщик и записи | light/dark | light/dark | отказ в работе без verified proof, двойная бронь |
| Механик и QC | light/dark | light/dark | FAIL, запрет QC своих работ, незакрытая выдача |
| Склад и возвраты | light/dark | light/dark | чужой филиал, 409 по резерву, idempotency |
| Руководитель и смета | light/dark | light/dark | версия устарела, принятую нельзя менять |
| Бухгалтер | light/dark | light/dark | **нет** реальной кассы, SIM не платёж |
| Клиент и история | light/dark | light/dark | другой владелец, revoke/404, застарелая смета |
| Мобильное приложение | light/dark | light/dark | только planned, не выдавать web за app |

Отдельно проверить: [навигатор задач](ROLE_NAVIGATOR.md) доступен через sidebar и клавиатуру на 390/1280, карточки ролей ведут к существующим страницам, таблицы прокручиваются внутри контента и не создают горизонтальный overflow; найти текущую запись клиента, а отдельную настоящую кассу и mobile — только как `planned`. Проверить поиск по запросам «смета», «отзыв», «склад»,
открытие sidebar клавиатурой с Enter/Space, видимый фокус, AA-контраст,
отсутствие горизонтального overflow, работа относительных ссылок;
для каждой страницы проверить действующий `current-dev` либо честный
`planned` и отсутствие скрытой реальной операции.
Для backend сценариев — отрицательные PG17 RBAC/BOLA и replay,
зафиксированные в [матрице](ACCESS_AND_TEST_MATRIX.md).

## Что записать в протокол

- Дата и **точный Git SHA**, run ID/URL GitHub Actions, браузер/ОС.
- Синтетический fixture/отдельная роль; никакой утечки credentials и PII.
- Какие PNG доступны, какие страницы и пункты меню сравнивались.
- Результат PASS/FAIL для каждой строки, шаги воспроизведения дефекта.
- Подпись **независимого** QA и отдельные security/legal решения по #119.

Без такого протокола нельзя закрывать человеческие acceptance criteria
#173/#123/#124, считать Docsify публичной готовой справкой или выпускать
автомобильный продукт.


## Автомобильный визуальный аудит #92

Дополнительный Playwright-тест `apps/web/e2e/visual-audit.spec.ts`
создаёт **189 PNG**: 21 актуальный маршрут/состояние × 390/1280/1440 px ×
Light/Dark/Auto. В отличие от старой версии, главная страница не дублируется:
включены публичная главная, вход, клиентские 401/403, пустой список
подтверждённых автомобилей, запись, заказ-наряды, рабочее место СТО,
календарь, приёмка, диагностика, сметы, QC, исполнение, закупки, приход,
CRM, сверка, 404 и статическая UI-галерея.

**Объём автоматической проверки:** один `main` и видимый `h1`,
отсутствие root horizontal overflow, отсутствие неперехваченных JS-ошибок,
keyboard/dialog/disabled/status в `/dev/ui-gallery`.
Роуты авторизации и автомобильного API в этом тесте возвращают исключительно
синтетические ответы: `401`, `403` и `{ "items": [] }`; тест **не**
утверждает, что есть законный доступ к чужому аккаунту или реальная операция.
Действительные ACL/tenant/QC проверяются отдельно в PG17/HTTP тестах.

Каждый прогон пытается снять **все 21 состояния**, даже если один из
маршрутов не загрузился, не показал обязательный заголовок или не прошёл
проверку overflow. Скрипт сохраняет PNG и `manifest.json` с
`syntheticOnly=true`, `approvedBaseline=false` и отдельными полями
`captured`, `checks` (`PASS/FAIL`), `failureKinds` для каждого состояния.
При ошибках проверки или JavaScript итоговый тест возвращает FAIL **после**
сбора доступных снимков; `captured=true` означает только наличие PNG, а не
успешную проверку. В манифест не записываются response bodies, токены или
персональные данные. Любой `FAIL` требует просмотра trace и исправления
корневой причины; не принимать такой набор за утверждённый baseline.

PNG и `manifest.json` сохраняются в `apps/web/test-results`, которые уже публикуются
GitHub Actions как `roboport-browser-evidence` (14 дней). Это **candidate
screenshots для независимого просмотра**, не утверждённые golden baselines
и не автоматическая pixel-diff регрессия. Не объявлять завершённый дизайн-DoD
по факту наличия PNG или green CI.

### Негативная регрессия сборщика доказательств

В том же `apps/web/e2e/visual-audit.spec.ts` запускается отдельный
Playwright-тест **с намеренно сломанным синтетическим HTML-маршрутом**.
Он проверяет три последовательных состояния: исправная главная → экран
без переключателя темы → исправная страница входа. Ожидаемый результат:
`PASS → FAIL (RENDER_THEME) → PASS`, три PNG на диске и полноценный
`manifest.json` с `syntheticOnly=true` и `approvedBaseline=false`.
Это **проверка самого механизма отказа**, а не разрешение ослабить боевой
аудит: в основной матрице любая запись `FAIL` по-прежнему делает CI красным.

Для адресного повторного запуска в `apps/web`:

```bash
npx playwright test e2e/visual-audit.spec.ts --grep "visual evidence continues after a deliberately broken screen"
```

Проверяются реально созданные ненулевые файлы, порядок обхода и содержимое
манифеста; в сценарии нет реальных данных, секретов и внешних сервисов.

**Для полного закрытия #92:** независимый проверяющий сопоставляет
каждую группу изображений с утверждённым Auto Digital #110, реальными
пользовательскими сценариями, contrast WCAG AA, keyboard/focus и мобильной
иерархией. В протоколе указывает точный commit SHA, run ID, PASS/FAIL,
проблемы и утверждённые изображения; только после sign-off допустимо
зафиксировать golden PNG и threshold для автоматического pixel-diff.
Автоматическое обновление baseline при падении теста запрещено.


## Снимки гранулярных ограничений (current-dev #446)

Тест `apps/web/e2e/auto-document-access.spec.ts` воспроизводит
в тестовом браузере 390 px и 1280 px: `/staff/auto-admin`,
публикацию DENY и ALLOW правил, аудит, effective preview,
отзыв доступа и тёмную тему. PNG `admin-deny-390-dark.png`
и `admin-allowed-1280-dark.png` попадают в CI
`roboport-browser-evidence`. Все имена сотрудников и ID
в тесте синтетические. Открыть UI по прямому адресу недостаточно:
ACL проверяется сервером. Без отдельного owner sign-off изображения
**не** считаются утверждёнными baseline #92 и не доказывают
независимый WCAG AA/manual PASS.
