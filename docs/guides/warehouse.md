# Кладовщик и закупщик

> **Статус: current-dev synthetic:** доступны отдельные экраны инвентаризации, прихода, выдачи/возврата и пересортицы. Полноценный production-склад и коммерческие закупки planned. Запрещены реальные складские данные.

**Операции из текущего интерфейса:** [карта рабочих операций «БоксРитм»](STAFF_TASKS.md). Ссылка на справку по этому разделу доступна в `/staff` после проверки серверной роли; 401/403 остаются отказами, не подсказкой изменить чужой UUID. Ручная QA отложена.

## Для кого

Кладовщик или специалист по снабжению. Доступ к каждой операции должен проверяться по активной сессии, роли и конкретному объекту.

## Какие задачи появятся

Поиск OEM/aftermarket, подбор аналогов с подтверждённой применяемостью, проверка остатков, резервирование, закупки, выдача и возвраты.

## Что реально доступно сейчас

Доступны синтетические партии и складской ledger: инвентаризация, приход, выдача по наряду, возврат, пересортица, серийные перемещения, освобождение неиспользованного резерва. **Автомобильный OEM-каталог и внешние коммерческие поставщики не подключены**; цены/применяемость без лицензированного провайдера недостоверны.

## Подготовка пользовательской инструкции

Для ещё **не реализованных** операций отдельные экраны, скриншоты и пользовательские инструкции появятся только после согласования и проверки. Точные dev-операции и доказательства приведены ниже.

**Зависимости:** #111, #115, #123. [Текущая карта продукта](../auto/PRODUCT.md) · [правила актуальности](../DOCUMENTATION_POLICY.md) · [индекс ролей](INDEX.md).

**До релиза:** запрещены настоящие VIN, телефоны, клиентские документы и платёжные данные в dev-стенде.


## Инвентаризация партии — доступный synthetic dev UI (#168)

Откройте пункт **«Инвентаризация (dev)»** верхнего меню (`/staff/warehouse-stocktake`). Работает лишь при локальной synthetic API и действующей сессии; это не производственный склад. Для подсчёта нужна роль WAREHOUSE выбранного филиала. Введите UUID организации, филиала, партии, фактическое неотрицательное количество и причину. Нажмите **«Сохранить подсчёт»**. На экране появляется UUID подсчёта, однако остатки ещё не изменены.

Для второго этапа **другой сотрудник** с ролью MANAGER того же филиала входит в собственную сессию, указывает тот же филиал и UUID подсчёта, затем нажимает **«Утвердить корректировку»**. При успешном ответе создаётся неизменяемый журнал утверждения; расхождение корректирует общий и партийный остаток атомарно. Самостоятельное утверждение собственного подсчёта запрещено даже при двух ролях. Утверждение может вернуть 409, если партия изменилась между подсчётом и проверкой; потребуется новый пересчёт.

**Ошибки:** 403 — сессия/CSRF/роль отозваны или нет доступа к филиалу; 409 — конфликт остатков или уже применённый запрос; 422 — неверные UUID/количество/причина. При потере ответа UI блокирует новый запрос и показывает **«Повторить с прежним ключом»**, чтобы не удвоить операцию. При смене организации/филиала прежний ожидающий запрос очищается. Проверка E2E: `apps/web/e2e/warehouse-stocktake.spec.ts`.

Поиск партий, отдельные приходные документы и регистрация серий существуют в synthetic dev; мобильное сканирование, юридически значимые документы и production-налогообложение не реализованы. Остальное остаётся planned в #168/#115; перед production обязателен gate #119.


## Список партий филиала (current-dev, часть #168)

На странице **«Инвентаризация (dev)»** после ввода UUID организации/филиала нажмите **«Показать партии»**. API `GET /api/v1/dev/auto/organizations/{org_id}/stocktake/lots?locationId={loc}&limit=30` возвращает не более 30 партий с артикулом, кодом партии/ячейки, размещённым остатком, общим физическим остатком SKU и резервом. Доступ имеют только действующие WAREHOUSE или MANAGER данного филиала; чужая организация не раскрывает список. Кнопка **«Выбрать партию»** подставляет UUID для подсчёта; при наличии следующей страницы используется непрозрачный для пользователя UUID курсора `afterLotId` (только текущий филиал). При отзыве прав экран показывает «Нет доступа к партиям этого филиала» и очищает прежний список. Отсутствие партий, загрузка и ошибка соединения обрабатываются отдельно. Реальный production доступ остаётся выключен.


## Документ прихода партии (current-dev; синтетический UI доступен)

На тестовой PostgreSQL 17 внутренний сервис теперь поддерживает **создание черновика** приходного документа сотрудником WAREHOUSE и **независимое подтверждение** другим MANAGER соответствующего филиала. Черновик включает существующую партию, количество и источник поставки. До подтверждения остатки не меняются; после подтверждения количество поступает одновременно на SKU и выбранную партию. Самостоятельное подтверждение, повторное зачисление, чужая организация, отзыв роли и неполная транзакция блокируются. Синтетический экран dev существует, публичный production запуск запрещён до #119. Не путать данный internal current-dev с готовым приёмом товаров на production.


### Приход запчастей на синтетическом стенде

Перейдите в **«Приход (dev)»** (`/staff/warehouse-receiving`). Сотрудник с текущим WAREHOUSE-grant филиала вводит UUID организации и филиала, выбирает партию в списке (либо вводит UUID), количество 1–1 000 000 000 и номер документа поставки. Нажмите «Создать документ». До подтверждения остатки не изменяются. **Другой сотрудник**, уже авторизованный как MANAGER того же филиала, отдельно открывает этот экран, вводит выданный `documentId` и нажимает «Подтвердить приёмку». Двойное подтверждение и самостоятельная приёмка запрещены; после успеха остаток SKU и партия увеличатся вместе. При HTTP 403 проверяйте действующий grant и филиал; 409 означает конфликт или ранее завершённый документ; 422 — неверные данные. При потере сетевого ответа используйте «Повторить с прежним ключом», а не новую отправку. Используйте только синтетические данные; реальные supplier invoices, цены/НДС и production полномочия ещё не внедрены.


### 3. Указать закупочную стоимость и сумму входящего НДС (current-dev)

На экране «Приход (dev)» после физической приёмки иной сотрудник с текущей ролью MANAGER вводит UUID принятого документа, ISO-код валюты (например, RUB), закупочную цену единицы и сумму НДС по документу **в минимальных единицах валюты** (для RUB — копейки), ревизию источника цены и время этого источника с часовым поясом. Нажмите **«Сохранить закупочную стоимость»**. В отчёте по отдельному журналу рассчитываются чистая стоимость партии, отдельно НДС и общая сумма. **Это не продажная цена и не заявка поставщику**. Веб-форма допускает только безопасно представимые целые суммы, чтобы JavaScript не округлял крупные значения. На 403 проверьте MANAGER/grant и филиал, на 409 — возможно, оценка уже зафиксирована или параметры idempotency конфликтуют. Изменить или стереть утверждённую стоимость нельзя; требуется отдельный будущий документ корректировки. Не считать эту dev-процедуру бухгалтерским/налоговым отчётом для production.


## Выдача и возврат по заказ-наряду (internal dev API)

В синтетическом окружении при включённом `ROBOport_SYNTHETIC_AUTO_API=1` кладовщик с активной ролью WAREHOUSE данного филиала может вызвать закрытые API `POST /api/v1/dev/auto/organizations/{org_id}/warehouse/work-orders/issue` и `/return`. Тело: `locationId`, `workOrderId`, `lotId` и положительное `quantity`. Дополнительно требуются локальная сессия, CSRF и UUID `Idempotency-Key`. Перед выдачей запчасть должна быть зарезервирована именно на заказ-наряд; возврат допускается лишь в пределах фактически выданного количества. 201 возвращает идентификатор immutable события, 403 означает отсутствие доступа, 409 — конфликт количества/резерва/повтора, 422 — неверный ввод. Веб-форма выдачи/возврата существует в закрытом synthetic dev, но подписи механика и передаточного документа пока нет; это не production операция. Подробнее: [автомобильный склад](../auto/PARTS_STOCK.md).


### Экран выдачи и возврата по заказ-наряду (current-dev)

Откройте **«Выдача (dev)»** (`/staff/warehouse-work-orders`). Укажите UUID организации, филиала, заказ-наряда и партии, положительное целое количество до 1 000 000 000. Сотрудник с активной ролью WAREHOUSE данного филиала нажимает **«Выдать из партии»** только после предварительного резерва на этот заказ-наряд; **«Вернуть в партию»** допускается для количества не больше фактической ранее выполненной выдачи. После 201 выводится UUID события, физический и партийный ledger меняются атомарно. Нельзя трактовать этот экран как подпись механика или оформленный расходный документ.

При 403/404 проверьте сессию, права филиала и включённый synthetic API; при 409 — резерв, количество либо повтор действия. При 422 исправьте входные данные. При 5xx, потере сети или некорректном ответе **не отправляйте новый запрос**: нажмите «Повторить с прежним ключом»; экран блокирует обе операции до этого повтора. При смене организации/филиала исходный ключ неопределённого запроса сохраняется, но повтор в другом контексте заблокирован: верните прежние UUID и используйте исходный ключ. Изменение пробелов в UUID также не сбрасывает операцию. Проверка browser E2E: `apps/web/e2e/warehouse-work-orders.spec.ts`.


## Подтверждение получения механиком (новый synthetic PG17 API; #168)

После успешной выдачи по заказ-наряду и получения `issueId` механик с действующим MECHANIC-grant того же филиала может подтвердить получение через закрытый `POST /api/v1/dev/auto/organizations/{org_id}/warehouse/work-orders/acknowledge`. Тело: `{"locationId":"UUID","issueId":"UUID"}`; требуются действующая локальная сессия, CSRF и новый UUID `Idempotency-Key`. Ответ 201 возвращает `handoffId`. Складские остатки при этом **не меняются повторно**: подтверждение ссылается на уже проведённую выдачу и записывает получателя в immutable журнал. Повтор с исходным ключом возвращает тот же результат; попытка вторичного подтверждения другим ключом — 409; неверный scope или отзыв MECHANIC — 403. Проверки: `tests/integration/test_pg_auto_stock_mechanic_handoff.py`. На экране «Выдача (dev)» механик в собственной сессии вводит полученный после выдачи UUID в поле «UUID выдачи» и нажимает «Подтвердить получение». Это подтверждение не проводит складские остатки повторно. Пока нет квалифицированной электронной подписи или юридически значимого акта. Только синтетический стенд; #168 остаётся открыт.


**Уточнение фактической передачи:** подтверждение механиком невозможно, если все выданные по соответствующему заказ-наряду и партии детали уже возвращены на склад (409); после частичного возврата подтверждение остаётся доступным для ненулевого непогашенного количества. Это дополнительная целостность synthetic ledger, а не юридический акт.


## Проверка целостности остатков (synthetic PG17, #168)

В базе доступно представление `auto_stock_reconciliation` для сверки SKU по организации и филиалу: `on_hand` (физический остаток), `reserved` (резерв), `lot_allocated` (сумма по партиям), `unallocated` (неразмещённый остаток), `available` (доступный остаток) и `discrepancy` (логический признак расхождения). Представление только для контролируемых внутренних диагностик; `SELECT` не должен предоставляться неавторизованным пользователям, публичного production API нет. Отрицательные значения, превышение резерва или размещения над физическим остатком считаются расхождением. Этот отчёт не заменяет акт инвентаризации или бухгалтерскую сверку.


## Серийные номера конкретной партии (только внутренний PG17, #168)

Синтетический сервис `register_lot_serial` привязывает уникальный в организации и SKU серийный номер к размещённой партии. Требует действующую сессию кладовщика WAREHOUSE именно указанного филиала, UUID запроса для безопасного повтора, точную идентичность партии и номер длиной 3–120 символов. Запись неизменяемая; на одном SKU нельзя дважды зарегистрировать одинаковый номер, а число регистраций в партии не должно превышать размещённый остаток на момент регистрации. При отзыве права повтор запрещён. Для регистрации серийного номера доступен закрытый dev HTTP и экран выдачи; сквозного движения отдельных экземпляров всё ещё нет. **Важно:** это регистрация происхождения, а не полный tracking единицы при выдаче/возврате или межфилиальном перемещении; существующие движения пока количественные. Для production и полного выполнения #168 необходим серийный movement ledger и все связанные отрицательные тесты.


### Регистрация серийного номера через интерфейс (synthetic dev)

В экране `/staff/warehouse-work-orders` выберите организацию, филиал и партию, затем введите «Серийный номер» и нажмите «Зарегистрировать серийный номер». Для операции требуется роль `WAREHOUSE`, действующая сессия, CSRF и `Idempotency-Key`. API: `POST /api/v1/dev/auto/organizations/{org_id}/warehouse/serials`, тело `{"locationId":"UUID","lotId":"UUID","serialNumber":"..."}`, ответ `201 {"serialId":"UUID"}`. При 5xx/потере ответа новая операция блокируется и повторяется исходный запрос с тем же ключом. Это регистрация идентификатора партии, **не** серийный журнал движения или разрешение использовать реальные данные.


## Пересортица запчастей — synthetic dev (#168)

Выберите пункт меню **«Пересортица (dev)»** (`/staff/warehouse-reclassification`). Кладовщик с WAREHOUSE филиала указывает UUID организации и филиала, **исходную** и **целевую** партии с разными SKU, положительное количество и причину. Кнопка **«Создать акт пересортицы»** сохраняет неизменяемый черновик; на этом этапе остатки не изменяются. Другой сотрудник с MANAGER того же филиала входит в свою сессию, указывает UUID акта и нажимает **«Утвердить пересортицу»**. Система атомарно списывает из исходных SKU/партии и зачисляет в целевые SKU/партию. Самоподтверждение, попытка списать резерв, пересортица зарегистрированных серий и чужого филиала запрещены.

При 403 проверьте разрешения, филиал и CSRF; 409 — уже принято, недостаточно остатка, серийные экземпляры либо несовпадающий повтор UUID; 422 — неверные поля. При временной ошибке или потере ответа **нельзя** создавать новый запрос: нажмите «Повторить с прежним ключом». При смене филиала возврат к исходному контексту обязателен для разблокирования повтора. Доступны только синтетические данные. Это не налоговый или юридически значимый первичный документ; стоимость и входной НДС не перераспределяются, реальные provider / customer flows закрыты до gate #119 и #111/#114/#115/#166.


## Движение серийной детали — synthetic dev (#168)

После создания серийной записи на странице выдачи скопируйте её UUID. Откройте **«Серии (dev)»** (`/staff/warehouse-serial-movements`), укажите организацию, **исходный** филиал и UUID серийной записи. Для выдачи введите UUID заказ-наряда с существующим резервом и нажмите **«Выдать серийную деталь»**. Для возврата того же экземпляра по наряду нажмите **«Вернуть серийную деталь»** — количество в исходной партии восстанавливается. Для перевода в другой филиал введите UUID целевой партии с тем же артикулом и нажмите **«Переместить серийную деталь»**; понадобятся действующие складские права обоих филиалов. После перевода исходным филиалом следующих операций становится филиал назначения.

Ошибки: 403 — нет сессии, CSRF или склада/филиала; 409 — неверное состояние единицы, резерв, повтор не того же запроса или недостаточный физический остаток; 422 — обязательный UUID либо структура тела невалидны. При 5xx/пропавшем ответе **не выполняйте новую операцию**: возвратите исходные организацию и филиал (если меняли их во время запроса) и нажмите **«Повторить с прежним ключом»**. `Idempotency-Key` сохраняется вместе с телом запроса.

Это работа только с синтетическим PG17, а не запуск реальных закупок. Списание поставщику, пересортица зарегистрированных серий, выдача клиенту и юридическая первичка требуют отдельных моделей и gate #119; проход CI не заменяет security/legal sign-off.


## Возврат поставщику с отдельной закупочной оценкой (синтетический dev)

Экран **«Возврат поставщику (dev)»** расположен по адресу `/staff/warehouse-supplier-returns`. Кладовщик `WAREHOUSE` выбирает организацию, филиал, UUID **ранее принятого и оценённого прихода**, количество, причину и номер обращения поставщику. Кнопка **«Создать акт возврата»** не меняет физический остаток. Другой сотрудник с правами `MANAGER` того же филиала открывает экран под своей сессией и утверждает UUID акта. Остаток партии и SKU уменьшается только после его утверждения; отдельно фиксируются закупочная стоимость и часть входного НДС исходного прихода.

При 403 проверьте актуальную роль, организацию, филиал и CSRF. При 409 проверьте исходный приход/оценку, доступное нерезервированное количество, серийные номера, идентичность approving employee и отсутствие повторно утверждённого акта. При неопределённом ответе нельзя создавать новый `Idempotency-Key`: верните исходный филиал и нажмите **«Повторить с прежним ключом»**. Это не подтверждённая кредит-нота поставщика: НДС к вычету или возмещению, расчёты и реальные PII недоступны до юридической и security приёмки #119. Нужна отдельная production бухгалтерская обработка.

## Очереди приёмки и оценки приходных документов (current-dev, #168)

На экране **«Приход (dev)»** сначала кладовщик WAREHOUSE своего филиала создаёт черновик с партией, количеством и источником. Черновик не меняет остатки. **Другой** сотрудник MANAGER в своей сессии выбирает **«Показать черновики»**. Список содержит артикул, партию/ячейку, количество и номер поставки, только для своего филиала. Нажмите «Выбрать черновик», сверьте товар и нажмите **«Подтвердить приёмку»** — физический SKU и партия увеличатся атомарно.

После подтверждения обе очереди обновляются: документ исчезает из черновиков и появляется в **«Принятые документы без оценки»**. Руководитель выбирает его кнопкой «Выбрать для оценки», указывает ISO-валюту, закупочную цену за единицу и НДС в минимальных денежных единицах, ревизию и время котировки, затем сохраняет оценку. После успешного сохранения документ исчезает и из второй очереди. Оба списка имеют постраничную навигацию (20 строк по умолчанию), загрузку и ошибки.

При изменении организации/филиала прежний список очищается. 403 означает отзыв MANAGER либо чужую организацию; ошибки ответа не открывают старые документы. Выбор из очереди не заменяет повторную серверную проверку права, другого автора, однократности приёмки и оценки. При неизвестном результате POST **повторите с прежним ключом**, не создавайте второй запрос.

Это synthetic dev без поставщиков и юридических оригиналов документов. Фактический налоговый вычет, бухгалтерская стоимость и production запуск остаются ограничены #119.

## Заказ поставщику по дефициту заказа-наряда (current-dev, #443)

1. В `/staff` выберите **«Заказы поставщикам (dev)»** → `/staff/warehouse-supplier-orders`, введите UUID своей синтетической организации/филиала, WorkOrder и партии SKU. Укажите количество, требуемое для работы; сервер под блокировкой SKU вычитает свободный остаток. **Без дефицита заказ создать нельзя**.
2. Сравните **две непроверенные offline оферты** (цена в копейках, количество, срок в днях, ревизия), укажите один выбранный вариант и нажмите **«Создать заказ поставщику»**. Ни реальной закупки, ни проводки в stock ledger пока нет.
3. Нажмите **«Обновить заказы»**, **«Выбрать заказ ...»**, введите число доставленных единиц (не более остатка к поставке) и номер синтетического документа. Нажмите **«Принять частичную поставку в черновик»**.
4. Независимый **MANAGER** завершает действующий процесс через `/staff/warehouse-receiving`: отдельно принимает физическую партию, затем фиксирует цену/НДС по выбранной ревизии оферты. PostgreSQL отклоняет цену, не совпадающую с неизменяемой офертой. Приход без этого подтверждения **не увеличивает остатки**.
5. Для следующей части повторите шаги 3–4. Если часть не поступит, установите чекбокс **«Подтверждаю отмену только непоставленного остатка заказа»**, затем **«Отменить непоставленный остаток»**. Принятые документы и их cost provenance нельзя отменить таким способом.
6. При 403/404 проверьте именно свой tenant/branch/grant. 409 означает конфликт объёма, конкуренции, цены, уже отменённого заказа или истёкшей оферты. При неизвестном результате POST используйте **«Повторить с прежним ключом»**, не отправляйте заказ заново с новым UUID.

Детальный [контракт заказа поставщику, стоимости и отката](../auto/SUPPLIER_PURCHASES.md). Этот сценарий работает только с синтетическими данными, **не** отправляет заказ внешнему поставщику; реальный OEM/оплата/юридическая первичка `planned` и gated #119.


## Ограничения на закупочные цены и документы (#446, current-dev)

WAREHOUSE может видеть и изменять заказы поставщику только при активном
назначении в своём филиале и соответствующем `SUPPLIER_ORDER`:
`READ` — список и дата истории, `CREATE` — новый заказ,
`EDIT` — частичный приход, `CLOSE` — отмена остатка.
`WRITE=DENY` запрещает все изменения. `PRICE_PURCHASE=DENY`
скрывает точную закупочную цену в уже созданных заказах:
`purchaseUnitMinor:null`, `purchasePriceHidden:true`,
на экране — **«скрыта настройкой доступа»**; создать новый заказ
по скрытой цене тоже нельзя, даже если `CREATE=ALLOW`.
Администратор может ограничить дату истории; старые заказы
не включаются в серверный список. Чужой филиал/отозванная
роль возвращают 403; не переключайте UUID для обхода.
Поставщики и деньги здесь только искусственные, реальных
закупок не производится. [Права и отрицательные тесты](../auto/DOCUMENT_ACCESS.md).

## Материалы публичной заявки — DEV #442

Публикация строк `skuId,PART|CONSUMABLE,количество` требует MANAGER+WAREHOUSE. Исполнение после verified-claim требует INTAKE+WAREHOUSE. Одна транзакция резервирует stock и создаёт appointment/CRM; при нехватке 409 без фантомного резерва. [Подробно](../auto/PUBLIC_BOOKING.md).

### Перенесённая запись и заказ поставщику (#443)

Если клиент перенёс запись на другое время, исходная бронь отменена, но тот же WorkOrder продолжает существовать. В разделе **«Заказы поставщикам (dev)»** можно создать заказ по доказанному дефициту только тогда, когда **новая актуальная бронь** жива в том же филиале. Система ищет её по последнему событию переноса и на уровне API, и через PostgreSQL. После отмены актуальной записи новый заказ запрещён (403), а ранее зарегистрированные частичные приходы остаются в журнале. При конфликте 409 перечитайте заказ; не меняйте `Idempotency-Key` при неизвестном исходе POST. [Технический контракт, тесты и откат](../auto/SUPPLIER_PURCHASES.md). Безопасная работа только с synthetic-документами; реальные поставщики и OEM-применяемость не разрешены до #119.


## Номенклатура, аналоги, цены и XLSX (#447, current-dev)

Откройте `/staff` → **«Номенклатура (dev)»** → `/staff/warehouse-catalog`. Для изменения нужны одновременно WAREHOUSE+MANAGER и разрешения на закупочные/продажные цены. Укажите UUID синтетических филиала и организации, нажмите **«Загрузить номенклатуру»**. В разделе **«Карточка новой детали»** задайте артикул, категорию, UOM, опциональные бренд/штрихкод и тестовые цены в целых копейках; **«Создать SKU и исходную версию цены»** сохраняет карточку и журнал версии, но не двигает склад.

Для обновления заполните **«Строки обновления цены»** форматом `skuUUID;version;purchaseMinor;saleMinor` (до 100 строк) → **«Сохранить пакет версий цен»**. Несовпадение `expectedVersion` → 409 и отмена всей пачки. Для аналога выберите исходный/целевой SKU и причину: **«Сохранить аналог (не OEM-подтверждение)»**. Это **не** проверка применяемости и не автоматическое право заменить деталь в наряде. Для дублей выберите source/target, подтвердите неизменность старых документов и нажмите **«Объединить SKU с сохранением истории»**. Операция допустима только при нулевом текущем остатке/резервах исходного SKU и отсутствии serial; FK в документах не перезаписываются.

Для XLSX нажмите **«Проверить XLSX без записи в каталог»** и сверьте SHA-256/артикулы/версии. Затем **«Подтвердить весь XLSX атомарно»**; 409 означает, что версия цены или карточка менялась после просмотра. Формулы, макросы, скрытые листы, иностранные ссылки, дубли и опасные файлы отклоняются. Для отчётной выгрузки — **«Экспортировать XLSX»** при полном доступе к обеим ценам. После 403 скрытые цены не копировать; после 503 повторить **с прежним ключом**, не создавать двойной импорт. Полный [контракт, тесты и откат](../auto/SKU_CATALOG.md). Только synthetic dev; OEM, фактическая бухгалтерская цена и release #119 остаются запрещены.

**Безопасное объединение после выдачи деталей (#447).** Даже если на карточке нулевые остатки, но хотя бы один WorkOrder ещё не вернул ранее выданные детали (`ISSUE − RETURN > 0`), сервер откажет в объединении с HTTP 409. Сначала выполните предусмотренный складской возврат по **исходному SKU** и проверьте фактический остаток; не пытайтесь переназначать исторические движения на целевой UUID. Это PostgreSQL-инвариант, не предупреждение интерфейса. Подробнее: [SKU CATALOG](../auto/SKU_CATALOG.md).

**Черновики приходов и merge (#447).** Нельзя объединять SKU с ожидающим подтверждения приходным документом — даже когда `on_hand=0`. Сначала независимый MANAGER подтверждает приход, затем проводится предусмотренная складская обработка оставшихся остатков. Попытка объединения во время ожидания должна вернуть 409, существующий draft остаётся доступным и может быть проведён. Это относится также к закупкам поставщикам, привязанным к такому документу. [Контракт и PG17 тест](../auto/SKU_CATALOG.md).


### Безопасное объединение SKU при пересортице (#447, current-dev)

До объединения артикулов убедитесь, что все документы пересортицы с их участием **независимо подтверждены MANAGER**. Открытая пересортица даже на пустую партию запрещает объединение: после merge исходный UUID не примет обязательное движение склада. При 409 откройте исходный документ пересортицы, завершите проверку другим сотрудником и проверьте реальные остатки; не пытайтесь заменить UUID вручную. После логического объединения нельзя создать новый документ пересортицы со старым SKU — сервер и база данных отклонят действие. Детали и негативная PG17-проверка: [контракт SKU и объединения](../auto/SKU_CATALOG.md). Сценарий синтетический, без реальных поставок и бухгалтерских операций.


### Возврат поставщику после объединения артикула (#447, current-dev)

Перед объединением SKU завершите независимое подтверждение всех возвратов поставщику, связанных с этим SKU. Даже при остатке 0 непроведённый возврат с ранее оценённого прихода запрещает merge (409), иначе MANAGER не сможет провести исходный документ. Если SKU уже логически объединён, новый возврат по старому артикулу создать нельзя — PostgreSQL откажет. Не заменяйте SKU в документе вручную: сначала урегулируйте историческую поставку и склад в исходном контуре. Проверенная регрессия и условия отката: [SKU catalog](../auto/SKU_CATALOG.md). Только synthetic, не реальный акт/кредит-нота.

## Проверка происхождения цены партии (current-dev, #448)

Отчёт /staff/auto-material-cost-evidence доступен только MANAGER филиала с SUPPLIER_ORDER READ/PRICE_PURCHASE и HANDOVER READ. Роль WAREHOUSE сама по себе не даёт доступа к закупочной цене. При выявлении отсутствующих оценок кладовщик готовит штатную независимую приёмку и оценку в /staff/warehouse-receiving, после чего MANAGER перечитывает отчёт. Смешанные приходы нельзя считать достоверной себестоимостью конкретной выдачи. При 403 обратиться к администратору, при 409 сузить период, при 422 исправить даты; методика в docs/auto/REPORTING.md.


## Запрет закупочной цены при совмещении MANAGER и WAREHOUSE (#498)

Сотрудник с двумя ролями не обходит ограничения закупочных документов:
новый запрет администратора для любой действующей роли немедленно
относится к **созданию заказов поставщику, их приходам и отмене,
очередям цен прихода, оценке, ценам номенклатуры и XLSX**.
При 403 **не** переключайте маршрут и не повторяйте прежний ключ
без проверки доступа; обратитесь к ADMIN за корректным правом в
том же scope и повторите действие только после разрешения.
Экран скрывает недоступную цену и очистит результаты при отказе
сервера; UI не заменяет проверку PostgreSQL. Для просмотра цен продажи
одного `WAREHOUSE` недостаточно даже при разрешённой закупочной цене.
Руководство по ограничительным шаблонам:
[DOCUMENT_ACCESS](../auto/DOCUMENT_ACCESS.md).
Это current-dev, не разрешение реальных закупок или платежей.
