# Администратор

> **Статус: частично current-dev.** Журнал назначений и отзывов в `/staff/auto-admin` доступен в закрытом синтетическом контуре. Production bootstrap организаций, реальное управление пользователями и интеграции — **planned**.

**Операции из текущего интерфейса:** [карта рабочих операций «БоксРитм»](STAFF_TASKS.md). Ссылка на справку по этому разделу доступна в `/staff` после проверки серверной роли; 401/403 остаются отказами, не подсказкой изменить чужой UUID. Ручная QA отложена.

## Для кого

Администратор сервиса. Доступ к каждой операции должен проверяться по активной сессии, роли и конкретному объекту.

## Какие задачи появятся

Подготовка организации и филиалов, справочников, рабочих постов; создание и отзыв пользователей/ролей; просмотр журналов, настройки интеграций и защита персональных данных.

## Что реально доступно сейчас

Реально работает **просмотр** журнала полномочий ADMIN своей организации через `/staff/auto-admin`, подтверждённый браузерными и PG17 тестами. Публичный bootstrap, создание организации и пользовательский интерфейс массового назначения — **не реализованы**. Тестовые роли хранятся в PostgreSQL, данные не должны быть реальными.

## Подготовка пользовательской инструкции

Для ещё **не реализованных** операций отдельные экраны, скриншоты и пользовательские инструкции появятся только после согласования и проверки. Точные dev-операции и доказательства приведены ниже.

**Зависимости:** #112, #113, #119, #123. [Текущая карта продукта](../auto/PRODUCT.md) · [правила актуальности](../DOCUMENTATION_POLICY.md) · [индекс ролей](INDEX.md).

**До релиза:** запрещены настоящие VIN, телефоны, клиентские документы и платёжные данные в dev-стенде.


## Доступно только в закрытом synthetic dev-контуре

При отдельном включении synthetic auto API, активной сессии ADMIN данной организации и HTTPS loopback внутренний маршрут `GET /api/v1/dev/auto/organizations/{org_id}/staff/audit` выдаёт до 100 последних событий выдачи и отзыва ролей. По умолчанию публичный интерфейс отсутствует, настоящий оператор не может пользоваться этой функцией в production. Без сессии или при чужой организации — 403; при неверном числе событий — 422; выключенный dev API — 404. Не использовать реальные имена и данные сотрудников. UI назначения/отзыва сотрудника и аудит доступны только в synthetic dev; полноценный production HR/IAM и экспорт аудита planned.


## Экран журнала сотрудников — synthetic dev (current)

На локальном dev стенде откройте `/staff/auto-admin`, укажите UUID организации, для которой у текущей сессии есть ADMIN. В разделе «Журнал назначений и отзывов» выберите 10/30/100 записей и нажмите «Показать журнал». В результате сервер возвращает выдачу и отзыв полномочий с идентификаторами сотрудника, исполнителя, роли, филиала и временем действия. Отозванные полномочия остаются в истории. При смене организации данные сбрасываются, чужая организация возвращает 403 и журнал скрывается. При ошибке формата ответа экран не отображает неподтверждённые записи. Публичный production доступ к экрану и доверенный bootstrap ADMIN пока **planned**, реальные персональные данные в тестах запрещены. Playwright: `apps/web/e2e/auto-staff-console.spec.ts`; PG17: `tests/integration/test_pg_auto_org_staff_http.py`.


### Импорт Excel для тестового стенда — доступно только разработчикам

В изолированной среде доступна **командная** конвертация XLSX с искусственными автомобилями и услугами в проверяемый CSV. Команды и ограничения приведены в `docs/auto/DATA_MIGRATION.md`. Это **не функция интерфейса администратора**: экран загрузки реальных данных и перенос истории с подтверждением согласий остаются `planned`. Пользовательские файлы, VIN и сведения о клиентах не следует использовать в этом тестовом механизме до production gate #119.


### Реестр исходных данных перед будущей миграцией

Для тестового комплекта клиентов, контрагентов, истории ремонтов и документов реализован только локальный реестр SHA-256/происхождения. Его инструкция находится в `docs/auto/DATA_MIGRATION.md`. Наличие идентификатора доказательства в манифесте **не** подтверждает согласие клиента и не разрешает production импорт. Фактический интерфейс переноса клиентов и истории остаётся `planned`.


## Проверенная область роли (current-dev, 03.11.2026)

**Куда нажать:** `/staff/auto-admin` → «Журнал назначений и отзывов» → «Показать журнал». **Кто:** ADMIN только собственной организации. **Результат:** неизменяемые события выдачи/отзыва, без массового управления сотрудниками. **При 403:** организация чужая или сессия недействительна; **при 422:** некорректный лимит. [UI/PG17](ACCESS_AND_TEST_MATRIX.md) и [общий FAQ](FAQ.md). Скриншоты синтетические, ручной sign-off не выполнен.


## Cutover существующей базы (внутренний synthetic-режим, #172)

**Пользовательского экрана импорта пока нет.** В dev/QA используется только внутренняя PG17-библиотека, поэтому администратору **нельзя** подгружать пользовательские CSV с клиентами, VIN и документами в интерфейсе или выполнять произвольные SQL INSERT в production. Тестовый сценарий [«Атомарный synthetic cutover»](../auto/SYNTHETIC_CUTOVER.md) требует отдельные активные филиальные роли `MANAGER` и `WAREHOUSE`; он переносит только искусственные автомобили без ownership, услуги без цен и товары/остатки без закупочных документов. При конфликте целый пакет откатывается, безопасный replay не дублирует ledger, ошибка не выводит VIN или содержимое источника. Полный реальный импорт, восстановление клиента/истории и права доступа после cutover **планируются** и заблокированы #119/#165/#172 до согласия юридических и эксплуатационных ответственных.


## Выгрузка проверенного синтетического пакета (current-dev, #172)

Для тестового переноса между изолированными средами внутренняя функция `export_reconciled_synthetic_cutover` после полного cutover формирует приватный пакет **трёх** synthetic CSV с манифестом SHA-256. Требует живых MANAGER **и** WAREHOUSE ролей своего филиала и не поддерживает реальные VIN, клиентские документы, историю ремонта или customer links. Отдельный офлайн-валидатор проверяет созданный каталог без подключения к БД. **Это не кнопка администратора:** HTTP и пользовательского экрана нет, рабочий перенос остаётся `planned`. Разработчикам: [инструкция экспорта, проверок и безопасного отката](../auto/DATA_MIGRATION.md). При `FORBIDDEN` проверяйте действующие полномочия; при `SOURCE_MISMATCH` не повторяйте выгрузку с новым хешем без независимого расследования расхождения. При `OUTPUT_UNAVAILABLE` укажите новый, не существующий каталог. Нельзя публиковать содержимое CSV в GitHub issues, скриншотах и журналах.


**Проверка перед импортом в тестовый стенд:** после получения приватного synthetic комплекта запустите `auto_cutover_export_verify.py --synthetic-only` из инструкции `DATA_MIGRATION.md`. Проверка отклоняет самосогласованные по SHA подмены с неверным VIN, чужим tenant/филиалом, дублированными услугами или неполным SKU/STOCK. Это не заменяет отдельной независимой передачи manifest SHA, а также юридической проверки происхождения и согласия владельца реальных данных. Экран импорта по-прежнему `planned`.


## Гранулярные ограничения по документам и ценам — current-dev (#446)

После доверенного **offline** назначения ADMIN откройте `/staff/auto-admin`
и укажите UUID **своей** организации. Нажмите
**«Показать ограничения документов»**. В форме
**«Новая версия правила»** выберите роль `MANAGER/INTAKE/MECHANIC/WAREHOUSE`,
вид документа `INTAKE_ACT/ESTIMATE/HANDOVER/SUPPLIER_ORDER`,
действие `READ/CREATE/EDIT/CLOSE/WRITE/PRICE_SALES/PRICE_PURCHASE/DISCOUNT`
и **«Результат политики»** `DENY` или `ALLOW`.
Оставьте UUID сотрудника пустым для шаблона всей роли либо задайте
конкретного **уже назначенного** сотрудника и UUID филиала.
Опционально `READ=ALLOW` ограничьте **«История с даты (UTC)»**.
Нажмите **«Сохранить правило»**. Сервер добавит неизменяемое
событие в аудит, автор и время видны в этом же журнале.

**`ALLOW` не выдаёт роль:** оно лишь отменяет прежний запрет на том же
точном scope. Если у роли шаблон `DENY`, личное исключение `ALLOW`
его не преодолеет. `WRITE=DENY` запрещает все `CREATE/EDIT/CLOSE`,
разрешение `EDIT` не делает редактируемыми immutable документы.
Для проверки введите UUID филиала/сотрудника, выберите документ и нажмите
**«Проверить эффективные права»**. Результат показывает роль и политику,
но не позволяет читать чужой заказ или обходить истёкшую сессию.

**403** — сессия/ADMIN/филиал или назначение отсутствуют.
**409** — конфликт ключа, филиала либо пользователя без соответствующего
гранта. **422** — неверные коды, время или формат.
При потере ответа нажмите **«Повторить исходное правило»** с прежним
`requestKey`, иначе **«Перечитать правила»** до следующей отправки.
Нет POST-пути для самовыдачи ADMIN. Изменение правил не разрешает
production или работу с реальными сотрудниками.
[Полный контракт и технический аудит](../auto/DOCUMENT_ACCESS.md).


## Назначить кассира тестового контура — #445

В `/staff/auto-admin` действующий ADMIN организации назначает
отдельную роль **CASHIER** конкретному сотруднику и филиалу.
MANAGER создаёт тестовые счета; только CASHIER может принимать
условные авансы/платежи, возвращать и закрывать день.
Отзыв гранта мгновенно запрещает новые обращения к кассе,
в том числе повтор уже записанного запроса. Наличие legacy FINANCE
не означает этого права; не назначайте CASHIER по одной только
галочке в меню. Права только synthetic-dev, не для настоящих денег.
[Контракт кассы](../auto/FINANCE.md).
