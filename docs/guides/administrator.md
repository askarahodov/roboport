# Администратор

**Сквозной тестовый маршрут:** [от записи автомобиля до условной сверки по шести ролям](END_TO_END_WORKSHOP.md). ADMIN: проверьте действующие полномочия и журнал организации перед началом тестового заказа; не имитируйте production onboarding. Для каждого шага там приведены маршрут, состояние, запрет и тест; исполнители действуют только через собственные synthetic сессии.

> **Статус: частично current-dev, только синтетика.** `/staff/auto-admin` поддерживает назначения/отзывы, журнал, одноразовые приглашения существующих аккаунтов и аудит; `/staff/auto-setup` управляет филиалами, постами и сменами. Production bootstrap, регистрация, внешняя доставка приглашений и реальное управление пользователями — **planned**.

**Операции из текущего интерфейса:** [карта рабочих операций «БоксРитм»](STAFF_TASKS.md). Ссылка на справку по этому разделу доступна в `/staff` после проверки серверной роли; 401/403 остаются отказами, не подсказкой изменить чужой UUID. Ручная QA отложена.

## Для кого

Администратор сервиса. Доступ к каждой операции должен проверяться по активной сессии, роли и конкретному объекту.

## Какие задачи появятся

Подготовка организации и филиалов, справочников, рабочих постов; создание и отзыв пользователей/ролей; просмотр журналов, настройки интеграций и защита персональных данных.

## Что реально доступно сейчас

Работают current-dev назначения и отзывы сотрудников, неизменяемый аудит, создание/отзыв приглашений уже существующих активных учётных записей, принятие приглашения под точной учётной записью, а также управление филиалами/постами/сменами. Всё это требует HTTPS loopback, dev feature flags, disposable PG17 и активного ADMIN выбранной организации. Создание организации через API, self-service регистрация, email/SMS доставка, юридическая проверка владельца и production IAM — **не реализованы**. Тестовые роли и приглашения не предназначены для реальных сотрудников.

## Подготовка пользовательской инструкции

Для ещё **не реализованных** операций отдельные экраны, скриншоты и пользовательские инструкции появятся только после согласования и проверки. Точные dev-операции и доказательства приведены ниже.

**Зависимости:** #112, #113, #119, #123. [Текущая карта продукта](../auto/PRODUCT.md) · [правила актуальности](../DOCUMENTATION_POLICY.md) · [индекс ролей](INDEX.md).

**До релиза:** запрещены настоящие VIN, телефоны, клиентские документы и платёжные данные в dev-стенде.


## Доступно только в закрытом synthetic dev-контуре

При отдельном включении synthetic auto API, активной сессии ADMIN данной организации и HTTPS loopback внутренний маршрут `GET /api/v1/dev/auto/organizations/{org_id}/staff/audit` выдаёт до 100 последних событий выдачи и отзыва ролей. По умолчанию публичный интерфейс отсутствует, настоящий оператор не может пользоваться этой функцией в production. Без сессии или при чужой организации — 403; при неверном числе событий — 422; выключенный dev API — 404. Не использовать реальные имена и данные сотрудников. UI назначения/отзыва сотрудника и аудит доступны только в synthetic dev; полноценный production HR/IAM и экспорт аудита planned.


## Экран сотрудников, приглашений и аудита — synthetic dev (current)

На локальном dev стенде откройте `/staff/auto-admin`, укажите UUID организации, для которой у текущей сессии есть ADMIN. Раздел «Активные назначения» показывает роль и UUID субъекта/филиала; прямое назначение по UUID и отзыв требуют CSRF и подтверждения. В блоке «Пригласить сотрудника» укажите login уже существующей активной учётной записи, роль и опциональный филиал, затем срок 1–30 дней. Сервер выдаёт одноразовый случайный код только один раз; он не сохраняется в открытом виде и не возвращается в списке. Скопируйте код и передайте по проверенному каналу. Сотрудник должен войти именно под приглашённым login и открыть `/staff/auto-invitation`; после успешного принятия grant создаётся атомарно. Ожидающее приглашение можно отозвать; принятые, отозванные и истёкшие остаются в списке и аудите. При смене организации состояние/секрет очищаются; чужая организация возвращает 403. Внешняя email/SMS доставка, регистрация новых аккаунтов, production IAM и доверенный bootstrap остаются **planned**. Реальные персональные данные запрещены. Playwright: `apps/web/e2e/auto-staff-console.spec.ts` и `apps/web/e2e/auto-staff-invitation.spec.ts`; PG17: `tests/integration/test_pg_auto_org_staff_http.py` и `tests/integration/test_pg_auto_org_staff_invitation_http.py`.


### Импорт Excel для тестового стенда — доступно только разработчикам

В изолированной среде доступна **командная** конвертация XLSX с искусственными автомобилями и услугами в проверяемый CSV. Команды и ограничения приведены в `docs/auto/DATA_MIGRATION.md`. Это **не функция интерфейса администратора**: экран загрузки реальных данных и перенос истории с подтверждением согласий остаются `planned`. Пользовательские файлы, VIN и сведения о клиентах не следует использовать в этом тестовом механизме до production gate #119.


### Реестр исходных данных перед будущей миграцией

Для тестового комплекта клиентов, контрагентов, истории ремонтов и документов реализован только локальный реестр SHA-256/происхождения. Его инструкция находится в `docs/auto/DATA_MIGRATION.md`. Наличие идентификатора доказательства в манифесте **не** подтверждает согласие клиента и не разрешает production импорт. Фактический интерфейс переноса клиентов и истории остаётся `planned`.


## Проверенная область роли (current-dev, 03.11.2026)

**Куда нажать:** `/staff/auto-admin` → «Журнал назначений и отзывов» → «Показать журнал». **Кто:** ADMIN только собственной организации. **Результат:** неизменяемые события выдачи/отзыва, без массового управления сотрудниками. **При 403:** организация чужая или сессия недействительна; **при 422:** некорректный лимит. [UI/PG17](ACCESS_AND_TEST_MATRIX.md) и [общий FAQ](FAQ.md). Скриншоты синтетические, ручной sign-off не выполнен.


## Cutover существующей базы (внутренний synthetic-режим, #172)

**Пользовательского экрана импорта пока нет.** В dev/QA используется только внутренняя PG17-библиотека, поэтому администратору **нельзя** подгружать пользовательские CSV с клиентами, VIN и документами в интерфейсе или выполнять произвольные SQL INSERT в production. Тестовый сценарий [«Атомарный synthetic cutover»](../auto/SYNTHETIC_CUTOVER.md) требует отдельные активные филиальные роли `MANAGER` и `WAREHOUSE`; он переносит только искусственные автомобили без ownership, услуги без цен и товары/остатки без закупочных документов. При конфликте целый пакет откатывается, безопасный replay не дублирует ledger, ошибка не выводит VIN или содержимое источника. Полный реальный импорт, восстановление клиента/истории и права доступа после cutover **планируются** и заблокированы #119/#165/#172 до согласия юридических и эксплуатационных ответственных.


## Выгрузка проверенного синтетического пакета (current-dev, #172)

Для тестового переноса между изолированными средами внутренняя функция `export_reconciled_synthetic_cutover` после полного cutover формирует приватный пакет **трёх** synthetic CSV с манифестом SHA-256. Требует живых MANAGER **и** WAREHOUSE ролей своего филиала и не поддерживает реальные VIN, клиентские документы, историю ремонта или customer links. Отдельный офлайн-валидатор проверяет созданный каталог без подключения к БД. **Это не кнопка администратора:** HTTP и пользовательского экрана нет, рабочий перенос остаётся `planned`. Разработчикам: [инструкция экспорта, проверок и безопасного отката](../auto/DATA_MIGRATION.md). При `FORBIDDEN` проверяйте действующие полномочия; при `SOURCE_MISMATCH` не повторяйте выгрузку с новым хешем без независимого расследования расхождения. При `OUTPUT_UNAVAILABLE` укажите новый, не существующий каталог. Нельзя публиковать содержимое CSV в GitHub issues, скриншотах и журналах.


**Проверка перед импортом в тестовый стенд:** после получения приватного synthetic комплекта запустите `auto_cutover_export_verify.py --synthetic-only` из инструкции `DATA_MIGRATION.md`. Проверка отклоняет самосогласованные по SHA подмены с неверным VIN, чужим tenant/филиалом, дублированными услугами или неполным SKU/STOCK. Это не заменяет отдельной независимой передачи manifest SHA, а также юридической проверки происхождения и согласия владельца реальных данных. Экран импорта по-прежнему `planned`.


## Гранулярные ограничения по документам и ценам — current-dev (#446)

После доверенного **offline** назначения ADMIN откройте `/staff/auto-admin`
и укажите UUID **своей** организации. Нажмите
**«Показать ограничения документов»**. В форме
**«Новая версия правила»** выберите роль `MANAGER/INTAKE/MECHANIC/WAREHOUSE`,
вид документа `INTAKE_ACT/ESTIMATE/HANDOVER/SUPPLIER_ORDER`,
действие `READ/CREATE/EDIT/CLOSE/WRITE/PRICE_SALES/PRICE_PURCHASE/DISCOUNT`
и **«Результат политики»** `DENY` или `ALLOW`.
Оставьте UUID сотрудника пустым для шаблона всей роли либо задайте
конкретного **уже назначенного** сотрудника и UUID филиала.
Опционально `READ=ALLOW` ограничьте **«История с даты (UTC)»**.
Нажмите **«Сохранить правило»**. Сервер добавит неизменяемое
событие в аудит, автор и время видны в этом же журнале.

**`ALLOW` не выдаёт роль:** оно лишь отменяет прежний запрет на том же
точном scope. Если у роли шаблон `DENY`, личное исключение `ALLOW`
его не преодолеет. `WRITE=DENY` запрещает все `CREATE/EDIT/CLOSE`,
разрешение `EDIT` не делает редактируемыми immutable документы.
Для проверки введите UUID филиала/сотрудника, выберите документ и нажмите
**«Проверить эффективные права»**. Результат показывает роль и политику,
но не позволяет читать чужой заказ или обходить истёкшую сессию.

**403** — сессия/ADMIN/филиал или назначение отсутствуют.
**409** — конфликт ключа, филиала либо пользователя без соответствующего
гранта. **422** — неверные коды, время или формат.
При потере ответа нажмите **«Повторить исходное правило»** с прежним
`requestKey`, иначе **«Перечитать правила»** до следующей отправки.
Нет POST-пути для самовыдачи ADMIN. Изменение правил не разрешает
production или работу с реальными сотрудниками.
[Полный контракт и технический аудит](../auto/DOCUMENT_ACCESS.md).


## Назначить кассира тестового контура — #445

В `/staff/auto-admin` действующий ADMIN организации назначает
отдельную роль **CASHIER** конкретному сотруднику и филиалу.
MANAGER создаёт тестовые счета; только CASHIER может принимать
условные авансы/платежи, возвращать и закрывать день.
Отзыв гранта мгновенно запрещает новые обращения к кассе,
в том числе повтор уже записанного запроса. Наличие legacy FINANCE
не означает этого права; не назначайте CASHIER по одной только
галочке в меню. Права только synthetic-dev, не для настоящих денег.
[Контракт кассы](../auto/FINANCE.md).

## Гранулярная политика FINANCE и CASHIER — dev #446

В разделе `/staff/auto-admin` нажмите **«Показать ограничения документов»**.
Теперь можно выбрать `FINANCE`, роль `CASHIER` (или `MANAGER`) и отдельно
ограничить `READ`, `PRICE_SALES`, `CREATE`, `EDIT`, `CLOSE`, `WRITE`.
Запрет цен действует на кассу/остатки/журнал, включая повтор запросов,
а запрет WRITE — на авансы, возвраты и закрытие дня. Пример:
`CASHIER + FINANCE + PRICE_SALES + DENY` на своём филиале — тестовая касса
возвращает 403; личный `ALLOW` не обходится через шаблонный `DENY`.
При подтверждении `READ=ALLOW` с историческим cutoff запрещаются
старые WorkOrder; общий финансовый отчёт, где невозможно ограничить
каждую строку по заказу, безопасно возвращает 403.

**Кассир не становится ADMIN:** добавление FINANCE в шаблоны не выдаёт
роль CASHIER, а CASHIER не может менять политики. При 403 сохраняйте
идентификаторы из тестового стенда и проверьте назначения; не обходите
денежную ACL под другим URL. Сверка путей и миграция 0122 —
[контракт](../auto/DOCUMENT_ACCESS.md). Настоящие платёжные разрешения
не появляются до #119.


## Проверка совмещённых ролей закупок (#498, current-dev)

При назначении сотруднику `MANAGER` и `WAREHOUSE` не пытайтесь
разрешить запрещённую цену личным ALLOW в другой роли:
**запрет любой действующей роли сохраняется**. В
`/staff/auto-admin` выберите организацию, филиал и шаблон
`SUPPLIER_ORDER` с возможностями `READ / CREATE / EDIT / CLOSE /
PRICE_PURCHASE`. Проверьте effective preview, затем на синтетическом
сотруднике повторите `/staff/warehouse-supplier-orders` и
`/staff/warehouse-receiving`: при DENY запрос должен завершиться
403 без обновления документа или стоимости. После ALLOW того же scope
проверяйте повторное чтение, а не используйте старую вкладку.
`ESTIMATE/PRICE_SALES` независимо ограничивает видимость цен
продажи в `/staff/warehouse-catalog`; только роль WAREHOUSE не
открывает эти суммы. При ошибке 403 не копируйте UUID, секреты,
коммерческие цены и PII в публичную задачу.
[Инварианты ACL](../auto/DOCUMENT_ACCESS.md). Не production gate #119.



## Все версии ограничений документов — current-dev (#515)

Если правила для документа менялись многократно, более
500 старых версий **не** блокируют чтение действующей
сметы и ADMIN-предпросмотр прав: сервер вычисляет
последнюю версию каждого точного scope,
не удаляя предыдущие `DENY`/`ALLOW` из аудита.
В `/staff/auto-admin` укажите UUID собственной
организации, нажмите **«Показать ограничения документов»**.
Показываются последние 50 событий. Используйте
**«Более ранние правила»**, чтобы перейти к предыдущей
истории, и **«Предыдущая страница правил»**, чтобы
вернуться; номер страницы всегда виден.

При добавлении новой версии правило отображается
на первой странице. Не предполагается, что старый
`ALLOW` отменяет `DENY` шаблона или что найденное
в журнале событие выдаёт право: результат считается
из **действующих** ролей и всех применимых scope.
Проверьте сотрудника кнопкой
**«Проверить эффективные права»**, затем выполните
действие только его собственной synthetic-сессией.

Неверный/чужой `before` (UUID события) — 422,
отозванная роль ADMIN или сессия — 403: журнал и
ранее проверенные права скрываются. При проблеме сети
повторите чтение; при неоднозначном результате POST
используйте исходный `requestKey`, не создавайте
наугад новое разрешение. Без реальных персональных,
финансовых и клиентских данных; не production IAM.
[Алгоритм, API, тесты и откат](../auto/DOCUMENT_ACCESS.md).


## Приглашение сотрудника — закрытый synthetic dev (#166)

1. Откройте **«Организации (dev)»** → введите UUID своей организации.
2. В разделе **«Пригласить сотрудника»** укажите login уже существующей активной учётной записи. Это не email-рассылка и не регистрация нового пользователя.
3. Выберите роль (`MANAGER`, `INTAKE`, `MECHANIC`, `WAREHOUSE`, `CASHIER`), при необходимости филиал и срок 1/7/14/30 дней.
4. Нажмите **«Создать приглашение»**. Код показывается один раз; скопируйте его и передайте сотруднику по отдельному проверенному каналу. Сервер сохраняет только SHA-256 digest. Не вставляйте код в issue, чат, screenshot или логи.
5. Сотрудник входит под тем же login, открывает `/staff/auto-invitation`, вставляет код и принимает приглашение. Только после этого сервер создаёт grant.
6. Ожидающее приглашение можно отозвать. Принятый grant отзывается в списке активных назначений. Истёкшие и отозванные приглашения остаются в журнале.

Сервер связывает токен с точным `target_user_id`, проверяет живую сессию, срок, активность организации/филиала и полномочия пригласившего ADMIN на момент принятия. Повторное принятие невозможно. При 403 проверьте login и сессию; при 409 проверьте статус приглашения/активный grant; при 410 запросите новый код. Внешняя доставка, email verification и создание аккаунта здесь отсутствуют.

## Филиалы, посты и смены — закрытый dev-контур (#166)

Для администратора организации доступен раздел **«Филиалы и посты (dev)»**
в верхней навигации, адрес `/staff/auto-setup`.

1. Введите UUID своей организации. Экран откроется только при активной
   сессии и действующем назначении ADMIN этой организации.
2. Создайте филиал: задайте уникальный код и IANA часовой пояс
   (например, `Europe/Berlin`). Проверьте созданную строку в списке.
3. Выберите филиал и создайте рабочий пост с уникальным кодом.
4. Для назначения смены выберите филиал, укажите UUID существующей
   активной учётной записи сотрудника и время начала/окончания в формате
   ISO 8601 с UTC offset, например `2030-04-10T09:00:00+02:00`.
   Интервал должен быть положительным и не превышать 24 часа. Сотруднику
   заранее требуется действующее назначение организации/филиала.
5. Пересекающиеся смены одного сотрудника не принимаются (409).
   Отмена смены недоступна, пока у сотрудника остаётся активная резервация.
6. Отключение поста блокируется активной будущей бронью. Отключение филиала
   блокируется активными постами, сменами, будущими бронями, филиальными
   назначениями, неистёкшими приглашениями и привязками автомобилей.
   Сначала отзовите ожидающие приглашения. Отключение необратимо.

Внизу экрана находится неизменяемый журнал создания/отключения филиалов
и постов, назначения/отмены смен с UUID актора. При 403 проверьте
назначение ADMIN именно в выбранной организации; при 409 сначала
разрешите связанные брони/смены/назначения; при 422 проверьте IANA-зону,
код и явный offset даты.

Создание филиала, поста и смены отправляет `Idempotency-Key`; при сетевой
ошибке повторяйте ту же операцию без изменения полей — интерфейс повторно
использует ключ в памяти вкладки. Повтор с другим содержимым потребует новой
операции; сервер вернёт 409 при повторном использовании ключа с другим payload.

Это synthetic-only интерфейс: приглашение возможно только для уже существующей активной учётной записи и требует ручной передачи одноразового кода по проверенному каналу. Новые аккаунты не регистрируются; внешняя доставка, юридическое подтверждение владения организацией, production bootstrap/recovery и production-полномочия отсутствуют. Реальные данные запрещены до gate #119.
