# Модель доступа и безопасности

## Принцип

**Deny by default:** **RBAC** определяет допустимое действие роли; **ACL/отношения к ресурсу** — доступ к конкретной заявке, роботу, смете, акту; **ABAC** дополнительно проверяет состояние и назначение. Проверка проводится в backend use-case до доступа к объекту. Субъект берётся только из локальной серверной сессии (#13), а не из `customerId`, телефона, serial или клиентского заголовка. Реализация прав — #27.

## Роли и минимальные права

| Роль | Доступ | Ограничения |
|---|---|---|
| PUBLIC | опубликованный каталог/FAQ | приватные обращения/акты запрещены |
| CLIENT | собственные устройства, обращения, версии смет, документы | только подтверждённая account↔customer связь и ticket relationship |
| INTAKE | заявки/приёмка в назначенном контуре | не изменяет QA и не читает всё PII |
| ENGINEER | диагностика/сервисные работы по назначению | SAFETY_HOLD блокирует действия |
| STOCK | партии, совместимость, резервы | не подтверждает клиентские сметы |
| MANAGER | разрешённые escalations и контроль | не универсальное чтение PII |
| FINANCE | финансы/сметы по назначению | не получает все личные документы |
| ADMIN | управление ролями, настройками | не универсальное право на клиентские файлы |
| AUDITOR | неизменяемый журнал согласно регламенту | без права редактирования событий |

## Обязательные отрицательные сценарии

1. Client A знает UUID заявки/вложения B → доступ закрыт и чужие данные не раскрываются.
2. Device перешёл к B → B не видит ticket/attachment прежнего владельца A.
3. Link/сессия отозваны → новый HTTP и idempotency replay не дают доступа.
4. Прислали поддельный `X-Customer-ID`, `customerId` или несвойственную роль → отказ.
5. Неизвестная модель/деталь → статус подтверждённого обслуживания не появляется.
6. `SAFETY_HOLD`, `QC_FAILED`, устаревшая версия сметы → сервер блокирует операцию.
7. Документ в quarantine и неавторизованный ключ файла → отказ, private storage не отдаёт напрямую.

## Технические контроли

Локальная аутентификация: Argon2id для паролей; случайная opaque-сессия хранится в cookie `rp_session` (`HttpOnly`, `SameSite=Lax`, `Secure` на HTTPS), в PostgreSQL хранится только hash токена; абсолютный и idle TTL, ротация, logout/revocation, аудит входа, rate limits и антибрутфорс. Для POST/PATCH/DELETE обязательны CSRF-token/Origin checks; dev HTTP cookie без `Secure` допустима исключительно на loopback, а не в общедоступном окружении. Не использовать самодельное шифрование и dev fixture bearer в защищённых маршрутах.

Права: таблицы `role`, `user_role`, `acl_entry` (явные делегирования с отзывом и сроком), `account_customer_link` (подтверждённый субъект), `ticket.customer_id`; политика по объекту **не определяется одним serial/номером заявки**. ADMIN не может читать все приватные файлы по одному имени роли. `Idempotency-Key` не отменяет повторную проверку роли и связи.

Документы: private MinIO в dev (#28), adapter `FileStorage` (#25). **MinIO не знает доменную ACL:** backend сначала выполняет объектный guard, потом отдаёт поток; публичные bucket и постоянные ключи в браузере запрещены. Quarantine запрещает доступ. Signed URL — только отдельным ADR. Ошибки `Error {code,message,requestId}`; пароли, сессии, токены, MinIO ключи и PII не писать в лог/Issue. Реальные PostgreSQL+HTTP+MinIO тесты — обязательны для отметки безопасности; фикстуры их не заменяют.


## Реализуемый срез PostgreSQL ACL (#27)

Миграция `0008_authorization` вводит `role`, `user_role`, `acl_entry` и append-only `authorization_audit`.
Предметные права ticket в `authorization.py` намеренно меньше общей целевой матрицы:

| Роль | Разрешённые ticket actions | Объектное условие |
|---|---|---|
| PUBLIC | нет | частные операции запрещены |
| CLIENT | ticket.read | активная роль и account_customer_link к исходному customer заявки |
| INTAKE | ticket.read, ticket.intake | действующая acl_entry на конкретный ticket/action |
| ENGINEER | ticket.read, ticket.diagnose | действующая acl_entry на ticket/action |
| STOCK | нет | складские операции в другом модуле |
| MANAGER | ticket.read, ticket.manage | действующая acl_entry на ticket/action |
| FINANCE | нет | денежные операции в другом модуле |
| ADMIN | нет | администрирование роли не раскрывает PII |
| AUDITOR | нет | только отдельный безопасный журнал |

Для `ticket.diagnose` состояние `SAFETY_HOLD` запрещает действие; для `ticket.manage` дополнительно запрещено `QC_FAILED`.
Роль или ACL без активной серверной сессии недостаточны. Одна лишь связь с устройством
не даёт читать старую историю: доступ к заявке связан с неизменяемым `service_ticket.customer_id`.
Отзыв роли/ACL необратим на уровне триггеров.

**Граница реализации:** `authorize_ticket` — внутренний сервисный guard, а не законченный
HTTP API. Аудит принятия/отклонения запросов, idempotency replay, ACL вложений,
гарантия подтверждённости `account_customer_link` и защищённые staff HTTP-маршруты
ещё требуют отдельной реализации и тестов; до этого #27 остаётся открытой.


## Сметы: серверная политика и отзывы (#27)

После миграции `0010_estimate_acl` разрешения `estimate.read` и
`estimate.approve` привязываются к `ticket_id`, а не к угадываемому номеру
сметы. `authorization.authorize_estimate` использует живую серверную
сессию, срок/отзыв роли, активную связь с исходным customer и/или явное
назначение сотрудника.

- CLIENT читает только SENT/APPROVED/DECLINED своей заявки и может
  подтвердить **только последнюю** версию со статусом SENT.
- FINANCE читает смету по точному ACL, не получает автоматическое право
  подтверждения.
- MANAGER с явным ACL может читать смету; подтверждение ограничено
  последней версией SENT.
- ADMIN/INTAKE/ENGINEER/STOCK/AUDITOR не получают финансовые данные
  по имени роли.
- Следующий запрос после отзыва роли/ACL/account-customer-link запрещён;
  HTTP-проба `/api/v1/dev/estimates/{id}/access` пишет ALLOW/DENY без PII.

Dev HTTP-проба не является публичным API, доступна только HTTPS loopback с
явным synthetic opt-in. Реальный approval use-case при появлении маршрута
обязан повторить ту же политику *в транзакции мутации*, до обработки
Idempotency-Key.
