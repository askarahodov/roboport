Эти решения вносятся отдельным ADR до изменения стека. Переход на микросервисы, Kubernetes, Redis или Kafka без доказанной необходимости запрещён.


## ADR-032 — Каноническая модель заявки и границы контракта (16.10.2026)

**Статус: принято для синтетического dev-контура, будущие поля отмечены отдельно.**

1. Владелец сервисной истории — зафиксированная сторона заказа `service_ticket.customer_id`, доступ клиента требует живой `account_customer_link` и роли `CLIENT`. Текущее владение устройством само по себе не предоставляет доступ к прежним заявкам; `device_ownership` и `service_ticket.customer_id` — разные сущности.
2. Фиксированный набор из 20 состояний `Ticket.state` совпадает с `docs/domain/TICKET_FSM.md` и SQL CHECK. `Transition.targetState` использует те же имена без `DRAFT`; допустимость конкретного перехода определяется картой `TICKET_TRANSITIONS.json` и серверным guard. Названия `DIAGNOSTICS`, `WAITING_PARTS`, `IN_REPAIR`, `QC`, `READY_FOR_RETURN`, `ESTIMATE_PENDING` исключены как устаревшие и не должны вновь появляться.
3. Строка `Estimate.total` в API является десятичным форматированием `estimate.total_minor` в целых копейках; само денежное значение никогда не рассчитывается float. `Estimate.status=SUPERSEDED` — **только вычисляемое представление** устаревшей версии, в БД это состояние не записывается. Реальная устарелость определяется по последней версии `estimate.version` заявки.
4. `Ticket.reference`, `CreateTicket.symptoms`, `Ticket.modelVariantId` и `Transition.reason` в опубликованном **draft** контракте пока не имеют прямого соответствия столбцу либо готовому production handler. Решение: не выдумывать сохранённые значения. До отдельной миграции/валидированного handler их статус — `planned`, а не `implemented`; API не считается выполненным по этим свойствам.
5. Idempotency для разных операций пока хранится в специализированных ledger/receipt таблицах; `idempotency_request` — исторический базовый реестр, а не доказательство общей кросс-операционной гарантии. До единого ledger отдельные receipt остаются нормой.
6. Каталог `service_capability` и доказательный `part_compatibility` относится к #18. Склад #21 без независимого подтверждения SKU/model/region/revision/evidence остаётся строго synthetic-only. Реальный approval из флага `verified` не выводить.
7. Исторические шесть пустых `db/legacy_drafts/*.sql` — не миграции. Источник реального SQL — ревизии Alembic `0001_core`–`0014_estimate_decision` в main; схемы #21 отложены до его принятия.

Матрица полей, прав и тестов: `docs/data/SCHEMA_FIELD_MATRIX.json`. Контракт OAS 0.15.0-draft меняет только несовместимый `Transition.targetState`, не объявляя несуществующие runtime операции готовыми.
