# CRM: тестовые обращения, стадия и запись (#169)

> **Статус: current-dev synthetic-only, PostgreSQL 17 и HTTPS loopback.**
> Это не реальная CRM с контактными данными, перепиской или отправкой сообщений.
> До #119 запрещены реальные ФИО, телефоны, email, SMS, IP-телефония,
> рассылки и передача данных интеграторам.

## Законченный сценарий для мастер-приёмщика / руководителя

1. На закрытом dev-стенде войдите с **действующей** ролью `INTAKE`
   или `MANAGER` нужного филиала. Откройте `/staff/auto-crm-leads`.
2. Введите UUID организации и филиала. Список ограничен последними
   **50** обращениями филиала и содержит только UUID, условный источник,
   стадию, ответственного, технические даты и причину отказа.
   Ни имени, телефона, email, текста переписки, VIN, платежей, ни сообщения
   клиенту система **не** хранит/не показывает/не отправляет.
3. Для создания введите UUID ответственного с действующей ролью
   `INTAKE`/`MANAGER` именно в этом филиале, выберите источник
   `WALK_IN`, `PHONE_NOT_RECORDED`, `WEB_FORM_TEST` или
   `STAFF_REFERRAL`. Кнопка создаёт одно обращение `NEW`.
   UUID `intakeKey` — синтетический ключ входящего случая для
   дедупликации. `requestKey` — ключ точного повтора.
   Ни один из источников не запускает телефонный звонок / веб-форму
   или отправку исходящих сообщений.
4. Для успешного пути используйте **«Контакт обработан»**
   (`NEW → CONTACTED`), вставьте существующий UUID назначения
   `auto_appointment` того же филиала и нажмите
   **«Привязать запись»**, затем **«Записан»** (`CONTACTED → BOOKED`)
   и **«Успешно»** (`BOOKED → WON`). Привязка добавляется
   **один раз**, не меняется и не создаёт вторую календарную запись.
   Стадия `WON` — условный финал CRM, а не факт визита,
   отгрузки, оплаты, акта выдачи или закрытия заказ-наряда.
5. Для отказа из `NEW`, `CONTACTED`, `BOOKED`
   выберите код `NO_RESPONSE`, `CUSTOMER_DECLINED`,
   `DUPLICATE` или `OTHER` и нажмите **«Отказ»**.
   Код — стандартизованная причина, не свободный персональный текст.
   `WON` и `LOST` терминальные. В рамках одного обращения
   история стадий append-only; попытки изменить старый статус запрещены.
6. Если исход POST неизвестен из-за сети, **«Повторить тот же запрос»**
   использует прежнее тело JSON с прежним ключом. Не создавайте новый
   ключ, пока не проверите серверный список. При 409 обновите список,
   поскольку стадия или связь могли уже измениться. При 403 перепроверьте
   роль и филиал; 422 означает неверные UUID, стадию или причину.
   Отзыв доступа или смена филиала очищает прежний список.

### Точные ограничения и гарантии

- Таблицы: `auto_crm_lead` (неизменяемая идентичность, живой назначенный
  сотрудник, scoped источник и `(organization_id,location_id,intake_key)`
  UNIQUE), `auto_crm_lead_stage_event` (только append-only переходы с
  `request_key UNIQUE` и проверкой FSM на уровне PostgreSQL) и
  `auto_crm_lead_booking` (однократная, неизменяемая связь с Appointment
  этого же филиала). Нельзя поправить плохую CRM-историю с UPDATE/DELETE.
- Состояния: `NEW → CONTACTED → BOOKED → WON`; из первых
  трёх можно перейти в `LOST` с обязательной причиной.
  Для `BOOKED/WON` нужна подтверждённая существующая запись в пределах
  organization/location. Менеджер может работать с обращением своего филиала,
  приёмщик — с обращениями, где он назначен ответственным;
  список филиала доступен обоим. Отзыв сессии/гранта действует сразу.
- Инварианты дублей: повтор с прежними `requestKey`, `intakeKey` и тем
  же payload возвращает `replayed:true`; новый ключ для той же
  `intakeKey` или использование ключа с другим содержимым → 409.
  Транзакционная advisory-lock по tenant/scope/intakeKey сериализует
  конкурентные повторы. Уникальность и DB-trigger дополнительно защищают
  от прямого обхода сервисной функции.
- RBAC/BOLA: живые `INTAKE` или `MANAGER`, live session, scoped
  organization/location, CSRF на каждом POST; GET/POST содержат
  `Cache-Control:no-store` и не публикуются в публичном OpenAPI.
  403 на чужой филиал и чужое обращение, 404 при выключенном synthetic
  feature-gate, 422 на некорректный UUID/поле, 409 при конфликте FSM
  или дублях.
- Персональные данные **отсутствуют**. `PHONE_NOT_RECORDED` — только
  условное название источника, номер не записывается. Нет таблицы
  согласий, отписки, задач, внешних adapters, CRM-funnel KPI,
  платёжной привязки, реального workflow рекомендаций ТО: всё это
  **planned** и не должно имитироваться реальной рассылкой.

### API

```text
GET  /api/v1/dev/auto/organizations/{org}/locations/{loc}/crm-leads
POST /api/v1/dev/auto/organizations/{org}/locations/{loc}/crm-leads
  {"requestKey":"<UUID>","intakeKey":"<UUID>",
   "ownerId":"<UUID>","sourceCode":"WALK_IN"}
POST /api/v1/dev/auto/organizations/{org}/locations/{loc}/crm-leads/{lead}/booking
  {"requestKey":"<UUID>","appointmentId":"<UUID>"}
POST /api/v1/dev/auto/organizations/{org}/locations/{loc}/crm-leads/{lead}/stage
  {"requestKey":"<UUID>","stage":"CONTACTED","reasonCode":null}
POST /api/v1/dev/auto/organizations/{org}/locations/{loc}/crm-leads/{lead}/stage
  {"requestKey":"<UUID>","stage":"LOST","reasonCode":"CUSTOMER_DECLINED"}
```

Для POST требуется та же session-cookie и `X-CSRF-Token`, что в других
dev-операциях. При первой записи HTTP 201; при точном повторе HTTP 200
и `replayed:true`; для конфликтов HTTP 409. GET возвращает
`{"syntheticOnly":true,"items":[...]}` с текущими стадиями и числом
неизменяемых событий. Список bounded (50), без серверных контактов.

### Полная проверка, откат и выход в production

`tests/integration/test_pg_auto_crm_leads_http.py`: синтетическая связка
с реальной Appointment → NEW → CONTACTED → booking-link → BOOKED → WON,
idempotency при POST, запрещённые переходы и несогласованная причина
LOST, A/B изоляция, роль MANAGER, отзыв INTAKE, запрет mutation
истории и конкурентный exact-key replay PG17. Также отдельный путь
NEW → LOST. `apps/web/e2e/auto-crm-leads.spec.ts`: 390/1280,
dark, русские кнопки и стадии, переходы через mock HTTPS API,
сброс при смене scope/403 и fail-closed при ошибочном JSON.

Миграция `0098_auto_crm_lead.py`: downgrade **отказывается**, если есть
хоть один CRM lead; для удаления реальных append-only доказательств
требуется изолированный backup и отдельно утверждённая процедура.
Никаких реальных ПДн и внешних уведомлений не добавлено.

согласий, отписки, задач, интеграций, legal/security/ops gate #119.
