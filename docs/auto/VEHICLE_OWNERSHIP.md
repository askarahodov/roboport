# Привязка автомобиля к клиенту — синтетический dev-workflow

**Статус:** `current (development only)` для API `/api/v1/dev/auto/`, **не** готовая пользовательская функция и **не** юридическая проверка права собственности.  
**Задача:** [#130](https://github.com/askarahodov/roboport/issues/130). Реализация: `0022_auto_vehicle_claim.py`, `auto_vehicle_claim.py`, `auto_vehicle_claim_http.py` и интеграционные тесты.

## Роли и ограничения

| Участник | Предусловие | Возможность |
|---|---|---|
| Мастер-приёмщик (`INTAKE`) | Активная сессия + роль + явное `auto_vehicle_staff_assignment` на конкретную машину (INTAKE) | Однократно выдаёт случайное доказательство для заранее созданной `pending` привязки |
| Клиент (`CLIENT`) | Активная сессия + роль + `account_customer_link` с клиентом данной привязки | Предъявляет доказательство в течение 20 минут |
| Руководитель (`MANAGER`) | Активная сессия + роль + отдельное `auto_vehicle_staff_assignment` (MANAGER) для той же машины | Независимо принимает/отклоняет заявку, отзывает связь |
| Другой пользователь | Нет соответствующих роли и объектного назначения | Доступ запрещён, независимо от знания VIN/UUID |

**Важно:** назначение сотрудников на авто пока выполняется в синтетических PostgreSQL fixture, пользовательского процесса provision/branch scope пока нет. Сотрудник должен проверить доказательства вне API; текущая тестовая система **не принимает** личные данные или сканы документов. Аддитивная таблица `auto_vehicle_claim` хранит **только SHA-256 доказательства** и UUID действующих акторов; audit не содержит текст доказательства/VIN.

## Процедура для тестового мастер-приёмщика

1. Подготовить синтетические `auto_vehicle`, `customer`, действующую `account_customer_link` и отдельное назначение INTAKE на машину. Создать pending-связь через `POST /api/v1/dev/auto/vehicles/{vehicle_id}/links` с JSON `{"customerId":"<UUID синтетического клиента>"}`. Ответ `201` содержит `linkId` и статус `PENDING`; повтор при активной связи — `409`. Ручной INSERT в таблицу связи больше не требуется для этого dev-сценария.
2. Использовать только HTTPS loopback с активной cookie `rp_session`, `Origin` и `X-CSRF-Token`, на локальном PG17.
3. `POST /api/v1/dev/auto/links/{link_id}/issue-proof` без тела. Возвращаются `claimId` и одноразовый `proof` только в закрытом HTTPS-ответе сотруднику. **Не помещать proof в Issue, снимки экрана, аудиторские журналы и логи.**
4. Второй вызов для той же привязки должен отказать: запрет повторной выдачи.
5. Передать доказательство клиенту исключительно через отдельно согласованный закрытый тестовый канал. Production-процесс подтверждения ещё не утверждён.

## Процедура для синтетического клиента

1. Войти локальной тестовой учётной записью, имеющей отношение к тому же `customer` (действующая `account_customer_link` и роль `CLIENT`).
2. `POST /api/v1/dev/auto/claims/{claim_id}/redeem`, JSON `{"proof":"<синтетический секрет>"}`.
3. При успехе статус `PENDING_REVIEW` — **автомобиль всё ещё недоступен в личном списке**, пока не принято независимое решение. Ошибочное доказательство даёт `REJECTED`, после пяти попыток заявка блокируется.
4. Вопросы о чужом автомобиле, отозванной роли, истёкшем proof или неправильном `Origin` получают отказ без раскрытия истории.

## Процедура для независимого менеджера

1. Использовать отдельную активную сессию MANAGER с назначением на данный автомобиль; автор и проверяющий должны быть **разными** пользователями.
2. `POST /api/v1/dev/auto/claims/{claim_id}/review`, JSON `{"approve":true}` либо `false`.
3. Одобрение атомарно устанавливает `verified_at`/`verified_by` только конкретной `auto_vehicle_customer_link`; отказ меняет статус на `DECLINED` без выдачи доступа.
4. `POST /api/v1/dev/auto/links/{link_id}/revoke` немедленно отзывает доступ к конкретной связи, не стирая аудита.
5. Действия требуют корректных cookie, `Origin` и CSRF; после удаления роли, назначения или сессии права не действуют.

## Конфиденциальность и гарантия изоляции

- Одна лишь строка VIN, UUID автомобиля или новая pending-связь не открывают никакой приватный ресурс.
- Право на автомобиль не даёт право на прежние `service_ticket`, сметы, вложения. История ремонта проверяется по заказчику **самого наряда**.
- `GET /api/v1/dev/auto/vehicles` показывает только подтверждённые и неотозванные связи; полный VIN не возвращается (есть только `vinLast4`).
- Аудиторские события `ISSUED`, `PROOF_ACCEPTED`, `PROOF_REJECTED`, `VERIFIED`, `DECLINED`, `REVOKED` неизменяемы.
- Продакшен-контракт `/api/v1/auto/`, назначение филиалов/сотрудников через UI, юридическая проверка собственности, процедуры восстановления и мобильный доступ — **planned** в #112/#131/#119.

## Усиление DB-инвариантов назначений — 0023_auto_staff_guard

Аддитивная миграция `0023_auto_staff_guard` запрещает менять actor, vehicle и role уже созданного `auto_vehicle_staff_assignment`, отменять отзыв `revoked_at` и удалять строку назначения. Это необходимо потому, что объектная проверка `_role_scoped` зависит от точной и действующей записи назначения. После отзыва новая выдача доступа оформляется **отдельной** записью, старые доказательства отзыва сохраняются. PostgreSQL тест: `tests/integration/test_pg_auto_staff_guard.py`.


## Новый этап: предложение связи через API (#130)

**Статус — current только для синтетического dev.** Миграция `0024_auto_link_intake` вводит append-only аудит `auto_vehicle_link_intake_audit`. Мастер-приёмщик создаёт лишь неподтверждённую связь, если у него активная роль `INTAKE` и персональное назначение на автомобиль, а у клиента существует действующая связка аккаунта с `customer` и роль CLIENT. Все проверки требуют HTTPS loopback, cookie-сессии, корректного Origin и CSRF.

Операция сериализует конкурентные запросы блокировкой автомобиля, проверяет уникальность активной пары и записывает событие аудита в той же транзакции. Она **не устанавливает** `verified_at/verified_by`, не раскрывает VIN или старые наряды и не заменяет независимое доказательство/проверку MANAGER. Аудит содержит только UUID сотрудника и связи, тип действия и метку времени, без клиентских данных.

Проверка: `PYTHONPATH=apps/api python -m pytest -q tests/integration/test_pg_auto_pending_link_http.py` после Alembic upgrade head на одноразовом PostgreSQL 17. Публичная регистрация автомобилей, staff provisioning через UI и production idempotency пока planned.

## UI checkpoint #130 — staff и клиент (development only)

В тестовом кабинете **`/staff` → «Автомобили (dev)»** мастер-приёмщик (`INTAKE`) может создать pending-связь по UUID автомобиля и клиента и выдать одноразовый код; руководитель (`MANAGER`) может принять/отклонить предъявленную заявку по UUID подтверждения или отозвать связь. Роли видимы в меню только после положительной серверной проверки `/api/v1/dev/staff/access`; **каждую** мутацию отдельно разрешает backend по конкретному `auto_vehicle_staff_assignment`, Origin, cookie и CSRF.

Клиент в **`/account/vehicles`** после проверки серверной сессии может предъявить выданный код через `POST /api/v1/dev/auto/claims/{claim_id}/redeem`. Поле секрета имеет тип password, очищается после запроса, не записывается в URL, localStorage или аналитику. Положительный ответ `PENDING_REVIEW` сам по себе не даёт доступа к автомобилю; требуется независимый `MANAGER`.

Процесс работает **только** с уже созданными синтетическими машинами, клиентами и объектными staff-назначениями. Пользовательское делегирование возможно только для INTAKE, при уже выданном MANAGER object scope; отсутствуют назначение MANAGER, филиалы и список заявок auto review, загрузки юридических доказательств, надёжных процедур безопасной доставки секрета, резервирования операций по idempotency key и production-безопасности. Это не готовый бизнес-процесс. QA: `apps/web/e2e/auto-staff-review.spec.ts` плюс реальные PostgreSQL негативные тесты `tests/integration/test_pg_auto_vehicle_claim_http.py`.

## Безопасное делегирование INTAKE (dev checkpoint #130)

При наличии роли `MANAGER` и **действующего отдельного назначения `MANAGER` на этот же автомобиль** в `/staff` → «Автомобили (dev)» доступна форма «Делегирование приёмщика (dev)». Менеджер вводит UUID *уже существующего* синтетического автомобиля и UUID сотрудника, у которого *уже есть действующая* роль `INTAKE`; нажимает «Назначить приёмщика». Затем «Обновить назначения» показывает активные делегирования только по запрошенной машине. Кнопка «Отозвать назначение» делает отзыв необратимым. Повторный отзыв безопасен и не пишет второй audit.

Соответствующие **закрытые** endpoints: `GET/POST /api/v1/dev/auto/vehicles/{vehicle_id}/intake-assignments`, `POST /api/v1/dev/auto/vehicles/{vehicle_id}/intake-assignments/{assignment_id}/revoke`. Существующие `ROBOport_SYNTHETIC_AUTO_API=1`, `ROBOport_SYNTHETIC_AUTH_API=1`, HTTPS loopback и local PostgreSQL обязательны. POST использует Origin и session-bound CSRF. Назначение никогда не меняет глобальную роль `user_role`, не выдаёт `MANAGER`, `ADMIN`, доступ к другим машинам или чужой истории. Менеджер не может назначить самого себя.

События `INTAKE_GRANTED` и `INTAKE_REVOKED` фиксируются в `auto_vehicle_staff_assignment_audit` (Alembic `0025_auto_intake_delegation`) без VIN, email, паролей, текстов доказательств и документов. PostgreSQL trigger запрещает редактирование и удаление audit. Конкурентное назначение на один объект сериализуется; повторная выдача действующего назначения возвращает 409. После отзыва доступ приёмщика запрещается сервером, даже если UI ещё не обновлён.

**Границы:** исходное назначение `MANAGER` и глобальную роль `INTAKE` по-прежнему создаёт только доверенный dev-fixture, **не** браузер. У филиалов пока нет DB-модели, поэтому никакого «управления филиалами» этот checkpoint не реализует. Идемпотентность с ключом запроса, legal proof, production hardening и персональные данные остаются в #130/#119.

## Retry с Idempotency-Key — checkpoint #130

В dev-контуре поддержан заголовок `Idempotency-Key` длиной **16–128 печатных ASCII-символов без пробелов** для двух операций создания: `POST /api/v1/dev/auto/vehicles/{vehicle_id}/links` и `POST /api/v1/dev/auto/vehicles/{vehicle_id}/intake-assignments`.

При потере ответа повторяйте **тот же payload с тем же ключом**; ответ `201` содержит прежний `linkId` или `assignmentId`. При другом payload/объекте с тем же ключом, отозванной созданной записи или новой попытке без исходного ключа при уже активном объекте сервер возвращает `409` (при отсутствии актуальной роли/объектного полномочия — отказ, без replay). Транзакционный `auto_create_receipt` создаётся атомарно с новым объектом и аудитом; журнал хранит только SHA-256 ключа, отпечаток payload, UUID и момент создания — **не хранит** cookie, VIN, proof или реальные клиентские данные. Конкурентные запросы сериализованы на уровне PostgreSQL. UI сохраняет ключ между повторами после неопределённой сетевой ошибки, но не сохраняет его в localStorage или URL.

Без заголовка сохранена прежняя семантика `409` для повторного создания. **Не использовать этот протокол для `/issue-proof`**: случайный секрет возвращается однократно и не записывается в receipt, его безопасное восстановление и rate-limit требуют отдельного проектирования. Для `redeem` и `review` с версии `0027_auto_claim_retry` поддержан отдельный транзакционный receipt с тем же форматом заголовка; `revoke` остаётся без нового ключа, его текущий ответ повторяем, но отдельный idempotency contract не вводился. Хранение receipts сейчас append-only, перед production необходима формализованная политика retention/архивирования — нельзя удалять записи произвольно без последствий для повторов.


## Безопасный повтор предъявления и независимого решения — `0027_auto_claim_retry`

Для `POST /api/v1/dev/auto/claims/{claim_id}/redeem` и `POST /api/v1/dev/auto/claims/{claim_id}/review` допускается необязательный `Idempotency-Key` из 16–128 печатных ASCII-символов без пробелов. При отсутствии заголовка прежняя single-use семантика сохранена. Receipt создаётся **атомарно в той же транзакции**, что обновление счётчика proof/решения и audit, содержит только хеши ключа/отпечатка, идентификаторы, статус результата и время — не открытый одноразовый код.

Повтор `redeem` с тем же actor, claim, proof и ключом возвращает прежний `PENDING_REVIEW` либо `REJECTED` без дополнительных попыток или событий аудита. Различное тело с прежним ключом — `409`. Валидация принадлежности клиента и роли повторяется при каждой попытке. После перехода заявки в финальный статус, истечения срока кода или отзыва доступа успех не воспроизводится. Лимит **пяти различных предъявлений** сохраняется, повтор того же receipt не тратит новую попытку.

Повтор `review` с тем же actor, claim, решением и ключом возвращает ранее зафиксированный `VERIFIED`/`DECLINED` **только** при неизменённом состоянии и актуальном назначении MANAGER, независимости проверяющего и действующей клиентской связи. Иное решение с тем же ключом, отзыв автомобиля/прав или изменение статуса приводят к отказу или `409` без повторного audit.

UI хранит ключ операции в памяти вкладки, но не записывает его в URL/localStorage. Открытый proof после отправки очищается, поэтому после неопределённой сетевой ошибки клиент должен **заново ввести тот же код**, чтобы получить прежний ключ. Это не полноценный rate-limit по IP/учётной записи; сейчас действует лимит на одну заявку и TTL 20 минут. Отдельные throttling, safe proof recovery, retention receipts и production security gates остаются открытыми задачами.


## Общий лимит попыток по пользователю — `0028_auto_proof_throttle`

В закрытом synthetic API с PostgreSQL действует общий **скользящий по началу окна** (fixed window) серверный бюджет:
- `ISSUE` — **12 новых выдач одноразового доказательства в 60 минут** на одного аутентифицированного сотрудника INTAKE, даже по разным машинам и клиентским связям;
- `REDEEM` — **8 новых предъявлений за 15 минут** на одного аутентифицированного CLIENT, даже по нескольким заявкам/автомобилям. Прежний максимум 5 доказательств на один конкретный claim остаётся дополнительным ограничением.

Проверяется активная сессия и право на объект **до** учёта попытки. Допустимый повтор с прежним `Idempotency-Key` читает receipt перед расходом общего лимита, не увеличивает счётчик и не создаёт новый audit. Новый ключ — новая попытка. PostgreSQL `INSERT ON CONFLICT DO UPDATE` сериализует конкурентные запросы и ограничивает значение счётчика. При превышении API возвращает `429 RATE_LIMITED`, `Cache-Control: no-store`, заголовок `Retry-After: 900` для REDEEM либо `3600` для ISSUE; новый одноразовый код и audit при этом не создаются. Счётчик хранит только UUID пользователя, тип действия, число попыток и начало окна.

**Не является полной защитой от перебора в production:** пока нет доверенного proxy boundary и безопасного выделения client IP, поэтому `X-Forwarded-For` намеренно **не используется** для лимита по IP. Глобальное ограничение на сетевой границе, мониторинг/тревоги, архивирование счетчиков и юридическая процедура владельца остаются задачами #130/#119.


## Однократный перевыпуск при утрате HTTP-ответа ISSUE — `0029_auto_proof_reissue`

Если `POST /api/v1/dev/auto/links/{link_id}/issue-proof` уже создал claim, но ответ с кодом был потерян, **старый код восстановить невозможно и нельзя**. Исходный `link_id` известен INTAKE до ISSUE. Приёмщик с **той же учётной записью, которая выдала исходный код, и с неизменённой активной ролью/назначением на автомобиль** может ровно **один раз** вызвать `POST /api/v1/dev/auto/links/{link_id}/reissue-proof` с CSRF и session cookie. Это **новая выдача**, а не повтор старого ответа.

Предусловия: исходная запись `auto_vehicle_claim` в состоянии `PENDING`, клиент ещё не предъявлял **ни одной** попытки (`proof_attempts = 0`, `claimant_id IS NULL`), ссылка автомобиля не подтверждена и не отозвана, прежнего перевыпуска не было. Даже после истечения исходных 20 минут можно выдать новую замену, если этих нарушений нет. Новый случайный 256-битный proof действует **20 минут с перевыпуска**, исходный proof **становится недействительным немедленно**; claim ID остаётся прежним. `auto_vehicle_claim` и его триггер иммутабельности не меняются: новый хеш/TTL пишется только в `auto_vehicle_claim_reissue` (одна запись на claim, запрет UPDATE/DELETE), audit получает append-only событие `REISSUED`.

Ответ `200` содержит `claimId`, **новый** `proof` и статус `REISSUED` с `Cache-Control:no-store`/ `Pragma:no-cache`. При повторе, чужом сотруднике, отзыве роли, предъявленной попытке, финальном решении или отзыве ссылки — единый `403` без повторного секрета. Перевыпуск учитывается в общем лимите **12 выдач/час** для INTAKE, при исчерпании — `429 RATE_LIMITED` без создания записи. PostgreSQL блокирует claim/link на время выдачи и предъявления; после блокировки чтение версии proof выполняется **отдельным SQL запросом**, чтобы исключить гонку видимости нового секрета.

UI: в /staff → «Автомобили (dev)» приёмщик вводит известный UUID связи, отмечает **«Подтверждаю замену и аннулирование предыдущего кода»** и нажимает «Перевыпустить код однократно». Секрет виден только в ответе и может быть скрыт, не хранится в БД открытым текстом, URL, localStorage или журнале событий. Если **ответ перевыпуска** потерян, повтор невозможен. Для нового кода понадобится управляемое аннулирование связи и создание новой pending-связи, это отдельный dev-процесс, не автоматическая повторная генерация без лимита.

**Production-gate остаётся открытым:** настоящее доказательство владения, безопасный канал доставки секрета, recovery более сложных аварий, trusted IP limit и retention должны быть разработаны отдельно. Ни исходный, ни новый код не являются правоустанавливающим документом.

## Конкурентный отзыв полномочий во время proof/review (#130)

**Статус: current только для закрытого synthetic dev API.** Результат положительной проверки `INTAKE`/`MANAGER` привязан к действующим строкам `user_role` и `auto_vehicle_staff_assignment`, а предъявление и review требуют действующей роли `CLIENT`, активного `app_user` и `account_customer_link`. Для мутаций выдачи/перевыпуска, предъявления proof и решения менеджера PostgreSQL держит `FOR SHARE` на этих строках полномочий **до завершения транзакции**. Если отзыв завершился до проверки — операция запрещается; если операция успела получить блокировку — конкурентный отзыв ожидает commit, а следующий запрос уже видит отзыв. Это закрывает TOCTOU между SELECT активного права и его использованием при мутации. `auto_vehicle_claim` и `auto_vehicle_customer_link` по-прежнему сериализуются `FOR UPDATE`.

Проверка на одноразовой PostgreSQL 17: `PYTHONPATH=apps/api python -m pytest -q tests/integration/test_pg_auto_claim_scope_locks.py`. Негативные тесты запускают второе соединение с ограниченным `lock_timeout`: попытки отозвать роль INTAKE, объектное назначение INTAKE/MANAGER или клиентскую связь до commit должны блокироваться; после завершения и отзыва новые операции получают отказ, без обхода прав и без раскрытия секретов. Никаких новых endpoints, миграций или пользовательских разрешений этот шаг **не добавляет**. Это не завершает production-процесс удостоверения владения; юридическая проверка, полномочия филиалов, доставка proof, retention receipts и #119 остаются отдельными гейтами.

Это **не** очистка подтверждений собственности и не изменение лимитов выдачи.

## Отзыв сессии и деактивация учётной записи во время auto-мутации (#130)

**Статус: только закрытый synthetic dev API.** В дополнение к `FOR SHARE` на активных ролях и объектных назначениях операции выдачи/перевыпуска proof, предъявления клиентом, независимого решения MANAGER, создания pending-связи и делегирования INTAKE теперь блокируют строки действующей **`app_user`, затем `user_session`** до commit бизнес-транзакции (именно в таком порядке, как при смене пароля). Это исключает гонку: положительная проверка сессии не может завершиться, после чего другой запрос аннулирует сессию/отключит пользователя **раньше**, чем завершится выпуск proof или решение. Если отзыв завершён первым — следующий запрос отклоняется; если действие получило блокировку первым — отзыв ждёт commit. Это сериализация, а не запрет отзыва.

При создании pending-связи также удерживаются строки `account_customer_link`, `user_role` и `app_user`, на основании которых подтверждена возможность связать машину с действующим клиентом. Деактивация или отзыв клиентского полномочия не может пересечься между проверкой и созданием pending-link. **Новая связь сама по себе не подтверждает владение** и не открывает историю нарядов. Для чтения `GET` не добавляются write-блокировки сессии; маршрут `/staff` по-прежнему не выдаёт `MANAGER` и не создаёт production филиалы.

Регрессионная проверка на disposable PostgreSQL 17:

```bash
PYTHONPATH=apps/api python -m pytest -q tests/integration/test_pg_auto_session_revocation.py
```

Тесты дополнительно проверяют реальную очередь блокировок при смене пароля, чтобы исключить deadlock и HTTP 500. Они используют отдельное соединение PostgreSQL с коротким `lock_timeout` для отзыва сессии, отключения клиента/сотрудника и отзыва клиентской связи во время операции. После commit новые запросы должны быть отклонены, без лишних записей proof/audit. Протокол, UI, Alembic и модель ролей не расширены; production bootstrap MANAGER/филиалов, safe delivery, юридическая проверка собственности и release gate #119 остаются отдельными задачами.

## Пилот ограничения staff-операций филиалом — `0030_auto_location_scope` (#130)

**Статус: реализован только опциональный synthetic/dev-контур, не production bootstrap.** Для проверки филиальной изоляции добавлены три аддитивные PostgreSQL-таблицы: `auto_service_location` (технический код филиала), `auto_vehicle_location_binding` (один закреплённый филиал автомобиля), `auto_location_role_grant` (выданное право `INTAKE` или `MANAGER` на конкретный филиал). Удаление всех трёх типов записей запрещено; перенести автомобиль в другой филиал простым `UPDATE` нельзя; отзыв полномочия и отключение филиала необратимы. Указанный `code` — синтетический идентификатор, а не юридический адрес или реквизиты.

Для **явного dev-пилота** сервер дополнительно принимает переменную `ROBOport_SYNTHETIC_AUTO_BRANCH_SCOPE=1` при уже обязательных `ROBOport_SYNTHETIC_AUTO_API=1` и локальной auth/PG17. При значении `1` каждая выдача и перевыпуск proof, решение `MANAGER`, отзыв связи, создание pending-связи и просмотр/выдача/отзыв назначения `INTAKE` требуют одновременно:

- активную сессию, активного сотрудника и актуальную глобальную роль `user_role`;
- назначение `auto_vehicle_staff_assignment` на **конкретный** автомобиль и ту же роль;
- неизменяемую привязку этого автомобиля к **активному** филиалу и действующий `auto_location_role_grant` на **тот же филиал, роль и сотрудника**.

При отсутствии любой части или при отключении филиала — отказ без раскрытия чужих машин/доказательств. Простой филиальный grant **не** выдаёт глобальную роль `MANAGER`, не создаёт назначение на автомобиль, не позволяет назначить самого себя или эскалировать роль; `CLIENT` не получает staff-полномочий. Положительная проверка филиала и grant удерживаются через PostgreSQL `FOR SHARE` до commit операции: конкурентный отзыв дожидается её завершения.

**Как тестировать:** только на одноразовом PG17 со случайными synthetic UUID; роли, филиалы, автомобильные назначения и филиальные grants тестируются через специальные PostgreSQL fixtures, а **не** через пользовательский bootstrap. Запуск: `PYTHONPATH=apps/api python -m pytest -q tests/integration/test_pg_auto_location_scope.py`. Пилот не включает создание/удаление филиалов из UI/API, передачу машин между филиалами, массовые права, штатную выдачу роли MANAGER или аудит реального процесса approval; отдельный безопасный bootstrap с независимой авторизацией и протоколом изменений — следующая задача.

**Совместимость:** значение `ROBOport_SYNTHETIC_AUTO_BRANCH_SCOPE=0` (по умолчанию) сохраняет прежние синтетические тестовые сценарии с назначением на автомобиль без филиала. Неизвестные/ошибочные значения переменной (например `yes`) не отключают проверку, а возвращают отказ. Значение `1` без настроенной привязки **запрещает все staff auto-мутации**, а не пропускает старые записи. Это не рабочая политика миграции legacy данных и не production-модель организации; допуск реального филиала, полномочий менеджеров и ПД по-прежнему заблокирован #119.

## Защита транспортного контекста от поддельных proxy-заголовков (#159)

**Готово только для synthetic/dev auto HTTP.** Пока не утверждён доверенный TLS-terminating reverse proxy, автомобильные маршруты `/api/v1/dev/auto` и `/api/v1/dev/auto/*` **не используют и не принимают** клиентские `Forwarded`, `X-Forwarded-*`, `X-Real-IP`, `X-Original-Host` и схожие алиасы. Такие запросы получают общий `404 NOT_FOUND` с `Cache-Control: no-store` **до подключения к БД**. Они не меняют счётчик выдачи proof, не создают claim или audit. Простые одноимённые поля в JSON не интерпретируются как peer/TLS; `Origin` и CSRF по-прежнему обязательны для mutations.

Контейнер `apps/api/Dockerfile` теперь явно запускает Uvicorn с `--no-proxy-headers`; небезопасное `--forwarded-allow-ips=*` запрещено. Таким образом, запросы через HTTP reverse proxy нельзя представить безопасными HTTPS только подстановкой `X-Forwarded-Proto: https`. Без подтверждённой схемы TLS на прямом loopback HTTPS synthetic endpoints могут намеренно оставаться недоступны из существующего Compose/Nginx. Это **fail-closed**, не ошибка, которую допустимо обходить отключением TLS-guard. Для реального reverse proxy нужно отдельное архитектурное и security решение с защитой peer identity, доверенными источниками, собственным TLS, ретестом CSRF/cookie и rate-limit.

Проверки: `PYTHONPATH=apps/api python -m pytest -q tests/bootstrap/test_auto_proxy_boundary.py tests/integration/test_pg_auto_proxy_boundary.py` на disposable PG17. HTTP/PG тесты подтверждают, что spoof заголовки не открывают proof даже для настоящего INTAKE, а запрос без них по прежнему выдаёт ровно одно подтверждение и audit. **Этот gate не реализует IP rate limiting**, не определяет IP клиента за proxy и не подтверждает продакшен инфраструктуру. Следующий этап #130/#119 — отдельный доверенный ingress и multi-worker rate limiting по проверенному peer, без чтения поддельного `X-Forwarded-For`.

## Сетевой лимит по прямому peer для synthetic auto POST (#161)

**Статус: opt-in локальный dev-пилот, не production.** В дополнение к actor limit (ISSUE 12/ч и REDEEM 8/15 мин) появилась отдельная **общая квота 30 HTTP POST на 15 минут** для одного прямого сетевого peer. Её проверяют **до CSRF, сессии, UUID и бизнес-операции**, включая повторные запросы с тем же Idempotency-Key, невалидные payload, 403 и 404. 31-й запрос возвращает `429 RATE_LIMITED`, `Retry-After: 900`, `Cache-Control: no-store` **без нового claim или audit**. Повторный ключ не расходует повторно *бизнес*-бюджет попыток, но, поскольку это **новый HTTP запрос**, он расходует сетевую квоту. Запросы `GET` не лимитируются этим счётчиком.

Для явного включения **только на disposable PG17 + прямом loopback HTTPS** задайте отдельным защищённым способом `ROBOport_SYNTHETIC_AUTO_PEER_LIMIT=1` и `ROBOport_SYNTHETIC_AUTO_PEER_HMAC_KEY` (не менее 32 байт UTF-8 случайного секрета); обычные `ROBOport_SYNTHETIC_AUTH_API=1`, `ROBOport_SYNTHETIC_AUTO_API=1` и локальный `ROBOport_DATABASE_URL` обязательны. **Никогда не коммитьте сам секрет в Git, не пишите его в URL, журнал и screenshots.** Значение по умолчанию `0` оставляет существующие synthetic fixtures без сетевой квоты; ошибочный флаг, отсутствующий/слабый HMAC ключ, нераспознанный или не-loopback peer **запрещают** авто-POST, а не переходят на `X-Forwarded-For`. Недоступный PostgreSQL даёт общий `503 UNAVAILABLE` (fail-closed).

Источник адреса — `request.scope['client']`, переданный Uvicorn от **прямого TCP-сокета**, а не `Host`, `X-Real-IP`, `Forwarded` или `X-Forwarded-For` (последние уже запрещены #159). Допускается только числовой IPv4/IPv6 **loopback**; локальные порты не меняют fingerprint. Код использует HMAC-SHA256 с ключом окружения и меткой домена, хранит в `auto_peer_throttle` только 64 hex-символа хеша и окно; конкурентные процессы разделяют атомарный PostgreSQL `ON CONFLICT` с насыщением на 31. Операция счётчика коммитится **отдельно** до бизнес-запроса, так что 403/сетевые сбои не возвращают квоту. Это лимит прямого *локального* адреса; при NAT или reverse proxy он не идентифицирует настоящего удалённого пользователя. Изменение HMAC ключа меняет fingerprint и обнуляет фактическое использование прежнего счётчика — секрет должен быть стабильным в рамках тестового стенда и не ротироваться без отдельного согласованного действия.

Проверка на одноразовом PG17:
```bash
PYTHONPATH=apps/api python -m pytest -q tests/bootstrap/test_auto_peer_throttle_policy.py tests/integration/test_pg_auto_peer_throttle.py
```

Не используйте этот режим как обход HTTPS или как защиту публичного сервиса. Для production необходимы отдельно одобренная TLS/ingress архитектура, строгая аутентификация trusted peer, NAT/fairness политика, уровни лимитов, стратегия удаления сетевых счётчиков и юридическая проверка. Не смешивать `auto_peer_throttle` (операционный счётчик) с immutable evidence/receipt; автоматическая очистка из данной задачи не предусмотрена, миграционный `downgrade` разрешён только на disposable стенде. Gate #119 остаётся **закрытым**.
