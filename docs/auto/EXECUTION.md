# Выполнение согласованного заказ-наряда: работы, материалы, независимый QC

> **Статус: current-dev, только synthetic HTTPS loopback.** Это завершённый
> тестовый бизнес-сценарий **от одобренной сметы до независимого QC**, но **не**
> законная сдача ремонта, кассовая операция, фискализация или выдача автомобиля.

## Предусловия

Существует автомобильный WorkOrder с подтверждённой и неотозванной связью
клиент–автомобиль, действующей записью и привязкой к филиалу. Приёмщик (INTAKE)
зафиксировал неизменяемый осмотр, менеджер (MANAGER) опубликовал версию сметы по
**всем** выбранным услугам, а клиент (CLIENT) одобрил именно последнюю версию.
Если клиент отклонил смету или связь была отозвана, начало работ запрещено.

Для движения деталей заранее созданы синтетический SKU, партия, физический остаток,
партионное размещение и **резерв на этот конкретный заказ-наряд**. Складской
ledger не подменяется новой таблицей: используются существующие атомарные
`record_auto_stock_lot_work_order_issue` и
`record_auto_stock_mechanic_handoff`.

## Сквозной процесс на экране

Экран `/staff/auto-execution` работает в закрытом dev-кабинете. Введите UUID
организации, филиала и WorkOrder. Для действий нужны разные действующие
роли филиала; всё повторно проверяется сервером. Наличие кнопки недостаточно.

1. **MANAGER:** после `APPROVED` и осмотра нажмите **«Начать работы (MANAGER)»**.
   Состояние перейдёт в `IN_PROGRESS`. Запись immutable; повтор идентичного
   запроса с тем же `requestKey` не начинает второй процесс.
2. **MECHANIC:** напротив **каждой** услуги одобренной сметы укажите
   **«Фактические минуты»** (1–1440), нажмите **«Зафиксировать работу»**.
   Запись по услуге неизменяема. Неподтверждённая или посторонняя услуга
   не может оказаться в факте; разрешить её можно только через новую
   смету до решения клиента.
3. **WAREHOUSE:** если нужны детали, сначала отдельно зарегистрируйте
   резерв и партию. Введите **«UUID партии»**, **«Количество»**, нажмите
   **«Выдать из резерва (WAREHOUSE)»**. Под капотом существующий ledger
   одновременно уменьшает физический и заказной резерв. Нехватка или
   чужой склад → отказ, нельзя получить отрицательный остаток.
4. **MECHANIC:** выберите UUID из списка **«Выдача для получения»** и
   нажмите **«Подтвердить получение (MECHANIC)»**. Каждая выдача
   подтверждается ровно один раз. Незакрытая выдача блокирует завершение.
5. **MECHANIC:** когда зафиксированы все одобренные услуги и приняты все
   выданные детали, нажмите **«Завершить выполнение (MECHANIC)»**.
   Состояние `READY_FOR_QC`; новые записи труда и новые выдачи
   через этот сценарий запрещены. SQL-триггер также запрещает выдачу из
   партии после финализации.
6. **Другой MECHANIC:** откройте `/staff/auto-workshop-qc` и
   независимо зафиксируйте результат проверки качества после
   исполнения. Исполнитель, уже указанный в фактических работах,
   не может быть QC-проверяющим. `FAIL` остаётся в append-only журнале;
   `PASS` даёт `QC_ACCEPTED`, но `releaseAllowed` **всегда false**.

Для сценария без материалов шаги 3–4 пропускаются. Если после сетевого сбоя
неясен результат, **«Повторить тот же запрос»** сохраняет тело с
прежним `requestKey`; при выборе «Перечитать журнал» исходный ключ не
подменяется как будто операция гарантированно откатилась. При 403
ранее показанные данные удаляются из интерфейса.

## API и контракт

Префикс `/api/v1/dev/auto/organizations/{org}/locations/{loc}/orders/{order}/execution`:

| Метод | Путь | Роль | Данные |
|---|---|---|---|
| GET | `/` (без завершающего слеша) | MANAGER/WAREHOUSE/MECHANIC | status, approvedVersion, labor, materials, qcStatus, releaseAllowed=false |
| POST | `/start` | MANAGER | requestKey |
| POST | `/labor` | MECHANIC | requestKey, serviceId, actualMinutes |
| POST | `/materials/issue` | WAREHOUSE | requestKey, lotId, quantity |
| POST | `/materials/receive` | MECHANIC | requestKey, issueId |
| POST | `/finish` | MECHANIC | requestKey |

Все POST требуют cookie-сессию, same-origin Origin и session-bound CSRF.
Впервые 201; точный безопасный повтор start/labor/finish 200; 403 при
чужом филиале, заказе, отзыве прав или подтверждения; 409 при неполном
исполнении, чужом сервисе, недостатке резерва, повторном завершении.
Поля суммы, PIN, VIN, фото или ПДн в API не включаются. Ответы
`Cache-Control: no-store`; маршруты скрыты из публичного OpenAPI.

## Данные, конкурентность и независимый аудит

Alembic `0087_auto_execution` добавляет три immutable таблицы:
`auto_work_order_execution` (один старт по одобренной точной ревизии),
`auto_work_order_labor_entry` (не более одной записи на услугу),
`auto_work_order_execution_finish` (одна финализация). Срабатывают
серверная сериализация `FOR UPDATE` на WorkOrder и SQL-триггеры:
нельзя записать труд по чужой услуге, завершить без всех фактов/получений,
провести QC до `finish`, выполнить QC собственных трудозатрат или
выдать новую партию после `finish`. Остатки/резервы и складская
идемпотентность сохраняются за существующим ledger.

Доказательства: `tests/integration/test_pg_auto_work_order_execution_http.py`,
`apps/web/e2e/auto-work-execution.spec.ts` и предыдущие интеграционные
тесты ledger, оценки и QC. Downgrade допустим только для disposable
синтетического PG17 без юридически значимых данных.

## Условная сверка после QC (current-dev)

После `QC_ACCEPTED` менеджер может сверить согласованную сумму с синтетическим журналом `SIM_PAYMENT/SIM_REFUND`, кладовщик закрывает неиспользованный резерв, после чего формируется неизменяемый технический пакет с SHA-256. **Пакет не является актом выдачи, кассовым чеком или платежом.** [Пошаговая инструкция и API](DEMO_CLOSE.md). Юридические и security gates #119 по-прежнему блокируют реальную выдачу.


## Сверка с менеджерской аналитикой (current-dev, #171)

После фиксации `/labor` руководитель может открыть `/staff/auto-bay-occupancy` за локальный день **регистрации** события и увидеть увеличение «Записи труда» и «Минуты по журналу» на сохранённый `actualMinutes`. Идемпотентный повтор с тем же `requestKey` не увеличит значения. `/finish` увеличивает «Завершено исполнений» в день регистрации. Эти числа не являются табелем, зарплатой, подтверждением QC PASS или выдачей. [Формулы и ограничения](REPORTING.md).


## Безопасные повторы после завершения исполнения и QC (#114/#167, current-dev)

Если ответ HTTP на запись труда, выдачу зарезервированной партии или подтверждение получения потерян, тот же `requestKey` и неизменённый payload можно повторить **даже после** `READY_FOR_QC` либо `QC_ACCEPTED`. При действующей роли, подтверждённой связи клиента с автомобилем и том же исходном WorkOrder сервер возвращает **200, `replayed:true`**, актуальное состояние этапа и первоначальный `issueId` / `handoffId` там, где они применимы. Новые действия после завершения всё равно получают **409 `NOT_IN_PROGRESS`**: повтор никогда не создаёт новые записи труда, выдачу из партии или дополнительный handoff.

Данные журнала неизменяемы: повтор со старым ключом, но другим исполнителем, сервисом, количеством или партией получает **409**. Отзыв роли/связи, чужая организация либо филиал по-прежнему дают **403** и не позволяют повтором обойти авторизацию. Для `/labor` уникальность включает конкретного исполнителя и исходную пару service/actualMinutes, для `/materials/issue` — заказ/партию/количество; для `/materials/receive` — исходную выдачу и сотрудника. Новые идентификаторы при replay не генерируются.

Проверено реальным PG17 HTTP сценарием `tests/integration/test_pg_auto_work_order_execution_http.py` (начало → труд → выдача → получение → finish → независимый QC; повторы и запрет новых действий после переходов; счётчики immutable записей ровно по одному), а также Playwright `apps/web/e2e/auto-work-execution.spec.ts` (потеря ответа, повтор прежнего тела/ключа и смена этапа). Миграции/production API не меняются, release gate #119 остаётся закрытым.
