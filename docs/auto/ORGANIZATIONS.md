# Организации и филиалы автомобильного сервиса

**Статус: current-dev database foundation; API/UI/production planned.** Задача [#166](https://github.com/askarahodov/roboport/issues/166). Синтетическая модель, без реальных персональных данных.

## Реализованная часть

Миграция `0033_auto_organization` добавляет `auto_organization` с уникальным кодом и неизменяемой идентичностью, а также nullable `auto_service_location.organization_id`. Существующие синтетические филиалы сохраняются **без привязки**: ни legacy `user_role`, ни `auto_location_role_grant` не означают полномочий в новой организации. Привязка филиала к организации однократная и не может быть отозвана/изменена простой UPDATE. Запрет изменения и удаления организации защищён триггерами PostgreSQL. Отзыв через `disabled_at` необратим.

## Что запрещено считать готовым

Нет production ADMIN/bootstrap, создания организации через API, приглашений, графиков и постов, tenant-scoped customer/WorkOrder/Stock/Finance, UI управления и полноценной межорганизационной авторизации. Nullable `organization_id` — миграционный карантин, **не** допуск к данным; все новые endpoints обязаны deny-by-default для NULL и проверять tenant + location + actor + object. До #119 production запрещён.

## Проверки и откат

`PYTHONPATH=apps/api python -m pytest -q tests/integration/test_pg_auto_organization.py` на disposable PG17 после Alembic upgrade head. Тесты проверяют отсутствие неявной привязки, FK, попытку повторного назначения, изменение identity и необратимость disable. Downgrade удаляет данные новой схемы; **только для одноразовой тестовой БД**, никогда для production.

## Записи полномочий (миграция 0034; только каркас)

Добавлена таблица `auto_organization_role_grant` для штатных ролей `MANAGER`, `INTAKE`, `MECHANIC`, `WAREHOUSE`, с привязкой к организации и необязательному филиалу. База запрещает добавлять назначение к филиалу другой организации, повторять активный grant, менять идентичность записи или отменять отзыв. Связанные организации/филиалы должны быть действующими при создании назначения.

**Это ещё не безопасный процесс выдачи прав:** существующая БД не имеет доверенного API выдачи ролей, actor audit и утверждённого ADMIN bootstrap. Пока новая таблица недоступна из HTTP и не используется в проверках реальных прав; прямые записи допускаются только из закрытых тестовых fixtures. Не выдавать `MANAGER` или `INTAKE` через legacy `user_role` на основании этой схемы. Реальные операции требуют отдельного service-layer с сериализацией отзывов, проверкой сессий и авторизованного администратора, audit и E2E. Задача #166 остаётся открытой.

Проверки: `PYTHONPATH=apps/api python -m pytest -q tests/integration/test_pg_auto_org_grants.py` на disposable PG17 после `alembic upgrade head`.

## Серверная проверка роли организации — пилот #166

Добавлена функция `organization_role_allows` в `auto_org_authority.py`. Она требует действительную PostgreSQL-сессию и активную отдельную роль организации, проверяет филиал того же tenant, состояние организации/филиала и отзыв grant. Старый глобальный `user_role` не учитывается. Для опасных операций вызывающий обязан открыть транзакцию и использовать `for_mutation=True`, что добавляет блокировки сессии, организации и назначения, а также запрошенного филиала; после завершённого отзыва следующий запрос доступа не получает.

**Важно:** механизм пока не подключён к production API, не создаёт ADMIN, не выдаёт/отзывает роли и не заменяет обязательное независимое подтверждение первоначального администратора. Сквозные операции, audit и UI остаются planned в #166/#119. Проверка: `tests/integration/test_pg_auto_org_authority.py` на синтетическом PG17.

## Неизменяемый аудит назначений (0035)

Миграция `0035_auto_org_grant_audit` записывает `GRANTED` при добавлении и `REVOKED` при первом отзыве в отдельную таблицу с запретом UPDATE/DELETE и уникальностью пары (grant, action). Исторический субъект `actor_id` пока **не устанавливается**: прямые SQL-вставки синтетических fixtures не являются доказательством санкционированной выдачи прав. Не считать этот аудит полноценным акторским журналом или ADMIN bootstrap. Для production нужны доверенная server-side процедура назначения и отзыва с контекстом authenticated actor, независимая процедура первого ADMIN и тесты конкурентных отзывов. Без них #166 остаётся открытой.

Проверка: `tests/integration/test_pg_auto_org_grant_audit.py`, только synthetic PostgreSQL 17. Откат 0035 уничтожает аудит и возможен исключительно на disposable БД.

## Закрытый сервис назначения сотрудников — срез 0036

**Статус: current-dev, internal only; не production.** Миграция `0036_auto_org_admin` разрешает организационную роль `ADMIN` только без филиала, добавляет неизменяемый журнал `auto_org_staff_action` с обязательным `actor_id` для действий сервиса. `auto_org_staff.py` выполняет `grant_staff` / `revoke_staff` через живую PostgreSQL-сессию активного ADMIN **именно данной организации**. Запрещено самоназначение, выдача `ADMIN` через сервис, работа в чужой организации, выдача роли в чужом филиале и изменение чужой записи назначения. Отзыв идемпотентен, журналируется атомарно с изменением grant.

**Bootstrap ADMIN остаётся блокером:** в тестовом контуре ADMIN создаётся исключительно прямой синтетической SQL-fixture из доверенного теста. Это не операторская процедура и не право production-пользователя; никаких HTTP-маршрутов назначения сотрудников пока нет. Фактический production bootstrap должен установить независимую проверку личности/организации, two-person review, неизменяемый audit источника доверия, процедуру восстановления и отказа; нельзя считать ручное выполнение SQL безопасной выдачей прав. До #119 запрещён публичный доступ. Проверка: `tests/integration/test_pg_auto_org_staff.py` на disposable PostgreSQL 17.

## Проверки конкурентного отзыва (дополнение #166)

Интеграционный PG17 тест `test_revoke_and_authorization_are_serialized_at_pg17` проверяет блокировку отзыва в ходе транзакционной проверки полномочий и немедленный отказ после завершённого отзыва. `test_regrant_after_revocation_uses_fresh_identity_and_audit` проверяет, что повторная выдача после отзыва создаёт новую запись и сохраняет историю обоих назначений. Это проверка внутреннего synthetic-сервиса, не производственный HTTP/E2E сценарий.

## Закрытый HTTP-контур управления сотрудниками — current-dev

Доступны только при явном `ROBOport_SYNTHETIC_AUTO_API=1` и прямом HTTPS loopback, без доверия proxy-заголовкам: `POST /api/v1/dev/auto/organizations/{org_id}/staff` с JSON `userId`, `role`, необязательным `locationId`, а также `POST /api/v1/dev/auto/organizations/{org_id}/staff/{grant_id}/revoke`. Требуются активная session cookie, `Origin` и CSRF; активная организационная роль `ADMIN` независимо от legacy-роли. Ответы: `201` с `grantId`, `200` со статусом отзыва, `403` при недостатке полномочий, `409` при повторном активном назначении, `422` при ошибочном вводе. Ответы не кэшируются. Первый `ADMIN` доступен исключительно через закрытую синтетическую fixture, публичного bootstrap нет.

**Важное ограничение:** эти маршруты предназначены только для одноразового dev PostgreSQL, не для реальных пользователей. Здесь нет приглашения сотрудника, подтверждения владения организацией, production ingress и UI. Все эти пункты остаются обязательными для #166 и #119. Проверка `tests/integration/test_pg_auto_org_staff_http.py` покрывает неавторизованный доступ, CSRF, чужую организацию, запрет выдачи ADMIN, повторное назначение, отзыв и атрибуцию аудита.

## Первичный ADMIN: закрытый signed-bootstrap (0037, current-dev)

Новый модуль `auto_org_bootstrap.py` выполняет **однократную** выдачу первого `ADMIN` организации исключительно из доверенного внутреннего Python-контекста, **без HTTP endpoint**. Требуются две независимые HMAC-SHA256 подписи одного statement `auto-admin-v1:{organizationId}:{targetUserId}:{expiresUnix}:{nonce}` с различными ключами длиной не меньше 32 байт, ограниченным сроком действия 15 минут; ключи не сохраняются в БД. Транзакция блокирует организацию, проверяет активного пользователя, отсутствие прежнего ADMIN и записывает назначение вместе с неизменяемым `auto_org_bootstrap_receipt`, содержащим SHA256 statement (не ключи). Повторная выдача первого ADMIN запрещена даже после его отзыва; дальнейшее восстановление требует самостоятельной утверждённой процедуры.

**Не является production bootstrap:** две подписи доказывают контроль над двумя ключами, но сами по себе не подтверждают юридическую идентичность владельца или независимость операторов. Внешнее хранение, разграничение доступа к ключам, верификация личности, подтверждение организации и recovery должны пройти #119 до работы с реальными пользователями. Запрещено передавать ключи в HTTP или сохранять их в GitHub/логах. Реальные персональные данные не используются. Проверка: `tests/integration/test_pg_auto_org_bootstrap.py` в disposable PG17; downgrade удаляет доказательства и только для synthetic стенда.

## Экран администратора сотрудников (current-dev, только синтетика)

Маршрут `/staff/auto-admin` — отдельная автомобильная страница, не часть старого robot staff-портала. Администратор вводит UUID организации и видит активные назначения (только роль, UUID пользователя/филиала, UUID назначения), затем может назначить одну из ролей `MANAGER`, `INTAKE`, `MECHANIC`, `WAREHOUSE` или отозвать назначение после подтверждения. Экран использует `GET /api/v1/dev/auto/organizations/{org_id}/staff` и уже существующие закрытые POST-операции. Сервер всегда проверяет действующую сессию и активный ADMIN конкретной организации; GET ограничен 100 активными назначениями и не возвращает ФИО, почту, телефоны или историю другой организации. После отзыва список загружается повторно. При 403/404 отображается отказ, при ошибке — повторный запрос. CSRF запрашивается сервером перед изменением, а не хранится в localStorage.

**Ограничения:** экран доступен через синтетические маршруты при HTTPS loopback, соответствующих dev feature flags и disposable PG17, а не для production. UUID организации вводится вручную, нет каталога приглашений/постов, search/pagination, юридической проверки владельца, recovery ADMIN или полноценных tenant customer/stock/finance операций. Не закрывать #166 и #119 по этому dev экрану. Код: `apps/web/src/pages/staff/AutoStaffAdmin.tsx`, `apps/api/roboport_api/auto_org_staff_http.py`; тест `tests/integration/test_pg_auto_org_staff_http.py`.

## Браузерная регрессия административной панели

`apps/web/e2e/auto-staff-console.spec.ts` проверяет изоляцию панели при 403, создание назначения с CSRF и точным tenant path, отзыв с явным двухшаговым подтверждением (без системного browser dialog), проверкой ровно одного POST и очисткой списка, обработку 409 без ложного успеха, а также мобильный экран 390px в тёмной теме. Сетевые ответы mock-синтетические; проверки реальной PostgreSQL авторизации выполняются отдельно в `tests/integration/test_pg_auto_org_staff_http.py`. Оба типа проверки обязательны, но ни один сам по себе не доказывает production-гарантии.
