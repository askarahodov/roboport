# Синтетическая проверка автомобильного CSV перед миграцией

## Назначение и ограничения

Это **локальный dry-run**, не реальный импорт. Используйте только искусственно созданные данные. Скрипт `scripts/auto_migration_dry_run.py` не подключается к PostgreSQL, ничего не записывает, не обрабатывает ПДн, историю ремонтов, документы, платежи, VIN и XLSX. Он не разрешает релиз #119 и не заменяет cutover/restore #165/#172.

## Команда

```bash
python scripts/auto_migration_dry_run.py --synthetic-only ./synthetic_inventory.csv
```

Формат UTF-8 CSV с колонками в точном порядке:

```csv
record_type,source_id,organization_id,location_id,article,quantity
SKU,SKU-1,00000000-0000-4000-8000-000000000001,00000000-0000-4000-8000-000000000002,FILTER-001,0
STOCK,EVENT-1,00000000-0000-4000-8000-000000000001,00000000-0000-4000-8000-000000000002,FILTER-001,25
```

Допустимы `SKU` с количеством 0 и `STOCK` с целым количеством от 0 до 1 000 000 000. Все записи привязаны к UUID организации и филиала. Артикулы и source ID ограничены латинскими прописными буквами, цифрами, `-`, `_`, `.`. Проверяются повторяющиеся source ID, повторные SKU и остатки без SKU в **том же** tenant/филиале. Порядок записей не важен. Суммарное количество всех `STOCK`-строк одного артикула в одном tenant/филиале не должно превышать 1 000 000 000: нарушение возвращает `STOCK_TOTAL_LIMIT` с номером строки. Остатки разных филиалов и артикулов считаются отдельно.

## Результат и ошибки

На stdout выдаётся только JSON с `ok`, `counts`, `errors` с номерами строк и кодами ошибок, `mode: DRY_RUN_ONLY`, `writes: 0`. Исходные значения, персональные поля и UUID не выводятся. Код процесса 0 означает корректную структуру синтетических данных, код 1 — обнаруженную ошибку. Повторное чтение того же файла даёт тот же отчёт. Максимум 50 000 строк и 5 МБ. CSV только с заголовком без записей отвергается с `EMPTY_INPUT`: пустой пакет не должен ошибочно выглядеть успешной проверкой миграции. Некорректные непустые строки продолжают получать свои конкретные коды ошибок.

## Следующие обязательные этапы

Полный CSV/XLSX mapping и deduplication клиентов, авто, работ, доказательство владения и согласия на историю, импорт через авторизованный интерфейс, reconciliation источника и приёмника, резервная копия, dry-run восстановления, rollback и независимые privacy/security/operations решения **не реализованы** этим скриптом. До их подтверждения #119, #165 и #172 остаются открытыми.


## Reconciliation синтетического источника

Для сверки ожидаемых количеств укажите все три неотрицательных параметра вместе: `--expect-rows`, `--expect-sku`, `--expect-stock`. Например: `python scripts/auto_migration_dry_run.py --synthetic-only --expect-rows 2 --expect-sku 1 --expect-stock 1 synthetic_inventory.csv`.

`rows` означает число строк данных, `SKU` и `STOCK` — количество принятых записей этих типов. Несовпадение означает `RECONCILIATION_ROWS`, `RECONCILIATION_SKU` или `RECONCILIATION_STOCK` и exit 1. Неполный набор либо отрицательные значения дают exit 2. Результаты не раскрывают исходные идентификаторы. Это не сверка с БД и не доказательство идемпотентного импорта.


## Контроль целостности исходного синтетического CSV

Для воспроизводимой проверки укажите заранее вычисленный SHA-256 **байтов файла**: `python scripts/auto_migration_dry_run.py --synthetic-only --expect-sha256 <64-hex-digest> ./synthetic_inventory.csv`. Допустимы только 64 строчные шестнадцатеричные цифры. Скрипт вычисляет хеш однократно считанных ограниченных 5 МБ данных и парсит именно этот снимок; при несовпадении возвращает `SOURCE_CHECKSUM`, `ok: false`, код процесса 1 и не раскрывает исходные поля или хеш. Неверный формат аргумента даёт код 2. Хеширование не подтверждает подлинность источника: доверенный digest должен поступать отдельно и до проверки. Это **не** выполняет загрузку в PostgreSQL и не разрешает работу с настоящими данными.


## Изолированное синтетическое staging-хранилище PostgreSQL 17 (current-dev, #172)

После миграции `0074_auto_migration_staging` доступна **внутренняя библиотечная функция** `stage_synthetic_csv(conn, path, organization_id=..., batch_id=..., expected_sha256=...)` из `scripts/auto_migration_pg_staging.py`. Её вызывают **только** из одноразового тестового окружения PostgreSQL 17 с правами владельца БД и искусственными данными. HTTP API и рабочая команда для сотрудников отсутствуют; никакие данные не поступают в рабочий `auto_stock_sku` или `auto_stock_event`. В production включать нельзя до #119 и дизайна DB grants / RBAC.

Проверка читает исходные байты **один раз** (не более 5 МБ), сверяет обязательный заранее известный SHA-256 и запускает прежний CSV preflight по идентичному снимку. После проверки в одной PostgreSQL-транзакции создаются `auto_migration_staging_batch` и `auto_migration_staging_line`. Таблицы ограничены scope организации и филиала, защищены от UPDATE/DELETE триггерами, не допускают повторных source ID для филиала/пакета. Повтор `batch_id` с тем же digest и счётчиками возвращает `replayed: true` **только после побайтово-логической сверки всех сохранённых строк в исходном порядке** (номер строки, scope, тип, source ID, артикул, количество), не добавляя строки; изменённый digest или другая организация вызывают отказ. В конце транзакции проверяются фактически записанные количества; SQL-ошибка откатывает пакет полностью. Отчёт возвращает только количества и режим `SYNTHETIC_STAGING`, без source identifiers.

Тест одноразовой PG17: `PYTHONPATH=apps/api python -m pytest -q tests/integration/test_pg_auto_migration_staging.py`. Он проверяет replay, scope, tamper и rollback, а также отсутствие записи в рабочий журнал запчастей. Непроверенное и запрещённое: реальная миграция остатков, клиенты/VIN/ремонты, authorization на сотрудников, межтабличная reconciliation с рабочим ledger, конкурентная проверка с пользовательскими ролями, backup/restore переноса, production cutover. Downgrade staging уничтожает синтетическую историю и допустим лишь в disposable CI. Общие #172, #165, #119 остаются открытыми.


## Безопасное открытие staging CSV

Внутренний синтетический PG17 staging открывает CSV через дескриптор с `O_NOFOLLOW` и `O_NONBLOCK`, затем проверяет `fstat`, что источник — обычный файл, и только затем читает не более 5 МБ. Это предотвращает следование символьной ссылке, подменённой между проверкой пути и открытием, а также зависание на FIFO. Если платформа не поддерживает `O_NOFOLLOW`, операция отклоняется; серверный доступ к файлам и реальные ПДн по-прежнему запрещены до security-gate #119.


## Проверка tenant до retry (#172)

Перед созданием staging-пакета **и до проверки идемпотентного replay** каждая CSV-строка должна принадлежать UUID организации, явно переданному вызывающим кодом. Смешанный экспорт организаций и replay чужого источника отвергаются с `staging tenant mismatch`, включая случай, когда ранее сохранённый пакет совпадает по хешу и количеству строк. Ни данные клиента, ни исходные UUID в тексте исключения не возвращаются. Это локальный privileged synthetic-only guard, не замена авторизации пользователя.


## Деактивация организации/филиала и replay

При каждом обращении к staging, включая идемпотентный повтор с тем же `batch_id`, проверяется, что организация и все филиалы исходного CSV не отключены. Проверка и запись защищены PostgreSQL `FOR SHARE` на строках scope, чтобы параллельная деактивация не обходила guard. Исторические записи остаются неизменяемыми, но replay для отключённого филиала/tenant отвергается общим `staging scope unavailable`. Действует только в синтетическом привилегированном окружении; полноценная авторизация сотрудников всё ещё не реализована.


## Независимая сверка staging с источником (синтетическая PG17)

После staging можно **отдельно** вызвать `reconcile_synthetic_staging(conn, path, organization_id=..., batch_id=..., expected_sha256=...)` из `scripts/auto_migration_pg_staging.py`. Функция повторно проверяет SHA-256 и CSV и использует **только SELECT** к PostgreSQL; она не добавляет новые batch/line, не вызывает складские операции и не выполняет импорт. Проверяется совпадение метаданных пакета, количества строк, всех полей каждой строки, филиала, организации и порядка. При расхождении возвращается исключение без данных источника; успешный отчёт содержит `mode: SYNTHETIC_RECONCILIATION`, `writes: 0` и количества.

PG17 integration покрывает отсутствие пакета (без создания), чужую организацию и отличающееся содержимое при одинаковом числе строк. Эта сверка **не является** проверкой рабочего stock ledger, backup/restore или доказательством полноты импорта клиентов, автомобилей и документов. Применение допустимо только к искусственным данным на одноразовом стенде; авторизация сотрудника и юридические решения #119 по-прежнему отсутствуют.


## CI-проверка восстановления синтетического staging (#172)

PostgreSQL 17 job в `.github/workflows/ci.yml` формирует искусственные tenant/филиал и staging-пакет (один SKU и одно STOCK-событие), выполняет **реальный** `pg_dump -Fc` → `pg_restore` в отдельную базу. После восстановления проверяет метаданные пакета, количество строк и сумму количества, запрет UPDATE неизменяемой строки и отказ вставки строки чужого филиала. Это воспроизводимая проверка **только синтетического staging**, а не восстановление реальной пользовательской базы и не полноценный операционный rollback/cutover. Она не отменяет отдельные backup/recovery и approval по #119/#165/#172.


## Предварительная проверка автомобилей (synthetic-only, #172)

Реализована отдельная локальная **проверка искусственного CSV автомобилей** без подключения к БД:

```bash
python scripts/auto_vehicle_migration_preflight.py --synthetic-only ./synthetic_vehicles.csv
```

Обязательные колонки (строгий порядок): `record_type,source_id,organization_id,location_id,vin,make,model,source_system`. Тип записи только `VEHICLE`; `source_id` и `source_system` используют безопасные заглавные ASCII-символы; организации и филиалы представлены UUID. VIN содержит **ровно 17** прописных разрешённых символов (без I/O/Q); это проверка **формата**, а не международной подлинности/check-digit или права владения. Поля `make`/`model` допускают только синтетические ASCII-подписи, не формулы. Совпадающие source IDs внутри одного tenant/филиала/системы и повторные VIN в пакете отклоняются. Поддержка существующих записей БД, XLSX, сопоставления разных источников и deduplication с реальными клиентами **не реализована**.

Поля клиента, владельца, телефона, истории ремонтов и дополнительных доказательств отвергаются целиком как нарушение схемы. **VIN никогда не служит основанием для доступа к чужой истории.** Отчёт включает только счётчики, коды ошибок и номера строк, никогда полный VIN или source ID. Никакие `auto_vehicle` или `auto_vehicle_customer_link` не создаются. Проверка использует ограниченное чтение до 5 МБ и не следует по символическим ссылкам. До завершения правовой и security-проверки #119 применять только к полностью искусственным тестовым VIN.


## Изолированное хранилище синтетических автомобилей в PG17 (#172)

Миграция `0075_auto_vehicle_stage` создаёт неизменяемые `auto_vehicle_migration_batch` и `auto_vehicle_migration_line`. Внутренняя библиотека `scripts/auto_vehicle_migration_pg_staging.py` предоставляет `stage_synthetic_vehicles(conn, path, organization_id=..., batch_id=..., expected_sha256=...)` **только для одноразовой PG17 и искусственных VIN**. Перед записью входной CSV проходит синтетический preflight, SHA-256 снимка и проверку единственной организации; scope действующих филиалов блокируется на время транзакции. Повтор с тем же `batch_id` сверяет каждую сохранённую строку и возвращает `replayed: true` без записи; неверный digest/tenant или изменённая строка отвергаются. Ошибки откатывают весь пакет, результаты не содержат VIN.

**Никакие** рабочие `auto_vehicle`, `auto_vehicle_customer_link` или история ремонта не меняются. Отсутствуют сотруднические роли, полноценный импорт/экспорт, проверка правообладателя истории, реальные ПДн, UI и production разрешение. PG17 тест: `PYTHONPATH=apps/api python -m pytest -q tests/integration/test_pg_auto_vehicle_migration_staging.py`. Откат миграции с удалением staging-таблиц допустим только в disposable CI, не в production.


## Авторизованный внутренний синтетический импорт автомобилей (#172)

В `apps/api/roboport_api/auto_vehicle_import_service.py` реализована библиотечная функция `stage_authorized_synthetic_vehicles(conn, token, path, organization_id=..., location_id=..., batch_id=..., expected_sha256=...)`. Она проверяет действующую сессию и роль `MANAGER` **именно для организации/филиала**, удерживает SQL-блокировки авторизации до завершения staging и ограничивает весь исходный CSV **только указанным филиалом**. Отозванные сессии и grants, роль `WAREHOUSE` и чужой филиал отвергаются; повторная загрузка не обходит проверку прав. Проверки проводятся на искусственных данных в одноразовой PG17, без HTTP/API для пользователей. Прямой привилегированный доступ владельца БД к низкоуровневому staging пока не закрыт отдельной DB role policy; эту функцию нельзя считать production RBAC gate.

Тест: `PYTHONPATH=apps/api python -m pytest -q tests/integration/test_pg_auto_vehicle_import_service.py`. В таблицы автомобилей/связи владельцев/историю ничего не записывается. Для production требуются #119, независимое ревью, ограничения DB grants, согласия и юридически подтверждённое происхождение данных.


## Восстановление синтетических автомобилей (PG17 CI, #172)

Обязательный CI теперь дополнительно сохраняет искусственный пакет `auto_vehicle_migration_batch` и строку `auto_vehicle_migration_line` в дамп PostgreSQL 17. После `pg_restore` в новую базу проверяются количество строк, тот же VIN, **отсутствие появления автомобиля в рабочей `auto_vehicle`**, неизменяемость staging-строк и отказ записи с несуществующим филиалом. Это доказательство работоспособности восстановления **синтетического staging**, а не полного recovery клиентских данных, связей владения или истории работ. Для production по-прежнему требуются отдельные операционные RPO/RTO, legal/security approval и завершённый #119/#165/#172.


## Предотвращение совпадения VIN с существующим автомобилем (#172)

Перед вставкой нового или повторной проверкой прежнего синтетического staging-пакета `stage_synthetic_vehicles` выполняет запрос к `auto_vehicle` на наличие **любого** VIN из проверенного источника. Если совпадение есть, вся операция отвергается с общим кодом `vehicle identity conflicts with existing data`, не раскрывая VIN, владельца или историю; новых batch/line записей не создаётся. PG17 regression проверяет как исходный конфликт, так и конфликт, возникший после staging, перед replay. Это только **моментальная проверка конфликта** на искусственной БД: она не решает конкурентный импорт в рабочую `auto_vehicle`, не подтверждает легитимность правообладателя и не разрешает production. Для реального cutover потребуется единая транзакционная схема уникальности, ручной разбор конфликта и approvals по #119/#165/#172.


## Конкурентная уникальность VIN между staging-пакетами (#172)

Миграция `0076_vehicle_stage_unique_vin` вводит уникальный индекс `ux_auto_vehicle_migration_vin_global` на VIN всей синтетической таблицы `auto_vehicle_migration_line`, а не только внутри одного пакета. Это исключает второй пакет, претендующий на тот же VIN, включая конкурентные INSERT. При конфликте внутренний сервис возвращает общее `vehicle staging identity conflict` без VIN и PostgreSQL DETAIL; тесты PG17 покрывают второй пакет и блокировку конкурентной транзакции. Такое ограничение **не связывает staged VIN с владельцем** и не заменяет атомарное сопоставление с рабочим `auto_vehicle`, проверку согласия и security/ops approval #119.


## Явное продвижение искусственных автомобилей в рабочую таблицу (dev-only, #172)

Миграция `0077_vehicle_stage_promotion` добавляет неизменяемую таблицу связей `auto_vehicle_migration_promotion` (исходный пакет/строка → автомобиль). Внутренний сервис `roboport_api.auto_vehicle_promotion_service.promote_synthetic_vehicles` при `synthetic_only=True` и действующей сессии с ролью `MANAGER` для **конкретного филиала** атомарно создаёт только записи `auto_vehicle` из полностью проверенного синтетического пакета. Повторная операция сверяет сохранённые связи и автомобили и возвращает `replayed=True, writes=0`. Противоречивые VIN отклоняются, включая уникальные конфликты при конкуренции; ошибки не содержат VIN. SQL-транзакция защищает и создание автомобилей, и сохранение их происхождения. Не создаются `auto_vehicle_customer_link`, история ремонтов, заказ-наряды, документы и финансовые операции. Тестируется отрицательный доступ и отзыв role grants, чужой филиал, повторная операция и rollback.

**Это dev-путь, не production import.** Флаг `synthetic_only=True` сам по себе не является техническим доказательством искусственности данных: владельцу БД и вызывающему коду доверяют в изолированном CI. Не публиковать HTTP endpoint и не применять к реальным VIN/ПДн до отдельного контроля DB grants, разрешений #119, подтверждения происхождения, dedupe/customer ownership consent, backup/recovery и release approval #165. Отмена миграции `0077` допустима только в disposable CI и не должна использоваться как production rollback.


## Проверка происхождения автомобиля на уровне PostgreSQL (#172)

Миграция `0078_vehicle_lineage_guard` добавляет SQL-trigger для `auto_vehicle_migration_promotion`: ссылка staging-строка → созданный автомобиль принимается только если совпадают VIN, марка и модель, организация пакета и филиала, а филиал и организация действуют. Проверка выполняется с блокировками строк до COMMIT. Это не позволяет даже привилегированному коду записать в таблицу происхождения связь с посторонним автомобилем или автомобилем с отличающейся моделью без срабатывания проверки. PG17 integration проверяет поддельный VIN и модель, а также обычный авторизованный перенос. Уровень защиты не исключает bypass владельцем СУБД через отключение триггеров и не доказывает безопасность работы с настоящими VIN: DB least privilege, аудит, права на персональные данные и production approval ещё не реализованы.


## Разделение прав на чтение отчёта миграции в PostgreSQL (#172)

Миграция `0079_vehicle_audit_role` создаёт кластерную роль `roboport_vehicle_migration_auditor` с `NOLOGIN`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE` и `NOINHERIT`. Она получает **только** SELECT метаданных из `auto_vehicle_migration_batch` (ID пакета, организация и число записей). У неё нет прав читать SHA-256 источника или время создания, VIN из `auto_vehicle_migration_line`, таблицу продвижения или рабочие `auto_vehicle`/`auto_vehicle_customer_link`; нет прав записи в эти таблицы. PG17 integration явно переключает роль и проверяет невозможность чтения VIN, `SELECT *` и записи пакета. Эта роль не даёт клиентского доступа к UI и не используется для выполнения импорта. Перед предоставлением прав внешнему сотруднику нужны отдельные tenant-scoped views/RLS и аудит: **метаданные без RLS могут раскрыть существование чужого пакета**. Владельцу БД права остаются доступны; это не завершённый production DB grants gate #119.


## Явный mapping колонок CSV автомобилей — synthetic-only (#172)

Утилита `scripts/auto_vehicle_column_mapping.py` преобразует **только искусственный** CSV с произвольным порядком колонок и явно заданными именами полей в строгую схему `record_type,source_id,organization_id,location_id,vin,make,model,source_system` для уже существующих `inspect_vehicle_csv` и `stage_synthetic_vehicles`. Полное и однозначное сопоставление задаётся восьмью аргументами `--field SOURCE=TARGET`; неопознанные, повторные, лишние колонки (включая имя владельца и историю ремонтов) отклоняются, без угадывания значений и автопереименования. Перед созданием файла срабатывают ограничения по размеру/числу строк, строгий CSV-парсер и существующий VIN/source/tenant/dedupe preflight. Исходник читается без перехода по символьным ссылкам; результат не перезаписывается, создаётся с правами `0600`. CLI выводит лишь число строк и SHA-256 канонического файла, не VIN, source ID или организацию. Например:

```bash
python scripts/auto_vehicle_column_mapping.py --synthetic-only \
  --field тип=record_type --field внешний_id=source_id \
  --field организация=organization_id --field филиал=location_id \
  --field номер=vin --field марка=make --field модель=model \
  --field источник=source_system ./demo_vehicles.csv ./canonical_vehicles.csv
python scripts/auto_vehicle_migration_preflight.py --synthetic-only ./canonical_vehicles.csv
```

Файл `canonical_vehicles.csv` содержит сами искусственные VIN и должен храниться только в изолированной тестовой среде. Это **не XLSX**, не mapping реальных клиентов/сервисов/документов, не сверка существующей базы или независимое подтверждение прав на историю; никаких production-данных до #119. Чтобы записать искусственный пакет в staging, использовать только авторизованную внутреннюю функцию с MANAGER grant и проверенным digest. Результат работы утилиты сам по себе не разрешает импорт.


## Синтетический каталог услуг — полноценный CSV→PG17 staging (#172)

Миграция `0080_auto_service_import` добавляет отдельные неизменяемые `auto_service_import_batch` и `auto_service_import_line`, не смешивая услуги с существующими заказ-нарядами и финансовыми записями. Внутренний модуль `roboport_api.auto_service_import` реализует `inspect_synthetic_services(path, expected_sha256=...)` и `stage_synthetic_services(conn, token, path, organization_id=..., location_id=..., batch_id=..., expected_sha256=...)`. CSV имеет строгий порядок шести колонок: `record_type,source_system,source_id,code,title,duration_minutes`. Тип строки `SERVICE`. Проверяются безопасные ASCII-коды, время выполнения 5–1440 минут, дубль source-system/source-id или кода услуги внутри пакета, подозрительные формульные значения и SHA-256 исходного файла. Отчёт не содержит названий, исходных ID или данных клиентов. Никакие VIN, ПДн, владелец и история ремонта не допускаются.

Запись требует действующей сессии с `MANAGER` grant указанной организации и филиала и происходит атомарно в PG17; повторный пакет сверяет содержимое и пишет 0 строк, изменённый пакет отвергается. Тесты проверяют отзыв grant, чужой филиал/организацию, дубли, формулы, транзакционный откат и неизменяемость. **Это первый каталог услуг только в synthetic staging; он не используется в ценообразовании/нарядах и не является production import.** Для полноценной задачи #172 ещё нужны CSV/XLSX произвольных контрагентов/услуг, customer/repair-history consent, безопасные файлы документов, продовые роли и восстановление. Работа с настоящими данными до #119 не разрешена.


## XLSX → канонический CSV: автомобили и услуги (синтетический режим, #172)

Реализован офлайн-конвертер `scripts/auto_synthetic_xlsx.py`. Он принимает одно-листовые обычные XLSX с неизменёнными заголовками **в заданном порядке**, поддерживает строки OOXML `inlineStr` и `sharedStrings`, создаёт закрытый для перезаписи CSV-файл (права 0600) и запускает тот же строгий preflight, что используется для CSV автомобилей либо услуг. Дополнительные колонки — в том числе данные владельца/история — не допускаются. Выражения Excel, макросы, внешние ссылки, вложения и несколько/скрытые листы отвергаются; ограничены размер архива, суммарный размер распаковки и число строк.

```bash
PYTHONPATH=apps/api python scripts/auto_synthetic_xlsx.py --synthetic-only --kind VEHICLE ./fictional-vehicles.xlsx ./fictional-vehicles.csv
PYTHONPATH=apps/api python scripts/auto_synthetic_xlsx.py --synthetic-only --kind SERVICE ./fictional-services.xlsx ./fictional-services.csv
```

Результат CLI: только тип, количество, SHA-256 результата и статус, без идентификаторов исходных записей, VIN и содержимого XLSX. Извлечённый CSV **содержит сами вымышленные значения**, поэтому хранить его следует только в изолированной тестовой среде. Это не универсальный Excel-импорт: произвольные названия колонок XLSX, форматирование, вычисление формул, скрытые файлы, реальные клиенты и история не поддерживаются. После конвертации применяются уже реализованные staging-операции и обязательная проверка прав `MANAGER`; сам XLSX-конвертер **не пишет в БД**. Production PII, consent, tenant-scoped API, реальный cutover #119/#165 не разрешены.


## Каталог услуг: активация из синтетического staging (#172)

Миграция `0081_auto_service_catalog` вводит веточно-ограниченный каталог `auto_service_catalog` и неизменяемую связку `auto_service_import_activation` между записью исходного пакета и услугой каталога. В отличие от предыдущего этапа, это **создаёт запись каталога услуг**, но пока не подключает её к заказ-нарядам или денежным операциям. Вызов `roboport_api.auto_service_activation.activate_synthetic_services(conn, token, organization_id=..., location_id=..., batch_id=..., synthetic_only=True)` требует живую сессию с полномочием MANAGER данного филиала, полное совпадение количества строк staged-пакета и отсутствие конфликтующего кода услуги. Работа в одной PG17-транзакции; повтор проверяет происхождение и возвращает `writes: 0`. SQL-триггер не позволяет создать фиктивную связь происхождения с чужой услугой или несовпадающими title/duration/code/tenant/branch; таблицы неизменяемы. Интеграционные тесты покрывают поддельное происхождение, повтор, отсутствие роли, чужой филиал, конфликт и rollback.

**Границы:** только искусственные данные в изолированной БД; услуги ещё не опубликованы для клиентов, ценообразования или заказ-нарядов. Никаких прав на реальные клиентские сведения или ремонтную историю не добавлено; #119/#165/#172 production approvals не заменены. Удаление таблиц downgrade безопасно только в disposable PG17 CI.


## Услуга из каталога в заказ-наряд — синтетический контур (#172)

Миграция `0082_order_service` вводит неизменяемую строку `auto_work_order_service`, связывающую существующий заказ-наряд с услугой из каталога того же филиала и организации. PostgreSQL-триггер проверяет совпадение филиала и организации, активность подразделения и неизменность записи. Внутренняя операция `add_synthetic_order_service` требует действующую сессию `MANAGER`, явный `synthetic_only=True`, выполняется транзакционно и не создаёт повторную связь при идентичном запросе. Есть отрицательные PG17-проверки BOLA, попытки прямого SQL-обхода, отзыва прав и повторного выполнения. Стоимость работ и клиентские/финансовые записи не изменяются. Это **внутренняя синтетическая связь, не публичный production API**, и она не разрешает использование реальных клиентских историй; обязательные согласия и #119 остаются открытыми.


## Отзыв подтверждения автомобиля блокирует новые услуги заказа (#172)

Миграция `0083_order_service_consent` усиливает уже существующий `auto_work_order_service`: при каждой новой записи SQL-триггер заново проверяет активную `auto_vehicle_customer_link` с `verified_at`, отсутствие `revoked_at`, соответствие автомобилю назначения, неизменный tenant/branch и неотменённую запись на сервис. Проверка проводится с `FOR SHARE`, в том числе при обходе Python-сервиса прямым SQL. `add_synthetic_order_service` делает ту же проверку **до** попытки создания новой связи и до ветки replay, поэтому после отзыва подтверждения не выдаёт успешный идемпотентный результат. Существующие связи не удаляются — сохраняется аудит; новых исторических прав сам VIN не создаёт. PG17-тесты проверяют отзыв уже после создания заказ-наряда, отказ прямого INSERT и отказ авторизованной функции. Это синтетический контур, а не юридическое подтверждение согласия для production: реальную историю и документы до #119 импортировать нельзя.


## Реестр происхождения четырёх доменов — обязательный подготовительный checkpoint (#172)

Скрипт `scripts/auto_migration_provenance_bundle.py` проверяет синтетический комплект `CUSTOMER`, `COUNTERPARTY`, `REPAIR_HISTORY`, `DOCUMENT` по файлам и SHA-256, не читая и не выводя содержимое данных в отчёт. Для каждой записи JSON-манифеста нужны: `kind`, `file` (без путей), `sha256`, `bytes`, `records`, `source_system`, `legal_basis_ref`, `owner_proof_ref`. На уровне комплекта: `schema: 1`, `synthetic_only: true`, `organization_id`, `location_id`, `sources`. В исходном каталоге требуются обычные файлы без символьных ссылок. Подмена файла/отсутствующий домен/лишние поля/пустые ссылки на доказательства отвергаются.

```bash
python scripts/auto_migration_provenance_bundle.py --synthetic-only ./synthetic_manifest.json
```

Даже при успешном результате возвращается `approval: NOT_VERIFIED`, `release_allowed: false`, `writes: 0`. **Ключевой момент:** непрозрачные `legal_basis_ref` и `owner_proof_ref` — только идентификаторы для будущей независимой проверки, а не юридическое подтверждение, согласие, право на историю, факт ознакомления с оригиналом либо разрешение запускать импорт. Никаких клиентов, контрагентов, истории ремонтов, документов и персональных данных этот скрипт **не переносит**. Для реальной загрузки нужны доступные проверенные источники, lawful basis, owner consent или эквивалентное подтверждение прав, одобренные правила хранения, tenant-scoped механизмы, подписанное security/legal/ops approval #119 и эксплуатационная сверка с восстановлением #165. Запрещено выдавать synthetic fixtures за реальные.


## Строгий JSON-контракт provenance preflight (#172)

`auto_migration_provenance_bundle.py` отклоняет повторяющиеся JSON-ключи на любом уровне манифеста (`SCHEMA`), включая случаи, когда стандартный парсер принял бы последнее значение. Версия `schema` должна быть именно целым числом `1`: JSON `true` не считается версией `1` (`APPROVAL_REQUIRED`). Эти проверки работают только с синтетическим пакетом и не дают разрешения на реальный импорт, обработку персональных данных или production release.


Парсер также отклоняет не входящие в стандарт JSON числовые константы `NaN`, `Infinity`, `-Infinity` с кодом `SCHEMA`, даже если они встречаются в поле, которое будет отклонено последующей проверкой структуры. Никакая некорректная запись не переводит preflight в режим реального импорта.


## Ограничение суммарного размера синтетического комплекта (#172)

Помимо лимита отдельного файла 10 МБ, предварительная проверка ограничивает суммарный заявленный размер источников **40 МБ** (`BUNDLE_LIMIT`). Порог проверяется до чтения файла, превысившего бюджет, чтобы ограничить стоимость одного синтетического preflight. Это ограничение не разрешает production-импорт и не заменяет отдельную оценку ресурсов для будущего авторизованного переноса.


Слишком глубокие JSON-структуры, вызывающие ограничение рекурсии парсера, также завершают preflight контролируемым отказом `SCHEMA` (без traceback и без операций записи).


Манифест должен быть закодирован в UTF-8: UTF-16/UTF-32 не принимаются через автоматическое определение кодировки JSON-парсером. Ошибочная кодировка возвращает `SCHEMA`, без чтения исходных payload-файлов и записи данных.


## Безопасное открытие исходного CSV для dry-run (#172)

Локальный `auto_migration_dry_run.py` открывает синтетический CSV одним файловым дескриптором с `O_NOFOLLOW` и `O_NONBLOCK`, затем проверяет `fstat`, что открыт обычный файл и размер не превышает 5 МБ. Это исключает следование symlink при открытии и зависание на FIFO. На платформе без `O_NOFOLLOW` проверка отказывает с `UNAVAILABLE`. Исходный CSV остаётся только для offline preflight, без записи в БД и без настоящих персональных данных.


## Fail-closed CSV dry-run при ошибках чтения (#352)

Вызовы `inspect_csv()` из Python-кода и через CLI возвращают одинаковый безопасный JSON при некорректной UTF-8 кодировке, ошибочном CSV quoting и некорректных параметрах сверки: `ok=false`, `writes=0`, `mode=DRY_RUN_ONLY`, `UNREADABLE`, без исходных значений и traceback. Позитивные синтетические пакеты и ограничения размера/SHA-256 продолжают проверяться прежним способом. Это не разрешение на импорт реальных данных.


### Единый формат всех ответов CSV preflight (#352)

Любой ответ `inspect_csv()`, включая ранние отказы `UNAVAILABLE`, `SCHEMA`, `SOURCE_CHECKSUM` и `UNREADABLE`, содержит `ok`, `counts`, `errors`, `mode: DRY_RUN_ONLY` и `writes: 0`. Вызов из Python и CLI сохраняют единый контракт; `writes: 0` не является разрешением на реальный импорт.


## Атомарная публикация результата mapping (current-dev, #355)

`auto_vehicle_column_mapping.py` после успешного канонического preflight записывает приватный временный CSV в каталоге назначения, выполняет `fsync`, затем публикует его через создание жёсткой ссылки без замены существующего пути. Ошибка записи/публикации не оставляет частичного **итогового** файла, временный файл удаляется в `finally`. Доступ к директории назначения и существующие файлы контролируются вызывающим процессом; операция локальная, только с синтетическими данными, без DB/HTTP и production import.


## Сверка исходного SHA-256 перед mapping CSV автомобилей (#172)

Для `auto_vehicle_column_mapping.py` обязателен параметр `--expect-sha256` — заранее полученный из доверенного отдельного источника digest в формате 64 строчных hex-символов. Библиотечный вызов `map_synthetic_vehicle_csv` принимает `expected_sha256`. Сверяется SHA-256 **ровно тех байтов**, которые затем разбираются; отсутствие или неверный формат дают `SOURCE_DIGEST_REQUIRED`, несовпадение — `SOURCE_CHECKSUM`. Во всех случаях итоговый файл не публикуется. SHA не подтверждает права на данные, не заменяет consent и не разрешает production импорт.


## Целостность XLSX и атомарный результат (current-dev, #172)

Офлайн-конвертер `scripts/auto_synthetic_xlsx.py` для **синтетических** `VEHICLE` и `SERVICE` теперь требует `--expect-sha256` (64 строчных hex-символа) от независимого доверенного источника; Python API `convert_synthetic_xlsx(..., expected_sha256=...)` имеет тот же контракт. Отсутствие или некорректная форма — `SOURCE_DIGEST_REQUIRED`, подмена исходного XLSX — `SOURCE_CHECKSUM` до распаковки и создания output. После успешного CSV preflight файл полностью записывается в приватный временный путь (0600), синхронизируется `fsync` и публикуется через атомарное создание hardlink без замены имеющегося назначения; ошибки `OUTPUT_UNAVAILABLE` не оставляют частичный итоговый CSV, временный файл очищается. На файловых системах без hardlink публикация запрещена. Это не обработка реальных ПДн и не production-импорт; #119 остаётся обязательным gate.


## Явное сопоставление столбцов XLSX (current-dev, #172)

Для синтетических `VEHICLE` и `SERVICE` файлов XLSX поддерживается полный явно заданный mapping заголовков: CLI `--field ИСХОДНАЯ_КОЛОНКА=canonical_field` (параметр указывается для каждого поля) либо Python `convert_synthetic_xlsx(..., mapping={...})`. При указании mapping обязательны все канонические поля ровно по одному разу, запрещены повторяющиеся исходные заголовки, дополнительные и пропущенные поля, в том числе `owner` и `history`. Порядок колонок исходной таблицы может отличаться от канонического. Без mapping по-прежнему требуется прежний строгий порядок. Проверка SHA-256 XLSX, запрет формул и опасных архивов, существующий VEHICLE/SERVICE preflight, атомарная публикация результата без перезаписи сохраняются. Это только offline synthetic staging, не импорт клиентов или истории и не разрешение на production.


## Пакетная подготовка VEHICLE + SERVICE XLSX без частичных результатов (#172, current-dev)

`scripts/auto_synthetic_batch.py` принимает **два синтетических** XLSX: `--vehicle` и `--service`, заранее независимо подтверждённые `--vehicle-sha256` и `--service-sha256`, а также существующий пустой каталог `--destination`. Пример запуска:

```bash
python scripts/auto_synthetic_batch.py --synthetic-only --vehicle synthetic_vehicles.xlsx --vehicle-sha256 <64-lowercase-hex> --service synthetic_services.xlsx --service-sha256 <64-lowercase-hex> --destination ./synthetic_output
```

Выполняется сквозной сценарий: сверка исходных байтов обоих файлов, ограниченный безопасный OOXML-разбор, канонический CSV и повторное использование проверок VEHICLE и SERVICE. Только после успешного завершения обоих preflight публикуются `vehicle.csv` и `service.csv` с правами `0600`. Уже существующий результат, в том числе symlink, не заменяется. При ошибке во время нормального выполнения публикации второй части первый опубликованный файл удаляется. JSON-отчёт содержит только количества строк по двум доменам и SHA256 итоговых CSV, `writes: 0`, `release_allowed: false`; исходные идентификаторы не выводятся. При отказе `ok: false` и стабильный `code`.

**Граница атомарности:** каждая публикация отдельного файла атомарна, но завершение процесса посередине двух последовательных публикаций (kill, сбой питания) **не является атомарной транзакцией всего набора**; оператор обязан проверить каталог и восстановить чистое состояние перед повтором. Исходный каталог назначения должен быть доверенным и не доступным для параллельной записи посторонних процессов. Это не DB transaction и не импорт реальных клиентов, автомобилей, услуг или истории. Для реальной загрузки и эксплуатационного cutover нужны права доступа, backup/restore, сверка целевой БД и независимые approvals #119/#165/#172.


## Пакетный CLI с независимым mapping двух XLSX (current-dev, #172)

Пакетный запуск `scripts/auto_synthetic_batch.py` поддерживает оба набора `--vehicle-field ИСХОДНОЕ=КАНОНИЧЕСКОЕ` и `--service-field ИСХОДНОЕ=КАНОНИЧЕСКОЕ` совместно с обязательными SHA-256 каждого файла. Для каждого вида разрешено либо не передавать mapping и использовать стандартные заголовки, либо передать **весь** mapping: все восемь колонок VEHICLE и все шесть колонок SERVICE. Нельзя пропустить столбец, сопоставить несколько полей с одним назначением, добавить owner/history или повторить исходный заголовок. Перед публикацией любого из двух CSV оба источника должны пройти свои проверки полностью. Ошибка mapping любой книги возвращает безопасный JSON `code: MAPPING` или `SCHEMA` без публикации обоих результатов. Эта функция относится только к офлайн synthetic данным, не выполняет импорт в DB и не разрешает production.


## Пакет VEHICLE+SERVICE как единый каталог (current-dev, #172)

Офлайн инструмент `scripts/auto_synthetic_batch.py` поддерживает флаг `--atomic-bundle`. Вместо последовательной публикации двух файлов в существующий каталог назначения он сначала подготавливает оба валидированных файла во временном приватном подкаталоге, сверяет SHA-256, а затем публикует **весь каталог** `vehicle-service-bundle` одним `os.rename`. До успешного завершения обеих проверок ни один CSV не виден по итоговому пути. При ошибке до переименования временный комплект удаляется; существующий `vehicle-service-bundle` вызывает `OUTPUT_CONFLICT`. Итоговые `vehicle.csv` и `service.csv` остаются в каталоге `vehicle-service-bundle` и сверяются с `sha256` и `rows` из JSON-отчёта.

Пример: `python scripts/auto_synthetic_batch.py --synthetic-only --atomic-bundle --vehicle synthetic_vehicles.xlsx --vehicle-sha256 <hex> --service synthetic_services.xlsx --service-sha256 <hex> --destination ./synthetic_output`. Аргументы `--vehicle-field` и `--service-field` совместимы с этим режимом. `--destination` должен существовать, быть доверенным каталогом и **не предоставлять параллельную запись** посторонним процессам. Стандартная библиотека Python не гарантирует атомарную операцию rename без замены существующего **пустого** каталога при конкурентном изменении назначения; проверка существования является ограничением режима, не строгим POSIX no-clobber в присутствии злоумышленника. Атомарная видимость каталогов на локальной файловой системе не означает долговечность после потери питания без отдельного fsync родительского каталога. Отсутствуют PostgreSQL transaction, production consent или разрешение на обработку настоящих персональных данных.


### Усиленная безопасная публикация atomic-bundle (current-dev)

Режим `--atomic-bundle` теперь требует Linux с доступной операцией `renameat2(RENAME_NOREPLACE)`, а также поддержкой `fsync` каталогов. В отличие от обычной пары `exists → rename`, операция публикации **не заменяет даже пустой существующий каталог** при конкуренции. Перед публикацией выполняется синхронизация каталога с двумя CSV, после — каталога назначения. При отсутствии необходимых системных примитивов результат `OUTPUT_UNAVAILABLE`, без подмены небезопасной альтернативой. `OUTPUT_CONFLICT` означает существующий результат или гонку; чужой каталог не изменяется.

После успешного переименования отказ `fsync` родительского каталога может вернуть `OUTPUT_UNAVAILABLE` **при уже видимом каталоге**. Оператор обязан осмотреть `vehicle-service-bundle`, сверить контрольные суммы и определить необходимость повтора в чистом отдельном каталоге. Не предполагайте, что отказ всегда означает отсутствие файла. Для физических аварий остаются ограничения конкретной файловой системы и оборудования; заявлять абсолютную гарантию долговечности нельзя. На Windows/macOS этот усиленный режим fail-closed, тогда как обычная подготовка отдельных CSV остаётся доступной по её собственному контракту.


## Восстановление связанного живого автомобильного цикла из полного synthetic dump (#119/#172)

После staged SKU/Vehicle pg_dump/pg_restore-тестов CI теперь создаёт **отдельную** искусственную live-цепочку Appointment → WorkOrder → две складские позиции `PART`/`CONSUMABLE` → перемещение брони → `ISSUE/RETURN` → synthetic финансовую историю → outbox. До копирования вычисляется SHA-256 связанного graph, затем после `pg_restore --exit-on-error` он сверяется на source и отдельном restored database; PostgreSQL immutable, tenant scope, конфликт брони и запрет отмены при резерве повторно оспариваются на restored clone. Источник не мутируется отрицательными тестами. Обязательные шаги в `.github/workflows/ci.yml`; скрипт `scripts/auto_restore_lifecycle_probe.py`, проверки manifest и loopback-only DSN `tests/contract/test_auto_restore_lifecycle_probe.py`. [Подробная процедура](RESTORE_CHECKPOINT.md). **Только disposable synthetic PostgreSQL 17**; это не перенос настоящих клиентов/истории и не валидированный RPO/RTO. Производственный backup/restore и разрешение на миграцию остаются открытыми #119/#165/#172.


## Цельный synthetic cutover трёх видов данных: VEHICLE + SERVICE + SKU/STOCK (#172)

Миграция `0094_auto_inventory_activation` и внутренняя библиотека `auto_synthetic_cutover.py` теперь завершают **одной PG17-транзакцией** уже реализованные CSV/этапы: исходные digest и строгая offline-проверка → staging автомобилей/услуг/SKU+STOCK → самостоятельные vehicle/service activations → **реальные складские SKU и RECEIPT с неизменяемым line-by-line provenance** → независимая сверка live объектов и receipt quantities. Требуются **обе** живые tenant/branch роли MANAGER и WAREHOUSE, `synthetic_only=True`; нельзя присоединять владельца или его старые ремонты по VIN. При ошибке третьего этапа уже созданные первые два каталога и все staging-записи откатываются; повтор того же источника и batch-id даёт `replayed:true,writes:0` после проверки разрешений. При уже активированном автомобильном VIN replay разрешён **лишь** при принадлежности тому же immutable migration lineage; чужой VIN отклоняется. PG17 тест `tests/integration/test_pg_auto_synthetic_cutover.py` проверяет весь путь, конкуренцию, rollback, cross-branch и SQL-tampering. **Это не эксплуатационный импорт клиентов/документов, фактическая инвентаризация или законная передача истории.** [Полный сценарий и ограничения](SYNTHETIC_CUTOVER.md). #119/#165/#172 остаются OPEN.


### Восстановление всей активированной synthetic связки после реального pg_restore

В едином PR #172 новый `scripts/auto_cutover_restore_probe.py` засевает контрольный VEHICLE/SERVICE/SKU+STOCK пакет перед `pg_dump -Fc`, сохраняет SHA-256 связей source→staging→live вне дампа, сверяет оригинальную и восстановленную базы по отдельному manifest и повторно оспаривает immutable/tenant защиту **только** на clone.
