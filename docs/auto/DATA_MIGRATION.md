# Синтетическая проверка автомобильного CSV перед миграцией

## Назначение и ограничения

Это **локальный dry-run**, не реальный импорт. Используйте только искусственно созданные данные. Скрипт `scripts/auto_migration_dry_run.py` не подключается к PostgreSQL, ничего не записывает, не обрабатывает ПДн, историю ремонтов, документы, платежи, VIN и XLSX. Он не разрешает релиз #119 и не заменяет cutover/restore #165/#172.

## Команда

```bash
python scripts/auto_migration_dry_run.py --synthetic-only ./synthetic_inventory.csv
```

Формат UTF-8 CSV с колонками в точном порядке:

```csv
record_type,source_id,organization_id,location_id,article,quantity
SKU,SKU-1,00000000-0000-4000-8000-000000000001,00000000-0000-4000-8000-000000000002,FILTER-001,0
STOCK,EVENT-1,00000000-0000-4000-8000-000000000001,00000000-0000-4000-8000-000000000002,FILTER-001,25
```

Допустимы `SKU` с количеством 0 и `STOCK` с целым количеством от 0 до 1 000 000 000. Все записи привязаны к UUID организации и филиала. Артикулы и source ID ограничены латинскими прописными буквами, цифрами, `-`, `_`, `.`. Проверяются повторяющиеся source ID, повторные SKU и остатки без SKU в **том же** tenant/филиале. Порядок записей не важен. Суммарное количество всех `STOCK`-строк одного артикула в одном tenant/филиале не должно превышать 1 000 000 000: нарушение возвращает `STOCK_TOTAL_LIMIT` с номером строки. Остатки разных филиалов и артикулов считаются отдельно.

## Результат и ошибки

На stdout выдаётся только JSON с `ok`, `counts`, `errors` с номерами строк и кодами ошибок, `mode: DRY_RUN_ONLY`, `writes: 0`. Исходные значения, персональные поля и UUID не выводятся. Код процесса 0 означает корректную структуру синтетических данных, код 1 — обнаруженную ошибку. Повторное чтение того же файла даёт тот же отчёт. Максимум 50 000 строк и 5 МБ. CSV только с заголовком без записей отвергается с `EMPTY_INPUT`: пустой пакет не должен ошибочно выглядеть успешной проверкой миграции. Некорректные непустые строки продолжают получать свои конкретные коды ошибок.

## Следующие обязательные этапы

Полный CSV/XLSX mapping и deduplication клиентов, авто, работ, доказательство владения и согласия на историю, импорт через авторизованный интерфейс, reconciliation источника и приёмника, резервная копия, dry-run восстановления, rollback и независимые privacy/security/operations решения **не реализованы** этим скриптом. До их подтверждения #119, #165 и #172 остаются открытыми.


## Reconciliation синтетического источника

Для сверки ожидаемых количеств укажите все три неотрицательных параметра вместе: `--expect-rows`, `--expect-sku`, `--expect-stock`. Например: `python scripts/auto_migration_dry_run.py --synthetic-only --expect-rows 2 --expect-sku 1 --expect-stock 1 synthetic_inventory.csv`.

`rows` означает число строк данных, `SKU` и `STOCK` — количество принятых записей этих типов. Несовпадение означает `RECONCILIATION_ROWS`, `RECONCILIATION_SKU` или `RECONCILIATION_STOCK` и exit 1. Неполный набор либо отрицательные значения дают exit 2. Результаты не раскрывают исходные идентификаторы. Это не сверка с БД и не доказательство идемпотентного импорта.


## Контроль целостности исходного синтетического CSV

Для воспроизводимой проверки укажите заранее вычисленный SHA-256 **байтов файла**: `python scripts/auto_migration_dry_run.py --synthetic-only --expect-sha256 <64-hex-digest> ./synthetic_inventory.csv`. Допустимы только 64 строчные шестнадцатеричные цифры. Скрипт вычисляет хеш однократно считанных ограниченных 5 МБ данных и парсит именно этот снимок; при несовпадении возвращает `SOURCE_CHECKSUM`, `ok: false`, код процесса 1 и не раскрывает исходные поля или хеш. Неверный формат аргумента даёт код 2. Хеширование не подтверждает подлинность источника: доверенный digest должен поступать отдельно и до проверки. Это **не** выполняет загрузку в PostgreSQL и не разрешает работу с настоящими данными.


## Изолированное синтетическое staging-хранилище PostgreSQL 17 (current-dev, #172)

После миграции `0074_auto_migration_staging` доступна **внутренняя библиотечная функция** `stage_synthetic_csv(conn, path, organization_id=..., batch_id=..., expected_sha256=...)` из `scripts/auto_migration_pg_staging.py`. Её вызывают **только** из одноразового тестового окружения PostgreSQL 17 с правами владельца БД и искусственными данными. HTTP API и рабочая команда для сотрудников отсутствуют; никакие данные не поступают в рабочий `auto_stock_sku` или `auto_stock_event`. В production включать нельзя до #119 и дизайна DB grants / RBAC.

Проверка читает исходные байты **один раз** (не более 5 МБ), сверяет обязательный заранее известный SHA-256 и запускает прежний CSV preflight по идентичному снимку. После проверки в одной PostgreSQL-транзакции создаются `auto_migration_staging_batch` и `auto_migration_staging_line`. Таблицы ограничены scope организации и филиала, защищены от UPDATE/DELETE триггерами, не допускают повторных source ID для филиала/пакета. Повтор `batch_id` с тем же digest и счётчиками возвращает `replayed: true` **только после побайтово-логической сверки всех сохранённых строк в исходном порядке** (номер строки, scope, тип, source ID, артикул, количество), не добавляя строки; изменённый digest или другая организация вызывают отказ. В конце транзакции проверяются фактически записанные количества; SQL-ошибка откатывает пакет полностью. Отчёт возвращает только количества и режим `SYNTHETIC_STAGING`, без source identifiers.

Тест одноразовой PG17: `PYTHONPATH=apps/api python -m pytest -q tests/integration/test_pg_auto_migration_staging.py`. Он проверяет replay, scope, tamper и rollback, а также отсутствие записи в рабочий журнал запчастей. Непроверенное и запрещённое: реальная миграция остатков, клиенты/VIN/ремонты, authorization на сотрудников, межтабличная reconciliation с рабочим ledger, конкурентная проверка с пользовательскими ролями, backup/restore переноса, production cutover. Downgrade staging уничтожает синтетическую историю и допустим лишь в disposable CI. Общие #172, #165, #119 остаются открытыми.
