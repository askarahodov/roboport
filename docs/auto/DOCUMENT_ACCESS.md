# Гранулярный доступ к документам, ценам, скидкам и истории (DEV, #446)

> **Статус: current-dev для перечисленных операций, production — planned.**
> Только HTTPS loopback + синтетические данные «БоксРитм». Это **дополнительные
> запреты**, а не выдача полномочий. Наличие роли, разрешения ALLOW или
> доступность экрана не отменяет live session/tenant/branch/customer-proof
> и иных бизнес-проверок. Нельзя использовать это как production IAM.

## Что доступно

Администратор с действующим **ADMIN** (из доверенного offline-bootstrap,
без публичной регистрации ADMIN) открывает `/staff/auto-admin`, указывает
UUID организации, затем **«Показать ограничения документов»**.
Форма **«Новая версия правила»** позволяет задать:

- **Роль политики:** `MANAGER`, `INTAKE`, `MECHANIC`, `WAREHOUSE`, `CASHIER`.
- **Документ политики:** `INTAKE_ACT`, `ESTIMATE`, `HANDOVER`,
  `SUPPLIER_ORDER`, `FINANCE`. `FINANCE` охватывает **только**
  синтетический финансовый журнал, кассы, авансы, возвраты и ДДС; это
  не юридическая первичка и не право на настоящие платежи. `HANDOVER` означает только синтетический пакет,
  условную сверку и техническое закрытие, не реальную выдачу.
- **Действие:** `READ`, `CREATE`, `EDIT`, `CLOSE`, `WRITE` (запрет
  всех изменений), `PRICE_SALES`, `PRICE_PURCHASE`, `DISCOUNT`.
  Недоступные в документе действия остаются запрещены базовой ролью
  либо не имеют никакой операции: например, старые акты приёмки нельзя
  редактировать, даже при `EDIT=ALLOW`.
- **Результат:** `DENY` ограничивает, `ALLOW` отменяет предыдущую
  запись **только в том же точном scope**. Не может обойти `DENY` шаблона
  роли, другого применимого scope, `WRITE=DENY`, отозванную роль
  или запрет приложения. Правила шаблона — пустой UUID сотрудника;
  правило для конкретного сотрудника допускается лишь при существующем
  активном назначении соответствующей роли в этом филиале.
- **UUID филиала:** опционален для правила всей организации.
  **UUID сотрудника:** опционален для шаблона роли.
- **История с даты (UTC):** только для `READ=ALLOW`. Сервер сравнивает
  реальный `created_at` заказ-наряда для документа либо дату
  создания строки заказа поставщика — **не** дату, присланную браузером.
  Более строгий cutoff любого применимого правила побеждает. Другие
  методы не получают возможности переписывать историческую первичку.

После отправки **«Сохранить правило»** сохраняется неизменяемое событие
с автором и временем; более позднее событие в том же scope заменяет
его для расчёта действующего права, но не удаляет историю. Показ журнала ограничен 100 событиями **на страницу**; доступна
курсорная навигация ко всем старым версиям. Прямой SQL
`UPDATE/DELETE` запрещён.

Для проверки без имперсонации введите UUID сотрудника и филиала,
выберите документ, нажмите **«Проверить эффективные права»**.
Появится матрица действий и фактических активных ролей. Она отражает
только ролевой срез и политику, с `subjectToObjectACL=true`, **не**
подтверждает права на конкретный VIN, WorkOrder, фото или чужую бронь.

## Реальное применение в существующем backend

| Документ | Чтение и цены | Создание/изменение/закрытие |
|---|---|---|
| Акт приёмки `INTAKE_ACT` | Staff `READ` проверяет актуальный WorkOrder + порог истории. CLIENT прежнего владельца работает только через собственную customer ACL, без staff-rule | INTAKE `CREATE`, новые immutable версии; изменение существующей версии не существует |
| Смета `ESTIMATE` | Staff MANAGER `READ` + `PRICE_SALES`; при deny возвращается 403, **никакая сумма не утечёт**. CLIENT собственной сметы продолжает читать её | MANAGER `CREATE` для версии, `EDIT` для ответа на уточнение, `DISCOUNT` обязательно для ненулевого `discountBps`; действует общий `WRITE` deny |
| Технический пакет `HANDOVER` | MANAGER/WAREHOUSE `READ` + `PRICE_SALES`, обычный клиент только по подтверждённому исходному заказу | MANAGER `CREATE` — условное движение и технический POSTED; WAREHOUSE `EDIT` — освободить резерв; MANAGER `CLOSE` — seal-preview и `CLOSED_TECHNICAL`; `WRITE` deny блокирует все три |
| Заказ поставщику `SUPPLIER_ORDER` | WAREHOUSE/MANAGER `READ`, сервер фильтрует историю; при `PRICE_PURCHASE=DENY` отдаёт `purchaseUnitMinor:null`, `purchasePriceHidden:true` (UI показывает «скрыта настройкой доступа»). Менеджерская очередь прихода/оценки полностью запрещена при price deny или историческом cutoff: в ней есть supplier quote | WAREHOUSE `CREATE` требует `PRICE_PURCHASE` для выбора предложения; `EDIT` — частичный приход; `CLOSE` — отменить непоставленный остаток; менеджерский `record_receipt_valuation` требует `PRICE_PURCHASE`; `WRITE` deny распространяется на операции заказа |

| Финансовый документ `FINANCE` | MANAGER/CASHIER `READ` и `PRICE_SALES`; защищены `financial-balance/history`, менеджерский `demo-finance-report`, все кассовые accounts/orders/report и CSV/привязанные суммы, а также ответ после повтора операции. Исторический cutoff проверяется на WorkOrder, общие филиальные отчёты с нефильтруемой историей блокируются | MANAGER `CREATE` — открыть синтетическую кассу, `EDIT` — корректировка `CHARGE/CREDIT`; CASHIER `EDIT` — аванс/платёж/возврат, `CLOSE` — закрытие дня. Во всех случаях чтение и цены необходимы отдельно; `WRITE=DENY` сильнее личного `EDIT=ALLOW` |

Отчёт CRM→техническое закрытие→SIM (`/crm/outcomes` и CSV) требует дополнительно `FINANCE READ/PRICE_SALES` по всем активным MANAGER/CASHIER ролям. При FINANCE cutoff до даты создания WorkOrder такие заказы исключаются из денежных сумм, но неподтверждённая финансовая история не раскрывается. Текущие `bookedLeads` не являются денежным показателем.

**Дополнительные пути цен основной сметы:** допработы ЗН (`/extras`) используют `ESTIMATE READ/PRICE_SALES`, `CREATE` для новой версии и `DISCOUNT` при ненулевой скидке; WAREHOUSE/MECHANIC не получают продажные суммы из `/execution` (значения `approvedTotalMinor`/`approvedExtraTotalMinor` становятся `null`), даже при успешной работе/QC. Каталог комплексов `/work-complexes` и тарифы `/tariff-policies` также требуют `ESTIMATE PRICE_SALES`, каталог не показывает исторические тарифы/цены при применимом cutoff; запись/выбор комплексов и новые тарифы дополнительно проверяют `CREATE`/`EDIT` и `DISCOUNT` где применимо. Для получения цен сотрудником обязателен live MANAGER, отдельно от обычного права видеть объём работы.

**Fail-closed:** приложению нельзя использовать `ALLOW` как выдачу новой роли
или новой предметной области. В проверках удерживаются совместимые
PostgreSQL locks на действующих session/grant/tenant, а изменение
правила сериализуется по строке организации. Завершившееся ограничение
запрещает все новые запросы сотрудника. Решения CLIENT в этих четырёх
вертикалях отдельно проверяют исходную связь owner↔vehicle; политика
staff не даёт права читать документы клиента.

## Контракт API (closed synthetic dev)

Префикс `/api/v1/dev/auto/organizations/{org}/access-policies`.
Только живой ADMIN этой организации может читать журнал или добавлять правила.

`GET /` → `{"syntheticOnly":true,"items":[...]}`;
`GET /effective?locationId=<uuid>&userId=<uuid>&documentKind=ESTIMATE`
→ `{syntheticOnly:true,subjectToObjectACL:true,roles,capabilities,...}`.
Без действующего назначения указанной роли preview скрыт.

`POST /` с same-origin `Origin`, session-cookie, `X-CSRF-Token`:

```json
{
  "requestKey": "11111111-1111-4111-8111-111111111111",
  "role": "MANAGER",
  "locationId": "22222222-2222-4222-8222-222222222222",
  "userId": "33333333-3333-4333-8333-333333333333",
  "documentKind": "ESTIMATE",
  "capability": "READ",
  "allowed": false,
  "notBefore": null
}
```

Все ID — **только искусственные**. `201` новая запись, `200` точный
идемпотентный повтор. `409` повтор ключа с другим payload, чужой
филиал или несуществующее целевое назначение; `422` невалидные
значения/временная зона; `403` сессия без ADMIN или чужая организация.
Все ответы `Cache-Control: no-store`. Функция не включена в
production OpenAPI.

Если сеть оборвалась после отправки, **«Повторить исходное правило»**
передаёт тот же `requestKey` и то же содержимое. Если результат
неизвестен и оригинального ключа нет, сначала **«Перечитать правила»**,
не отправлять новое разрешение вслепую.

## Техническая верификация и откат

- Миграция `0119_auto_document_acl` после `0118_auto_document_lifecycle`:
  append-only таблица `auto_document_access_policy`, role/scope/check
  constraints, SQL guard ADMIN и принадлежности филиала/сотрудника,
  уникальный `request_key`, запрет прямых UPDATE/DELETE.
- Сервис `auto_document_access.py` повторно вычисляет разрешения
  перед чтением/записью существующих документов. Разрешение как
  отсутствие специального DENY **не заменяет** проверку бизнеса.
- Миграция `0122_auto_financial_document_acl` (после `0121_auto_public_booking`) расширяет неизменяемую таблицу проверяемыми enum-check на `FINANCE`/`CASHIER`. Откат до `0121` разрешён **только если не было ни одного** финансового ACL события: иначе БД откажет, чтобы не уничтожить аудит. Реальных банковских таблиц/проводок/сессий миграция не создаёт.
- Интеграционный PG17/HTTPS тест
  `tests/integration/test_pg_auto_document_access_http.py` и `tests/integration/test_pg_auto_document_acl_completion.py`:
  пересечение шаблона/исключения, разные роли/филиалы, ненулевые скидки,
  сокрытие закупочной цены и коммерческой сметы, ограничения истории,
  replay/409/403/422, отзыв grant и конкуренция с ADMIN-публикацией.
- Browser E2E `apps/web/e2e/auto-document-access.spec.ts`: интерфейс
  ADMIN 390/1280 + Dark, список истории и effective preview, потеря
  ответа/точный повтор, 403 и скрытие прежних данных. Скриншоты
  остаются **кандидатами** для review #92, не approved golden baselines.

**Rollback:** только на disposable synthetic PG17 без записей нового типа:
`alembic downgrade 0121_auto_public_booking` вернёт прежний набор типов без удаления журнала; если есть `FINANCE`/`CASHIER` события, migration **намеренно остановится**. 
`alembic downgrade 0118_auto_document_lifecycle` удалит весь журнал
ограничений и не является безопасным production rollback. Нельзя применять на производственной БД или удалять
действующий аудит. Базовая роль ADMIN по-прежнему создаётся только
в доверенном offline synthetic bootstrap; настоящая identity,
GDPR/PII, право реальных финансовых операций, независимые QA,
security и legal signoff и production release #119 остаются blocked.

**Границы:** инвентаризация показателей на текущих dev API закрывает документные и ценовые пути: базовый акт, смету, допработы, тарифы, комплексы, техпакет, закупку, очередь прихода/оценку и финансовые журналы/кассы. Quantity-only склад, записи и CRM не получают разрешений на цены через эту политику. Это **не универсальная production IAM** для всех будущих API, не legal approval и не основание закрывать #119. Любой новый денежный/первичный API обязан встроить live-document ACL и отдельный regression test до релиза.


## Пересечение двух действующих ролей MANAGER + WAREHOUSE (#498)

**Закрытый synthetic-dev:** закупочная цена и действия в `SUPPLIER_ORDER`
не получают приоритета одной «удобной» роли. Если сотрудник одновременно
`MANAGER` и `WAREHOUSE`, сервер проверяет правила обеих **действующих**
ролей: явный `DENY` одной запрещает операцию независимо от `ALLOW`
другой. Это распространяется на заказ поставщику (создание, приход,
отмену с live permission и idempotency replay), очередь приемки/оценки
приходных документов, фиксацию покупной стоимости, создание/изменение
цен SKU и XLSX-операции через общий scope. Отсутствующая роль сама
по себе не запрещает действие другой, если ранее необходимая
базовая роль **остаётся действующей**. `WAREHOUSE` не превращается
в `MANAGER` для просмотра коммерческих цен `ESTIMATE`.

**Контроль:** ADMIN организации публикует `MANAGER/SUPPLIER_ORDER/
PRICE_PURCHASE DENY` для сотрудника с обеими ролями; после этого
`POST supplier-orders` обязан вернуть 403 без записи в
`auto_supplier_purchase_order`. Обратная комбинация
`WAREHOUSE/PRICE_PURCHASE DENY` запрещает выдачу `purchaseQuote`
из очереди приёмки и `POST valuation` даже при `MANAGER ALLOW`.
`MANAGER/SUPPLIER_ORDER CREATE/EDIT/CLOSE DENY` блокирует
создание/доставку/отмену покупки через точные маршруты; повтор той же
команды после отзыва прав тоже проверяется заново. Запреты по цене
закупки и цене реализации в каталоге независимы, но после объединения
ролей каждый применимый шаблон должен действовать. Для коррекции
требуется новая явно опубликованная `ALLOW` **в том же scope**;
личная ALLOW другой роли не снимает DENY.

PG17/HTTPS доказательство:
`tests/integration/test_pg_auto_dual_role_purchase_acl_http.py`
использует действительные grants, immutable policies, CSRF,
проверяет 403 без новых SQL rows и разрешённый happy path после
снятия запрета; существующие `test_pg_auto_document_acl_completion.py`,
`test_pg_auto_supplier_purchase_http.py`,
`test_pg_auto_sku_catalog_http.py` и браузерные
`warehouse-receiving.spec.ts`, `warehouse-supplier-orders.spec.ts`,
`warehouse-catalog.spec.ts` защищают прямые URI и UI. Нет изменений
DDL/OpenAPI; приватный dev API остаётся без реальных данных.
Rollback — revert PR, однако это **снова откроет обход**; только
для тестового стенда. Для production требуется gate #119.



## Управляемая история ACL после 500+ событий — current-dev (#515)

Проблема прежнего механизма: для каждого запроса документа считывались
**201 последних аудиторских событий**, после чего возвращался
`ACL_LIMIT`, хотя действующих комбинаций `capability / location|null /
user|null` всего несколько. В ADMIN-preview аналогичный предел
на **501 историческое событие** запрещал предпросмотр. Изменив
правило `DENY` на более новый `ALLOW`, администратор не мог вернуть
доступ, потому что длинный журнал сам блокировал вычисление.

**Теперь текущие права рассчитываются PostgreSQL по последней версии
каждого _точного_ scope** `(role_code, document_kind, capability,
location_id|null, user_id|null)`, с сортировкой
`created_at DESC, id DESC` и `DISTINCT ON`. Все исторические
версии сохраняются в append-only таблице. `DENY` применимого
шаблона или более узкого scope по-прежнему сильнее `ALLOW`
другого scope, `WRITE=DENY` блокирует изменения,
`READ=ALLOW` с `notBefore` сравнивается с настоящей
датой создания WorkOrder. Наличие роли, verified link,
объектный scope и клиентская ACL остаются обязательными.
Проверка удерживает `FOR SHARE` организации;
ADMIN публикует новые версии с `FOR UPDATE` той же строки,
поэтому новые правила не появляются между чтением scope
и завершением документа. Журнал не переписывается и не удаляется.

**Полный журнал:** только ADMIN данной организации вызывает

`GET /api/v1/dev/auto/organizations/{org}/access-policies?limit=50`

Сервер возвращает `syntheticOnly:true`, до `limit` событий
в `items` (максимум **100** на запрос) и, если есть ещё,
`nextBefore: "<UUID последнего события страницы>"`.
Для следующих записей используйте
`GET .../access-policies?limit=50&before=<nextBefore>`.
Курсор указывает на реально сохранённое событие **этой**
организации, сравнение — строгий keyset
`(created_at,id) < (created_at_курсора,id_курсора)`.
Новые события во время чтения не появляются на старых
страницах и не дублируют уже выданное. Неверный/чужой,
дублированный или несуществующий курсор — `422 INVALID_INPUT`
без раскрытия истории другой организации. Отзыв ADMIN
или сессии — `403` на следующий запрос; `Cache-Control:no-store`.
Это не выдача ADMIN права по UUID и не impersonation сотрудника.

В `/staff/auto-admin` раздел «Ограничения документов и цен»
показывает 50 событий на страницу, кнопки
**«Более ранние правила»** и **«Предыдущая страница правил»**,
номер страницы и пустое состояние. Повторное
«Показать ограничения документов» или сохранение нового правила
перечитывают первую страницу. После 403 старые события,
предпросмотр и формы мутаций скрываются; смена организации
очищает ранее выданное. Кнопки клавиатурно доступны на 390/1280;
доверенные доказательства — только synthetic dev.

**Проверка:** реальный PostgreSQL17 + HTTPS
`tests/integration/test_pg_auto_document_policy_history_http.py`:
520+ неизменяемых версий одного scope, read DENY→ALLOW,
проверка actual estimate, cutoff, шаблон против personal ALLOW,
ADMIN-preview, все страницы без пропуска после конкурентной вставки,
чужой cursor, отзыв ADMIN, SQL immutable audit и блокировка
ADMIN-публикации во время чтения. Browser
`apps/web/e2e/auto-document-access.spec.ts`: три страницы,
390/1280, Dark, клавиатура, ошибка контракта, отзыв 403,
очистка, сброс курсора после POST. Дополнительные индексы
в миграции `0128_auto_policy_history` не удаляют данные;
на disposable DB downgrade удаляет **только эти два индекса**.
Возврат старой логики без данного исправления вновь откроет
ложный `ACL_LIMIT` для длинного журнала — не производить
rollout/rollback без плана восстановления и gate #119.

**Ограничения:** никакого production IAM, легализации денег,
настоящих ПДн/регламентов хранения, утверждённого
security/legal sign-off и расширения базовых ролей.
Родитель #446 и запуск #119 остаются отдельными задачами.


## Политика приёмки, истории визитов и технического пакета (#446/#441, current-dev)

Для персонала `INTAKE_ACT:READ` с действующими INTAKE/MANAGER/MECHANIC проверяется не только при GET/PNG/ZIP, но и перед созданием/повтором акта. При сравнении визитов cutoff ограничивает **дату создания предыдущего заказ-наряда** до выбора последней строки SQL; старый визит не попадает ни в GET, ни в POST/replay текущего акта. Сохранены точная связь владельца, тот же филиал и проверка действующего текущего наряда. Новая версия требует INTAKE CREATE и EDIT (включая WRITE); первая версия — CREATE. ADMIN preview отражает EDIT только для INTAKE. Клиентский просмотр/подтверждение остаётся отдельным путём по исходному verified proof, не зависит от правил персонала.

Все прямые операции технического пакета HANDOVER (условная сверка, снятие резерва, запечатывание, POSTED и CLOSED_TECHNICAL), чтение и экспорт для персонала применяют общий READ/cutoff, PRICE_SALES и нужный CREATE/EDIT/CLOSE (+WRITE) на **обеих активных ролях MANAGER/WAREHOUSE**. Базовая роль конкретной операции остаётся обязательной; DENY второй роли не обходится прямым POST или replay. ADMIN preview учитывает этот пересекающий запрет для CREATE/EDIT/CLOSE. Досье требует MANAGER и разрешённое вложенное чтение INTAKE_ACT или отдельную авторизацию исходного клиента без подмены отказа staff. Отказ не меняет immutable журнал; UI скрывает ранее загруженный акт/сверку и печатные данные. Запоздалые ответы записи и скачивания акта из уже сменённого scope не восстанавливают данные прежнего заказа. Прежние скачанные/распечатанные копии не отзываются автоматически.

PG17/HTTPS: расширены существующие `test_pg_auto_intake_act_http.py`, `test_pg_auto_document_lifecycle_http.py`, `test_pg_auto_technical_dossier_http.py` без новых тяжёлых lifecycle fixtures; Playwright: `auto-intake-act.spec.ts`, `auto-document-lifecycle.spec.ts`. Нет изменения DDL/production API. Откат только revert кода/тестов/docs на тестовом стенде; старый код вновь откроет обход. Техническое закрытие не разрешает выдачу или production.


### Совмещённые роли в проекциях заказ-наряда (#446/#166, current-dev)

Прямые GET `/orders/{order}/customer` и `/orders/{order}/workspace` требуют действующего INTAKE или MANAGER и точного объекта/филиала/verified proof. Дополнительно применяется READ/cutoff всех действующих INTAKE, MANAGER и MECHANIC, как при чтении акта и осмотра. Если у совмещённой роли MECHANIC есть DENY или cutoff исключает наряд, нельзя открыть UUID клиента или состояния рабочего места через альтернативный URL: 403/no-store. MECHANIC без INTAKE/MANAGER не получает новые права; личный ALLOW INTAKE не отменяет DENY MECHANIC. Восстановление после публикации ALLOW в том же scope сохраняет историю политики. PG17/HTTPS regression в `tests/integration/test_pg_auto_order_customer_read.py` сверяет ADMIN preview, customer/workspace/inspection-qc, cutoff, восстановление и отзыв базовой роли. UI и форматы ответов не изменены; production и полная приёмка #446/#119 остаются открытыми. Откат — revert только на синтетическом стенде.
