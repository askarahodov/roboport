# Гранулярный доступ к документам, ценам, скидкам и истории (DEV, #446)

> **Статус: current-dev для перечисленных операций, production — planned.**
> Только HTTPS loopback + синтетические данные «БоксРитм». Это **дополнительные
> запреты**, а не выдача полномочий. Наличие роли, разрешения ALLOW или
> доступность экрана не отменяет live session/tenant/branch/customer-proof
> и иных бизнес-проверок. Нельзя использовать это как production IAM.

## Что доступно

Администратор с действующим **ADMIN** (из доверенного offline-bootstrap,
без публичной регистрации ADMIN) открывает `/staff/auto-admin`, указывает
UUID организации, затем **«Показать ограничения документов»**.
Форма **«Новая версия правила»** позволяет задать:

- **Роль политики:** `MANAGER`, `INTAKE`, `MECHANIC`, `WAREHOUSE`.
- **Документ политики:** `INTAKE_ACT`, `ESTIMATE`, `HANDOVER`,
  `SUPPLIER_ORDER`. `HANDOVER` означает только синтетический пакет,
  условную сверку и техническое закрытие, не реальную выдачу.
- **Действие:** `READ`, `CREATE`, `EDIT`, `CLOSE`, `WRITE` (запрет
  всех изменений), `PRICE_SALES`, `PRICE_PURCHASE`, `DISCOUNT`.
  Недоступные в документе действия остаются запрещены базовой ролью
  либо не имеют никакой операции: например, старые акты приёмки нельзя
  редактировать, даже при `EDIT=ALLOW`.
- **Результат:** `DENY` ограничивает, `ALLOW` отменяет предыдущую
  запись **только в том же точном scope**. Не может обойти `DENY` шаблона
  роли, другого применимого scope, `WRITE=DENY`, отозванную роль
  или запрет приложения. Правила шаблона — пустой UUID сотрудника;
  правило для конкретного сотрудника допускается лишь при существующем
  активном назначении соответствующей роли в этом филиале.
- **UUID филиала:** опционален для правила всей организации.
  **UUID сотрудника:** опционален для шаблона роли.
- **История с даты (UTC):** только для `READ=ALLOW`. Сервер сравнивает
  реальный `created_at` заказ-наряда для документа либо дату
  создания строки заказа поставщика — **не** дату, присланную браузером.
  Более строгий cutoff любого применимого правила побеждает. Другие
  методы не получают возможности переписывать историческую первичку.

После отправки **«Сохранить правило»** сохраняется неизменяемое событие
с автором и временем; более позднее событие в том же scope заменяет
его для расчёта действующего права, но не удаляет историю. Показ журнала
ограничен 100 событиями; прямой SQL `UPDATE/DELETE` запрещён.

Для проверки без имперсонации введите UUID сотрудника и филиала,
выберите документ, нажмите **«Проверить эффективные права»**.
Появится матрица действий и фактических активных ролей. Она отражает
только ролевой срез и политику, с `subjectToObjectACL=true`, **не**
подтверждает права на конкретный VIN, WorkOrder, фото или чужую бронь.

## Реальное применение в существующем backend

| Документ | Чтение и цены | Создание/изменение/закрытие |
|---|---|---|
| Акт приёмки `INTAKE_ACT` | Staff `READ` проверяет актуальный WorkOrder + порог истории. CLIENT прежнего владельца работает только через собственную customer ACL, без staff-rule | INTAKE `CREATE`, новые immutable версии; изменение существующей версии не существует |
| Смета `ESTIMATE` | Staff MANAGER `READ` + `PRICE_SALES`; при deny возвращается 403, **никакая сумма не утечёт**. CLIENT собственной сметы продолжает читать её | MANAGER `CREATE` для версии, `EDIT` для ответа на уточнение, `DISCOUNT` обязательно для ненулевого `discountBps`; действует общий `WRITE` deny |
| Технический пакет `HANDOVER` | MANAGER/WAREHOUSE `READ` + `PRICE_SALES`, обычный клиент только по подтверждённому исходному заказу | MANAGER `CREATE` — условное движение и технический POSTED; WAREHOUSE `EDIT` — освободить резерв; MANAGER `CLOSE` — seal-preview и `CLOSED_TECHNICAL`; `WRITE` deny блокирует все три |
| Заказ поставщику `SUPPLIER_ORDER` | WAREHOUSE/MANAGER `READ`, сервер фильтрует историю; при `PRICE_PURCHASE=DENY` отдаёт `purchaseUnitMinor:null`, `purchasePriceHidden:true` (UI показывает «скрыта настройкой доступа») | WAREHOUSE `CREATE` требует `PRICE_PURCHASE` для выбора предложения; `EDIT` — частичный приход; `CLOSE` — отменить непоставленный остаток; `WRITE` deny распространяется на все операции |

**Fail-closed:** приложению нельзя использовать `ALLOW` как выдачу новой роли
или новой предметной области. В проверках удерживаются совместимые
PostgreSQL locks на действующих session/grant/tenant, а изменение
правила сериализуется по строке организации. Завершившееся ограничение
запрещает все новые запросы сотрудника. Решения CLIENT в этих четырёх
вертикалях отдельно проверяют исходную связь owner↔vehicle; политика
staff не даёт права читать документы клиента.

## Контракт API (closed synthetic dev)

Префикс `/api/v1/dev/auto/organizations/{org}/access-policies`.
Только живой ADMIN этой организации может читать журнал или добавлять правила.

`GET /` → `{"syntheticOnly":true,"items":[...]}`;
`GET /effective?locationId=<uuid>&userId=<uuid>&documentKind=ESTIMATE`
→ `{syntheticOnly:true,subjectToObjectACL:true,roles,capabilities,...}`.
Без действующего назначения указанной роли preview скрыт.

`POST /` с same-origin `Origin`, session-cookie, `X-CSRF-Token`:

```json
{
  "requestKey": "11111111-1111-4111-8111-111111111111",
  "role": "MANAGER",
  "locationId": "22222222-2222-4222-8222-222222222222",
  "userId": "33333333-3333-4333-8333-333333333333",
  "documentKind": "ESTIMATE",
  "capability": "READ",
  "allowed": false,
  "notBefore": null
}
```

Все ID — **только искусственные**. `201` новая запись, `200` точный
идемпотентный повтор. `409` повтор ключа с другим payload, чужой
филиал или несуществующее целевое назначение; `422` невалидные
значения/временная зона; `403` сессия без ADMIN или чужая организация.
Все ответы `Cache-Control: no-store`. Функция не включена в
production OpenAPI.

Если сеть оборвалась после отправки, **«Повторить исходное правило»**
передаёт тот же `requestKey` и то же содержимое. Если результат
неизвестен и оригинального ключа нет, сначала **«Перечитать правила»**,
не отправлять новое разрешение вслепую.

## Техническая верификация и откат

- Миграция `0119_auto_document_acl` после `0118_auto_document_lifecycle`:
  append-only таблица `auto_document_access_policy`, role/scope/check
  constraints, SQL guard ADMIN и принадлежности филиала/сотрудника,
  уникальный `request_key`, запрет прямых UPDATE/DELETE.
- Сервис `auto_document_access.py` повторно вычисляет разрешения
  перед чтением/записью существующих документов. Разрешение как
  отсутствие специального DENY **не заменяет** проверку бизнеса.
- Интеграционный PG17/HTTPS тест
  `tests/integration/test_pg_auto_document_access_http.py`:
  пересечение шаблона/исключения, разные роли/филиалы, ненулевые скидки,
  сокрытие закупочной цены и коммерческой сметы, ограничения истории,
  replay/409/403/422, отзыв grant и конкуренция с ADMIN-публикацией.
- Browser E2E `apps/web/e2e/auto-document-access.spec.ts`: интерфейс
  ADMIN 390/1280 + Dark, список истории и effective preview, потеря
  ответа/точный повтор, 403 и скрытие прежних данных. Скриншоты
  остаются **кандидатами** для review #92, не approved golden baselines.

**Rollback:** только на disposable synthetic PG17:
`alembic downgrade 0118_auto_document_lifecycle` удалит журнал
ограничений. Нельзя применять на производственной БД или удалять
действующий аудит. Базовая роль ADMIN по-прежнему создаётся только
в доверенном offline synthetic bootstrap; настоящая identity,
GDPR/PII, право реальных финансовых операций, независимые QA,
security и legal signoff и production release #119 остаются blocked.

**Границы:** эта вертикаль защищает перечисленные staff-пути, но
**не объявляет** универсальную готовность ACL во всех складских,
CRM, user management и налоговых API; полная инвентаризация
потребителей чувствительных закупочных цен/документов нужна для
закрытия общего #446 и релизного #119.
