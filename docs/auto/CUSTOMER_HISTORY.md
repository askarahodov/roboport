# Личный кабинет — мои автомобильные заказ-наряды и безопасная история (dev)

> **Статус: current-dev / synthetic HTTPS loopback.** Реальный автомобильный
> заказ-наряд, юридически значимое согласование, запись клиента, платёж и
> выдача автомобиля в production **не реализованы**. Не вводите реальные VIN,
> телефоны, фото, паспорта или платёжные данные.

## Зачем

Клиенту больше не требуется угадывать UUID автомобиля, филиала и заказ-наряда,
чтобы найти свою смету. Закрытый экран `/account/auto-orders` показывает **только
заказы, созданные с его собственной подтверждённой связью с конкретным авто**.
История остаётся собственностью заказчика, даже если позднее другая учётная
запись подтвердит владение той же машиной. Ввод одного VIN или UUID не создаёт
права на историю, старые `service_ticket` роботов не участвуют в запросе.

## Сценарий глазами клиента

1. Войдите тестовой ролью **CLIENT** на HTTPS loopback-стенде и откройте
   «Личный кабинет» → **«Мои заказ-наряды (dev)»**, URL
   `/account/auto-orders`. При отсутствии серверной сессии кабинет вообще
   не открывает этот раздел (401/403 в зависимости от уровня проверки).
2. После **«Загрузка собственных заказ-нарядов…»** появятся свои заказы с
   тестовыми маркой, моделью, датой записи, её статусом и маской `VIN ••••6543`.
   **Полный VIN, контакты, внутренние данные других покупателей и SKU/лоты
   склада здесь не возвращаются.** При отсутствии подтверждённых заказов
   показывается «Заказ-нарядов с подтверждённой связью пока нет».
3. Нажмите **«Подробнее о заказе»**. Карточка показывает действующее или
   отменённое бронирование (включая дату после переноса), приёмочный осмотр,
   историю версий сметы с перечнем и суммами в **копейках**, факт работ в
   минутах, статус QC и наличие технического пакета с SHA-256.
   Документ — только synthetic pre-handover preview, без подписи, PDF-акта,
   кассового чека или разрешения на выдачу.
4. Если последняя смета **ещё не получила решения** и запись действующая,
   проверьте все строки и сумму и нажмите **«Согласовать последнюю версию»**
   либо **«Отклонить последнюю версию»**. Клиент отправляет точный UUID и
   `requestKey` уже существующему серверному API решения; сервер заново
   проверяет клиентскую сессию, свою связь, последнюю ревизию и право
   согласования. Прежние версии уже нельзя согласовать.
5. После сетевой ошибки с неизвестным результатом нажмите
   **«Повторить то же решение»** с первоначальным ключом либо
   **«Перечитать карточку»**, чтобы запросить актуальное состояние. При 409
   смета изменилась или уже имеет решение; перечитайте суммы, не отправляйте
   новое согласие автоматически.
6. Для истории из более чем 20 записей используйте
   **«Показать ещё заказ-наряды»**. Ключ продолжения подписан и привязан
   к текущей сессии; интерфейс при подгрузке **перепроверяет все уже
   показанные страницы**, чтобы не сохранять отозванные записи в памяти
   страницы. **«Обновить заказ-наряды»** проверяет доступ заново.
7. При выходе из учётной записи, отзыве роли CLIENT,
   `account_customer_link` или точной `auto_vehicle_customer_link`
   сервер отказвает либо возвращает пустой список; интерфейс скрывает
   ранее показанную карточку. При 404 заказ не существует **или**
   не принадлежит текущему клиенту — эти случаи специально не различаются.

## Кто имеет право видеть заказ?

- Нужны действующие `app_user` + `user_session` + `user_role.CLIENT`.
- `account_customer_link` должен указывать на **customer_id из того
  `auto_vehicle_customer_link`, который был указан в `auto_appointment`**,
  а не просто на текущего владельца того же VIN/vehicle_id.
- `auto_vehicle_customer_link` требует `verified_at`, `verified_by`
  и отсутствия `revoked_at`; организация и филиал активны и совпадают с
  исходным автомобильным заказом, привязка автомобиля к филиалу действующая.
- Независимое подтверждение нового владельца **не переносит** историю
  старого заказчика. Сервисные документы прежнего владельца и legacy
  робототехнические заявки не открываются автоматически.

## Проверяемый закрытый API

| Маршрут | Роль и ответ |
|---|---|
| `GET /api/v1/dev/auto/customer/orders?limit=20` | CLIENT, `items[]`, `nextCursor`, `syntheticOnly:true`, `releaseAllowed:false` |
| `GET /api/v1/dev/auto/customer/orders/{orderId}` | CLIENT и original bound link, `appointment`, `estimates`, `inspection`, `labor`, `qcStatus`, `document`, `canDecide` |
| `POST /api/v1/dev/auto/organizations/{org}/locations/{loc}/orders/{order}/estimates/decision` | CLIENT, существующий CSRF + exact-revision `requestKey` / `revisionId` / `APPROVED` либо `DECLINED` |

Ответы `Cache-Control:no-store`, API не публикуется в production
`/openapi.json`; нет внешнего токена mobile и публичного endpoint.
`401` — нет активной сессии, `403` — роль CLIENT отозвана, `404`
— чужой или несуществующий заказ, `422` — неверные `limit`/`cursor`.
`limit` 1–30, страницы по 20, signed keyset cursor привязан к сессии
(после перезапуска процесса курсор теряет силу, повторить с первой страницы).
При отмене брони **история остаётся видимой первоначальному клиенту**,
но новое согласие сметы через старый API запрещено.

  заказ**, отмена/перенос, смета и настоящее client decision, QC и технический
  preview, пагинация и чужие курсоры.
- Playwright: `apps/web/e2e/customer-auto-orders.spec.ts` — 390/1280,
  Light/Dark/Auto, клавиатура, реальное изменение видимых данных после
  одобрения, отзыв с пустой страницей и повторная проверка страниц.
- Изменения только **аддитивные без миграции данных**: для отмены используйте
  revert PR. Нет destructive DDL, production не включается без gate #119.

  фото/подписи, уведомления, история PDF, реальная касса/возвраты и
