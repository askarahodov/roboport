# Рабочий график филиала, закрытые дни и запись (#113)

**Статус: current-dev / только synthetic HTTPS loopback.** Это реальный технический контракт PostgreSQL 17 в тестовом контуре, а не production-доступ. Для выпуска в эксплуатацию обязательны #119, настройки реальных филиалов, согласия на ПДн и ручной QA.

## Как настроить (MANAGER)

В `/staff/auto-calendar` укажите UUID организации и филиала. В секции **«Часы работы и закрытые даты»** пользователь с активной scoped ролью `INTAKE` или `MANAGER` может прочитать конфигурацию; **сохранить** может только `MANAGER` соответствующей организации/филиала и с живой сессией/CSRF.

Добавьте до **28 непересекающихся интервалов** для дней недели: ISO weekdays 1 = понедельник, …, 7 = воскресенье; начало в формате `HH:MM` (00:00..23:59), окончание до `24:00` (следующая полночь). Перерыв оформляется двумя интервалами одного дня; пересечение запрещено. Для полного закрытия можно оставить список интервалов пустым. В **«Закрытые даты»** укажите до 120 уникальных дат `YYYY-MM-DD` через запятую или новую строку; они имеют приоритет над недельным расписанием. Дополнительные рабочие часы в закрытый день в текущем dev не поддерживаются (planned). Время интерпретируется в установленной IANA-зоне филиала, а не зоне браузера.

Нажмите **«Сохранить график филиала»**. Интерфейс отправляет ожидаемую версию: если параллельно другой MANAGER изменил расписание — `409 OPENING_POLICY_CONFLICT`; откройте актуальный график перед новым сохранением. Если новая конфигурация **вывела бы существующую активную будущую бронь** за часы работы — тот же `409`, но предыдущий график и запись останутся без изменений. История предыдущих версий хранится append-only; SQL UPDATE/DELETE истории запрещены.

Для переноса записи сотрудник выбирает новые свободные слоты в календаре. Поиск одновременно проверяет границы графика, актуальную занятость поста, смену назначенного специалиста и суммарную длительность работ. Кандидаты `guaranteed:false` не резервируют время. Подтверждение повторно проверяется **не только API, но и PostgreSQL INSERT trigger**; при нарушении графика возвращается `409 LOCATION_CLOSED`, **без** нового Appointment/WorkOrder, reschedule event, notification outbox или складского RESERVE. Ранее созданные записи не переписываются при смене расписания.

## Конфигурация по умолчанию и production-ограничение

**Ненастроенный филиал** (ещё нет строки `auto_location_opening_policy`) сохраняет **старое synthetic поведение без ограничения часами работы** для совместимости с историческими тестами и API. GET возвращает `configured:false,version:0`; ответы поиска содержат `openingHoursConfigured:false`, UI явно предупреждает. Это **не означает 24-часовой бизнес-график** и запрещает считать такой филиал production-ready. Менеджер обязан отдельно подтвердить рабочее расписание; если филиал закрыт по всем дням, он сохраняет `windows:[]`, а не оставляет конфигурацию отсутствующей.

## API (скрытый dev-only, не OpenAPI)

`GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/opening-hours` доступен scoped `INTAKE` или `MANAGER`; возвращает `{"configured":false,"version":0,"windows":[],"closedDates":[],"timeZone":"Europe/Berlin","syntheticOnly":true}` без данных клиентов. Для настроенного филиала `configured:true`, версия от 1, полный набор `windows`, даты закрытия. `Cache-Control:no-store`, `403` чужой филиал/нет прав, `422` неверные UUID.

`POST /api/v1/dev/auto/organizations/{org}/locations/{loc}/opening-hours` только `MANAGER` + `X-CSRF-Token`, `Origin` и session:
```json
{
  "expectedVersion": 0,
  "windows": [
    {"weekday": 1, "opensMinute": 540, "closesMinute": 780},
    {"weekday": 1, "opensMinute": 840, "closesMinute": 1080},
    {"weekday": 2, "opensMinute": 540, "closesMinute": 1080}
  ],
  "closedDates": ["2030-01-01"]
}
```
Это пример локальных часов для *синтетического* филиала (пн 09:00–13:00 и 14:00–18:00, вт 09:00–18:00). Остальные дни закрыты. `expectedVersion=0` используется только при первом сохранении; при дальнейшем изменении передайте текущую версию. Неверный JSON/дата/тип/пересечение/лимит → `422 INVALID_INPUT`; чужой MANAGER или CSRF → `403 FORBIDDEN`; конфликт версии или активной брони → `409 OPENING_POLICY_CONFLICT`; успех → `200` + новая версия + канонические интервалы/даты.

`GET /api/v1/dev/auto/customer/booking/slots` и `GET /api/v1/dev/auto/organizations/{org}/slot-candidates` сохраняют прежние query-поля и теперь добавляют `openingHoursConfigured:boolean`; если график настроен, возвращают только интервалы целиком **внутри одного рабочего окна** и не в закрытую дату. Без вариантов — пустой `items:[]`, `guaranteed:false`, без фантомной брони.

`POST` создания и переноса для INTAKE/CLIENT возвращают `409 LOCATION_CLOSED` при закрытом интервале. Учитываются 23/25-часовые IANA сутки и повторный час осенью; соответствие проверяется по **абсолютным** timestamp-instant начала/конца и локальным границам. Ночные интервалы, пересекающие локальную полночь, необходимо разделить на два окна по соседним дням; одна запись за полночь в этом dev-режиме пока не поддерживается (planned). End ровно в 24:00 допускается.

## Внутренние инварианты и тестирование

`apps/api/alembic/versions/0093_auto_location_opening_hours.py`: tenant-bound `auto_location_opening_policy`, `auto_location_opening_history`, DB-функция `auto_location_hours_allow`, проверки минут/дней, отсутствие overlap, запрет инвалидировать активные будущие брони при обновлении, защитный `BEFORE INSERT` на `auto_bay_booking`. Локация блокируется совместно с созданием брони; обновление конфигурации атомарно. Без удалений/изменений старой истории; Alembic downgrade отказывается исполняться, если уже есть сохранённые версии расписания.

Сервис `auto_opening_hours.py` нормализует payload и выполняет scoped MANAGER optimistic compare-and-swap; `auto_slot_candidates.py` отсекает закрытые окна SQL; `auto_appointment_service.py` отдельно преобразует конфликт с графиком в `AppointmentHoursClosed`, HTTP = `409 LOCATION_CLOSED`. Схема расширена без изменения старых dev контрактов.

Реальный PG17 + HTTP: `tests/integration/test_pg_auto_location_opening_hours.py` (roles, клиенты/приёмщики, закрытые даты, отрицательная бронь SQL, 409 и отсутствие phantom, смена графика при активной записи, optimistic version, весна/осень IANA). Playwright: `apps/web/e2e/auto-calendar.spec.ts` (390/1280, editor, CSRF, отказ без MANAGER). Для production остаются: реальные графики/праздники каждого филиала, смены/роли, согласия, уведомления, расчёт стоимости, мониторинг и release gate #119.
