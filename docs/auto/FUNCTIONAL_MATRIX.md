# Матрица функций: AutoDealer как benchmark → целевая автомобильная система

**Актуализация:** 28.10.2026 · **Issue:** #174 · **Статус:** продуктовые требования, **не** подтверждение реализации.

## Источники и ограничения

Внешний функциональный ориентир: [AutoDealer Онлайн — о программе](https://autodealer.ru/online/help/o-programme.html), [заказ-наряд](https://autodealer.ru/online/order), [запись и посты](https://autodealer.ru/online/help/zapis-na-remont/index.html), [CRM](https://autodealer.ru/online/help/crm/index.html), [склад и функциональный перечень](https://autodealer.ru/online/shop), [база знаний](https://autodealer.ru/support/knowledge-base). Эти страницы подтверждают **классы функций AutoDealer**, но **не** конкретные API, бизнес-правила, лицензии и фактическую реализацию ROBOport. Детальные правила, глубина модулей и приоритеты ниже — **наши проектные требования**, не цитаты из AutoDealer.

**Цель:** самостоятельная полнофункциональная платформа СТО (рабочий frontend/backend/DB), не «робототехническое приложение плюс автомобиль». AutoDealer нельзя копировать по коду, закрытым каталогам, фирменному UI или базе нормо-часов без прав. Реальное состояние оценивается по проверенным исходникам. `partial-dev` означает локальный synthetic-срез, **не production-ready**. `planned` означает отсутствие законченного автомобильного сценария; наличие одноимённых legacy ticket/stock таблиц НЕ считается выполнением.

Приоритеты: **P0** — архитектура и безопасность до продукта; **M1** — основная рабочая система автосервиса; **M2** — полнота коммерческих операций; **M3** — мобильное развитие. Все строки имеют owner Issue; второе поле — ключевая зависимость.

## Разделение существующей реализации и целевого продукта

- **Current-dev, проверено ранее:** Alembic автомобильных таблиц и синтетическая привязка владельца; закрытые API проверки доступа; частичный кабинет автомобилей; Docsify и CI. Функциональные идентификаторы: B02/B03/F04/F07, частично A05/F10. Все эти элементы не открывают production и не обеспечивают полное обслуживание автомобиля.
- **Legacy-only, не готовый автомобильный модуль:** robot_device, service_ticket, estimate, stock_lot, старые public/staff маршруты, старые документы. Они могут давать технические решения/алгоритмы, но их доменные данные и полномочия не наследуются.
- **Planned:** остальные строки. Актуальность меняется **только при подтверждённом PR, контракте, миграции, E2E и документации**.

## Непреложные бизнес-правила

1. Один автомобиль имеет историю **нарядов конкретных заказчиков**, VIN не даёт доступ к истории другого лица.
2. Время рабочего поста бронируется атомарно: два подтверждённых приёма в одном интервале невозможны.
3. После отправки смета неизменяема; новые работы только в новой версии с явным решением клиента.
4. Резерв/расход запчастей атомарны, double-booking/oversell исключены.
5. Оплаты, возвраты и первичные документы учитываются с неизменяемым audit; фискализация включается только с юридически проверенным провайдером.
6. Все права ограничены организацией, филиалом и конкретным объектом. Автомобильный MANAGER **не становится** руководителем legacy домена.
7. Редактирование/архивация legacy robot данных невозможны без плана сверки, backup и восстановления.

## Покрытие приёмки

Покрытие требований означает **52 позиции с привязкой к задачам**, а не 52 выполненные функции. Для каждой реализации Issue добавляет Given/When/Then, happy/negative, PG17 concurrency, BOLA/ACL, OpenAPI, ролевую инструкцию и E2E. Итоговая сквозная приёмка проводится по [дорожной карте](FEATURE_ROADMAP.md).
