# Загрузка постов: текущие бронирования по дням (#171)

> **Статус: current-dev, только synthetic PostgreSQL 17 + закрытый HTTPS loopback.**
> Не production BI, не регламентные нормо-часы, не расчёт зарплат, выручки, прибыли,
> фактически отработанных часов, SLA или финансовых документов. Без PII/VIN.

## Руководителю: воспроизводимый рабочий сценарий

1. Войдите в тестовый стенд с действующей сессионной ролью `MANAGER` нужной организации и филиала. Откройте **«Загрузка постов (dev)»** (`/staff/auto-bay-occupancy`).
2. Укажите UUID **своей** организации, UUID филиала и начало/конец периода как даты в локальном календаре филиала. Максимум **31 день включительно**.
3. Нажмите **«Сформировать отчёт»**. В таблице для каждого дня отображаются число актуальных записей, занятые часы, число посто-часов и процент занятости. Сервер возвращает IANA `timeZone`, количество **сейчас включённых** постов и явный признак методологии.
4. Для проверки переноса/отмены обновите отчёт после изменения записи в календаре: старые исторические брони **не** считаются. Выбранная запись учитывается по **текущей** броне и только по пересечению с нужными локальными сутками.
5. Если роль отозвана, филиал выключен или чужой — `403`, таблица очищается. Период неверен или длиннее 31 суток — `422`. Сбой сети/некорректный ответ очищает таблицу и позволяет повторить запрос.

Клиент/INTAKE/WAREHOUSE без MANAGER не получает агрегаты филиала. Ни frontend, ни сервер не выводят ФИО, VIN, автомобиль, идентификатор клиента, смету, банковские данные или индивидуальное расписание работника. Гипотеза «текущая загрузка» ≠ историческая аналитика выручки.

## HTTP API и контракт

```text
GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/bay-occupancy
    ?fromDay=2030-03-31&toDay=2030-04-01

200 Cache-Control: no-store
{
  "syntheticOnly": true,
  "basis": "CURRENT_BOOKINGS_CALENDAR_DAY",
  "timeZone": "Europe/Berlin",
  "bayCount": 1,
  "items": [
    {"localDay":"2030-03-31","daySeconds":82800,
     "activeAppointments":1,"occupiedSeconds":3600,
     "calendarCapacitySeconds":82800,"occupancyBasisPoints":434}
  ]
}
```

Считается только последняя **активная** бронь каждого `auto_appointment`, в пределах пары organization/location, с текущим включённым `auto_work_bay`. Для дня с границами `[D 00:00, (D+1) 00:00)` в IANA зоне:
- `occupiedSeconds = Σ duration(intersection(booking, local day))` по каждому активному appointment. Перенос и отмена исключают старую бронь; бронь на стыке суток учитывается в двух днях только своими частями.
- `daySeconds` = реальные секунды суток, поэтому локальные DST-дни могут составлять **23 / 24 / 25 часов**.
- `calendarCapacitySeconds = daySeconds × bayCount`, где `bayCount` — количество **сейчас включённых** постов филиала (не исторический состав парка, не график работы, не часы смен). Нерабочее время входит в знаменатель. Показатель **не следует** называть процентом производственной утилизации или нормо-часами.
- `occupancyBasisPoints = floor(occupiedSeconds × 10000 / calendarCapacitySeconds)` — целое число сотых долей процента; когда нет действующих постов, `null` («Нет активных постов»), не искусственные 0%.
- `activeAppointments` — число актуальных записей, пересекающих локальный день. Одна запись может встречаться в двух днях; суммировать daily counts как уникальных клиентов нельзя.

День и даты периода канонические `YYYY-MM-DD`; 31 включительно; отсутствие правильной сессии/роли/филиала — `403 FORBIDDEN`; неправильный UUID/дата/период — `422 INVALID_INPUT`. Идентификаторы и отчёт не кэшируются; сессия и живые назначения `MANAGER` проверяются заново на **каждый** запрос. Доступ к публичному OpenAPI и реальной мультиорганизационной BI остаётся `planned`.

## Агрегированная загрузка назначений сотрудников (current-dev, #171)

В **том же** отчёте руководителя за локальные сутки теперь присутствует дополнительная группа **«Сотрудники в сменах / Часы смен / Назначения / Часы назначений / Доля назначений от смен»**. Никаких ФИО, employee UUID, смен конкретного сотрудника, зарплаты или кадровой информации API не отдаёт.

- `scheduledEmployees`: количество **различных сотрудников**, имеющих действующую неперекрывающуюся смену филиала, которая пересекает локальный день. Это число **не суммируется** как уникальные сотрудники за месяц: один человек может присутствовать в нескольких днях.
- `scheduledShiftSeconds`: сумма пересечений действующих `auto_staff_shift` c локальными сутками в IANA зоне филиала. Отменённые смены исключены; благодаря PostgreSQL exclusion constraint смены одного сотрудника не перекрываются. **Это запланированная доступность**, а не табель и не факт присутствия.
- `activeAssignments`: число действующих **назначений специалиста на актуальную бронь** `auto_appointment` в отчётных сутках. Требуется непогашенная `auto_employee_reservation` и действующая смена, покрывающая весь резерв; исторические назначения отменённых и перенесённых броней не учитываются.
- `assignedSeconds`: сумма фактических пересечений этих **плановых резервов** с локальным днём. Она не может превышать `scheduledShiftSeconds` при неперекрывающихся сменах/назначениях.
- `assignmentBasisPoints = floor(assignedSeconds × 10000 / scheduledShiftSeconds)` — сотые доли процента. При нуле действующих смен возвращается `null` («Нет действующих смен»), а не фиктивное 0%.

**Ограничения:** отчёт показывает текущие планы и доступные в момент запроса смены, а не исторические изменения расписания, соблюдение смены работником, качественный результат ремонта, учёт труда, billing, KPI/премии или payroll. Он не должен использоваться для расчёта зарплаты. При отзыве смены соответствующий резерв больше не входит в метрику действующих смен, даже если старое назначение осталось в immutable истории. Отзыв MANAGER или переход на чужой филиал остаётся fail-closed. 31 день, no-store, no PII, dev-only неизменны.

**Доказательства:** PostgreSQL `test_pg_auto_bay_occupancy_http.py`: действующая смена на 25-часовых сутках, назначение на бронь, перенос с `clear_employee`, отзыв смены, A/B изоляция и проверка отсутствия user UUID в ответе; browser `auto-bay-occupancy.spec.ts`: отображение агрегатов, невозможное превышение часов, 403/переключение филиала, мобильный 390 и 1280. API возвращает дополнительные поля только в `items[]`; сумма/финансы не добавлены, миграция не требуется. Откат безопасен: предыдущий API/UI не сохранял эти вычисляемые значения.


## Зарегистрированные факты исполнения (current-dev, #171)

Отдельно от **плановых** бронирований и смен таблица показывает три агрегата по неизменяемому журналу заказ-нарядов. `recordedLaborEntries` — число строк `auto_work_order_labor_entry`, `recordedLaborMinutes` — сумма сохранённых `actual_minutes`, `finishedExecutions` — число `auto_work_order_execution_finish`. Дата каждого значения — именно локальная дата **регистрации события** `created_at` (часовой пояс филиала), а не день бронирования или календарная дата завершения клиентом. События привязаны к `execution → work_order` и перепроверяются по organization/location; в ответе нет UUID сотрудников, клиентов, услуг, заказов или VIN. Идемпотентный повтор POST `/labor`/`/finish` не создаёт новых строк, поэтому не повышает цифры. Отмена/перенос брони не стирает ранее зарегистрированный факт.

Это **не** табель, физически отработанное время, норма труда, зарплата, бухгалтерская проводка, оплата или выпуск автомобиля. `finishedExecutions` не означает QC PASS. Ноль — отсутствие событий в этом журнале, а не утверждение об отсутствии реальной работы. Роль MANAGER, диапазон 1–31 день, read-only, no-store, проверка отзыва доступа и synthetic-only неизменны. Доказательства: PG17 тест `test_immutable_recorded_labor_and_finish_report_full_execution_lifecycle` (одобрение, начало, сохранение труда, повтор, finish, tenant и отзыв прав) и Playwright `auto-bay-occupancy.spec.ts` (три колонки, отказ от отрицательных минут, очистка старой таблицы). Никакого payroll и production до #119.
