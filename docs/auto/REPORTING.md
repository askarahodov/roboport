# Загрузка постов: текущие бронирования по дням (#171)

> **Статус: current-dev, только synthetic PostgreSQL 17 + закрытый HTTPS loopback.**
> Не production BI, не регламентные нормо-часы, не расчёт зарплат, выручки, прибыли,
> фактически отработанных часов, SLA или финансовых документов. Без PII/VIN.

## Руководителю: воспроизводимый рабочий сценарий

1. Войдите в тестовый стенд с действующей сессионной ролью `MANAGER` нужной организации и филиала. Откройте **«Загрузка постов (dev)»** (`/staff/auto-bay-occupancy`).
2. Укажите UUID **своей** организации, UUID филиала и начало/конец периода как даты в локальном календаре филиала. Максимум **31 день включительно**.
3. Нажмите **«Сформировать отчёт»**. В таблице для каждого дня отображаются число актуальных записей, занятые часы, число посто-часов и процент занятости. Сервер возвращает IANA `timeZone`, количество **сейчас включённых** постов и явный признак методологии.
4. Для проверки переноса/отмены обновите отчёт после изменения записи в календаре: старые исторические брони **не** считаются. Выбранная запись учитывается по **текущей** броне и только по пересечению с нужными локальными сутками.
5. Если роль отозвана, филиал выключен или чужой — `403`, таблица очищается. Период неверен или длиннее 31 суток — `422`. Сбой сети/некорректный ответ очищает таблицу и позволяет повторить запрос.

Клиент/INTAKE/WAREHOUSE без MANAGER не получает агрегаты филиала. Ни frontend, ни сервер не выводят ФИО, VIN, автомобиль, идентификатор клиента, смету, банковские данные или индивидуальное расписание работника. Гипотеза «текущая загрузка» ≠ историческая аналитика выручки.

## HTTP API и контракт

```text
GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/bay-occupancy
    ?fromDay=2030-03-31&toDay=2030-04-01

200 Cache-Control: no-store
{
  "syntheticOnly": true,
  "basis": "CURRENT_BOOKINGS_CALENDAR_DAY",
  "timeZone": "Europe/Berlin",
  "bayCount": 1,
  "items": [
    {"localDay":"2030-03-31","daySeconds":82800,
     "activeAppointments":1,"occupiedSeconds":3600,
     "calendarCapacitySeconds":82800,"occupancyBasisPoints":434}
  ]
}
```

Считается только последняя **активная** бронь каждого `auto_appointment`, в пределах пары organization/location, с текущим включённым `auto_work_bay`. Для дня с границами `[D 00:00, (D+1) 00:00)` в IANA зоне:
- `occupiedSeconds = Σ duration(intersection(booking, local day))` по каждому активному appointment. Перенос и отмена исключают старую бронь; бронь на стыке суток учитывается в двух днях только своими частями.
- `daySeconds` = реальные секунды суток, поэтому локальные DST-дни могут составлять **23 / 24 / 25 часов**.
- `calendarCapacitySeconds = daySeconds × bayCount`, где `bayCount` — количество **сейчас включённых** постов филиала (не исторический состав парка, не график работы, не часы смен). Нерабочее время входит в знаменатель. Показатель **не следует** называть процентом производственной утилизации или нормо-часами.
- `occupancyBasisPoints = floor(occupiedSeconds × 10000 / calendarCapacitySeconds)` — целое число сотых долей процента; когда нет действующих постов, `null` («Нет активных постов»), не искусственные 0%.
- `activeAppointments` — число актуальных записей, пересекающих локальный день. Одна запись может встречаться в двух днях; суммировать daily counts как уникальных клиентов нельзя.

День и даты периода канонические `YYYY-MM-DD`; 31 включительно; отсутствие правильной сессии/роли/филиала — `403 FORBIDDEN`; неправильный UUID/дата/период — `422 INVALID_INPUT`. Идентификаторы и отчёт не кэшируются; сессия и живые назначения `MANAGER` проверяются заново на **каждый** запрос. Доступ к публичному OpenAPI и реальной мультиорганизационной BI остаётся `planned`.

## Агрегированная загрузка назначений сотрудников (current-dev, #171)

В **том же** отчёте руководителя за локальные сутки теперь присутствует дополнительная группа **«Сотрудники в сменах / Часы смен / Назначения / Часы назначений / Доля назначений от смен»**. Никаких ФИО, employee UUID, смен конкретного сотрудника, зарплаты или кадровой информации API не отдаёт.

- `scheduledEmployees`: количество **различных сотрудников**, имеющих действующую неперекрывающуюся смену филиала, которая пересекает локальный день. Это число **не суммируется** как уникальные сотрудники за месяц: один человек может присутствовать в нескольких днях.
- `scheduledShiftSeconds`: сумма пересечений действующих `auto_staff_shift` c локальными сутками в IANA зоне филиала. Отменённые смены исключены; благодаря PostgreSQL exclusion constraint смены одного сотрудника не перекрываются. **Это запланированная доступность**, а не табель и не факт присутствия.
- `activeAssignments`: число действующих **назначений специалиста на актуальную бронь** `auto_appointment` в отчётных сутках. Требуется непогашенная `auto_employee_reservation` и действующая смена, покрывающая весь резерв; исторические назначения отменённых и перенесённых броней не учитываются.
- `assignedSeconds`: сумма фактических пересечений этих **плановых резервов** с локальным днём. Она не может превышать `scheduledShiftSeconds` при неперекрывающихся сменах/назначениях.
- `assignmentBasisPoints = floor(assignedSeconds × 10000 / scheduledShiftSeconds)` — сотые доли процента. При нуле действующих смен возвращается `null` («Нет действующих смен»), а не фиктивное 0%.

**Ограничения:** отчёт показывает текущие планы и доступные в момент запроса смены, а не исторические изменения расписания, соблюдение смены работником, качественный результат ремонта, учёт труда, billing, KPI/премии или payroll. Он не должен использоваться для расчёта зарплаты. При отзыве смены соответствующий резерв больше не входит в метрику действующих смен, даже если старое назначение осталось в immutable истории. Отзыв MANAGER или переход на чужой филиал остаётся fail-closed. 31 день, no-store, no PII, dev-only неизменны.

**Доказательства:** PostgreSQL `test_pg_auto_bay_occupancy_http.py`: действующая смена на 25-часовых сутках, назначение на бронь, перенос с `clear_employee`, отзыв смены, A/B изоляция и проверка отсутствия user UUID в ответе; browser `auto-bay-occupancy.spec.ts`: отображение агрегатов, невозможное превышение часов, 403/переключение филиала, мобильный 390 и 1280. API возвращает дополнительные поля только в `items[]`; сумма/финансы не добавлены, миграция не требуется. Откат безопасен: предыдущий API/UI не сохранял эти вычисляемые значения.


## Зарегистрированные факты исполнения (current-dev, #171)

Отдельно от **плановых** бронирований и смен таблица показывает три агрегата по неизменяемому журналу заказ-нарядов. `recordedLaborEntries` — число строк `auto_work_order_labor_entry`, `recordedLaborMinutes` — сумма сохранённых `actual_minutes`, `finishedExecutions` — число `auto_work_order_execution_finish`. Дата каждого значения — именно локальная дата **регистрации события** `created_at` (часовой пояс филиала), а не день бронирования или календарная дата завершения клиентом. События привязаны к `execution → work_order` и перепроверяются по organization/location; в ответе нет UUID сотрудников, клиентов, услуг, заказов или VIN. Идемпотентный повтор POST `/labor`/`/finish` не создаёт новых строк, поэтому не повышает цифры. Отмена/перенос брони не стирает ранее зарегистрированный факт.

Это **не** табель, физически отработанное время, норма труда, зарплата, бухгалтерская проводка, оплата или выпуск автомобиля. `finishedExecutions` не означает QC PASS. Ноль — отсутствие событий в этом журнале, а не утверждение об отсутствии реальной работы. Роль MANAGER, диапазон 1–31 день, read-only, no-store, проверка отзыва доступа и synthetic-only неизменны. Доказательства: PG17 тест `test_immutable_recorded_labor_and_finish_report_full_execution_lifecycle` (одобрение, начало, сохранение труда, повтор, finish, tenant и отзыв прав) и Playwright `auto-bay-occupancy.spec.ts` (три колонки, отказ от отрицательных минут, очистка старой таблицы). Никакого payroll и production до #119.


## Воронка синтетических бронирований (current-dev, #171)

Руководитель получает по каждому локальному дню **два независимых среза**, не подменяющих фактическое посещение:

**Дни регистрации событий:**
- `createdAppointments` — количество immutable событий `auto_appointment_event.action='CREATED'` по `recorded_at` в IANA зоне филиала.
- `canceledAppointments` — immutable `BOOKING_CANCELED` по `recorded_at`, только **реальная отмена**, не освобождение старого окна при переносе.
- `rescheduleEvents` — количество переходов `auto_appointment_reschedule` по `created_at`. **Повторные переносы одного appointment считаются отдельными событиями**, не новыми клиентами или записями.

**Дни начала будущих/актуальных записей:**
- `scheduledStarts` — число `auto_appointment`, чья **текущая неотменённая** бронь начинается внутри локального календарного дня и находится на действующем посту. Перенос учитывается только в новом дне; старая отменённая бронь не добавляется.
- `scheduledCustomers` — число различных синтетических `customer_id` исходных связей на таких бронированиях в пределах **данного филиала и дня**. Если один клиент имеет несколько записей, в этом счётчике он один.
- `repeatBookingCustomers` — число таких уникальных клиентов, у которых **до текущего appointment** в том же филиале был хотя бы ещё один appointment того же customer_id (включая ранее отменённые брони). Это **повторное бронирование**, не доказанный повторный визит и не показатель удержания клиентов. Порядок определяется immutable парой `(auto_appointment.created_at, id)`. Один клиент с несколькими записями считается в этом поле один раз за день.

Событийные счётчики и расписание **нельзя складывать в одну «воронку конверсии»**: первое фиксирует дату действия, второе — день актуальной брони, поэтому это разные временные срезы. Никакого события фактического приезда/отъезда, клиентского чека, совершённой оплаты или статуса «визит состоялся» здесь нет. Никакие customer UUID, vehicle IDs, VIN или ФИО не отдаются; SQL использует идентификаторы только для внутренней дедупликации. Отчёт доступен лишь scoped MANAGER, 1–31 день, no-store, synthetic-only. При переключении филиала/403 UI очищает прежние значения.

PG17 проверяет: создание двух appointments одного клиента в разных транзакциях → перенос второго → настоящую отмену первого → **ровно два создания, одно событие переноса и одну отмену** на день действий, актуальное начало только в новом дне, один уникальный и один повторно бронирующий клиент, отсутствие чужих данных; повторный перенос той же записи внутри дня не создаёт второго клиента. Playwright проверяет колонки, 390/1280, dark, неверные агрегаты и отказ доступа. [Задача #171](https://github.com/askarahodov/roboport/issues/171); production stats/CRM/real visits и #119 остаются `planned`.

## Управленческая воронка CRM: когорты обращений (current-dev, #171)

Руководитель СТО с действующей филиальной ролью `MANAGER` открывает
`/staff/auto-crm-funnel` (пункт «Воронка CRM (dev)»), вводит UUID
тестовой организации/филиала, выбирает даты **создания обращений**
в местном часовом поясе филиала и нажимает «Построить воронку CRM».
Период от 1 до 31 календарного дня. Без роли MANAGER, при другом
филиале или отзыве полномочий сервер отвечает `403`; invalid dates
или неверные UUID — `422`; при переключении организации/филиала,
смене даты, ошибочном или повреждённом ответе старые показатели
исчезают из интерфейса (fail-closed).

```text
GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/crm/funnel?fromDay=2030-03-31&toDay=2030-03-31
```

Ответ `syntheticOnly=true`,
`basis=LEAD_CREATED_COHORT_CURRENT_STAGE`, `timeZone`,
`fromDay`, `toDay`, `summary`, `items` в порядке
`WEB / PHONE / WALK_IN`. Каждый агрегат содержит `sourceCode`,
`total`, `new`, `qualified`, `booked`, `lost`,
`bookedBasisPoints` (целая сотая доля процента, диапазон
0–10000, `null` при нуле обращений) и `lossReasons`
(`PRICE/TIMING/NO_RESPONSE/OTHER`). Общий `summary` имеет
`sourceCode=ALL`; сумма по источникам и этапам равна итогу,
причины отказа в сумме равны `lost`. UI проверяет эти равенства
перед отображением.

**Полная выгрузка CSV (current-dev).** После построения отчёта на
`/staff/auto-crm-funnel` нажмите **«Скачать воронку CRM в CSV»**.
Отдельный read-only endpoint

```text
GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/crm/funnel/export?fromDay=2030-03-31&toDay=2030-03-31
```

повторно проверяет сессию, MANAGER grant, филиал и действующие
подтверждения связи, независимо от ранее открытой страницы.
Файл UTF-8 с BOM и разделителем `;` содержит **все** строки:
«Все источники», «Сайт», «Звонок», «Личное обращение»,
текущие NEW/QUALIFIED/BOOKED/LOST, долю BOOKED в базисных
пунктах и четыре причины отказа. При пустой когорте доля
записанных остаётся пустой ячейкой, не 0%. Личные идентификаторы,
свободный текст и формулы в CSV отсутствуют.
При `403` и `422` скачивание не начинается, старые показатели
в интерфейсе очищаются. `Cache-Control:no-store`,
`X-Content-Type-Options:nosniff`; в CSV только фиксированные
названия агрегатов и числа. Это **новый живой SQL-срез**,
поэтому текущая стадия и число лидов могут измениться со времени
просмотра таблицы. Ни запись клиента, ни его согласие на коммуникации,
ни реальная выручка этим экспортом не подтверждаются.

**Словарь метрик и интерпретация:**

- **Когорта** — обращения, immutable `auto_crm_lead.created_at`
  которых попадает в включительный диапазон **локальных** дат
  филиала, пересчитанный через IANA timezone в UTC полуинтервал.
  Сутки на переводе часов могут длиться 23 или 25 часов.
- **Статус** — **последняя** запись `auto_crm_lead_stage` по
  `(created_at DESC,id DESC)` **на момент чтения**, либо `NEW`
  без событий. Это **не исторический снимок** этапа на дату
  создания и не лог событий. Переход `QUALIFIED→BOOKED`
  учитывается единожды как BOOKED, повторное чтение не дублирует
  контакт или сделку.
- **Источники** — `WEB` (сайт), `PHONE` (звонок как код
  источника, **не** реальный звонок), `WALK_IN` (личное
  обращение как код). Все три отображаются даже при нуле;
  источники не используются для определения юридического согласия.
- **Доля записанных** = `floor(booked × 10000 / total)`,
  выражена в сотых долях процента, а `null` означает
  **неопределённую долю при пустой базе**, не 0%.
  **Это не конверсия в фактический визит, продажу или оплату.**
- **Отказы** — текущий этап `LOST` и его последняя
  неизменяемая причина. Не считаются все предыдущие стадии.

Показатели отражают только **действующие, подтверждённые**
связи клиент–автомобиль и включённые организацию/филиал.
Отзыв proof или отключение филиала исключает обращение при
следующем чтении; в ответе нет ID лида, клиента, владельца,
автомобиля, бронирования, VIN, имени, телефона, денег, индивидуальных
сотрудников и сырых записей аудита. Сервер проверяет
session+tenant+location MANAGER до SQL, применяет live proof
**до GROUP BY**, выполняет один агрегирующий SQL-запрос с единым
MVCC snapshot и возвращает `Cache-Control:no-store`.
Это read-only отчёт: не меняет воронку и не отправляет коммуникации.

## Операционный ABC/XYZ выдач склада (current-dev, #171)

**Назначение:** руководитель филиала с действующей ролью
`MANAGER` открывает `/staff/auto-stock-abc-xyz`
(«ABC/XYZ склада (dev)»), вводит синтетические UUID организации
и филиала, выбирает **от 3 до 12 полностью завершённых**
календарных месяцев и нажимает «Построить ABC/XYZ».
Экран показывает весь ассортимент филиала **по 25 SKU на
страницу**, с кнопками «Следующая страница» и
«Предыдущая страница». Смена scope/периода немедленно
очищает прежние результаты; при `403`, `409`, `422`,
`5xx` или повреждённом JSON старые значения не сохраняются.

```text
GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/stock-abc-xyz?fromMonth=2026-07&toMonth=2026-09&offset=0
```

Ответ: `syntheticOnly=true`,
`basis=GROSS_ISSUE_UNITS_CLOSED_MONTHS`,
`moneyValuation=false`, `timeZone`, `fromMonth`,
`toMonth`, `months[]`, `pageSize=25`, `offset`,
`nextOffset`, `summary`, `items[]`.
В `summary` входят `skuCount` (все товары филиала),
`activeSkus` (с реальными выдачами), `grossIssued`,
`grossReturned`, `netPeriod=grossIssued-grossReturned`
и `classCounts` A/B/C/X/Y/Z/none. У каждого SKU:
`skuId`, `article`, валовые выдачи и возвраты,
разница за период, `monthlyIssued[]`, `abc`, `xyz`
и `variationBasisPoints`.

**Методика (точные правила и границы):**

1. Время событий неизменяемого `auto_stock_event.created_at`
   преобразуется в локальную зону филиала (IANA). Для
   заданного диапазона учитываются **только** действия `ISSUE`
   и `RETURN`. Нельзя путать `RECEIPT`, `RESERVE`,
   `RELEASE`, инвентаризационные разницы или перемещения
   с фактической выдачей. Валовые выдачи `ISSUE`
   используются для классификации; `RETURN` показаны
   отдельно, чтобы возврат прошлого месяца не создавал
   «отрицательное потребление» в XYZ. Поэтому
   `netPeriod` может быть отрицательным.
2. **ABC — ранжирование по объёму выданных единиц**
   (НЕ по рублёвой себестоимости или выручке).
   Товары сортируются по `grossIssued DESC,article ASC,skuId ASC`.
   Класс определяется **накопленной долей ДО текущей строки**:
   A — менее 80% общего объёма, B — от 80% до менее 95%,
   C — начиная с 95%. Такой способ относит крупнейшую
   позицию к A даже если она одна занимает более 80%.
   SKU с `grossIssued=0` не получает ABC.
3. **XYZ — регулярность месячных выдач** в 3–12 полностью
   завершённых месяцах, включая месяцы с нулём выдач.
   `CV = sqrt(N × Σ(q_i²) − (Σq_i)²) / Σq_i`, где
   `q_i` — валовая выдача одного SKU за локальный
   календарный месяц. X при CV ≤ 10%, Y при
   10% (исключая) – 25% (включая), Z выше 25%.
   Для нулевой серии XYZ и CV отсутствуют (`null`),
   а не показываются как 0%. Для границ классов
   сравниваются **точные целые величины** без float
   (CV² относительно 1/100 и 1/16), CV выводится
   в целых сотых процента через округление вниз.
4. Суммы выдач и возвратов по всем SKU рассчитаны по
   одному текущему SQL-срезу PostgreSQL 17. Переход
   между страницами перечитывает действующую роль
   `MANAGER`, организацию и филиал. Страницы могут
   измениться при корректировке архивного синтетического
   журнала владельцем БД; это живой отчёт, не freeze snapshot.
   При более **10 000 SKU** запрос возвращает явный
   `409 REPORT_LIMIT`, а не тихо обрезает итог. До тяжёлого
   JOIN с журналом событий выполняется ограниченная проверка
   только идентификаторов SKU своего филиала (не более 10 001 строки).
   Дополнительная защитная проверка остаётся после агрегации на
   случай конкурентного добавления SKU между SQL-срезами.
   Это не обещание производительности на больших объёмах без замеров.

**Выгрузка всей ведомости CSV (current-dev).** На странице
`/staff/auto-stock-abc-xyz` после построения отчёта выберите
**«Скачать весь отчёт CSV»**. Сервер повторно проверит действующую
роль MANAGER филиала и те же завершённые месяцы, рассчитает
**все** позиции до 10 000 SKU, а не только текущие 25 строк.
Файл UTF-8 с BOM, разделителем `;`, русскими заголовками,
месячными количествами и UUID SKU без персональных данных.
Для безопасности формулы в артикулах обезврежены как текст.
`403` очищает экран, `409` не выдаёт частичный файл,
`422` означает неверный период. Выгрузка — **новый живой
SQL-срез**, поэтому при изменении исходных складских событий
между просмотром и скачиванием значения могут различаться.
Эта операция не включает цены и не разрешает финансовые решения.

**Обязательное предупреждение:** исходная карточка
`auto_stock_sku` не содержит нормализованной единицы
измерения, а выданные количества разных SKU нельзя
считать финансово сопоставимыми. Классы A/B/C здесь
**только операционное ранжирование штук**, не
стоимостной ABC и не основание для закупки,
прогноза, расчёта себестоимости или зарплаты.
Узкая готовая операция не заменяет финансовый
ABC/XYZ, доходы и payroll всего #171. Возвраты
не проверяют поступление платежей. Производственные
данные и финансовые решения закрыты до #119.

**Безопасность:** endpoint private dev, исключительно
read-only, `Cache-Control:no-store`, проверка live
`MANAGER` филиала, активных org/location до чтения
складской агрегации. Нет клиентов, VIN, телефонных
номеров, работников, заказ-нарядов, цен и валюты.
Неверные `fromMonth/toMonth` (текущий месяц,
незавершённый месяц, менее 3 или более 12 месяцев),
чужой scope или некратный 25 `offset` получают
`422`/`403` соответственно.

**Доказательства:** PG17
`tests/integration/test_pg_auto_stock_abc_xyz_http.py`
создаёт 29 SKU и синтетические неизменяемые
`ISSUE/RETURN` по трём завершённым месяцам,
проверяет ABC A/B/C и XYZ X/Y/Z, отдельные возвраты,
точные пороги, все страницы без дубликатов, 403
при отзыве MANAGER, 422, foreign branch, 409 без
silent truncation; Playwright

сброс при смене филиала. Без миграции и новых

## Выработка механиков: трассируемые записи труда по техническому закрытию (current-dev, #448)

**Готовый синтетический сценарий:** `/staff/auto-mechanic-productivity`, только MANAGER организации и своего филиала с HANDOVER READ; период 1–31 **локальный день события CLOSED_TECHNICAL**, а не день исполнения/создания/завершения WorkOrder. Если механик закончил 26 октября, а менеджер закрыл заказ 27 октября, 45 минут попадают только в 27 октября. Каждый отчёт читается из реальных immutable PostgreSQL 17 событий `auto_order_demo_document_event(CLOSED_TECHNICAL/POSTED/CLIENT_ACK)`, `auto_work_order_execution_finish`, последнего `auto_work_order_qc_event(PASS)` и `auto_work_order_labor_entry`. QC PASS должен быть после finish, но не позже закрытия. Пока документ только POSTED или подтверждён клиентом, без CLOSED_TECHNICAL, его труд в отчёт не попадает.

**Как сверить:** у каждого механика/заказа есть `closedDay`, `closedEventId`, `finishEventId`, `qcEventId` и массив `laborEntries` с `laborEntryId`, `serviceId`, `actualMinutes`; `serviceCount` равен длине массива, `actualMinutes` — сумме записей. Один immutable labor-entry UUID должен присутствовать ровно один раз в одном отчёте. В UI раскройте «Первичные записи труда» рядом с заказом: отобразятся UUID закрытия, завершения, QC PASS, работ и их минуты. В CSV используются отдельные уровни ORDER (один итог по заказу и механику) и LABOR (каждая первичная запись труда). Суммировать оба уровня вместе **нельзя**. UTF-8 BOM, `;`, 12 колонок, только UUID, числовые значения, ISO day и фиксированные словарные статусы; не выводятся ФИО, VIN, телефон, контрагенты, цены или формулы Excel. CSV запрашивает новый snapshot и повторно проверяет ACL.

**Права и согласованность:** один REPEATABLE READ SQL snapshot с живыми MANAGER/HANDOVER:READ и cutoff по времени создания WorkOrder, активными ролями MECHANIC и staff, verified+unrevoked vehicle ownership и филиальной binding. Действующие grant/owner proof/binding/staff блокируются FOR SHARE; одновременный отзыв прав у старого MVCC-снимка вызывает 40001 → 409, а не подтверждение прежнего состояния. Отозванный механик **исключается** из повторного отчёта: это текущая аналитика действующих исполнителей, а не замороженный payroll-регистр. Отзыв MANAGER или DENY → 403. До 500 labor source rows за один запрос, больше → 409 `REPORT_LIMIT` без частичных сумм/CSV; конкурентный отзыв или конфликт транзакции (SQLSTATE 40001/40P01) → отдельный 409 `REPORT_CONFLICT` без частичных данных, с возможностью повторного чтения после стабилизации прав; неверный период → 422. Смена филиала, 403/409 и повреждённый JSON очищают прежние результаты браузера.

**Точный контракт:** `GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/reports/mechanic-productivity?fromDay=YYYY-MM-DD&toDay=YYYY-MM-DD` и `/export`, basis `CLOSED_TECHNICAL_LOCAL_DAY_QC_PASS_LABOR_SOURCES`, `periodBasis=CLOSED_TECHNICAL_LOCAL_DAY`; `syntheticOnly=true, realMoney=false, payrollAvailable=false, releaseAllowed=false, activeMechanicsOnly=true`. Границы 23/24/25-часовых локальных суток IANA независимо преобразуются в UTC; дата закрытия всегда пересчитывается в TZ филиала. Нет новых DDL или миграций; откат — общий revert read-only API/UI/tests/docs без удаления событий.

**Доказательства:** `tests/integration/test_pg_auto_mechanic_productivity_http.py` — полный акт/смета/работы/QC/posted/client ack/technical close, 0 до CLOSE, source UUIDs через SQL→JSON→CSV, отзыв/403, 409/422, чужой scope, DST; `apps/web/e2e/auto-mechanic-productivity.spec.ts` — 390/1280, Light/Dark, клавиатура, подробный drill-down, повреждение ID/minutes/day, 403/409 и очистка. ## Аудит первички материалов на заказ-наряды (current-dev, #448)

## Оценка расхода материалов технически закрытых заказов (#448, current-dev)

На `/staff/auto-demo-finance-report` выберите организацию, филиал и 1–31 локальный день закрытия, нажмите «Проверить расход материалов». Отчёт отбирает тот же набор подтверждённых `CLOSED_TECHNICAL` заказов, что реестр выше, но суммирует **все** зарегистрированные ISSUE/RETURN по их жизненному циклу, не только складские события периода. Для каждого движения проверяется связь stock_event ↔ work_order_stock_event ↔ lot issue/return ↔ allocation. Сведения чужих филиалов и отозванной связи владельца не выдаются. SKU и партии не суммируются в общие штуки.

Методика **оценки расхода без НДС по документированным приходам**, не бухгалтерский COGS:
- TRACED: вся текущая неизменяемая история распределений партии имеет ровно по одному валидному источнику на каждой записи (принятая приёмка, парная выдача или возврат на заказ); существует ровно один принятый приход; оценка в RUB зарегистрирована строго после принятого прихода и до первой выдачи партии по монотонному `cost_registration_seq` (не `now()`). Стоимость = (выдано − возвращено) × цена единицы без НДС из этой оценки. Источники — UUID прихода, приёмки, оценки, связанных складских и партионных событий. Повтор запроса с тем же ключом не удваивает расход.
- FIFO_TRACED: если в одной несерийной партии несколько независимых принятых приходов, вся история `cost_registration_seq` воспроизводится от начала по возрастанию (не по времени транзакции или UUID). Каждый приход создаёт слой количества и зарегистрированной стоимости RUB без НДС; выдача выбирает доступные слои от самого раннего, возврат сторнирует последние ещё не возвращённые части выдач **того же заказа и партии** в обратном порядке и восстанавливает исходный слой с прежним приоритетом. Стоимость = сумма количеств × цен выдач минус соответствующие суммы возвратов. Это явная условная методика FIFO/LIFO возвратов, не утверждённый бухгалтерский метод и не физическая идентификация отдельных деталей. Например, 3 шт. × 1250 коп. + 2 шт. × 2000 коп. − возврат 1 шт. × 2000 коп. = 5750 коп. `fifoSlices` хранит каждую часть движения, UUID складского события, партионного движения, оригинальной выдачи, прихода, приёмки, оценки, количество и цену. `source=null` для FIFO, а стоимость объясняется всеми slices. Одновременно перепроверяются количества событий и итог. Разные заказы не могут сторнировать выдачи друг друга.
- UNPROVEN: недоказанная история (ручное распределение, перемещение/инвентаризация без полного доказательства, несколько приходов серийной партии без точной связи serial→приход, старый NULL sequence), либо несогласованное количество. Серийный номер не подменяется условным FIFO; единственный подтверждённый приход с одной ценой по-прежнему допустим.
- UNVALUED / LATE_VALUATION / OTHER_CURRENCY: отсутствует оценка, она зарегистрирована после использовавшей этот слой выдачи или имеет валюту не RUB. Для нескольких приходов неизвестный источник делает оценку всей партии неопределённой.
- UNPAIRED: в журнале WorkOrder есть ISSUE/RETURN без согласованного партионного движения. Запись не скрывается и не оценивается.
- COMPLETE: все группы TRACED/FIFO_TRACED или зарегистрированных материальных движений нет (тогда именно зарегистрированный расход равен 0). INCOMPLETE: хотя бы одна группа не подтверждена; итог заказа и итог филиального периода — null, а не 0 и не сумма только известных групп. Это контроль покрытия, не прибыль.

## Внутренний расчёт прямых затрат закрытых заказов (#448, current-dev)

На `/staff/auto-demo-finance-report` руководитель задаёт организацию, филиал, 1–31 локальный день закрытия. «Прочитать внутренние ставки» → новый внутренний расчётный тариф в копейках RUB/час (0…10^10, целые) → «Предложить внутреннюю ставку» → другой действующий MANAGER этого филиала утверждает версию. Ставка едина для филиала, **не тариф продажи, не персональный заработок, не ФОТ, не удержания**. До утверждения новая версия не действует; следующий revision только после утверждения предыдущего. Идемпотентный повтор сохраняет исходный requestKey и не создаёт вторую запись; конкурентное предложение одной версии имеет одного победителя. Запрещено самоутверждение; SQL независимо проверяет живую роль и филиал. UI показывает историю и активную версию, но не содержит персональных зарплат.

Миграция `0130_auto_internal_labor_cost` добавляет append-only revision/approval, FK `auto_work_order_labor_entry.internal_cost_approval_id`, `internal_cost_registered_at` и branch epoch. При регистрации труда под общей блокировкой филиала серверный SQL-триггер закрепляет последнюю утверждённую ставку; изменение branch epoch при утверждении исключает stale RR. История immutable, новый revision не перепривязывает старые записи. Старые записи и труд без действующей ставки остаются без оценки, backfill запрещён. Утверждение ставки после записанного труда не оценивает его задним числом.

«Рассчитать внутренние затраты» читает один PostgreSQL REPEATABLE READ snapshot всех источников: технически закрытые наряды, запечатанная смета, сверка условных оплат/возвратов, история материалов по 0129, записи труда и закреплённые approvals. Дата отчёта — CLOSED_TECHNICAL, не дата выдачи или завершения услуги. Условная стоимость каждой записи труда = `(actualMinutes × rateMinorPerHour + 30) // 60` (целочисленное half-up в копейках), затем сумма строк. При отозванной роли механика/неактивной учётной записи строка не исчезает: INACTIVE_MECHANIC и null. Действующие допуски механиков, исходная связь владельца и привязка автомобиля к филиалу блокируются FOR SHARE, поэтому конкурентный отзыв со старым RR-снимком приводит к 409, а не выдаче прежних затрат. при отсутствии ставки NO_APPROVED_RATE и null. Нет идентификатора механика или клиента в денежном отчёте. Для материалов применяется предыдущая методика (без НДС, TRACED или FIFO_TRACED с детализацией slices). Если любая группа материалов или запись труда не доказана, итог прямых затрат/условная разница заказа и периода null. Нулевой зарегистрированный расход материалов допустим; пропущенный труд не заменяется нулём.

**Условная разница = утверждённая сумма заказа − оценка материалов − внутренний расчётный труд.** Может быть отрицательной. Это демонстрационная управленческая оценка, не gross margin, EBITDA, бухгалтерская прибыль или оплата сотрудника. Не учитывает налоговую базу, накладные расходы, реальную себестоимость/персональные ставки/удержания. `syntheticOnly=true, realMoney=false, payrollAvailable=false, marginAvailable=false, releaseAllowed=false`.

### Источник серийной детали из принятого прихода (0131, current-dev)

### Межфилиальная себестоимость подтверждённой серийной детали (current-dev, #448)

При наличии серийной детали, перенесённой из одного филиала в другой через реальный `auto_stock_interbranch_transfer`, отчёт проверяет **полную историю этой серии** (даже до и после выбранного периода), а не присваивает входящему TRANSFER_IN нулевую/новую цену. Источник — независимое подтверждение `serial-receipt-provenance` и принятый закупочный документ **исходного** филиала. Необходимы: подтверждение до первого движения, оцениваемая RUB-цена до первой выдачи/перемещения, 1:1 физическое количественное событие ↔ serial movement, точная пара дебет/кредит transfer, непрерывная цепочка source/destination lot, исходная цена при возврате и последующей выдаче. Партии с незарегистрированными перемещениями, чужой организацией, историческим NULL-sequence, неутверждённой ценой или неподтверждённым серийным источником остаются `UNPROVEN` / `UNVALUED` / `LATE_VALUATION` / `OTHER_CURRENCY`; никаких догадок из текущего остатка.

**Разграничение доступа:** кроме всех действующих прав руководителя для отчёта филиала-получателя требуется актуальная роль MANAGER филиала-источника, SUPPLIER_ORDER READ/PRICE_PURCHASE и FINANCE PRICE_PURCHASE там же. Любой DENY/cutoff, отзыв роли или 40001 при конкурентном изменении приводит к отказу всего отчёта (403/409); ни части закупочных цен, ни частичного агрегата не возвращается. В `fifoSlices` для SERIAL_TRACED дополнительный UUID `sourceLocationId`; для старой подтверждённой локальной серийной первички поле может отсутствовать. В обоих CSV добавлена финальная колонка «Филиал-источник UUID» (материалы — 23 поля, прямые затраты — 30); пустое поле для локального FIFO и прежних источников. ФИО, исходный текст документа, серийные номера, VIN и персональные начисления не выдаются. Само бухгалтерское основание исходной закупки не подтверждено, это synthetic current-dev, не законный COGS, валовая прибыль или payroll. ## Сверка действующих смен и технически закрытого труда (#448; current-dev)

**Задача пользователя:** руководитель филиала открывает `/staff/auto-mechanic-shifts`,
указывает UUID своей **синтетической** организации/филиала и период
от 1 до 31 локального дня, нажимает «Сопоставить смены и труд».
Результат показывает каждого действующего механика, у которого
за период есть активная смена **или** проверенные трудозатраты
по закрытым заказ-нарядам, включая работников с нулём закрытых работ.
Есть таблица, источник каждого расписания (UUID и временные границы)
и повторно авторизуемый CSV «Скачать сверку CSV».

**Источник правды:** `auto_staff_shift` (canceled_at IS NULL,
пересечение по UTC с локальным диапазоном филиала; 23/25-часовые дни
обрабатываются IANA TZ) + `app_user.ACTIVE` и живой MECHANIC grant.
Отчёт по фактическим минутам повторно использует **тот же**
`mechanic_productivity` по неизменяемым labor/finish/QC PASS/
`CLOSED_TECHNICAL` источникам с подтверждённым владельцем.
Все данные читаются **одним PostgreSQL REPEATABLE READ снимком**.
`shiftId`, `startsAt`, `endsAt`, `overlapSeconds` являются
ссылками для проверки расписания, а не персональными/платёжными данными.

**Разные основания периода:** смена учитывается по
*пересечению активного расписания* с периодом, а труд — по **локальному
дню события технического закрытия**, не моменту выполнения работ.
`recordedToScheduledBasisPoints` =
`round_half_up(recordedMinutes × 60 × 10_000 / scheduledSeconds)`,
может превышать 10 000 и **не является KPI производительности,
фактом присутствия, табелем, зарплатой, рентабельностью или выручкой**.
При нулевой смене отношение `null` и статус `NO_ACTIVE_SHIFT`,
при смене без закрытого труда — `NO_CLOSED_LABOR`.
Нельзя оплачивать работу по этому числу или выводить из него оплату.

**Контракт (private dev):**
`GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/reports/mechanic-productivity/shift-comparison?fromDay=YYYY-MM-DD&toDay=YYYY-MM-DD`
и `/shift-comparison/export` с теми же параметрами. Ответ включает
существующую проверяемую структуру отчёта о выработке и
`shiftComparison` с `basis=ACTIVE_SHIFTS_VS_CLOSED_TECHNICAL_LABOR`,

## Единый мост «закрытый ЗН → SIM-расчёт → прямые затраты» (#448, current-dev)

**Сценарий руководителя:** `/staff/auto-closed-contribution` →
UUID синтетической организации/филиала → даты закрытия 1–31 день
локального календаря → **«Сверить закрытые заказ-наряды»**.
Экран показывает доказанные технически закрытые `CLOSED_TECHNICAL`
заказы с независимым QC PASS, непротиворечивой `POSTED` /
`CLIENT_ACK` версией, точной ревизией согласованной сметы
и условными `SIM_PAYMENT/SIM_REFUND` из **того же закрытого
снимка**. Каждая строка может быть раскрыта до UUID закрывающего
события, оценки партии/склада, операции ISSUE/RETURN, записи
рабочего времени, подписанной (в dev смысле: независимо
одобренной) расчётной внутренней ставки и каждого условного
денежного события.

**Первичный источник и единый снимок:**
`auto_closed_contribution.report` вызывает
`auto_internal_order_costs.cost_report(include_base=True)`.
Это возвращает **одним PostgreSQL REPEATABLE READ чтением**
уже верифицированные расходы и приватную сверку закрытия
`auto_closed_order_report.report` без второго подключения или
новой транзакции. Сохраняются существующие ограничения
MANAGER филиала, FINANCE READ / PRICE_SALES / PRICE_PURCHASE,
ESTIMATE / HANDOVER, SUPPLIER_ORDER READ / PRICE_PURCHASE,
живые owner-link и сессия/роль, отсутствие history cutoff.
Сервер повторно связывает одинаковые `workOrderId`,
`closedEventId`, `previewId`, `previewDigest` и
`approvedTotalMinor`, проверяет точные суммы каждой
`SIM_PAYMENT`/`SIM_REFUND`, не допускает повторов UUID
платежей, записей труда и складских событий.

**Формула, не являющаяся бухгалтерской прибылью:**
`simulatedNetMinor=simulatedPaidMinor-simulatedRefundedMinor`
равно согласованной сумме для технически закрытого ЗН.
`directCostMinor=materialNetMinor+laborCostMinor`;
`syntheticDifferenceMinor=approvedTotalMinor-directCostMinor`,
включая **отрицательные** результаты.
Если нет доказательства стоимости хотя бы одного материала,
живого механика или заранее одобренной ставки труда —
`status=INCOMPLETE`, `directCostMinor=null`,
`syntheticDifferenceMinor=null`.
Любой INCOMPLETE в день делает *весь дневной и периодный*
итог затрат/разницы `null`, а не частичной «прибылью».
Согласованный объём и подтверждённые SIM-платежи показываются
отдельно. `marginAvailable=false`, `payrollAvailable=false`,
`realMoney=false`, `releaseAllowed=false` всегда.
Сюда **не** включаются движения третьего независимого
`auto_treasury_event` (#445), безвалютный `CHARGE/CREDIT`,
реальные платежи, НДС, overhead, фискальные документы или
начисление зарплаты. Утверждение внутренней ставки — не
юридическая подпись и не договор с работником.

**Контракт (private dev HTTPS):**
`GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/reports/closed-contribution?fromDay=YYYY-MM-DD&toDay=YYYY-MM-DD`
и `.../closed-contribution/export` с теми же параметрами.
`basis=CLOSED_TECHNICAL_QC_POSTED_SIM_SETTLEMENT_AND_PROVEN_DIRECT_COSTS`.
Ответ: `summary`, `days`, `items`; строка содержит
все immutable UUID источников с фиксированными суммами в копейках,
без ФИО, VIN, свободного текста и данных банковских счетов.
CSV — UTF-8 BOM, 16 фиксированных полей, уровни `DAY/ORDER/
SIM_CASH/LABOR/STOCK`, повторно читает PostgreSQL и
авторизует сессию перед выгрузкой, размер не более 1 MiB.
Сложение `closing` остатков по дням не производится.
Неверная дата/UUID → 422, отсутствие права/чужой tenant/
отозванная роль/history cutoff → 403, конфликт снимка/
неподтверждённая первичка/лимит источников → 409
**без частичного отчёта или CSV**.
UI стирает предыдущие результаты и при неудавшейся загрузке,
и при ошибке повторной авторизации CSV.

**Проверки:** `tests/integration/test_pg_auto_closed_contribution_http.py`
(настоящая PG17 последовательность сметы → акт/проведение →
QC/закрытие → SIM оплата → подтверждённый приход/склад →
нормо-записи труда; точный отрицательный результат, CSV,
отзыв FINANCE, отсутствие ставки/стоимости, чужой филиал,
невалидный период, 409) и
`apps/web/e2e/auto-closed-contribution.spec.ts`
(390/1280, Light/Dark, keyboard, доказательства UUID,
неопределённый итог, отказ CSV 403/409, повреждённые данные).
Публикуемые скриншоты только candidate, не manual
design/financial signoff #92/#76.

**Откат:** revert нового read-only private API/UI/tests/docs
и вспомогательного приватного `include_base` возвращаемого
значения расчёта внутренних затрат; **без** Alembic,
новых таблиц, изменения существующих immutable событий
или контрактов старых отчётов. Выпуск в production,
реальная прибыль и payroll остаются закрытыми до #119
и полного исходного scope #448.

**Разведение сумм CSV:** уровень `MATERIAL_GROUP` записывает
подтверждённый `materialNetMinor` **один раз на группу SKU/лот**,
с UUID лота (либо SKU), итоговым количеством и UUID valuation
при наличии. Уровни `STOCK` отдельно содержат UUID события,
направление `ISSUE/RETURN` и физическое количество, но
**пустую стоимость**. Это не даёт повторно учесть нетто-стоимость
для каждого движения, особенно при частичном возврате. CSV
никогда не назначает выдуманную unit cost отдельному ISSUE/RETURN;
точное распределение по FIFO/serial-срезам остаётся в проверяемом
source/provenance отчёте. PG17 регрессия проверяет
`ISSUE 2` + `RETURN 1`: один net group 100 коп.,
две отдельные строки источника без monetary amount.

**Нулевой согласованный заказ:** независимая техническая
процедура допускает цену `approvedTotalMinor=0` и
`simulatedPaidMinor=simulatedRefundedMinor=0` без
искусственно созданного `SIM_PAYMENT`. Тогда
`cashEvents=[]` — **валидная доказанная нулевая
сверка**, а не ошибка 409; неизвестные затраты на
материалы/труд по-прежнему дают `INCOMPLETE` и `null`.
При ненулевой согласованной сумме отсутствие событий
оплаты остаётся отказом 409. Этот случай отдельно проверен
композиционным тестом и Playwright UI, без изменения исходных
immutable событий/таблиц.

## Единая проверка закрытого ЗН: две независимые модели оплаты и прямые затраты (#448)

**Статус: current-dev, только synthetic PostgreSQL 17, без реальной оплаты,
прибыльности, фискализации или выдачи.** Руководитель открывает
`/staff/auto-closed-order-ledgers`, указывает UUID своей организации
и филиала и даты 1–31 календарный день **по локальной дате именно
технического закрытия**, нажимает «Сверить закрытые ЗН и два реестра».
В одном отчёте по каждому заказ-наряду видны:
- утверждённая клиентом сумма из неизменяемого CLOSE preview,
  постановка `POSTED`, подтверждение `CLIENT_ACK`, независимый
  `QC PASS` и `CLOSED_TECHNICAL` с точным digest/UUID;
- прямые **условные** материальные затраты, подтверждённые
  receipt/lot/FIFO/serial provenance, и трудозатраты только по
  независимой утверждённой ставке до завершения труда. При
  пропущенной первичке стоимость и разница `null`, **никогда 0**;
- два **разных, не складываемых** журнала:
  `auto_order_demo_cash_event` (`SIM_PAYMENT/SIM_REFUND`,
  нужен для технического закрытия) и
  `auto_treasury_event` (условный `ADVANCE/PAYMENT/REFUND_*`,
  `APPLY_ADVANCE`). Сводка отдельно показывает имитацию расчёта,
  признанное в тестовой кассе `settled`, незачтённый аванс,
  `treasuryDue = approvedTotal - settled`, `cashNet` и
  `demoMinusTreasury = demoNet - settled`.
  Важный пример: `CLOSED_TECHNICAL` с `SIM_PAYMENT=2500`
  и **без событий новой кассы** → `demoNet=2500`,
  `treasurySettled=0`, `treasuryDue=2500`, статус
  `NO_TREASURY_EVENTS`, никакого доказательства фактического платежа.
  При `ADVANCE=900` без зачёта `cashNet=900`,
  `unappliedAdvance=900`, `settled=0`, `due=2500`.
  При полном условном расчёте статус `SETTLED`, но это
  **не реальная касса и не подтверждение юридической выдачи**.
  `syntheticDifference = approvedTotal - directCost` не является
  валовой прибылью, бухгалтерской маржой, KPI или payroll.

### Первичка FIFO/serial при нескольких закупках одной партии

Для `FIFO_TRACED` и `SERIAL_TRACED` отсутствие одиночного
`materialGroup.source` **не означает** отсутствие доказанной оценки:
стоимость уже подтверждена несколькими отдельными
`fifoSlices`. Новый отчёт передаёт каждый исходный срез с
UUID документа прихода, независимой приёмки, оценки, складского
события и движения партии, ссылкой на исходную выдачу; для
серийной детали — UUID serial/approval/source location.
Сервер сверяет сумму `quantity × unitNetMinor` с учётом
`ISSUE/RETURN` против подтверждённой стоимости группы.
Сквозной CSV теперь содержит **36 фиксированных колонок**:
отдельные строки `FIFO_SLICE` с этими UUID/количествами,
не только агрегаты `MATERIAL_SOURCE`. Реальная PostgreSQL
регрессия `test_fifo_and_serial_primary_receipts_remain_traceable_in_report_and_csv`
охватывает обе модели. Эти поля лишь доказывают synthetic
provenance, не создают юридически принятую себестоимость.


### Согласованность повторного расчёта и CSV (#171)

Новый расчёт и переход на другую страницу ABC/XYZ отменяют незавершённый CSV предыдущего поколения отчёта, включая тот же филиал и период. Ответ старого экспорта не может запустить скачивание или заменить более свежий результат проверки полномочий. При изменении UUID/периода оба запроса отменяются. Сам сервер независимо проверяет действующую роль для каждого JSON/CSV запроса; отмена браузером не отзывает уже скачанный файл. Playwright проверяет оба порядка: поздний CSV 200 после нового 403 и поздний CSV 403 после нового 200. Это synthetic current-dev, не финансовая оценка и не release gate.
