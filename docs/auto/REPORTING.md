# Загрузка постов: текущие бронирования по дням (#171)

> **Статус: current-dev, только synthetic PostgreSQL 17 + закрытый HTTPS loopback.**
> Не production BI, не регламентные нормо-часы, не расчёт зарплат, выручки, прибыли,
> фактически отработанных часов, SLA или финансовых документов. Без PII/VIN.

## Руководителю: воспроизводимый рабочий сценарий

1. Войдите в тестовый стенд с действующей сессионной ролью `MANAGER` нужной организации и филиала. Откройте **«Загрузка постов (dev)»** (`/staff/auto-bay-occupancy`).
2. Укажите UUID **своей** организации, UUID филиала и начало/конец периода как даты в локальном календаре филиала. Максимум **31 день включительно**.
3. Нажмите **«Сформировать отчёт»**. В таблице для каждого дня отображаются число актуальных записей, занятые часы, число посто-часов и процент занятости. Сервер возвращает IANA `timeZone`, количество **сейчас включённых** постов и явный признак методологии.
4. Для проверки переноса/отмены обновите отчёт после изменения записи в календаре: старые исторические брони **не** считаются. Выбранная запись учитывается по **текущей** броне и только по пересечению с нужными локальными сутками.
5. Если роль отозвана, филиал выключен или чужой — `403`, таблица очищается. Период неверен или длиннее 31 суток — `422`. Сбой сети/некорректный ответ очищает таблицу и позволяет повторить запрос.

Клиент/INTAKE/WAREHOUSE без MANAGER не получает агрегаты филиала. Ни frontend, ни сервер не выводят ФИО, VIN, автомобиль, идентификатор клиента, смету, банковские данные или индивидуальное расписание работника. Гипотеза «текущая загрузка» ≠ историческая аналитика выручки.

## HTTP API и контракт

```text
GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/bay-occupancy
    ?fromDay=2030-03-31&toDay=2030-04-01

200 Cache-Control: no-store
{
  "syntheticOnly": true,
  "basis": "CURRENT_BOOKINGS_CALENDAR_DAY",
  "timeZone": "Europe/Berlin",
  "bayCount": 1,
  "items": [
    {"localDay":"2030-03-31","daySeconds":82800,
     "activeAppointments":1,"occupiedSeconds":3600,
     "calendarCapacitySeconds":82800,"occupancyBasisPoints":434}
  ]
}
```

Считается только последняя **активная** бронь каждого `auto_appointment`, в пределах пары organization/location, с текущим включённым `auto_work_bay`. Для дня с границами `[D 00:00, (D+1) 00:00)` в IANA зоне:
- `occupiedSeconds = Σ duration(intersection(booking, local day))` по каждому активному appointment. Перенос и отмена исключают старую бронь; бронь на стыке суток учитывается в двух днях только своими частями.
- `daySeconds` = реальные секунды суток, поэтому локальные DST-дни могут составлять **23 / 24 / 25 часов**.
- `calendarCapacitySeconds = daySeconds × bayCount`, где `bayCount` — количество **сейчас включённых** постов филиала (не исторический состав парка, не график работы, не часы смен). Нерабочее время входит в знаменатель. Показатель **не следует** называть процентом производственной утилизации или нормо-часами.
- `occupancyBasisPoints = floor(occupiedSeconds × 10000 / calendarCapacitySeconds)` — целое число сотых долей процента; когда нет действующих постов, `null` («Нет активных постов»), не искусственные 0%.
- `activeAppointments` — число актуальных записей, пересекающих локальный день. Одна запись может встречаться в двух днях; суммировать daily counts как уникальных клиентов нельзя.

День и даты периода канонические `YYYY-MM-DD`; 31 включительно; отсутствие правильной сессии/роли/филиала — `403 FORBIDDEN`; неправильный UUID/дата/период — `422 INVALID_INPUT`. Идентификаторы и отчёт не кэшируются; сессия и живые назначения `MANAGER` проверяются заново на **каждый** запрос. Доступ к публичному OpenAPI и реальной мультиорганизационной BI остаётся `planned`.

## Агрегированная загрузка назначений сотрудников (current-dev, #171)

В **том же** отчёте руководителя за локальные сутки теперь присутствует дополнительная группа **«Сотрудники в сменах / Часы смен / Назначения / Часы назначений / Доля назначений от смен»**. Никаких ФИО, employee UUID, смен конкретного сотрудника, зарплаты или кадровой информации API не отдаёт.

- `scheduledEmployees`: количество **различных сотрудников**, имеющих действующую неперекрывающуюся смену филиала, которая пересекает локальный день. Это число **не суммируется** как уникальные сотрудники за месяц: один человек может присутствовать в нескольких днях.
- `scheduledShiftSeconds`: сумма пересечений действующих `auto_staff_shift` c локальными сутками в IANA зоне филиала. Отменённые смены исключены; благодаря PostgreSQL exclusion constraint смены одного сотрудника не перекрываются. **Это запланированная доступность**, а не табель и не факт присутствия.
- `activeAssignments`: число действующих **назначений специалиста на актуальную бронь** `auto_appointment` в отчётных сутках. Требуется непогашенная `auto_employee_reservation` и действующая смена, покрывающая весь резерв; исторические назначения отменённых и перенесённых броней не учитываются.
- `assignedSeconds`: сумма фактических пересечений этих **плановых резервов** с локальным днём. Она не может превышать `scheduledShiftSeconds` при неперекрывающихся сменах/назначениях.
- `assignmentBasisPoints = floor(assignedSeconds × 10000 / scheduledShiftSeconds)` — сотые доли процента. При нуле действующих смен возвращается `null` («Нет действующих смен»), а не фиктивное 0%.

**Ограничения:** отчёт показывает текущие планы и доступные в момент запроса смены, а не исторические изменения расписания, соблюдение смены работником, качественный результат ремонта, учёт труда, billing, KPI/премии или payroll. Он не должен использоваться для расчёта зарплаты. При отзыве смены соответствующий резерв больше не входит в метрику действующих смен, даже если старое назначение осталось в immutable истории. Отзыв MANAGER или переход на чужой филиал остаётся fail-closed. 31 день, no-store, no PII, dev-only неизменны.

**Доказательства:** PostgreSQL `test_pg_auto_bay_occupancy_http.py`: действующая смена на 25-часовых сутках, назначение на бронь, перенос с `clear_employee`, отзыв смены, A/B изоляция и проверка отсутствия user UUID в ответе; browser `auto-bay-occupancy.spec.ts`: отображение агрегатов, невозможное превышение часов, 403/переключение филиала, мобильный 390 и 1280. API возвращает дополнительные поля только в `items[]`; сумма/финансы не добавлены, миграция не требуется. Откат безопасен: предыдущий API/UI не сохранял эти вычисляемые значения.


## Зарегистрированные факты исполнения (current-dev, #171)

Отдельно от **плановых** бронирований и смен таблица показывает три агрегата по неизменяемому журналу заказ-нарядов. `recordedLaborEntries` — число строк `auto_work_order_labor_entry`, `recordedLaborMinutes` — сумма сохранённых `actual_minutes`, `finishedExecutions` — число `auto_work_order_execution_finish`. Дата каждого значения — именно локальная дата **регистрации события** `created_at` (часовой пояс филиала), а не день бронирования или календарная дата завершения клиентом. События привязаны к `execution → work_order` и перепроверяются по organization/location; в ответе нет UUID сотрудников, клиентов, услуг, заказов или VIN. Идемпотентный повтор POST `/labor`/`/finish` не создаёт новых строк, поэтому не повышает цифры. Отмена/перенос брони не стирает ранее зарегистрированный факт.

Это **не** табель, физически отработанное время, норма труда, зарплата, бухгалтерская проводка, оплата или выпуск автомобиля. `finishedExecutions` не означает QC PASS. Ноль — отсутствие событий в этом журнале, а не утверждение об отсутствии реальной работы. Роль MANAGER, диапазон 1–31 день, read-only, no-store, проверка отзыва доступа и synthetic-only неизменны. Доказательства: PG17 тест `test_immutable_recorded_labor_and_finish_report_full_execution_lifecycle` (одобрение, начало, сохранение труда, повтор, finish, tenant и отзыв прав) и Playwright `auto-bay-occupancy.spec.ts` (три колонки, отказ от отрицательных минут, очистка старой таблицы). Никакого payroll и production до #119.


## Воронка синтетических бронирований (current-dev, #171)

Руководитель получает по каждому локальному дню **два независимых среза**, не подменяющих фактическое посещение:

**Дни регистрации событий:**
- `createdAppointments` — количество immutable событий `auto_appointment_event.action='CREATED'` по `recorded_at` в IANA зоне филиала.
- `canceledAppointments` — immutable `BOOKING_CANCELED` по `recorded_at`, только **реальная отмена**, не освобождение старого окна при переносе.
- `rescheduleEvents` — количество переходов `auto_appointment_reschedule` по `created_at`. **Повторные переносы одного appointment считаются отдельными событиями**, не новыми клиентами или записями.

**Дни начала будущих/актуальных записей:**
- `scheduledStarts` — число `auto_appointment`, чья **текущая неотменённая** бронь начинается внутри локального календарного дня и находится на действующем посту. Перенос учитывается только в новом дне; старая отменённая бронь не добавляется.
- `scheduledCustomers` — число различных синтетических `customer_id` исходных связей на таких бронированиях в пределах **данного филиала и дня**. Если один клиент имеет несколько записей, в этом счётчике он один.
- `repeatBookingCustomers` — число таких уникальных клиентов, у которых **до текущего appointment** в том же филиале был хотя бы ещё один appointment того же customer_id (включая ранее отменённые брони). Это **повторное бронирование**, не доказанный повторный визит и не показатель удержания клиентов. Порядок определяется immutable парой `(auto_appointment.created_at, id)`. Один клиент с несколькими записями считается в этом поле один раз за день.

Событийные счётчики и расписание **нельзя складывать в одну «воронку конверсии»**: первое фиксирует дату действия, второе — день актуальной брони, поэтому это разные временные срезы. Никакого события фактического приезда/отъезда, клиентского чека, совершённой оплаты или статуса «визит состоялся» здесь нет. Никакие customer UUID, vehicle IDs, VIN или ФИО не отдаются; SQL использует идентификаторы только для внутренней дедупликации. Отчёт доступен лишь scoped MANAGER, 1–31 день, no-store, synthetic-only. При переключении филиала/403 UI очищает прежние значения.

PG17 проверяет: создание двух appointments одного клиента в разных транзакциях → перенос второго → настоящую отмену первого → **ровно два создания, одно событие переноса и одну отмену** на день действий, актуальное начало только в новом дне, один уникальный и один повторно бронирующий клиент, отсутствие чужих данных; повторный перенос той же записи внутри дня не создаёт второго клиента. Playwright проверяет колонки, 390/1280, dark, неверные агрегаты и отказ доступа. [Задача #171](https://github.com/askarahodov/roboport/issues/171); production stats/CRM/real visits и #119 остаются `planned`.

## Управленческая воронка CRM: когорты обращений (current-dev, #171)

Руководитель СТО с действующей филиальной ролью `MANAGER` открывает
`/staff/auto-crm-funnel` (пункт «Воронка CRM (dev)»), вводит UUID
тестовой организации/филиала, выбирает даты **создания обращений**
в местном часовом поясе филиала и нажимает «Построить воронку CRM».
Период от 1 до 31 календарного дня. Без роли MANAGER, при другом
филиале или отзыве полномочий сервер отвечает `403`; invalid dates
или неверные UUID — `422`; при переключении организации/филиала,
смене даты, ошибочном или повреждённом ответе старые показатели
исчезают из интерфейса (fail-closed).

```text
GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/crm/funnel?fromDay=2030-03-31&toDay=2030-03-31
```

Ответ `syntheticOnly=true`,
`basis=LEAD_CREATED_COHORT_CURRENT_STAGE`, `timeZone`,
`fromDay`, `toDay`, `summary`, `items` в порядке
`WEB / PHONE / WALK_IN`. Каждый агрегат содержит `sourceCode`,
`total`, `new`, `qualified`, `booked`, `lost`,
`bookedBasisPoints` (целая сотая доля процента, диапазон
0–10000, `null` при нуле обращений) и `lossReasons`
(`PRICE/TIMING/NO_RESPONSE/OTHER`). Общий `summary` имеет
`sourceCode=ALL`; сумма по источникам и этапам равна итогу,
причины отказа в сумме равны `lost`. UI проверяет эти равенства
перед отображением.

**Полная выгрузка CSV (current-dev).** После построения отчёта на
`/staff/auto-crm-funnel` нажмите **«Скачать воронку CRM в CSV»**.
Отдельный read-only endpoint

```text
GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/crm/funnel/export?fromDay=2030-03-31&toDay=2030-03-31
```

повторно проверяет сессию, MANAGER grant, филиал и действующие
подтверждения связи, независимо от ранее открытой страницы.
Файл UTF-8 с BOM и разделителем `;` содержит **все** строки:
«Все источники», «Сайт», «Звонок», «Личное обращение»,
текущие NEW/QUALIFIED/BOOKED/LOST, долю BOOKED в базисных
пунктах и четыре причины отказа. При пустой когорте доля
записанных остаётся пустой ячейкой, не 0%. Личные идентификаторы,
свободный текст и формулы в CSV отсутствуют.
При `403` и `422` скачивание не начинается, старые показатели
в интерфейсе очищаются. `Cache-Control:no-store`,
`X-Content-Type-Options:nosniff`; в CSV только фиксированные
названия агрегатов и числа. Это **новый живой SQL-срез**,
поэтому текущая стадия и число лидов могут измениться со времени
просмотра таблицы. Ни запись клиента, ни его согласие на коммуникации,
ни реальная выручка этим экспортом не подтверждаются.

**Словарь метрик и интерпретация:**

- **Когорта** — обращения, immutable `auto_crm_lead.created_at`
  которых попадает в включительный диапазон **локальных** дат
  филиала, пересчитанный через IANA timezone в UTC полуинтервал.
  Сутки на переводе часов могут длиться 23 или 25 часов.
- **Статус** — **последняя** запись `auto_crm_lead_stage` по
  `(created_at DESC,id DESC)` **на момент чтения**, либо `NEW`
  без событий. Это **не исторический снимок** этапа на дату
  создания и не лог событий. Переход `QUALIFIED→BOOKED`
  учитывается единожды как BOOKED, повторное чтение не дублирует
  контакт или сделку.
- **Источники** — `WEB` (сайт), `PHONE` (звонок как код
  источника, **не** реальный звонок), `WALK_IN` (личное
  обращение как код). Все три отображаются даже при нуле;
  источники не используются для определения юридического согласия.
- **Доля записанных** = `floor(booked × 10000 / total)`,
  выражена в сотых долях процента, а `null` означает
  **неопределённую долю при пустой базе**, не 0%.
  **Это не конверсия в фактический визит, продажу или оплату.**
- **Отказы** — текущий этап `LOST` и его последняя
  неизменяемая причина. Не считаются все предыдущие стадии.

Показатели отражают только **действующие, подтверждённые**
связи клиент–автомобиль и включённые организацию/филиал.
Отзыв proof или отключение филиала исключает обращение при
следующем чтении; в ответе нет ID лида, клиента, владельца,
автомобиля, бронирования, VIN, имени, телефона, денег, индивидуальных
сотрудников и сырых записей аудита. Сервер проверяет
session+tenant+location MANAGER до SQL, применяет live proof
**до GROUP BY**, выполняет один агрегирующий SQL-запрос с единым
MVCC snapshot и возвращает `Cache-Control:no-store`.
Это read-only отчёт: не меняет воронку и не отправляет коммуникации.

## Операционный ABC/XYZ выдач склада (current-dev, #171)

**Назначение:** руководитель филиала с действующей ролью
`MANAGER` открывает `/staff/auto-stock-abc-xyz`
(«ABC/XYZ склада (dev)»), вводит синтетические UUID организации
и филиала, выбирает **от 3 до 12 полностью завершённых**
календарных месяцев и нажимает «Построить ABC/XYZ».
Экран показывает весь ассортимент филиала **по 25 SKU на
страницу**, с кнопками «Следующая страница» и
«Предыдущая страница». Смена scope/периода немедленно
очищает прежние результаты; при `403`, `409`, `422`,
`5xx` или повреждённом JSON старые значения не сохраняются.

```text
GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/stock-abc-xyz?fromMonth=2026-07&toMonth=2026-09&offset=0
```

Ответ: `syntheticOnly=true`,
`basis=GROSS_ISSUE_UNITS_CLOSED_MONTHS`,
`moneyValuation=false`, `timeZone`, `fromMonth`,
`toMonth`, `months[]`, `pageSize=25`, `offset`,
`nextOffset`, `summary`, `items[]`.
В `summary` входят `skuCount` (все товары филиала),
`activeSkus` (с реальными выдачами), `grossIssued`,
`grossReturned`, `netPeriod=grossIssued-grossReturned`
и `classCounts` A/B/C/X/Y/Z/none. У каждого SKU:
`skuId`, `article`, валовые выдачи и возвраты,
разница за период, `monthlyIssued[]`, `abc`, `xyz`
и `variationBasisPoints`.

**Методика (точные правила и границы):**

1. Время событий неизменяемого `auto_stock_event.created_at`
   преобразуется в локальную зону филиала (IANA). Для
   заданного диапазона учитываются **только** действия `ISSUE`
   и `RETURN`. Нельзя путать `RECEIPT`, `RESERVE`,
   `RELEASE`, инвентаризационные разницы или перемещения
   с фактической выдачей. Валовые выдачи `ISSUE`
   используются для классификации; `RETURN` показаны
   отдельно, чтобы возврат прошлого месяца не создавал
   «отрицательное потребление» в XYZ. Поэтому
   `netPeriod` может быть отрицательным.
2. **ABC — ранжирование по объёму выданных единиц**
   (НЕ по рублёвой себестоимости или выручке).
   Товары сортируются по `grossIssued DESC,article ASC,skuId ASC`.
   Класс определяется **накопленной долей ДО текущей строки**:
   A — менее 80% общего объёма, B — от 80% до менее 95%,
   C — начиная с 95%. Такой способ относит крупнейшую
   позицию к A даже если она одна занимает более 80%.
   SKU с `grossIssued=0` не получает ABC.
3. **XYZ — регулярность месячных выдач** в 3–12 полностью
   завершённых месяцах, включая месяцы с нулём выдач.
   `CV = sqrt(N × Σ(q_i²) − (Σq_i)²) / Σq_i`, где
   `q_i` — валовая выдача одного SKU за локальный
   календарный месяц. X при CV ≤ 10%, Y при
   10% (исключая) – 25% (включая), Z выше 25%.
   Для нулевой серии XYZ и CV отсутствуют (`null`),
   а не показываются как 0%. Для границ классов
   сравниваются **точные целые величины** без float
   (CV² относительно 1/100 и 1/16), CV выводится
   в целых сотых процента через округление вниз.
4. Суммы выдач и возвратов по всем SKU рассчитаны по
   одному текущему SQL-срезу PostgreSQL 17. Переход
   между страницами перечитывает действующую роль
   `MANAGER`, организацию и филиал. Страницы могут
   измениться при корректировке архивного синтетического
   журнала владельцем БД; это живой отчёт, не freeze snapshot.
   При более **10 000 SKU** запрос возвращает явный
   `409 REPORT_LIMIT`, а не тихо обрезает итог. До тяжёлого
   JOIN с журналом событий выполняется ограниченная проверка
   только идентификаторов SKU своего филиала (не более 10 001 строки).
   Дополнительная защитная проверка остаётся после агрегации на
   случай конкурентного добавления SKU между SQL-срезами.
   Это не обещание производительности на больших объёмах без замеров.

**Выгрузка всей ведомости CSV (current-dev).** На странице
`/staff/auto-stock-abc-xyz` после построения отчёта выберите
**«Скачать весь отчёт CSV»**. Сервер повторно проверит действующую
роль MANAGER филиала и те же завершённые месяцы, рассчитает
**все** позиции до 10 000 SKU, а не только текущие 25 строк.
Файл UTF-8 с BOM, разделителем `;`, русскими заголовками,
месячными количествами и UUID SKU без персональных данных.
Для безопасности формулы в артикулах обезврежены как текст.
`403` очищает экран, `409` не выдаёт частичный файл,
`422` означает неверный период. Выгрузка — **новый живой
SQL-срез**, поэтому при изменении исходных складских событий
между просмотром и скачиванием значения могут различаться.
Эта операция не включает цены и не разрешает финансовые решения.

**Обязательное предупреждение:** исходная карточка
`auto_stock_sku` не содержит нормализованной единицы
измерения, а выданные количества разных SKU нельзя
считать финансово сопоставимыми. Классы A/B/C здесь
**только операционное ранжирование штук**, не
стоимостной ABC и не основание для закупки,
прогноза, расчёта себестоимости или зарплаты.
Узкая готовая операция не заменяет финансовый
ABC/XYZ, доходы и payroll всего #171. Возвраты
не проверяют поступление платежей. Производственные
данные и финансовые решения закрыты до #119.

**Безопасность:** endpoint private dev, исключительно
read-only, `Cache-Control:no-store`, проверка live
`MANAGER` филиала, активных org/location до чтения
складской агрегации. Нет клиентов, VIN, телефонных
номеров, работников, заказ-нарядов, цен и валюты.
Неверные `fromMonth/toMonth` (текущий месяц,
незавершённый месяц, менее 3 или более 12 месяцев),
чужой scope или некратный 25 `offset` получают
`422`/`403` соответственно.

**Доказательства:** PG17
`tests/integration/test_pg_auto_stock_abc_xyz_http.py`
создаёт 29 SKU и синтетические неизменяемые
`ISSUE/RETURN` по трём завершённым месяцам,
проверяет ABC A/B/C и XYZ X/Y/Z, отдельные возвраты,
точные пороги, все страницы без дубликатов, 403
при отзыве MANAGER, 422, foreign branch, 409 без
silent truncation; Playwright
`apps/web/e2e/auto-stock-abc-xyz.spec.ts`
проверяет 390/1280, dark, Enter, 29 SKU,
next/previous, 403/409, повреждённые данные,
сброс при смене филиала. Без миграции и новых
изменяемых журналов; rollback — revert API/UI/docs.

## Выработка механиков по закрытым техническим работам (current-dev, #448)

**Что работает:** закрытый `synthetic HTTPS loopback` отчёт
`/staff/auto-mechanic-productivity` для действующего `MANAGER` филиала.
Это **фактические минуты**, не оценочные нормочасы, не payroll, прибыль,
выручка, касса или реальные документы. Источник:
`auto_work_order_labor_entry` → `auto_work_order_execution` →
`auto_work_order_execution_finish`, только если есть
`auto_order_demo_document_event(POSTED, CLOSED_TECHNICAL)` и последний
`auto_work_order_qc_event` имеет `PASS`, отмеченный после finish.

**Сценарий:** менеджер выбирает UUID своей организации и филиала, диапазон
локальных дат окончания работ 1–31 день и нажимает «Рассчитать выработку».
На экране — количество действующих механиков, уникальных закрытых
заказ-нарядов, услуг, минуты и подробные UUID заказов/сотрудников.
Нажатие «Скачать выработку CSV» повторно читает PostgreSQL и проверяет
полномочия, поэтому возможна разница с ранее показанным экраном.
CSV: UTF-8 BOM, разделитель `;`, только UUID и числовые значения без
формульных или персональных строк. Нет доступа по одному VIN.

**Инварианты и ограничения:**
- Сервер проверяет текущую сессию `MANAGER`, свою организацию/филиал,
  `HANDOVER:READ` и historical cutoff. При DENY — `403`; cutoff
  исключает более старые WorkOrder из данных, а не показывает их суммы.
- В выборку входят только актуальные подтверждённые owner-links,
  активные учётные записи механиков с неотозванным `MECHANIC` grant в
  этом филиале. Отзыв доступа сотрудника исключает его прошлые строки из
  нового отчёта; это **текущий scope**, не неизменяемый payroll ledger.
- Только документы `CLOSED_TECHNICAL` и независимый последний `QC PASS`
  после завершения работ. Незавершённые, отклонённые, чужие,
  отозванные и неоднозначные данные не попадают.
- События учитываются по `finish.created_at` с пересчётом локальной
  полуночи IANA в UTC для каждого края периода. День перехода DST может
  иметь 23 или 25 часов. Не объединять с SIM, CHARGE/CREDIT или
  синтетической казной; материальная себестоимость здесь не рассчитывается.
- Максимум **500 записей работ**, при превышении — явный `409 REPORT_LIMIT`
  без частичного отчёта или CSV; некорректные даты/диапазон — `422`;
  чужой scope или отозванный MANAGER — `403`. Только `GET` без мутаций,
  `Cache-Control: no-store`; не опубликовано в production OpenAPI.

**Контракт:** `GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/reports/mechanic-productivity?fromDay=YYYY-MM-DD&toDay=YYYY-MM-DD`,
плюс `/export`. Ответ содержит
`syntheticOnly:true`, `realMoney:false`, `payrollAvailable:false`,
`releaseAllowed:false`, `activeMechanicsOnly:true`, `basis`,
`timeZone`, `summary` и `items[].orders[]` с UUID и минутами.

**Доказательства:** PG17/HTTPS
`tests/integration/test_pg_auto_mechanic_productivity_http.py`
проверяет реальный закрытый lifecycle, статусы 403/422, отзыв прав,
сверку SQL→API→CSV и DST 23/25 часов. Playwright
`apps/web/e2e/auto-mechanic-productivity.spec.ts` —
390/1280, light/dark, клавиатура, повреждённый ответ, 409, 403 и
отзыв перед выгрузкой. Скриншоты искусственные. Миграций нет,
откат — revert нового read-only API, UI, тестов и документации.
Payroll/ставки/удержания, реальные финансовые отчёты и выпуск до
юридического #119 остаются `planned`.

## Аудит первички материалов на заказ-наряды (current-dev, #448)

**Завершённый технический сценарий synthetic dev; не COGS, маржа, прибыль, НДС или бухгалтерский документ.** Руководитель с действующим MANAGER и правами SUPPLIER_ORDER READ/PRICE_PURCHASE, HANDOVER READ открывает /staff/auto-material-cost-evidence, выбирает UUID своей организации/филиала и период от 1 до 31 локального дня, нажимает «Проверить документы материалов». Отчёт показывает неизменяемые выдачи/возвраты партий на WorkOrder, статус наличия документов и UUID первички. «Скачать аудит CSV» повторно проверяет доступ и формирует новый SQL-срез.

**Источник:** auto_stock_lot_work_order_issue / auto_stock_lot_work_order_return → auto_stock_receipt_document → auto_stock_receipt_acceptance → auto_stock_receipt_valuation. Состояния:
- NO_RECEIPT — документа прихода на эту партию нет.
- REVIEW_REQUIRED — есть неакцептованные/неоценённые или несколько приходов; стоимость выдачи не определяется.
- SINGLE_VALUED_RECEIPT — есть единственная принятая и оценённая приёмка; показывается только справочная цена единицы из её документа, НЕ стоимость конкретной выдачи. В партии может быть и иной запас, в том числе более ранний.

Группировка по WorkOrder и партии. grossIssued, grossReturned и netPeriod=grossIssued−grossReturned отражают **события выбранного периода**, не балансы/себестоимость; разница может быть отрицательной. Суммы разных SKU как штуки не сопоставимы; деньги из разных журналов не объединяются. Ответ всегда syntheticOnly:true, realMoney:false, marginAvailable:false, priceIsOnlyReceiptQuote:true, releaseAllowed:false.

**Security:** действующая MANAGER-роль своего филиала; все активные роли совместно проверяются на запрет SUPPLIER_ORDER READ/PRICE_PURCHASE и HANDOVER READ. Historical cutoff для branch-wide отчёта запрещает весь запрос, не позволяет раскрыть старые цены. Каждое движение обязано относиться к WorkOrder своего tenant/филиала и иметь сейчас verified, не отозванную связь автомобиля с владельцем. Не выводятся имена, VIN, телефоны, поставщик, личные примечания, коммерческая цена продажи. События и их provenance читаются одним PostgreSQL snapshot SELECT; на следующем запросе данные могут измениться после нового принятого прихода. От 1 до 31 дня по IANA зоне филиала; DST 23/25 часа. Свыше 500 событий — 409 без частичного JSON/CSV, неверный период — 422, отзыв или чужой филиал — 403.

**Private HTTPS API:** GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/reports/material-cost-evidence?fromDay=YYYY-MM-DD&toDay=YYYY-MM-DD и /export. CSV UTF-8 BOM, разделитель ;, предсказуемые UUID/enums/числа, маркер QUOTE_ONLY_NOT_COGS, no-store. PG17/HTTPS tests/integration/test_pg_auto_material_cost_evidence_http.py доказывает настоящий issue/return, принятие/оценку, неоднозначные приходы, CSV, отзыв и 403/409/422, DST. Playwright apps/web/e2e/auto-material-cost-evidence.spec.ts проверяет 390/1280, dark, клавиатуру, 403/409, повреждённые суммы и отзыв перед скачиванием. Без миграций, rollback — revert read-only API/UI/docs. Расчёт настоящей себестоимости/маржи/payroll требует дополнительных связей партий с источником единицы, бухгалтерской первички и gate #119. #448/#171 остаются OPEN.
