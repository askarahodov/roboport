# Услуги автомобильного заказ-наряда — текущий synthetic dev

> **Статус: current-dev только для синтетического стенда.** Реальные цены, материалы,
> производственная смета, выполнение и проведение наряда, документы и production **planned**
> (#114, #167, #170, #119).

## Что работает

Сотрудник с действующей ролью MANAGER в соответствующей организации и филиале может
открыть `/staff/auto-order-services`, указать UUID организации, филиала и **существующего**
автомобильного WorkOrder, просмотреть каталог синтетических услуг филиала и выбранные
услуги заказа, затем выбрать одну услугу. Backend независимо проверяет действующую
сессию, роль, филиал, наличие заказ-наряда, текущую неотменённую бронь (включая перенос)
и действующую **подтверждённую** связь автомобиля с клиентом. Перечень не раскрывает
VIN, имя клиента, телефон, документы или историю.

1. На локальном HTTPS loopback стенде войдите под синтетическим MANAGER нужного филиала.
2. Откройте `/staff/auto-order-services`. Введите UUID организации, филиала и заказ-наряда.
3. Дождитесь загрузки блоков **«Уже выбранные услуги»** и **«Каталог филиала»**.
4. Выберите **«Добавить услугу»** напротив подходящей позиции. Повторный выбор
   того же serviceId на том же WorkOrder идемпотентен — второй строки не создаётся.
5. Кнопка изменится на **«Уже добавлена»**. Используйте **«Обновить список»**
   для повторной серверной сверки.

При 401/403/404 экран скрывает ранее показанные позиции. Нельзя получать чужие
услуги подменой UUID. После отзыва полномочий, связи клиент–автомобиль либо
отмены брони добавление или чтение услуг прекращается. При ошибке сети результат
может быть неизвестен: сначала обновите список, затем повторите выбор.

## Закрытый HTTP-контракт

Все маршруты существуют только при включённом synthetic auto API на HTTPS loopback,
без публикации в production OpenAPI.

- `GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/service-catalog` —
  не более 100 услуг филиала (`id, code, title, durationMinutes`).
- `GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/orders/{order}/services` —
  только выбранные услуги активного заказа, без PII.
- `POST /api/v1/dev/auto/organizations/{org}/locations/{loc}/orders/{order}/services`
  — JSON `{"serviceId":"<synthetic-uuid>"}`, требуется серверная cookie-сессия,
  same-origin `Origin` и `X-CSRF-Token`. Впервые — 201 и `writes:1`,
  безопасный повтор — 200 и `writes:0`.

Некорректный UUID/JSON → 422; нет прав, чужой филиал, заказ, услуга или отзыв
подтверждения → 403 (без раскрытия существования записи); закрытый dev API → 404.
В каждом ответе `Cache-Control: no-store`. Нет `PATCH`, удаления позиции, списания,
резервирования, нормо-часовой цены или автоматической оплаты: все записи
`auto_work_order_service` неизменяемы.

## Приёмочный осмотр → независимый QC (current-dev, #167/#114)

В закрытом synthetic HTTPS loopback контуре реализована цепочка **один неизменяемый приёмочный осмотр → последовательность неизменяемых QC-событий** для уже существующего автомобильного WorkOrder. Это не приём реального автомобиля, не электронная подпись, не дефектная ведомость с фото, не завершение ремонта и **не разрешение на выдачу**.

1. Сотрудник с действующей ролью `INTAKE` своего филиала открывает `/staff/auto-workshop-qc`, задаёт UUID организации, филиала и существующего WorkOrder. После успешной проверки появляются `NOT_INSPECTED` и поля осмотра. Заполняет пробег (0–2 000 000 км), топливо (0–100%), состояние шин, света, утечку и категорию кузова; нажимает **«Зафиксировать осмотр»**. Запись становится `PENDING_QC`.
2. Независимый сотрудник с ролью `MECHANIC` в том же филиале открывает этот же экран и выбирает QC `FAIL` с кодом `DEFECT` или `REWORK`. Система показывает `QC_FAILED` и сохраняет историю.
3. После отдельной документированной доработки независимый механик отправляет `PASS` с причиной `NONE`, если результат действительно подтверждён. История `FAIL → PASS` остаётся неизменной; новый QC после `PASS` запрещён. Сотрудник, который внёс осмотр, не может выполнять QC того же заказа, даже имея роль MECHANIC.
4. **«Обновить журнал»** перечитывает состояние с сервера. После отзыва сессии, филиальных прав, подтверждения связи автомобиля или отмены текущей записи сервер возвращает запрет и экран скрывает сведения. Ошибка сети при QC не должна создавать повторную проверку: для повторной отправки используется тот же `requestKey`, либо сначала перечитывается журнал.

### HTTP/DB контракт

- `GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/orders/{order}/inspection-qc` — требует живую роль `INTAKE`, `MECHANIC` либо `MANAGER`, возвращает `status`, `inspection`, `qcEvents` (не более 50), `releaseAllowed: false`. Не раскрывает клиента или VIN.
- `POST .../inspection` — `INTAKE` + CSRF: `odometerKm`, `fuelPercent`, `tyresOk`, `lightsOk`, `fluidLeak`, `exteriorCode` (`CLEAR`/`DAMAGE`/`UNCHECKED`). Идентичный повтор → HTTP 200, изменение уже внесённого осмотра → 409.
- `POST .../qc` — `MECHANIC` + CSRF: UUID `requestKey`, `result` `PASS`/`FAIL`, `findingCode` `NONE`/`DEFECT`/`REWORK`. Повтор с тем же ключом и тем же содержимым → HTTP 200, иной payload по ключу → 409. Отсутствующий осмотр, QC после PASS → 409; недоступная роль, чужой заказ/филиал, отказ от связи или совмещение осмотра/QC → 403.
- Alembic `0085_auto_inspection_qc`: `auto_work_order_inspection` (ровно один), `auto_work_order_qc_event` (append-only), PostgreSQL scope/proof/current-booking trigger, запрет UPDATE/DELETE и разграничение исполнителей. Тесты `tests/integration/test_pg_auto_workshop_qc_http.py`, `apps/web/e2e/auto-workshop-qc.spec.ts`.

Ни один из этих этапов не проводит документ, не утверждает смету, не списывает детали, не утверждает оплату и не разрешает выдачу даже при `QC_PASSED`. Нужны отдельные consent, ставки, нормочасы, склад, подписи/фото, фискализация и независимая QA/security/legal приёмка #119.


## Неизменяемая смета и решение клиента (current-dev)

К выбранным услугам автомобильного WorkOrder добавлена отдельная версия цен и техническое решение клиента: `/staff/auto-estimates` (`MANAGER`) → `/account/auto-estimates` (`CLIENT`). Прежние снимки и решения append-only; после согласия нельзя тихо изменить цену или состав услуг. Детальный порядок, границы и доказательства: [смета и решение](ESTIMATES.md). Это не юридическая подпись, не проведённый документ и не разрешение на выдачу.


## Выполнение одобренной сметы (current-dev)

После согласования клиентом конкретной версии WorkOrder менеджер может начать исполнение, механик фиксирует факт трудозатрат по каждой согласованной услуге, кладовщик выдаёт зарезервированные партии, механик подтверждает получение, а затем завершает этап работ. Только после этого допускается независимый QC другим исполнителем. Подробные шаги и ограничения: [Выполнение, материалы и QC](EXECUTION.md). Даже после PASS выдача/оплата по-прежнему planned.


## Недельный обзор календаря — current-dev (#113)

`GET /api/v1/dev/auto/organizations/{org}/calendar/week?locationId={loc}&localDay=2030-03-31`
— только HTTPS loopback synthetic API с live `INTAKE` grant
для указанной организации и филиала.

Законченный workflow планирования: UI предоставляет переходы
на предыдущие/следующие семь локальных дат, сохраняя отдельно
от недельного диапазона выбранную дневную запись. Кнопка
**«Скачать неделю в CSV»** вызывает независимый закрытый
`GET /api/v1/dev/auto/organizations/{org}/calendar/week/export?locationId={loc}&localDay=2030-03-31`.
Он **заново** выполняет тот же INTAKE/tenant/branch проверенный
SQL-агрегат, а не выдаёт ранее полученный UI JSON. CSV:
UTF-8 с BOM, `;`, фиксированные колонки
«Дата филиала», «Действующие записи», «Занятые посты»,
ровно семь строк; ни UUID записей, ни клиентов, ни
автомобилей, ни свободных текстовых полей. Заголовки
`Cache-Control:no-store`, `X-Content-Type-Options:nosniff`,
`Content-Disposition:attachment`. Нет частичной выгрузки
при `403` или `422`; устаревший экран очищается,
а запрос отменяется при смене организации/филиала/недели.
Выгрузка может не совпадать с отображённой неделей при
конкурентном переносе или отмене записи, так как это новый
транзакционный snapshot. Формирование не изменяет
первичных документов и не выдаёт production permission.

Ответ `Cache-Control:no-store`: `syntheticOnly=true`,
`timeZone`, `fromDay` и семь `items[]`, каждый с
`localDay`, `appointments`, `occupiedBays`.
PostgreSQL строит семь IANA-local полуинтервалов,
включая летнее/зимнее время (23/25-часовые сутки).
`appointments` — число текущих неотменённых броней
с пересечением местных суток; при переносе учитывается только
последняя активная бронь. `occupiedBays` — число разных
постов с этими бронями за день. Бронь через полночь
законно учитывается в двух днях. Это не суммарные уникальные
Appointment, не факт обслуживания и не гарантированные
свободные слоты.

Запрос выполняется в tenant/location-scoped транзакции
после live role-check и доступности филиала, возвращает только
агрегаты без customer/vehicle/VIN/WorkOrder/employee UUID.
Неверные параметры/диапазон дат → `422`; чужой,
отключённый филиал или отзыв INTAKE → `403`.
UI автоматически убирает старую неделю при смене
scope, ошибке и недействительном JSON.

Проверки: `test_week_calendar_complete_dst_current_booking_and_live_revocation`
в `tests/integration/test_pg_auto_calendar_local_day.py`;
Playwright `weekly calendar` в `apps/web/e2e/auto-calendar.spec.ts`.
Миграции и production OpenAPI не меняются; полный #113 и
release gate #119 остаются открытыми.

## Очередь независимого контроля качества (current-dev, #167)

Новый read-only private synthetic endpoint:

```text
GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/inspection-qc/pending?limit=20&afterOrderId={uuid}
```

В ответе `syntheticOnly=true`, `items[]`, `nextOrderId`,
`Cache-Control:no-store`. Строка содержит только `orderId`,
`status` (`PENDING_QC` или `FAIL`) и
`lastFindingCode` (`NONE`, `REWORK`, `DEFECT`).
Отсутствуют личные данные, VIN, customer и actor IDs.
Действующий `MECHANIC` grant проверяется до чтения; SQL
ограничен org/location, активными организацией и филиалом,
действующим подтверждением связи и текущим неотменённым
бронированием. Нужен осмотр **другого** сотрудника.
Исполнитель незавершённого этапа работ или собственных
labor entries не может использовать очередь для обхода
независимого контроля. Последний QC `PASS` исключает наряд
из очереди, `FAIL` оставляет для повторного QC.

По умолчанию 20 строк, до 50 по параметру `limit`;
keyset-курсор `afterOrderId`, порядок UUID (не дата).
Отзыв роли или чужой филиал → 403, некорректные
UUID/лимит → 422. Переход из очереди на UI
подставляет UUID и загружает текущую карточку.
После успешной записи `QC` очередь загружается заново.
Это advisory reader: сам `POST /qc` независимо блокирует
WorkOrder и проверяет роль, разграничение исполнителей,
завершение работ, статус и идемпотентность. При гонках
возможны 403/409, никакая строка списка не даёт
разрешения на выдачу.

PG17: `tests/integration/test_pg_auto_workshop_qc_http.py`;
Playwright: `apps/web/e2e/auto-workshop-qc.spec.ts`.
DDL и production OpenAPI не меняются. Production gate #119
и полный scope #167 остаются открытыми.


## Обязательная доработка между QC FAIL и повторным PASS (current-dev, #167)

Завершённый synthetic-процесс **QC FAIL → неизменяемая запись корректирующего действия → независимый повторный PASS**. Это запрещает прежний прямой переход из FAIL в PASS без факта работы, но не превращает техническую запись в реальную дефектовку, юридическую подпись или разрешение на выдачу.

1. MECHANIC с действующей филиальной ролью фиксирует QC `FAIL` (код `REWORK` или `DEFECT`). Запись сохраняется неизменяемо.
2. Другой сотрудник с `MECHANIC` (или любой сотрудник с действующей ролью MECHANIC, который затем **не будет QC-проверяющим**) открывает тот же WorkOrder в `/staff/auto-workshop-qc`, выбирает тип доработки «Корректировка» (`ADJUSTMENT`), «Повторная диагностика» (`DIAGNOSTIC_RECHECK`) или «Проверка узла» (`COMPONENT_RECHECK`) и нажимает **«Зафиксировать доработку»**. Система записывает `failEventId` последнего FAIL и сотрудника. Это **техническое свидетельство**, не фактическое списание и не изменяемая смета.
3. Только **независимый от автора доработки** сотрудник с `MECHANIC`, который также не проводил приёмочный осмотр и не фиксировал собственные labor entries, может записать `PASS`. Без доработки или при совпадении автора и проверяющего — HTTP 409 `REWORK_REQUIRED`; повтор прежнего события с тем же ключом не создаёт дубликатов.
4. После нового FAIL цикл повторяется с **новым свидетельством именно к последнему FAIL**. После PASS новое свидетельство запрещено; `releaseAllowed` остаётся `false` даже после PASS.

**HTTP:** `POST /api/v1/dev/auto/organizations/{org}/locations/{loc}/orders/{order}/qc/rework`, JSON `{"requestKey":"<uuid>","failEventId":"<uuid>","actionCode":"ADJUSTMENT"}`, та же session+CSRF проверка, что и для QC. Ответ: 201 для нового события или 200 с `replayed:true` при неизменённом повторе. Неверный код/UUID: 422; отсутствующий последний FAIL, уже оформленная доработка, другой payload по прежнему ключу, прямой PASS, собственный QC: 409. Отозванная роль/подтверждение автомобиля, чужой филиал: 403. `GET .../inspection-qc` дополнен неизменяемым массивом `reworks[]` (id, failEventId, actorId, actionCode, createdAt), без VIN/контактов, Cache-Control:no-store.

**PG17:** Alembic `0103_auto_qc_rework_evidence`: отдельный append-only журнал, уникальность `fail_event_id` и `request_key`, SQL-защита прямого INSERT PASS; WorkOrder-лок сериализует конкурирующие операции. Тесты: `tests/integration/test_pg_auto_workshop_qc_http.py` (конкуренция, SQL bypass, ACL, replay), `apps/web/e2e/auto-workshop-qc.spec.ts` (390/1280, FAIL→rework→PASS, 403). Production gate #119 открыт. Данные только синтетические.


## Осмотр → структурированная диагностика → неизменяемая смета → решение клиента (#114/#167, current-dev)

Новый законченный **synthetic** маршрут между автомобильным приёмочным осмотром и техническим согласованием цены: сотрудник фиксирует неизменяемое диагностическое заключение по **уже выбранной услуге** WorkOrder; затем руководитель публикует версию сметы с этими заключениями; клиент видит ровно этот снимок и отдельно согласует или отклоняет его. **Не** подтверждает реальный физический ремонт/подпись/оплату/выдачу.

1. **INTAKE:** создать действующую запись + WorkOrder, выбрать услуги в `/staff/auto-order-services`, затем на `/staff/auto-workshop-qc` заполнить приёмочный осмотр. В блоке после осмотра перейти по ссылке **«диагностическое заключение (dev)»**: организация, филиал и WorkOrder передаются как UUID в адресе (без имени/VIN).
2. **MECHANIC:** в `/staff/auto-diagnostics` выбрать **«Услуга для диагностики»**, «Результат диагностики» (`NO_FAULT`, `MAINTENANCE_DUE`, `FAULT_CONFIRMED`, `FURTHER_CHECK`) и «Приоритет» (`ROUTINE`, `SOON`, `URGENT`). Без неисправности допустим только `ROUTINE`. Нажать **«Зафиксировать заключение»**. Журнал сохраняет одно неизменяемое заключение на услугу; без осмотра, выбранной услуги либо действующей роли запись не проходит. Заключение не заменяет смету или факт выполнения работ.
3. **MANAGER:** по ссылке **«Смета и согласование клиента (dev)»** перейти в `/staff/auto-estimates`, назначить цены всем выбранным услугам и нажать **«Опубликовать версию»**. Сервер собирает диагностику в детерминированном порядке по коду и UUID услуги, записывает `diagnostics_snapshot` в immutable revision и включает в SHA-256 версии. Прямой SQL INSERT сметы с пропущенным или подменённым заключением отвергается PostgreSQL. С первой версией сметы любые новые диагностики запрещены; старая история не меняется при выпуске следующей версии.
4. **CLIENT:** в `/account/auto-estimates` по своему заказу видит под каждой версией блок **«Диагностическое заключение, включённое в эту версию»** и точный SHA-256 версии; соглашается или отклоняет именно эту версию. Права CLIENT проверяются по текущей связке клиента/автомобиля, независимо от прав сотрудника; прямой GET `/diagnostics` клиенту запрещён.

**API:** `GET /api/v1/dev/auto/organizations/{org}/locations/{loc}/orders/{order}/diagnostics` (MECHANIC/INTAKE/MANAGER) возвращает `services[]`, `items[]`, `inspectionRecorded`, `estimatePublished`, `syntheticOnly:true`, `releaseAllowed:false` без VIN и контактов. `POST` на тот же путь требует MECHANIC + cookie + same-origin CSRF; JSON `{"requestKey":"<uuid>","serviceId":"<uuid>","findingCode":"FAULT_CONFIRMED","severityCode":"SOON"}`. Создание 201, точный повтор 200 и `replayed:true`; неправильный код/лишние поля 422; нет осмотра, услуга чужая или уже диагностирована, смета заморожена, другой payload по ключу — 409; нет полномочий, отозвана связь клиента с автомобилем или запись отменена — 403. `Cache-Control:no-store`, production OpenAPI не меняется.

**PG17:** Alembic `0104_auto_diagnostic_evidence` добавляет append-only `auto_work_order_diagnostic` (одна запись на выбранную услугу, глобально уникальный request key), защищённый FK, live mechanic grant/current booking/proof/inspection и заморозку после первой версии, а также `auto_work_order_estimate_revision.diagnostics_snapshot` с независимой SQL-сверкой при INSERT. Повторы сериализованы по WorkOrder. Тесты: `tests/integration/test_pg_auto_diagnostic_estimate_http.py` (HTTP/ACL/CSRF/BOLA, concurrent writes, SQL tampering/immutability, реальный client consent); `apps/web/e2e/auto-diagnostics.spec.ts` (390/1280, переходы от осмотра до решения клиента и очистка на 403). Откат миграции допустим только в disposable синтетической БД. До настоящих документов, фото, ставок, юридической подписи и #119 **planned**.


## Тарификация выбранных работ до технического согласия клиента (#114/#167, current-dev)

После выбора услуг и приёмки/диагностики MANAGER открывает `/staff/auto-estimates`, выбирает **«Способ расчёта стоимости» → «По нормо-часу и тарифной категории»**, указывает код категории и копейки за нормо-час для каждой услуги, проверяет целочисленную сумму и нажимает **«Опубликовать версию»**. Сервер использует плановую длительность услуги из выбранного каталога, а не введённое пользователем количество минут, рассчитывает цену с округлением 0,5 вверх и запечатывает ставку/категорию/минуты/сумму в SHA-256 неизменяемого документа. CLIENT читает те же строки в `/account/auto-estimates` и решает только по конкретной версии. Переписать тариф или старую смету нельзя: нужна новая версия до финального решения. Старый ручной режим сохраняется. [Формула, контракт, отрицательные тесты, ограничения](ESTIMATES.md). Не означает настоящего подтверждения квалификации, зарплатной ставки, платы по налоговому чеку или юридического согласия; #119 открыт.


## Версионированный акт приёмки автомобиля с фотографиями (#439, current-dev)

Вместо смешивания автомобильных вложений с legacy-робот заявками отдельный закрытый **synthetic HTTPS** сценарий связывает запись/заказ-наряд, неизменяемый приёмочный осмотр, зоны повреждений, комплектность, фотографии, версии и клиентский просмотр. **Это технический предпросмотр без юридической подписи или выдачи автомобиля.**

1. **INTAKE** оформляет исходный осмотр на `/staff/auto-workshop-qc` (пробег, топливо, свет/шины/утечки, кузов). После этого открывает **«версионированный акт повреждений и комплектности (dev)»** либо `/staff/auto-intake-act?org=<uuid>&loc=<uuid>&order=<uuid>`. В форме выбирает тип транспорта (`PASSENGER/SUV/VAN/TRUCK/MOTORCYCLE`), состояние всех пяти предметов комплектности (`KEYS/SPARE_WHEEL/TOOLS/DOCS/CHARGER`, допускается честное `NOT_CHECKED`), до 12 кодированных повреждений (зона `FRONT/REAR/LEFT/RIGHT/ROOF/CABIN`, тип `SCRATCH/DENT/CRACK/MISSING/CORROSION`, степень `MINOR/MODERATE/SEVERE`), от 0 до 3 фотографий.
2. При наличии повреждения обязателен хотя бы один снимок. Поддерживается исходный PNG/JPEG до 5 МБ; браузер преобразует его в ограниченный PNG без исходных метаданных/EXIF/GPS, сервер **независимо** проверяет PNG signature+CRC, только RGB(A) 8-bit noninterlaced, декомпрессию/размер и удаляет любые дополнительные chunks (включая metadata). Серверный PNG не более 196 608 байт, не более 262 144 пикселей; в этом dev-стенде изображение **атомарно** хранится как приватные bytes в той же immutable PG17 версии. Не делаются публичные MinIO URL, не сохраняются имена исходных файлов/EXIF.
3. **«Зафиксировать версию акта»** отправляет `requestKey`, `expectedVersion`, строго структурированную форму. Ответ 201; точный повтор того же тела/ключа возвращает 200 + `replayed:true` без новых фотографий. Модификация сохранённой версии запрещена DB-триггером; корректировки делаются только версией N+1 до публикации сметы или начала QC. Конкурентные правки проходят через блокировку WorkOrder и `expectedVersion`, поэтому лишь одна может стать следующей. Версии имеют собственный SHA-256 состояния и отдельные SHA-256 снимков. Прямой SQL INSERT с подменой фото digest / неполным списком комплектности запрещён.
4. **CLIENT** открывает из своего списка нарядов кнопку **«Посмотреть версии акта приёмки, повреждения и фотографии (dev)»** или `/account/auto-intake-act?org=<uuid>&loc=<uuid>&order=<uuid>`. Read-only просмотр включает историю, фото, комплектность и **сравнение с предыдущим визитом исключительно при совпадении исходного verified customer/vehicle link** — не по VIN и не по автомобилю нового собственника. Предпросмотр можно распечатать (кнопка **«Печатать предпросмотр акта»**). В фотомаршруте при **каждом** запросе заново проверяются живая сессия, роли/связь, org/loc/WorkOrder/act и целостность payload. Отзыв связи / организации / staff-grant → 403, UI удаляет весь кэш акта при обновлении. `Cache-Control:no-store`, `nosniff`, sandbox/CORP заголовки.

**API (закрыт и исключён из production OpenAPI):** `GET/POST /api/v1/dev/auto/organizations/{org}/locations/{loc}/orders/{order}/intake-acts`; `GET .../intake-acts/{act_id}/photos/{index}`. POST JSON `{"requestKey":"<uuid>","expectedVersion":0,"act":{"vehicleKind":"PASSENGER","damages":[{"areaCode":"FRONT","damageCode":"SCRATCH","severity":"MINOR"}],"inventory":[{"itemCode":"KEYS","condition":"PRESENT"},...],"photos":[{"areaCode":"FRONT","imageBase64":"<base64 encoded PNG>"}]}}`. Клиент имеет только GET при действующей исходной связке; INTAKE может POST, INTAKE/MANAGER/MECHANIC могут GET. Неверные enums/фото/лишние поля 422, осмотр отсутствует/версия устарела/QC/смета созданы 409, нет live access 403. `legalSignatureStatus="NOT_IMPLEMENTED"` и `releaseAllowed=false` **при любом состоянии**.

**Миграция:** `0106_auto_intake_photo_act` содержит append-only bounded версии с приватными PNG байтами в одной строке, immutable триггер, SQL live scope/INTAKE grant/verified proof, контроль списка пяти предметов, структурированных повреждений, номера версии, SHA-256 изображений. Хранение бинарных данных в PG — сознательно только для disposable synthetic/dev-теста; **production** требует утверждённого ObjectStorage/AV-scan, retention/backup, e-signature/акт и независимого security/legal approval #119.

**Тесты:** `tests/integration/test_pg_auto_intake_act_http.py` (HTTP PG17, санитарная проверка PNG/EXIF, SQL immutability, idempotency/409, race, ACL/revocation, клиент другого владельца, сравнение визитов) и `apps/web/e2e/auto-intake-act.spec.ts` (390/1280, staff→client, фото, сетевой retry, 403 очистка). Фото/подписи и настоящая распечатка формально утверждённого документа всё ещё относятся к gate #119 и scope #439, который остаётся OPEN до legal review.
