# ADR-AUTO-001 — полная замена robot-домена автомобильным продуктом

**Обновлён:** 28.10.2026 · **Статус:** архитектурное решение для разработки, не production · #109 / #165 / #174.

## Контекст

Исходный ROBOport технически содержит FastAPI, PostgreSQL/Alembic, React, сессии, ACL, сметы, склад и аудит, но их первичная предметная область — обслуживание роботов. Требование заказчика — **полностью автомобильная система класса AutoDealer Online**: филиалы, запись, заказ-наряды, склад, поставщики, CRM, финансы, аналитика и клиентское обслуживание. Нельзя считать глобальные legacy-роли или robot ticket историей автомобиля.

## Варианты

1. **Big bang rewrite:** быстрая концептуальная чистота, но большой риск утраты инвариантов и данных, невозможность сравнить результаты.
2. **Механическое переименование robot таблиц/маршрутов:** несовместимая бизнес-модель, утечки истории между владельцами, неверные ACL и отчёты.
3. **Модульный монолит + контролируемое замещение контекстов с обязательным sunset старого домена:** сохраняет работающие технические компоненты и тесты, но требует явного плана cutover.

## Решение

**Вариант 3 выбран исключительно как способ перехода; конечная архитектура не содержит robot business domain.** Технически переиспользуем инфраструктуру, auth-криптографию, аудит, idempotency, PostgreSQL и UI design system после независимых автомобильных тестов. Предметные модели и действия должны быть автомобильными:

- Organization/Tenant/ServiceLocation → users/roles и филиальные ACL;
- Customer/Vehicle → подтверждённая связь и история **конкретного заказчика**;
- Appointment/WorkBay → конкурентно безопасное расписание;
- WorkOrder/Inspection/Estimate → версии, согласование, QC;
- Parts/Supplier/InventoryLedger → остатки и финансовые движения;
- CRM/Communication/Payment/Reporting → заезды, деньги, документы и аналитика;
- Customer Portal/Mobile → один versioned backend без доступа к чужим данным.

Все данные привязаны к tenant/branch/object; **cross-domain grants запрещены**. Новая auto MANAGER permission не выдаёт `user_role MANAGER` для legacy ticket.

## Правила совместимости и удаления

Старые `robot_device`, `service_ticket`, исторические `estimate`, `stock_lot`, robot frontend/routes и legacy docs **не являются целевыми сущностями**. Они временно живут в изолированном legacy namespace ради аудита/миграции/отката, пока #165 и #172 не подтвердят map/reconcile/backup. Ни одна legacy роль, привязка, клиентская история или доступ к файлам не переносится автоматически по VIN, login или vehicle ID. В целевом build и публикуемом OpenAPI robot API не останется. Destructive удаления требуют отдельного подписанного миграционного решения и recovery drill (#119).

## Cutover-gates

1. В реестре #165 перечислены все legacy UI, API, DDL, docs, permissions, deployments и артефакты.
2. Автомобильный vertical slice M1 из [FEATURE_ROADMAP.md](FEATURE_ROADMAP.md) проходит полный browser/API/PG17 E2E.
3. В новом target build нет robot UI/menu/routes и публичного robot API. Старая история либо экспортирована/архивирована с контролируемым ACL, либо удалена только при одобренном retention policy.
4. Зафиксированы backup/restore, idempotent import/dry-run, dual-run reconciliation и rollback.
5. Owner организации/ADMIN bootstrap, лицензии, бренд, ПДн, юридические и security требования #119 подтверждены до production.

## Последствия и ограничения

Промежуточные периоды содержат два предметных домена **лишь как миграционную необходимость**; не объявлять legacy код готовым автомобильным модулем. Проверка миграций и API/ACL/CI обязательна для каждого шага. [Продукт](PRODUCT.md), [матрица функций](FUNCTIONAL_MATRIX.md) и [roadmap](FEATURE_ROADMAP.md) — единый источник требований. Источник AutoDealer: https://autodealer.ru/online/help/o-programme.html — только функциональный ориентир, без копирования закрытых решений.
