# План выпуска автомобильной платформы — не робототехнического модуля

Дата: 28.10.2026. Owner: #174 / Epic #107. Функциональный benchmark: AutoDealer Online. Все этапы **planned**, пока не указана проверка конкретного SHA. Приоритеты и owner: [матрица 52 функций](FUNCTIONAL_MATRIX.md).

## Продуктовый принцип

**Конечная сборка** — полная браузерная система СТО с CRM, записью, заказ-нарядами, складом, закупками, платежами, документами, отчётами, ролями и кабинетом клиента. Robot UI, API, термины и сценарии полностью исключаются из целевой поставки. **Strangler Pattern — только способ безопасного перехода**, не разрешение навсегда оставить робототехническую часть внутри продукта.

## Сквозная бизнес-приёмка (Given / When / Then)

1. **Клиент/авто:** Given клиент A и машина V с историей клиента B; When A подтверждает новую связь; Then он видит V и только принадлежащие A наряды, история B остаётся скрыта; чужой VIN не даёт доступ.
2. **Запись:** Given свободный пост P в филиале F; When два оператора одновременно выбирают одинаковый слот; Then только один получает подтверждение, второй — контролируемый конфликт.
3. **Приёмка:** Given запись и полномочный мастер; When выполнен осмотр с фото/пробегом; Then создаётся заказ-наряд с исходной неизменяемой версией акта; чужой филиал получает 403/404.
4. **Диагностика/смета:** Given список работ; When мастер отправил смету клиенту; Then версия SENT больше не редактируется, а дополнительные работы требуют новой версии и отдельного согласия.
5. **Резерв и склад:** Given остаток одна деталь; When два наряда одновременно резервируют её; Then только один резерв успешен, остаток не отрицателен и движения имеют audit.
6. **Ремонт/QC:** Given согласованные работы; When диагностика завершена, но QC_FAILED; Then выдача блокируется, а одобренные работы/расходники точно отражены в наряде.
7. **Оплата:** Given счёт, аванс и частичная оплата; When поступает повтор webhook; Then второй платёж не создаётся, возврат не превышает оплаченное и отчёт сверяется до копейки.
8. **История/документы:** Given выданный заказ; When клиент A открывает акт/чек; Then доступ только к документам его заказа; клиент B получает безопасный отказ.
9. **Организация/права:** Given два tenant и два филиала; When manager A запрашивает документы/деньги B либо legacy robot ticket; Then отказ, отсутствие утечек в логах/ответах и невозможность самоэскалации.
10. **Cutover:** Given legacy robot data snapshot и target build; When выполняется dry-run migration и переключение; Then reconciliation подтверждён, robot UI/API отсутствует в целевой поставке, recovery из backup протестирован.

Сценарии выше — **требования к будущей приёмке**, а не утверждение об уже выполненных E2E.

## Правила перехода без потери данных

1. Инвентаризировать robot frontend routes, OpenAPI, SQL таблицы, связи, ACL, docs, тесты, конфиги и CI (#165).
2. Определить по каждому объекту: **новая автомобильная реализация**, **архив с read-only доступом** или **удаление после юридического согласования**. Механически переименовывать robot_device/service_ticket в Vehicle/WorkOrder нельзя.
3. Построить автомобильную модель с tenant_id/location_id и новой матрицей ролей. Не копировать унаследованные MANAGER/grants в автомобильную область.
4. Сделать один воспроизводимый импорт synthetic данных с report/dedupe и сверкой балансов, без real PII (#172).
5. На staging проверить запрет robot UI/API, историю чужого клиента, backup и rollback. Тесты legacy сохранять до последнего cutover.
6. Только после approvals и удовлетворения #119 убрать robot реализацию из target build; destructive миграция допускается **отдельным** разрешённым этапом.

## Приоритет при конфликте

Рабочая система СТО важнее декоративного ребрендинга. **Не закрывать #107, #165, #174 или #119 только на основании новой документации.** Запрещено представлять planned как current и выдавать локальный synthetic proof/manager-bootstrap за готовое production управление СТО.
