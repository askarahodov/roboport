# Проверка происхождения доказательств выпуска — current `main` (#119)

**Назначение:** автоматический технический preflight автомобильного продукта. Скрипт не разрешает production, не проверяет подлинность юридических подписей, полноту реальных согласий, лицензий, миграции, ПДн и доступов. Он всегда возвращает `verdict=BLOCKED` и `productionApproved=false`; даже при `technicalChecksPassed=true` независимая процедура security/legal/ops и отдельное разрешение остаются обязательными. Реальные персональные и платёжные данные не использовать в synthetic стенде.

## Как запускать с текущим `main`

1. Получите **актуальный полный SHA** `main` в GitHub и `run_id` завершённого workflow `.github/workflows/ci.yml`, запущенного именно событием `push` для этого SHA. Должны быть **все пять** job `postgres`, `api`, `web`, `browser-e2e`, `windows-cmd` со статусом `completed/success`.
2. Подготовьте файл `evidence.json` **локально и только с разрешёнными ссылками**, соответствующий структуре `scripts/check_auto_release_evidence.py`: ровно восемь направлений `auto_e2e`, `tenant_admin_acl`, `legacy_cutover_restore`, `privacy_consent`, `parts_licensing`, `payments_compliance`, `monitoring_rollback`, `ci_main`. Потребуются реальный независимый `approved_by`, `approved_at` и доказательства; фиктивные значения недопустимы при фактическом релизе. Валидатор проверяет лишь формат полей и ссылки. Время утверждения допускается только в однозначном UTC-формате `YYYY-MM-DDTHH:MM:SS[.ffffff]Z` (максимум шесть цифр дробных секунд); сокращённые IPv4-адреса вроде `127.1` и числовые/hex IPv4 aliases запрещены. Он отклоняет localhost, частные IP и зарезервированные/непубличные DNS-зоны (`.local`, `.internal`, `.test`, `.example`, `.invalid`, `.onion`, `.localhost`); это синтаксический фильтр, **не** проверка DNS, доступности ссылки или полномочий подписанта.
3. В каталоге проекта выполните (здесь `SHA`, `RUN_ID` — **метапеременные, не реальные подтверждения**):

```bash
python -m pytest -q tests/contract/test_auto_release_preflight.py tests/contract/test_auto_release_ci.py
python -m scripts.check_auto_release_preflight --sha "$SHA" --run-id "$RUN_ID" --evidence ./evidence.json
```

Скрипт делает запросы к GitHub API: **вначале** получает `GET /repos/askarahodov/roboport/git/ref/heads/main`, далее проверяет выбранный `GET .../actions/runs/{run_id}`, полный список jobs и состояние требуемых issues, **в конце снова** получает текущий ref `main`. Проверка отклоняет старый успешный CI с SHA не равным текущему HEAD, подменённый ref, перепутанный workflow/run/attempt и новый push в `main` во время обращения к GitHub. Если `main` изменился **после** preflight, процедуру необходимо запускать повторно: единственный просмотр не является «вечным» разрешением.

## Контроль обязательных зависимостей полного автомобильного выпуска

Сверка закрытия GitHub issues (состояние `closed`, не фактическое утверждение) блокирует незавершённые направления: **#110** бренд и права, **#111** OEM/parts лицензии, **#113** бронь, **#114** заказ-наряд, **#115** склад/закупки, **#116** CRM/финансы, **#117** клиент/приватность, **#119** сам release gate, **#121/#123/#124** документация, **#165** отказ от legacy robot, **#166** роли/филиалы, **#170** деньги/фискализация, **#172** перенос базы и восстановление. Для конкретного урезанного релиза потребуется **отдельное документированное решение владельца продукта и независимой комиссии**: код не должен молча считать закрытыми отсутствующие обязательства.

Ни `closed` issue, ни валидная JSON-схема документов, ни зелёный CI **не подтверждают** действительность лицензионных разрешений, договоров, consent или фактического backup/restore реальной базы. Все открытые issues приводят к `ISSUE_<номер>_NOT_CLOSED`.

## Ответы и режим отказа

При проблемах в данных preflight печатает только **коды причин**, без содержимого evidence, токенов, клиентских данных, VIN или URL доказательств. Примеры кодов:

| Код | Значение и действие |
|---|---|
| `STALE_MAIN_SHA` | Указанный CI успешен для **предыдущей** версии `main`; обновить SHA и прогон |
| `MAIN_MOVED_DURING_PREFLIGHT` | HEAD изменился между двумя обращениями; повторить после стабилизации |
| `MAIN_REF_NOT_VERIFIED` | Нет достоверного `refs/heads/main` с 40-символьным commit SHA; fail closed |
| `CI_RUN_NOT_VERIFIED`, `CI_INCOMPLETE_JOB_LIST` | Неподтверждённый workflow или не все jobs; нужны новые доказательства |
| `ISSUE_113_NOT_CLOSED` (и другие) | Осталась незавершённая обязательная задача; завершить и независимо проверить |

Коды возврата: **0 отсутствует намеренно**, даже при полном техническом совпадении; **1** — `BLOCKED` с reasons и `productionApproved=false`; **2** — неправильные CLI-параметры, отсутствие/повреждение JSON, недоступность GitHub API. Локальный `GITHUB_TOKEN` при необходимости задаётся в переменных окружения, не сохраняется в репозитории и никогда не логируется. Для проверки исторического CI без утверждения актуальности `main` существует отдельный `python -m scripts.check_auto_release_ci`; его успех **нельзя** использовать вместо consolidated preflight.

Контрактные регрессии: `tests/contract/test_auto_release_preflight.py` (включая CLI заглушки API, stale SHA, движущийся HEAD, malformed ref и актуальный набор блокеров), `tests/contract/test_auto_release_ci.py`. Эти тесты входят в обязательную CI job `api` через `tests/contract`.

## Оставшиеся независимые работы

Технический preflight — только одна часть #119. Для безопасного production нужны реальная инвентаризация и зафиксированные RPO/RTO, восстановление из согласованного бэкапа, проверка действительных данных и tenant privileges, безопасный legacy cutover, авторизованные подписанты, правовые основания ПДн/фискализации и лицензий, мониторинг и ручной регрессионный QA. **Ничего из перечисленного скрипт не выполняет**. Только уполномоченные ответственные могут принять соответствующие решения, вне synthetic pipeline.
